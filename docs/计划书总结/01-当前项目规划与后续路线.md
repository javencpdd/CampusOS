# CampusOS 当前项目规划与后续路线

> 当前发布基线：`v0.13.0`
> 规划基线：分支 `djw-window`、G0 为 migration `000001-000043`；当前工作树已到 `000049`
> 更新日期：2026-09-01
> 状态：项目所有者已确认 v0.14-dev 当前代码验证完成并完成开发收尾，`v0.13.0` 仍是发布基线；Final 仍需目标环境与人工运营门禁

## 1. 当前结论

CampusOS 已形成可运行、可验证和可容器化交付的模块化单体。v0.13 仍是当前发布基线；v0.14-dev 已在不改变
Core Module、Built-in Feature、External Plugin、Resource Package 四类能力和单主机 Docker 边界的前提下完成 P0/P1 实现。

此前页面中的 P0/P1/P2 只是版本间候选。根据新的业务输入和当前代码审查，v0.14 已从候选中选择一条连续主线：

> 以 User Storage Object Layer 为数据基础，建立管理员治理的 AcademicTerm，并以 Personal Documents
> 验证个人工作区的文件、版本、安全和恢复能力。

完整范围以 [v0.14 正式项目计划](../项目计划书v0/项目计划v0.14/00-v0.14版本计划书.md) 为准，本页只提供当前摘要。

## 2. v0.14 实现状态与 Final 边界

| 主线 | 已实现事实 | 未完成的 Final 边界 |
| --- | --- | --- |
| G0 基线 | 已冻结 G0、生成合同和隔离 migration 证据；当前 migration 为 `000001-000049` | 最终发布的目标环境复验 |
| AcademicTerm / Schedule | 管理员 spring/fall、open/closed/default、服务端 Guard、旧 JSON 与不可变 Object 双写和历史采用命令已实现 | 有权管理员对真实历史数据审阅 dry-run 后决定是否 `--apply` |
| User Storage | Object ID、metadata、owner、Reservation、原子本地写、默认只读 reconcile、低基数运营指标已实现 | 目标环境的恢复/对账与容量证据 |
| Personal Documents | 私有文档、不可变版本、回收站、认证下载、TXT/Markdown/CampusDoc 安全编辑预览与受信 ReadPort 已实现 | 真实 Converter Runner 未交付；PDF/DOCX 继续安全降级为上传与下载 |
| Reliability/Recovery | 现有 Outbox/恢复演练及对象对账合同已覆盖 v0.14 基础路径 | Linux 目标环境 release-check、浏览器矩阵、正式发布审查 |

计划采用 `shadow -> dual -> enforce` 灰度。旧课表 JSON、头像、内容图片和 RichText 资产先盘点、再登记、
最后切换新写入；v0.14 不批量删除或静默重命名历史文件。

## 3. v0.14 非目标

- 多人协作文档、跨用户 ACL、分享链接和通用个人云盘。
- 完整 Office 在线兼容、PDF 编辑、OCR、AI 文档问答和全文/向量检索。
- S3/OSS/WebDAV 生产迁移、Google Drive/OneDrive 同步。
- 标准 MCP、真实 protobuf gRPC、远程插件市场、Agent Runner。
- 多节点 API/Worker、高可用数据库、自动 TLS。

这些方向仍是后续候选，不能从 Object Port、Converter 原型或接口预留推断为已经实现。

## 4. 实施顺序

```text
G0 真实基线
  ├─> AcademicTerm -> Admin/Term Guard -> Schedule 历史迁移
  └─> Storage Object -> Documents/Version -> Preview/Converter
                                          └─> 恢复与 Final
```

标准团队按 8 周执行；只有 1 名后端和 1 名前端时按 10–12 周安排，不通过取消迁移、并发、安全、恢复或
浏览器测试压缩周期。DOCX Preview 是可降级项；Storage 配额/一致性、课表历史数据和文档版本不可降级。

## 5. 当前与后续版本的边界

### v0.14 Final 前

- 应用版本和 README 继续显示 `v0.13.0`。
- 每项完成情况以 `docs/进度/v0.14-dev/` 的最新记录为准；当前开发收尾为 `v0.14.11-dev`，逐项审查与发布边界为 `v0.14.9-dev`，项目回顾位于 `docs/项目计划书v0/项目计划v0.14/01-v0.14计划逐项审查与项目回顾.md`，其中 P1 代码与测试证据位于 `v0.14.5-dev`。
- v0.14 migration 已顺序追加至 `000049`；生产回退优先关闭 Feature 并 forward-fix，不能以 down 删除用户数据。
- 未通过 Final Gate 的功能不能写成已发布；DOCX/PDF 保持安全降级，历史数据 `--apply` 必须保留人工授权。

### v1.0 已正式规划

v1.0 选择插件生态与三层授权作为下一主线：复用 Manifest v2、Host API v1/v2、本地插件目录、用户 Grant、
受管数据和签名预检，新增稳定插件身份、Capability Catalog、管理员逐能力 Grant、用户逐能力 Consent、统一判定、
升级 diff、即时撤销，以及事件/任务/Secret/Process Runtime 的共同边界。完整范围见
[v1.0 正式项目计划](../项目计划书v1/项目计划v1.0/00-v1.0版本计划书.md)。该计划尚未进入代码实施。

远程公共市场、完整进程沙箱、标准 protobuf gRPC/MCP、Agent Runner、多节点/HA 和跨用户协作仍是 P2 或后续候选。

后续版本立项仍需单独冻结基线、威胁模型、迁移、回滚和验收，不能提前并入 v0.14。

## 6. 不应回退的边界

- 不把模块化单体拆成无必要的微服务。
- 不把 Built-in Feature 或 Resource Package 放回普通插件生命周期。
- 不允许 External Plugin、Converter 或 Agent Runner 获取核心数据库、JWT、用户 Token 或完整宿主目录。
- 不在 Feature 停用、Plugin 卸载、资源切换、学期关闭或文档回收时隐式删除用户数据。
- 不为了通过测试移除权限、审计、清洗、配额、事务、路径或数据库约束。
- 不把 Local Provider 接口抽象宣传成已具备生产对象存储。
