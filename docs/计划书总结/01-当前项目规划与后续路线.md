# CampusOS 当前项目规划与后续路线

> 规划基线：`v0.13.0`
> 更新日期：2026-07-29
> 状态：版本间候选路线，不是已经立项的 v14 计划

## 1. 当前结论

CampusOS 已形成可运行的模块化单体：

- Core Module 承担 Identity、Community、Moderation、User Storage、Reliability、Observability、
  Email Delivery、Feature Registry 和 Plugin Platform 安全边界。
- Built-in Feature 承担 Personal Space、RichText、Schedule、Appearance、Webhook、AI、MCP-like、
  Message、Mutual Aid 和 Secondhand 等可启停能力。
- External Plugin 使用 Manifest v1/v2、Wasm 或受管进程、Host API/Extension Gateway、受管记录/文件、
  Catalog 和用户 Grant，不直接访问数据库或内部 Service。
- Resource Package 保存主题、首页包、个人主页风格、Skill、Prompt、Persona 和知识元数据，不拥有业务
  Runtime。
- Web、Admin、Docs 和 API 可以整体或分组件打包；Windows 通过 Docker Desktop Linux Containers，
  Linux 通过 Docker Engine + Compose v2 使用同一交付合同。

当前不应继续通过向 v13 计划追加任务来扩张范围。新的版本计划应从以下候选中选择有限主线，并先冻结基线。

## 2. P0：下一阶段优先候选

### 2.1 生产交付认证

- 在真实 Windows 10/11 Docker Desktop 和 Linux `arm64` Runner 复验四镜像、PowerShell、备份和恢复。
- 增加反向代理/TLS 示例，但不在 API 容器内自建证书生命周期。
- 建立镜像 SBOM、漏洞扫描、签名、来源证明和依赖升级策略。
- 对 SMTP、Prometheus 告警通知、备份保留和恢复频率做目标环境验收。

验收前提：不能把当前 Linux `amd64` 隔离验证写成所有平台已经发行认证。

### 2.2 文档与发布治理

- 为公开文档建立版本选择和 release notes，避免旧页面被搜索引擎当成当前操作指南。
- 保持 Help 生命周期索引、计划总结、OpenAPI、路由矩阵和 Admin 只读架构同步。
- 将 Windows/Linux/arm64 的真实运行证据接入 CI 或 release runner，而不是只依赖人工说明。

### 2.3 安全与运维闭环

- 为 TOTP、SMTP、插件签名和第三方 Secret 接入可替换 Secret Provider；CampusOS Token 永不导出。
- 为可靠 Worker、邮件、Webhook、数据库和 User Storage 建立目标环境 SLO、告警接收和长稳演练。
- 保持最后管理员、Step-up、板块作用域、required audit 和事务 Outbox 的默认拒绝语义。

## 3. P1：架构和生态候选

| 方向 | 目标 | 必须先满足的边界 |
| --- | --- | --- |
| 标准 MCP | 提供正式协议 Server 和版本化 Tool/Resource 合同 | 权限、用户确认、审计、限流和敏感数据投影 |
| 标准进程扩展协议 | 从历史 `runtime: grpc` 名称演进到真实 protobuf gRPC 或明确的新协议名 | 双版本兼容、健康、超时、签名和迁移文档 |
| 远程插件目录 | 下载、版本索引、审核和签名吊销 | 供应链扫描、透明审计、来源信任和失败回滚 |
| 共享 User Storage | S3/OSS/WebDAV 等 Provider | 所有权、配额、幂等、加密、迁移和多实例一致性 |
| 身份增强 | OAuth/OIDC、Passkey 或更多邮件 Provider | 账号合并、恢复、Step-up、审计和历史用户兼容 |
| 通知增强 | SSE/WebSocket 或外部邮件通知 | 当前轮询兼容、离线状态、限流和用户偏好 |
| 第三方 Adapter | Discord、OneBot 等真实生产适配器 | 独立插件、最小权限、重试、审计和平台变更隔离 |

## 4. P2：高风险或长期候选

- 多节点 API/Worker、高可用 PostgreSQL、分布式 Session/限流和共享缓存一致性。
- 隔离 Agent Runner、Knowledge Provider、Prompt/Persona 管理和代码执行审批。
- 公共插件市场的社区审核、评分、支付、恶意包分析和跨实例 Secret envelope。
- 个人云盘、跨插件统一搜索、向量检索和大规模内容索引。

这些方向不能在缺少威胁模型、隔离、资源配额、审计和恢复方案时提前开放。

## 5. 下一版立项入口

正式建立下一版计划前应完成：

1. 冻结 `v0.13.0` 的代码版本、40 个 migration、路由/OpenAPI、Module/Runtime Manifest 和数据目录。
2. 运行完整 `release-check`，记录真实操作系统、CPU 架构、Docker/Compose、浏览器和数据库版本。
3. 从 P0/P1 中选择一条主线，明确非目标，避免同时推进市场、Agent、集群和身份重构。
4. 为每阶段指定代码目录、迁移、兼容、回滚、负向测试和进度文档。
5. 新计划只有在正式文件创建后才获得版本承诺；本页不能被用来宣称某个候选已经实现。

## 6. 不应回退的边界

- 不把模块化单体拆成无必要的微服务。
- 不把 Built-in Feature 或 Resource Package 放回普通插件安装生命周期。
- 不允许 External Plugin、Agent Runner 或风格包取得数据库连接、JWT 私钥、用户 Token 或完整宿主文件系统。
- 不在 Feature 停用、Plugin 卸载或资源包切换时隐式删除用户数据。
- 不为了通过测试删除权限、审计、内容清洗、路径、配额、事务或数据库约束。
- 不默认明文导出 CampusOS 或第三方 Secret。
