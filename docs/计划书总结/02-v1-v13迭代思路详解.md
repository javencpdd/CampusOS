# CampusOS v1-v13 迭代思路详解

> 审查日期：2026-07-29  
> 当前发布基线：`v0.13.0`  
> 文档用途：解释每一版为什么出现、解决了什么，以及哪些结论仍约束当前开发

本页是版本决策导读，不替代原计划、代码或验收证据。版本号描述的是连续演进，不表示旧计划中的全部
设想仍然有效。当前行为应以代码、migration、生成合同、检查器和最新进度记录为准。

## 1. 总体演进路线

```text
平台蓝图与首批社区能力（v1-v2）
  -> 外部插件隔离与工具链（v3）
  -> 个人空间、集成和前端扩展（v4-v6）
  -> 模块化单体与四类能力边界（v7-v8）
  -> 多端插件生态、权限和物理隔离（v9-v10）
  -> 可靠事务、可信账号和结构化社区（v11-v12）
  -> 可观测、双端体验和可移植交付（v13）
```

## 2. 分版本决策

### v1：先建立平台蓝图

- **起点问题**：项目需要同时覆盖校园社区、身份、权限、事件、插件、API 和数据库，但尚无稳定实现基线。
- **核心取舍**：先描述完整平台和开发路线，再按优先级落地 PostgreSQL、JWT 和社区主流程。
- **形成结果**：建立了后续版本持续使用的领域词汇和平台方向，但部分技术选型、端口、表结构及完成状态
  只反映早期设想。
- **当前阅读方式**：只用于理解项目起源；优先读
  [开发路线图](../项目计划v1/10-开发路线图.md)，不要按 v1 文档部署当前系统。

### v2：让计划回到真实代码

- **起点问题**：v1 蓝图范围过大，计划描述与首批可运行代码出现偏差。
- **核心取舍**：基于真实实现修订架构，把用户 Web、Admin、RBAC、API 和帖子管理拆成可验证阶段。
- **形成结果**：确立了多前端和逐阶段验收思路，也首次系统记录 v1 到 v2 的差异。
- **当前阅读方式**：作为实现校准方法的历史样例；入口是
  [项目概览与 v2 修订说明](../项目计划v2/00-项目概览与v2修订说明.md)。

### v3：把插件从愿景变成交付能力

- **起点问题**：插件只有早期目录和概念，缺少运行时隔离、权限、打包、SDK、CLI 和测试闭环。
- **核心取舍**：优先交付 Wasm、受控 Host API、权限声明和开发工具，不允许插件直接取得核心数据库。
- **形成结果**：建立外部扩展的首个可执行合同和包治理基础。
- **当前阅读方式**：理解插件安全边界的起点；当前开发必须改读 Manifest v2 和官方插件教程。
  历史入口是 [v0.3-dev 计划书](../项目计划v3/02-v0.3-dev计划书.md)。

### v4：扩展个人与运营场景

- **起点问题**：核心社区可用后，个人主页、个人文件、风格、AI 和管理扩展能力不足。
- **核心取舍**：引入 Personal Space、风格包、AI Gateway 和导入闭环，同时保持资源内容受控。
- **形成结果**：为后续 User Storage、Appearance 和 Resource Package 提供原型；部分原计划范围没有在
  v4 内闭合并转入 v5。
- **当前阅读方式**：以 [v4 实现状态与后续规划总结](../项目计划v4/02-v4实现状态与后续规划总结.md)
  为结论，不按原计划中的理想范围推断功能。

### v5：从功能集合转向可运营闭环

- **起点问题**：集成、消息、备份、插件治理和管理入口分散，功能可以运行但难以长期维护。
- **核心取舍**：建设集成中心、Webhook、MCP-like、Message Local、备份恢复和插件治理。
- **形成结果**：形成了低风险集成和运维闭环，给 v6 的统一前后端扩展合同提供基础。
- **当前阅读方式**：以
  [v5 版本计划书第二版](../项目计划v5/01-v5版本计划书第二版.md) 为封版入口；第一版已失去执行作用。

### v6：统一插件前后端贡献方式

- **起点问题**：插件后端 Runtime、前端菜单和页面、配置、事件以及风格包各自演进，生命周期容易混淆。
- **核心取舍**：建立动态 UI、Extension Gateway、三轴生命周期、App Shell 和更严格的权限/数据库检查。
- **形成结果**：外部插件开始能够受控贡献前端体验，但内置业务仍与插件生命周期混在一起。
- **当前阅读方式**：以
  [v6 版本计划书第三版](../项目计划v6/02-v6版本计划书第三版.md) 为最终范围。

### v7：建立模块化单体和四类能力

- **起点问题**：Core、可启停内置功能、外部 Runtime 和纯资源包都被称为“插件”，安全和数据归属不清。
- **核心取舍**：引入 Module Kernel，将能力分为 Core Module、Built-in Feature、External Plugin 和
  Resource Package；通过 Port 和兼容 Adapter 渐进迁移。
- **形成结果**：Moderation、User Storage 等核心边界独立，RichText、Schedule、Appearance 进入
  Built-in Feature，外部插件只能走公开接口。
- **当前阅读方式**：以
  [v7 版本回顾与后续规划](../项目计划v7/01-v7版本回顾与后续规划.md) 为准。v7 只交付 Agent/Runner
  等安全合同，没有交付完整 Agent 产品。

### v8：让目录、装配和领域边界一致

- **起点问题**：v7 已建立分类，但历史目录、Bootstrap、Feature 装配和兼容入口仍有重复。
- **核心取舍**：按功能域收敛模块，保留旧 API、Manifest 和数据路径的 Adapter，逐步强化 Port 与所有权。
- **形成结果**：模块化单体从“分类合同”进入可维护的目录和装配结构。
- **当前阅读方式**：优先读
  [v8 架构重构最终回顾](../项目计划v8/02-v8架构重构最终回顾与后续路线.md)。

### v9：补齐多端插件生态

- **起点问题**：插件目录、用户授权、受管数据、签名预检和 Web/Admin 多端体验不完整。
- **核心取舍**：推出 Manifest v2、本地 Catalog、Grant、受管记录/文件和供应链预检，同时继续默认拒绝
  宿主数据库及完整文件系统权限。
- **形成结果**：外部插件形成从开发、导入、发布、授权到使用的本地闭环。
- **当前阅读方式**：以
  [v9 计划验收审查](../项目计划v9/02-v9计划验收审查与后续规划.md) 区分“功能完成”和当时的
  “环境复验证据”；后者已由后续发布门禁覆盖。

### v10：统一内容、权限和物理归属

- **起点问题**：内容状态存在多份事实，权限名称与操作归属不稳定，内置模块和外部插件的代码/数据仍有混放。
- **核心取舍**：建立 Permission Code、Operation、Owner 和统一内容事实，物理隔离 `modules`、
  `plugins`、`plugin_data` 与资源目录。
- **形成结果**：权限、模块、插件和数据归属可以被机器检查，管理端可以按能力类型展示。
- **当前阅读方式**：以
  [v10 最终全方位审计](../项目计划v10/03-v10最终全方位审计与后续路线.md) 为结论。

### v11：给高风险写操作增加可靠事务内核

- **起点问题**：高风险命令、领域事件和 Webhook 在进程崩溃、重试及多 Worker 下可能出现丢失或重复副作用。
- **核心取舍**：引入 TxKernel、事务 Outbox、lease/fencing、幂等、退避、dead-letter、重放和审计。
- **形成结果**：管理端具备可靠任务视图，关键写入可以追踪命令、事件、投递和失败恢复。
- **当前阅读方式**：优先读
  [v11 最终完成审查](../项目计划v11/02-v11最终完成审查与后续路线.md) 及当前可靠任务运维文档。

### v12：建立可信账号和结构化社区

- **起点问题**：注册/恢复缺少完整邮件验证与限流，管理员准入需要隔离；板块和普通帖子模型不足以表达互助、
  二手等业务。
- **核心取舍**：建设邮箱 Challenge/Ticket、Session、独立管理员准入、可配置频率策略、两级板块和
  结构化图文内容，并复用可靠事务内核。
- **形成结果**：校园互助和二手成为内置结构化内容能力，账号恢复与后台登录边界更清晰。
- **当前阅读方式**：以
  [v12 实施回顾与 v13 进入条件](../项目计划v12/10-v12实施回顾与v13进入条件.md) 为封版入口。

### v13：完成可运营、双端和可移植交付

- **起点问题**：系统能力较完整，但错误合同、容量证据、指标告警、管理员 MFA、移动端体验、风格包双端门禁
  和跨平台交付仍不统一。
- **核心取舍**：先建立测量和安全门禁，再完成统一错误、可观测、TOTP、响应式页面、治理通知与批量操作、
  PC/移动风格包标准，以及 API/Web/Admin/Docs 独立 Docker 镜像和整体 Compose。
- **形成结果**：`v0.13.0` 成为当前产品与交付基线；Windows 采用 Docker Desktop Linux Containers，
  真实发行认证仍以 Linux `amd64` 为主。
- **当前阅读方式**：以
  [v13 最终专业审计](../项目计划v13/02-v13最终专业审计与后续路线.md) 和
  [v0.13 进度证据](../进度/v0.13-dev/) 为准。

## 3. 哪些结论仍约束当前开发

1. CampusOS 保持模块化单体，不把核心业务拆成无必要的微服务。
2. Core、Built-in Feature、External Plugin 和 Resource Package 必须使用不同生命周期和数据归属。
3. 外部插件只能使用公开 API、Host API、Extension Gateway 或已声明的受管能力。
4. Feature 停用、Plugin 卸载和资源包切换不得隐式删除用户数据。
5. 高风险写入必须保留权限、作用域、审计、幂等和可靠事件边界。
6. 风格包必须通过 PC/移动双端合同、安全筛查和资源目录检查。
7. CampusOS Session、Access/Refresh Token、JWT 私钥和数据库凭据永不进入可导出包。

## 4. 当前规划如何形成

v1-v13 的共同趋势是把“能运行”逐步提升为“边界清晰、可以验证、能够恢复并可移植交付”。因此，
下一阶段不应重新堆叠无关功能，而应优先处理真实 Windows/arm64 发行认证、版本化文档、供应链、
Secret Provider 和目标环境运维证据。完整候选见
[当前项目规划与后续路线](01-当前项目规划与后续路线.md)。
