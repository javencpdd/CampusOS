# CampusOS 版本计划总结与有效性

> 审查日期：2026-08-31
> 当前发布基线：`v0.13.0`
> 当前状态：v13 是当前发布基线；v14-dev 的 P0/P1 实现已完成，仍有目标环境与人工 Final 门禁

本目录不替代各版本的原始计划和进度证据。它解决两个问题：

1. 哪些计划仍能指导当前开发，哪些只应作为历史材料。
2. 从 v1 到 v14，CampusOS 为什么逐步形成今天的架构，以及下一步应优先处理什么。

## 1. 使用规则

| 类型 | 含义 |
| --- | --- |
| 当前基线 | 描述现行产品和架构，可以作为新计划输入 |
| 已封版 | 计划范围已经关闭，只能用于追溯决策和验收 |
| 被后版替代 | 原计划中的执行顺序、目录、端口或范围已不再适用 |
| 原始输入 | “计划思路”、提示词和讨论摘录，不是正式计划 |
| 证据附件 | 基线 JSON、截图或容量预算，不是计划本身 |

任何“已完成”结论都必须能从代码、migration、生成合同、检查器和进度证据反向验证。旧计划中未实现的
愿景不会因为写在文档里自动变成当前能力。

## 3. v1-v14 迭代主线

| 版本 | 当时要解决的问题 | 形成的迭代思路 | 当前有效性 |
| --- | --- | --- | --- |
| v1 | 从零建立校园社区、事件、权限和插件愿景 | 先定义完整平台蓝图，再逐步落地核心社区 | 历史蓝图；大量技术栈、端口和“已实现”描述已失效 |
| v2 | v1 范围过大，与首批实现不一致 | 用真实代码修订路线，拆出 Web/Admin、RBAC 和插件阶段 | 历史实现快照；被后续模块化和权限合同替代 |
| v3 | 插件只有早期形态，缺少隔离与交付工具 | 交付 Wasm、Host API 权限、SDK/CLI、包治理和稳定化 | 已封版；现行插件开发应读 Manifest v2 和 docs-site |
| v4 | 平台需要 AI、个人主页、风格和运营能力 | 先建立 AI Gateway、Personal Space、风格包和导入闭环 | 原计划未全量完成；以 `02-v4实现状态与后续规划总结.md` 为历史结论 |
| v5 | v4 剩余集成过多，系统缺少可运维闭环 | 先做集成中心、Webhook、MCP-like、Message Local、备份和插件治理 | 已封版；第二版计划取代第一版执行状态 |
| v6 | 插件后端、前端贡献和风格包合同分散 | 建立动态 UI、Extension Gateway、三轴生命周期、App Shell 与权限/数据库加固 | 已封版；第三版计划取代早期 v6 计划 |
| v7 | 内置业务与外部插件混在同一生命周期 | 建立 Module Kernel、Core/Feature/Plugin/Resource 四分类和安全 Port | 已封版；完整 Agent 产品从未属于 v7 完成条件 |
| v8 | 分类已建立，但功能域和兼容装配仍分散 | 收敛模块目录、Feature 装配、兼容 Adapter 和所有权合同 | 已封版；作为当前模块化单体的结构基础 |
| v9 | 多端体验、Manifest v2、受管数据和本地市场不完整 | 在不开放宿主权限的前提下完善插件目录、用户授权、文件/记录和签名预检 | 功能已完成；当时未完成的环境复验已被后续完整发布门禁覆盖 |
| v10 | 内容状态、权限归属、四类扩展展示和物理目录仍有混用 | 统一内容事实、Permission Code/Operation/Owner、物理隔离和数据治理 | 已封版；当前模块/插件/资源目录规则源于此版 |
| v11 | 高风险写操作、事件和 Webhook 缺少可靠事务闭环 | 建立 TxKernel、Outbox、lease/fencing、重试、dead-letter、重放和审计 | 已封版并复审；是当前可靠任务内核 |
| v12 | 账号可信度、邮件恢复、分层板块和结构化内容不足 | 可信账号与 Session、独立管理员准入、两级板块、互助/二手和可靠事件收敛 | 已封版；是 v13 的业务基础 |
| v13 | 已有能力缺少容量边界、统一错误、可观测、安全管理、双端外观和可移植交付 | 先测量和治理，再补 MFA、响应式、通知/批量操作和 Windows/Linux Docker 交付 | 当前发布基线；计划已封版，不再继续向 v13 追加无边界功能 |
| v14 | 课表学期可由用户自由创建，User Storage 仍以路径/目录计量为主，个人空间缺少私有文档工作区 | 建立 AcademicTerm、Storage Object Layer 和 Personal Documents，使用迁移、版本、对账和隔离预览保护高价值数据 | `v0.14.9-dev` 已完成逐项审查、可恢复对账、文档预览安全降级 receipt 与文档同步；P0/P1 原始代码证据见 `v0.14.5-dev`。v0.13.0 仍是发布基线，历史数据 apply、Linux 目标环境、Converter Runner 与正式发布审查尚未完成 |

## 4. 哪些计划书已失去当前执行作用

### 全目录只作历史参考

- `docs/项目计划v1/`、`docs/项目计划v2/`、`docs/项目计划v3/`：早期架构、命令、端口、表结构和范围
  已被当前实现替代。
- `docs/项目计划v4/00-v4版本计划书.md`：原始范围未全量完成；当前只能结合 v4 总结阅读。
- `docs/项目计划v5/00-v5版本计划书.md`：被第二版及实际 `v0.5-dev` 进度替代。
- `docs/项目计划v6/01-v6版本计划书.md`：被第三版替代。

### 已完成但不再接收新任务

- v7-v13 的正式计划均已封版。它们仍是有效架构和验收历史，但不能继续充当“当前待办列表”。
- v9 文档保留当时“动态环境复验未闭合”的事实；后续版本的完整数据库、恢复和浏览器门禁已经覆盖该风险，
  不需要回写历史文档伪装成当时已通过。

### 不是正式计划

以下文件保留原始需求和推理过程，但不应被搜索结果误认为当前承诺：

- `docs/项目计划v8/功能域重构与兼容-v8计划.md`
- `docs/项目计划v9/多端适配与插件市场-v9计划.md`

- `docs/项目计划v11/v11版计划书思路.md`
- `docs/项目计划v12/v12计划思路.md`

## 6. 维护原则

1. 新版本先建立基线冻结和正式计划，原始讨论文件必须标记为输入材料。
2. 计划、实现和验收状态分开；没有运行证据时不能写“已验收”。
3. 已封版计划不追加无边界需求。新需求进入缺陷修复、明确补充阶段或下一版候选。
4. 历史文档不删除、不改写当时证据；当前入口通过本目录和 docs-site 维护。
5. v14 的当前状态以 [v0.14.9-dev 进度记录](../进度/v0.14-dev/v0.14.9-dev.md) 与
   [逐项审查与项目回顾](../项目计划v14/01-v14计划逐项审查与项目回顾.md) 为准，P1 的代码完成度以
   [v0.14.5-dev](../进度/v0.14-dev/v0.14.5-dev.md) 为准；范围与 Final 门禁以
   [v14 正式项目计划](../项目计划v14/00-v14版本计划书.md) 为准，不能因 P0/P1 已实现而提前宣称发布。

需要了解每版的起点问题、关键取舍、形成结果和当前阅读方式时，继续阅读
[v1-v13 迭代思路详解](02-v1-v13迭代思路详解.md)。
