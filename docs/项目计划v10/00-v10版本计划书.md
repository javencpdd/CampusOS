## 1. 计划结论

v10 不再进行一次新的底层架构重写。v7、v8 已建立模块化单体和四类扩展边界，v9 已建立 Manifest v2、受管数据、用户授权和本地插件市场基础；v10 的任务是让这些能力在真实产品流程中具有一致语义、清晰入口和可验证的安全边界。

本版本围绕五条主线展开：

1. 内容发布、审核、下架、整改、恢复和删除形成不可绕过的后端状态机。
2. 帖子列表、个人主页、搜索、管理端和集成查询共享 Community 内容事实源。
3. 外部插件、内置功能、资源包和集成在产品界面统一呈现，但继续保持不同生命周期。
4. Web、Admin 和动态插件 UI 从“断点适配”升级为按容器、方向、输入方式和信息密度适配。
5. 权限从角色内嵌的 `resource:action` 演进为稳定权限 Code、作用域、路由绑定和审计闭环。

项目目录和数据库整理必须建立在事实清点、弃用周期、备份和恢复演练之上。无法确认归属的文件或数据表只能进入调查清单，不能直接删除。

## 2. 已核验基线

以下结论来自当前代码、迁移、前端和 v9 验收记录，不以目录名称推断功能。

| 领域 | 当前事实 | v10 判断 |
| --- | --- | --- |
| v9 验收 | P0/P1 功能已实现；最新数据库动态检查和前端修改后的多视口回归受环境限制未闭合 | A0 必须先补跑并冻结基线，不能把历史证据冒充当前证据 |
| 内容状态 | Community 使用单一 `ThreadStatus`；RichText 另有 `draft/published/offline/deleted` | 两套状态含义会漂移，需要渐进引入发布、审核、删除三个维度 |
| 下架绕过 | RichText 下架后，作者编辑并调用发布可再次写成 `published` | P0 安全缺陷，先补失败测试，再修改后端转换规则 |
| 删除行为 | PostgreSQL Thread 删除为 `deleted_at`，Memory 实现存在行为差异 | A2 先形成 Adapter 一致性清单，A3 再统一回收站合同 |
| 个人主页 | `user_space_contents` 通过事件复制标题、摘要、版块、标签和状态，并有回填逻辑 | 投影不是公开可见性的最终事实源；先改读路径，再进入弃用周期 |
| 标签 | 存在 `tags` 关系模型、`threads.tags` 和版块默认标签等多条路径 | A2 统计读写和数据差异，ADR 决定唯一事实源，不预先删表 |
| 插件中心 | 用户只看 `published` Catalog；新发现 External Plugin 默认是 `draft` | 空列表符合治理逻辑，但缺少说明、申请入口和开发环境示例数据 |
| 示例插件 | v2 managed 示例主要是 Manifest/README，声明的运行命令没有形成普通用户可体验的完整闭环 | 需要一个可运行、可授权、可导出和可卸载的官方示例 |
| 响应式 | 已有安全区域、触控目标和基础媒体查询；课表等密集页面仍依赖横向滚动 | 新增布局能力层，优先改造实测问题页面，不全站一次重写 |
| Admin 信息架构 | 用户、版主、帖子、审核、外部插件、市场、内置功能均为平级菜单 | 按业务域聚合导航和路由；后台 Service 生命周期不合并 |
| 权限存储 | `permissions` 直接包含 `role_id/resource/action`；版主已有 category scope | 缺少独立权限定义、角色权限关联和稳定权限 Code |
| 路由登记 | Runtime Registry 使用 `http.*`；静态审计器使用 `httpapi.*`，均由路径推导 | A10 必须统一权威来源，并为旧 ID 保留别名和差异检查 |
| Admin 授权 UI | 当前支持角色查看、用户角色分配/撤销和版主版块作用域配置 | 尚无自定义角色、权限矩阵编辑和授权审计界面 |
| 集成中心 | Webhook 可配置；MCP 为内部 MCP-like；Message 是 Local Adapter | 页面必须显式显示成熟度、能力边界、配置状态和文档 |
| API 根路径 | 已创建 `/api/v1` Group，但没有根处理器和统一 API NoRoute | 增加内容协商后的 API Index 与结构化错误响应 |
| 数据迁移 | 计划起始基线为 `000001` 至 `000022`；当前已顺序追加至 `000026` | v10 只能追加迁移，禁止改写历史迁移 |
| 构建产物 | Web、docs-site 构建目录已有忽略规则；Admin 构建产物政策需纳入清点 | 先由 generated-files 检查器验证，再调整忽略或追踪策略 |

## 3. 范围与非目标

### 3.1 v10 范围

- 十个实测问题的自动化复现和责任模块映射。
- 内容三维状态、版本、审核案例、整改重提、回收站和审计。
- Community `ContentQuery` Port 与个人主页读路径切换。
- 用户插件中心空态、用途说明、风险说明和官方示例插件。
- 统一布局能力层与课表等重点页面的七视口适配。
- Admin 按业务域重组，保留旧 URL 重定向。
- 稳定权限 Code、路由操作 ID、角色权限矩阵、作用域和授权审计。
- Webhook、MCP-like、Message Local 的成熟度与文档入口。
- `/api/v1` Index、统一 API 404 和错误码合同。
- 项目目录、数据表、读写路径、兼容对象和生成物清单。
- 只对证据充分的对象执行渐进清理和追加迁移。
- 将编译期模块、External Plugin、Resource Package 及各自数据做可迁移、可回滚的物理隔离。

### 3.2 明确非目标

- 不重写 v7/v8 模块化单体，不拆成大量微服务。
- 不把 Built-in Feature、External Plugin 和 Resource Package 合并为同一种后端生命周期。
- 不在生产环境自动安装、启用或发布示例插件。
- 不实现任意条件表达式、跨租户 ABAC 或外部策略引擎。
- 不将插件用户 Grant、External Plugin Host API 权限并入管理员 RBAC 表。
- 不实现标准 MCP Server、远程公共插件商店或第三方消息生产 Adapter。
- 不用 `transform: scale()`、User-Agent 或整页缩放代替响应式布局。
- 不在同一阶段同时进行大规模目录移动和数据库模型清理。
- 不物理删除未知数据、历史迁移、用户文件或未完成弃用周期的兼容入口。

## 5. 核心设计合同

### 5.1 内容状态与审核

内容状态拆为三个正交维度：

```text
publication_status: draft | published | private
moderation_status: clear | pending | rejected | taken_down
deletion_status: active | trashed | purged
```

公开读取必须由后端统一执行：

```text
publication_status = published
AND moderation_status = clear
AND deletion_status = active
```

转换规则：

| 操作 | 前置条件 | 结果 | 额外要求 |
| --- | --- | --- | --- |
| 保存草稿 | 作者可编辑且未 purged | publication=draft | 写入 revision |
| 首次发布 | 内容合法，按版块策略决定是否审核 | clear+published 或 pending | 不能由客户端提交审核状态 |
| 管理员下架 | 已公开且有 `community.thread.take_down` | moderation=taken_down | 原因、操作者、版本和审计必填 |
| 作者整改重提 | taken_down/rejected 且作者有编辑权 | moderation=pending | 不能直接恢复 clear |
| 审核通过 | pending 且有审核权限 | moderation=clear；按意图恢复 published/private | 审计记录审核版本 |
| 管理员直接恢复 | taken_down 且有独立高风险权限 | moderation=clear | 二次确认、恢复原因和目标版本 |
| 移入回收站 | active 且有删除权 | deletion=trashed | 可恢复；公开查询立即隐藏 |
| 永久清除 | trashed 且满足保留期和高风险权限 | deletion=purged | 异步资产清理、不可恢复审计 |

兼容策略：

- 首次迁移增加新字段和新表，不删除现有 `status`。
- 先回填并双写，运行一致性检查；读路径稳定后再改为新状态为主、旧状态为兼容投影。
- RichText 与普通文本必须使用同一状态机应用服务，不允许各自实现发布或下架规则。
- PostgreSQL 与 Memory Adapter 必须通过同一合同测试，尤其验证删除、恢复和过滤语义。

建议新增的持久化对象在 A2/A3 ADR 后冻结：

```text
content_revisions
content_moderation_cases
content_moderation_actions
```

### 5.2 统一 ContentQuery

- Community 拥有帖子事实和公开可见性判断。
- `ContentQuery` 支持作者、状态、版块、标签、格式、关键词和稳定分页，但调用方只能使用公开 Port。
- 访客个人主页只读取公开谓词命中的内容；作者视图可读取本人非公开状态和原因摘要；管理端使用独立权限查询。
- Personal Space 保存个人资料、样式和展示偏好，不复制帖子正文或决定帖子可见性。
- 搜索、MCP-like 和其他只读集成复用相同可见性策略，不能各自拼接状态条件。
- `user_space_contents` 先进入只读比对和弃用期；完成数量、状态和标签差异报告后，才能停止写入或删除。
- 标签唯一事实源由 A2 的数据审计和 ADR 决定，不能仅凭表名选择。

### 5.3 插件与扩展产品语义

管理端提供“扩展与集成”聚合入口，并显示每项能力的真实类型：

| 类型 | 可执行操作 | 不允许的操作 |
| --- | --- | --- |
| External Plugin | 导入、审核、安装、启动、停用、升级、卸载 | 伪装成 Built-in Feature 或直读核心数据库 |
| Built-in Feature | 查看配置、按策略启停、查看重启要求 | 普通安装、卸载或删除其系统数据 |
| Resource Package | 校验、导入、应用、导出、删除未使用版本 | 注册业务进程或数据库迁移 |
| Integration Adapter | 配置、测试、查看健康和审计 | 把实验能力显示为生产就绪 |

用户插件中心遵守：

- Catalog 无已发布项时说明原因，并提供“提交安装建议”和文档入口。
- 普通用户优先看到用途、使用场景、数据使用、风险、关闭后数据和维护者；Manifest、Runtime 和权限原始值折叠展示。
- Manifest v2 仅增加可选用户体验元数据；旧包保持可解析，缺少字段时使用安全默认文案。
- 官方示例只能通过显式开发初始化命令导入和发布；生产启动不自动安装任何插件。
- 官方示例必须有真实 Runtime、受管数据/文件授权、中文教程、测试、签名、导出和卸载验证。

### 5.4 自适应布局合同

`useLayoutCapability()` 输出布局能力而不是设备名称：

```text
mode: compact-portrait | compact-landscape | regular | wide
containerWidth
orientation
pointer: coarse | fine
hover: available | unavailable
reducedMotion
density
```

实现优先级为 Container Query、`ResizeObserver`、`matchMedia` 和稳定设计 Token。页面可以根据任务选择表格、分组列表、紧凑卡片、抽屉或全屏编辑器，但不得通过缩放整页隐藏布局问题。

固定回归视口：

```text
320 x 568
360 x 800
393 x 852
768 x 1024
1024 x 768
1366 x 768
852 x 393 landscape
```

共同验收：无非预期横向滚动、文字和操作不重叠、触控目标不小于 44px、键盘焦点可见、正文和背景达到 WCAG AA 对比度、系统字体放大后仍可完成关键流程。

### 5.5 权限与路由合同

完整设计和入门说明见 `docs/help/系统设计相关/v10权限管理设计与使用入门.md`。v10 必须遵守以下分层：

```text
用户身份
  -> 角色分配（global/category）
  -> 角色拥有的稳定权限 Code
  -> 路由操作 ID 绑定权限 Code
  -> Service 使用服务端资源上下文执行作用域/所有权判断
  -> 授权结果与高风险操作审计
```

关键约束：

- 数据库数字 ID 只用于关联；代码、文档和审计使用稳定 Code。
- 权限 Code 使用 `<domain>.<resource>.<action>`，例如 `community.thread.take_down`。
- 路由操作 ID 和权限 Code 是两个概念；一个权限可保护多个路由。
- 路由操作 ID 由显式声明产生，不再仅从 URL 推导；旧 `http.*`/`httpapi.*` 保存为兼容别名。
- 首版只支持 `global` 与 `category` 角色作用域；资源所有者判断由服务端 Policy 完成，不伪装成客户端可填的 scope。
- Admin 路由中间件是第一道门禁，应用服务必须再次检查资源上下文和状态转换。
- Plugin User Grant、External Plugin Host 权限和管理员 RBAC 分开存储、分开授权。
- 禁止管理员给自己授予超出自身权限的角色；禁止删除最后一个有效系统管理员；系统角色受保护。

建议追加模型：

```text
permission_definitions
role_permissions
route_operations
route_permission_bindings
authorization_audits（若现有审计不能满足结构化字段时）
```

现有 `permissions(role_id, resource, action)` 不立即删除。先回填新目录、双读比对、切换读路径，再进入至少一个版本的弃用期。

### 5.6 API 与错误合同

- `GET /api/v1` 对 `Accept: application/json` 返回版本、健康、OpenAPI、文档和主要资源链接。
- 浏览器 HTML 请求返回简洁的 API 提示页或明确跳转，不暴露内部配置。
- `/api/v1/*` 未匹配路由统一返回 JSON：`code`、`message`、`request_id`、可选 `details`。
- 鉴权失败、权限不足、功能停用、状态冲突、校验失败和不存在使用稳定错误 Code。
- 非 API 前端 fallback 与 API NoRoute 分开处理。

## 6. 数据与兼容策略

1. 历史 migration `000001` 至 `000022` 只读；v10 使用新的顺序 migration。
2. 所有状态和权限迁移先新增、回填、双写、比对，再切读；禁止“建新表后立即删旧表”。
3. 每次回填记录行数、孤儿记录、冲突、耗时和 checksum；大数据量使用可恢复批次。
4. Feature 停用、插件停用和内容下架都不能隐式删除用户数据。
5. `modules`/`internal/modules` 只保存编译期模块合同与实现；`data/plugins`/`data/plugin_data` 只保存 External Plugin 实现与私有运行数据。
6. Built-in Feature 本地数据使用 `data/module_data`；Resource Package 统一使用 `data/resources`，不再把风格包当作插件数据。
7. 目录移动必须使用冲突安全脚本、移动状态记录和逆向回滚；跨文件系统操作不得假设原子 rename。
8. 删除表、目录或兼容 API 前必须有所有者、最后写入路径、读取统计、弃用公告、备份和恢复证据。
9. Memory 与 PostgreSQL Repository 必须共享合同测试，不能把仅在生产数据库出现的行为差异留到发布阶段。

## 10. 风险与禁止事项

- 禁止一次性替换内容、权限或插件平台全部实现。
- 禁止只修改前端按钮来修复下架、删除或权限绕过。
- 禁止客户端提交可信 `scope_id`、审核状态、操作者或资源所有者。
- 禁止使用路由数字主键或 URL 推导值作为业务权限 Code。
- 禁止 External Plugin、Agent Runner 或集成 Adapter 直接访问核心数据库、JWT 私钥、CampusOS Token 或内部 Service。
- 禁止把管理员 RBAC 和插件用户同意合并；管理员批准插件不等于用户授权个人数据。
- 禁止 Feature 停用、插件停用、内容下架或应用回退时删除用户数据。
- 禁止修改历史 migration，禁止未备份清表，禁止为了通过检查移除约束和审计。
- 禁止用整页缩放、无限横向滚动或仅靠设备名称处理移动端。
- 禁止把实验性 MCP-like 和 Message Local 宣称为标准或生产就绪能力。
- 禁止在 A2 事实清点完成前执行 A13/A14 删除动作。

## 11. 最终成功标准

v10 只有在以下条件同时成立时才能标记 `v0.10.0`：

1. 管理员下架后的普通文本和 RichText 都不能被作者直接重新公开。
2. 帖子列表、个人主页、搜索、Admin 和只读集成使用相同内容事实与可见性规则。
3. 用户插件中心即使没有已发布插件也能解释原因并完成安装建议；官方示例可在开发环境完整运行。
4. Core/Built-in Feature、External Plugin、Resource Package 和 Integration 在界面统一可发现，并在描述符、实现、Runtime、API 和数据目录保持独立生命周期。
5. 课表和首批重点页面在七个视口无关键重叠和非预期横向滚动。
6. 每个管理 API 都能追溯到唯一 route operation、模块所有者、稳定权限 Code、作用域和审计策略。
7. 角色和权限调整具备越权保护、最后管理员保护、版块作用域和审计记录。
8. `/api/v1` 和未知 API 返回可理解、稳定且不泄露内部信息的响应。
9. 每个活跃目录和数据表有所有者、用途和保留策略；模块数据、插件数据和资源包可机器检查，任何迁移/删除均有备份与回滚证据。
10. 全量测试、数据库迁移、联合恢复、浏览器回归和发布门禁均有 v10 当次通过证据。
