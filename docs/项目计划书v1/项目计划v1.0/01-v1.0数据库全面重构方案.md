# CampusOS v1.0 数据库全面重构方案与影响清单

> 文档状态：已实施并通过隔离数据库验证  
> 方案版本：`v1-db-baseline-v1`  
> 更新时间：2026-09-01  
> 决策来源：项目所有者明确允许删除全部测试数据，不要求旧 migration 或旧 Schema 兼容  
> 实施文件：`migrations/000001-000003`、`scripts/migrate.*`、`scripts/schema-contract.sql`

## 1. 目标与边界

本次工作不是继续修补旧 `000001-000049` 链，而是按当前代码实际依赖和 v1.0 业务方向重建数据库事实来源。目标是：

1. 任意空 PostgreSQL 16+ 数据库可由三份 migration 重建当前完整结构。
2. 删除已完成替代的旧权限双轨和 migration 内测试凭据。
3. 把身份、社区、存储、可靠性、插件等现行业务模型完整纳入单一基线。
4. 为 v1 插件稳定身份、不可变版本、三层授权、委托和 Secret 托管建立关系模型。
5. 统一时间、状态、JSON、外键、唯一性和索引规范。
6. 让 Windows 和 Linux 使用同一执行语义，并能检测 migration 篡改、并发执行和危险 reset。
7. 后续从 `000004` 开始恢复严格追加式演进，避免再次积累不可解释的修复链。

明确不做：

- 不支持旧 `schema_migrations` 原地升级；
- 不迁移、保留或自动识别旧测试数据；
- 不在 migration 中生成默认管理员、默认密码、邮箱或默认版块；
- 不因“以后可能有用”创建没有业务查询和约束含义的表或索引；
- 本次只交付插件 v1 数据基础，不宣称 AuthorizationService、Admin Grant UI、User Consent UI 已全部完成。

## 2. 重构前数据模型与需求清单

### 2.1 身份、认证与授权

| 模型 | 表 | 当前需求 |
| --- | --- | --- |
| 用户主体与凭据 | `users`、`accounts` | 用户状态、邮箱规范化、验证状态、密码版本、软删除 |
| 会话 | `sessions` | 只保存必填 Refresh 摘要与 IP 摘要、Token Family、轮换、撤销、MFA 强度、过期索引；不保留明文 Token 或原始 IP |
| 管理平面准入 | `identity_admin_accounts` | RBAC 授权与 Admin 登录准入分离，支持暂停/恢复/审计 |
| 邮箱验证与限流 | `identity_email_challenges`、`identity_challenge_rate_limits`、`identity_challenge_policies` | 验证码不明文入库、单用途 Ticket、服务端频率策略 |
| 恢复与历史标识 | `identity_account_recovery_cases`、`identity_legacy_email_placeholders`、`identity_reserved_identifiers` | 受控账号恢复、历史冲突留痕、禁止重用保留标识 |
| MFA | `identity_mfa_totp_methods`、`identity_mfa_tickets`、`identity_mfa_recovery_codes`、`identity_mfa_policies` | 加密 TOTP、摘要 Ticket/恢复码、管理员策略 |
| RBAC | `roles`、`user_roles`、`permission_definitions`、`role_permissions` | 稳定 Permission Code、global/category Scope、最小角色矩阵 |
| 路由合同与审计 | `route_operations`、`route_permission_bindings`、`authorization_audits` | 路由操作到权限的显式映射及高风险授权证据 |

重构决策：删除旧 `permissions(resource, action)`。代码中的两处 legacy 查询已改为读取
`role_permissions JOIN permission_definitions`，从而只保留一个权限事实来源。

同时删除 `sessions.refresh_token` 和 `sessions.ip_address` 两个仅为旧升级链保留的空列，将
`refresh_token_digest` 改为必填并保持全局唯一。触发函数固定 `pg_catalog, public` search path，防止连接级
search path 改变约束函数实际访问的对象。

### 2.2 社区、帖子与内容治理

| 模型 | 表 | 当前需求 |
| --- | --- | --- |
| 两级分类 | `categories`、`category_thread_type_policies` | group/board 两级约束、归档状态、允许帖子类型 |
| 帖子与回复 | `threads`、`posts` | 普通/互助/二手/图文类型、治理状态、楼层与父楼层快照 |
| 标签与互动 | `tags`、`likes`、`notifications` | 标签、点赞计数、用户通知和已读状态 |
| 内容治理 | `content_revisions`、`content_moderation_cases`、`content_moderation_actions` | 修订历史、审核案例、管理员动作 |
| 图文 | `richtext_article_contents`、`richtext_article_assets` | 受控 HTML/JSON、源文件元数据、上传者归属 |
| 互助 | `mutual_aid_details` | 类型、状态、联系方式、位置和作者一致性 |
| 二手 | `secondhand_details` | 以分为单位的整数金额、币种、成色、交易方式和状态 |

核心不变量由 CHECK、外键和触发器同时保护，避免只依赖 Web 表单验证。

### 2.3 用户空间、文件、学期与文档

| 模型 | 表 | 当前需求 |
| --- | --- | --- |
| 个人空间 | `user_spaces`、`user_space_contents`、`user_space_style_snapshots` | 主页配置、同步内容、样式快照 |
| 配额与对象账本 | `user_storage_quotas`、`user_storage_accounts`、`user_storage_reservations`、`storage_objects` | 配额授权、已用/预留字节、staging/ready/deleted 状态、对象摘要 |
| 学期与课表 | `academic_terms`、`user_schedule_terms`、`user_schedule_preferences` | 开放/关闭/默认学期、第一周快照、当前对象和查看偏好 |
| 个人文档 | `personal_documents`、`personal_document_versions`、`personal_document_previews` | 私有文档、不可变版本、源对象和预览任务 |

金额保持最小单位整数而不是浮点；对象内容仍位于受控文件存储，PostgreSQL 保存权威账本和关系。

### 2.4 当前插件 Runtime、市场和受管数据

`plugins`、`api_keys`、`plugin_permissions`、`plugin_logs`、`plugin_records`、
`plugin_file_metadata`、`plugin_user_grants`、`plugin_catalog_entries`、
`plugin_install_requests`、`plugin_releases`、`plugin_market_audits` 是当前代码仍在读写的运行模型。

这些表进入 `000001`，不是为了兼容旧数据库，而是因为它们仍属于当前业务实现。后续 v1 服务完成切换后，
才能用新的前向 migration 删除被完全替代的列或表。

### 2.5 可靠性、集成与平台治理

| 模型 | 表 |
| --- | --- |
| 事务事件与消费 | `platform_outbox`、`platform_outbox_attempts`、`outbox_consumer_receipts` |
| 命令、Worker 与操作 | `platform_command_audits`、`platform_worker_leases`、`platform_operation_runs` |
| 兼容和保留策略 | `platform_compatibility_usage`、`platform_retention_runs` |
| 功能与配置 | `builtin_feature_states`、`configurations` |
| 审计与集成 | `audit_logs`、`webhook_endpoints`、`webhook_deliveries`、`message_bindings`、`message_logs`、`mcp_audit_logs`、`ai_call_logs` |

### 2.6 v1 插件数据准备

| 新表 | 业务含义 | 关键约束/索引 |
| --- | --- | --- |
| `plugin_publishers` | 稳定发布者及信任状态 | active slug 唯一；trust CHECK；metadata 必须为 object |
| `plugin_versions` | 不可变包版本、摘要、签名和权限指纹 | 插件+版本/摘要唯一；每插件最多一个 active；SHA-256 格式检查 |
| `plugin_capability_declarations` | 某版本声明的逐项能力、用途、风险和数据分级 | 版本+能力唯一；code/risk/scope/data class CHECK |
| `plugin_admin_grants` | 管理员逐能力平台授权 | 联合外键指向声明；每项一条当前决策；revision 正数 |
| `plugin_user_consents` | 用户逐能力数据同意 | 用户+版本+能力一条当前决策；purpose hash；可撤销 |
| `plugin_delegations` | 有时效的后台任务委托 | 只存 Token digest；有效期、状态和能力数组约束 |
| `plugin_secret_values` | 宿主管理的插件密文 Secret | 密文/nonce 非空；系统级 NULL owner 也参与唯一性 |
| `plugin_authorization_decisions` | 每次授权判定证据 | request UUID 唯一；按插件/用户/拒绝时间索引 |

用户不需要手工生成长期 API Key 才能完成三层授权。用户在 Web 上确认 Consent；宿主如需后台执行，会签发短期
Delegation 的原始 Token，并且数据库只保存摘要。Secret 也只由宿主加密保存。

## 3. 新基线结构

```text
000001_v1_schema_baseline
  └─ 76 张现行业务表 + 约束/索引/函数/触发器

000002_v1_plugin_authorization_foundation
  └─ 8 张 v1 插件表 + plugins.publisher_id

000003_v1_reference_data
  └─ 4 个系统角色 + 76 个 Permission Code + 最小角色矩阵 + 身份安全策略

scripts/migrate.*
  └─ schema_migrations + schema_migration_locks
```

最终为 84 张业务表和 2 张 migration 系统表。

## 4. 逐步调整及影响

| 步骤 | 调整 | 正向影响 | 破坏性影响/处置 |
| --- | --- | --- | --- |
| 1 | 冻结旧 49 段最终 Schema 并在隔离库导出结构 | 避免人工重写遗漏约束、索引或触发器 | 旧 migration 编号不再代表当前建库路径 |
| 2 | 将最终结构规范化为 `000001`，删除 Session 明文 Token/IP 空列并固化函数 search path | 空库一次得到当前模型；时间和敏感数据边界统一 | 旧库必须 reset，不能原地 up |
| 3 | 删除 `permissions` 并修改 Repository 查询 | 消除双权限目录和授权漂移 | 任何仍直接访问旧表的外部 SQL 会失败，应改用 Permission Code |
| 4 | 去除管理员/邮箱/默认版块测试种子 | 不再传播默认密码或个人标识 | 首次管理员必须通过安全 bootstrap/CLI 创建 |
| 5 | 新增 `000002` 八张插件基础表 | v1 能在关系约束下实现三层授权和 Secret 托管 | 当前 Runtime 尚未切换到新表，不能把“表已存在”当成功能已完成 |
| 6 | 新增 `000003` 稳定参考数据 | 权限、角色和安全策略可重复且无业务测试数据 | 角色矩阵变化必须走新 migration |
| 7 | 重写跨平台执行器 | checksum、事务、互斥锁、单步 down、危险 reset 双确认 | 旧三列 `schema_migrations` 会被拒绝 |
| 8 | 收敛 schema/audit/hygiene 合同和 CI | 零建库、回滚、漂移、冗余、数据审计进入统一门禁 | 旧 v10-v14 drill 不再验证历史文件，旧命令仅转发新门禁 |
| 9 | 同步 Admin 数据架构视图和文档 | 86 张表、三段 migration 与当前代码一致 | 历史架构文档仅作版本快照，不能作为当前建库指南 |
| 10 | 从 `000004` 恢复追加式演进 | 后续升级有明确版本、down 和 checksum 合同 | 合并后的 `000001-000003` 禁止再改写 |

## 5. 字段、约束与索引设计规范

### 5.1 字段

- 时间点：`TIMESTAMPTZ`；学期第一周等日历日期：`DATE`。
- 金额：最小货币单位 `BIGINT`，避免浮点误差。
- ID：延续应用层分布式 `BIGINT` ID；外部请求标识可用 UUID。
- 状态：有界 `VARCHAR` + CHECK，状态切换由 Service 和数据库共同保护。
- JSONB：只承载扩展/快照/Manifest，必须检查顶层 object/array；关键授权事实不得塞回权限数组。
- Secret/Token/验证码：只存摘要、密文、nonce 和 key version，不存原文。
- 乐观并发：可变治理事实使用正整数 `version/revision`。
- 扩展准备：可演进元数据使用 `metadata JSONB DEFAULT '{}'`，但不能代替稳定核心列。

### 5.2 外键与删除

- 用户私有数据通常 `ON DELETE CASCADE`；
- 审计、版本和已被业务引用的目录使用 `RESTRICT`；
- 操作者、可选 Owner 和被撤销的证据引用使用 `SET NULL`；
- 所有删除语义必须显式写出，不接受 PostgreSQL 默认行为作为隐含设计。

### 5.3 索引

当前保留的索引分为：

1. 业务唯一性：用户名、规范化邮箱、角色权限、对象存储 Key、插件版本/摘要等。
2. 活动记录唯一性：软删除或 superseded 后允许重建，使用部分唯一索引。
3. 外键与清理：用户、帖子、对象、插件版本等关联扫描。
4. 列表查询：状态 + 更新时间/创建时间、Owner + ID/时间。
5. Worker 领取：状态、available/lease/attempt 条件。
6. 安全审计：拒绝判定、用户授权、过期 Grant/Consent/Delegation。

当前 97 个外键均由引用端前导索引覆盖，避免父记录更新/删除触发无界子表扫描；Schema 合同会阻止后续引入
无覆盖外键。`migration-hygiene.sql` 还会拒绝完全重复索引、重复约束和被同谓词复合 B-tree 严格覆盖的窄索引。

## 6. reset 与日常升级

旧开发库必须显式重置。Windows：

```powershell
$env:CAMPUSOS_SKIP_DOTENV = "true"
$env:PSQL_MODE = "docker"
$env:POSTGRES_CONTAINER = "campusos-dev-postgres-1"
$env:DB_NAME = "campusos"
$env:CAMPUSOS_ENV = "development"
$env:CAMPUSOS_RESET_CONFIRM = "campusos"
.\scripts\migrate.ps1 reset
```

Linux/Git Bash：

```bash
CAMPUSOS_SKIP_DOTENV=true \
PSQL_MODE=docker \
POSTGRES_CONTAINER=campusos-dev-postgres-1 \
DB_NAME=campusos \
CAMPUSOS_ENV=development \
CAMPUSOS_RESET_CONFIRM=campusos \
./scripts/migrate.sh reset
```

必须先确认目标确实是可丢弃的 CampusOS 开发/测试数据库。当前实现只接受 `development`/`test`，明确拒绝
production、staging 和其他环境标签，并要求确认字符串和真实 `DB_NAME` 完全相同。reset 后重新启动 API，
让安全 bootstrap 和运行时 seed 创建必要实例数据。

日常后续升级只执行 `up`，不再 reset：

```powershell
.\scripts\migrate.ps1 check
.\scripts\migrate.ps1 up
```

- 97 个外键均有引用端前导索引；

- 数据审计 78 项、违规 0；
- 索引/约束 hygiene 问题 0；
- Admin 架构视图 86/86 对齐。

```bash

make database-check
```

1. 从 `000004` 起追加，不再修改 `000001-000003`。
2. 实现 AuthorizationService，把 Host API、事件、任务、Secret 和受管数据统一接入判定。

4. 实现 Admin Grant、User Consent、升级权限 diff、即时撤销和 UI。
