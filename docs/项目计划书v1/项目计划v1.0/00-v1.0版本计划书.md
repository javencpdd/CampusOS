## 2. 项目背景与问题定义

CampusOS 已经具备可运行的本地插件闭环，而不是空白平台：

- Manifest v1/v2 可声明 Host API 权限、用户权限、配置 Schema、事件、受管记录和受管文件。
- Host API v1/v2 通过插件名与运行时令牌认证，按方法映射 `resource/action`，停用或停止插件会阻断调用。
- 用户可在 Web 插件中心选择授权项、撤销授权、查看和删除受管数据；授权与插件版本绑定。
- Admin 可管理插件生命周期、导入预检、签名状态、权限增删和本地目录发布。
- 插件包已有 SHA-256、Ed25519 信任、权限差异预检和失败恢复路径。
- Go SDK、TypeScript UI SDK、Harness 及 `campusosctl plugin init/build/test/pack/sign/install/verify/dev` 已存在。
- migration `000021` 起已有受管记录、文件、用户 Grant、目录、Release 与市场审计；`000025` 建立了平台 RBAC 权限目录。

当前缺口是这些能力仍分散：Host API 主要验证 Manifest 声明，管理员批准没有独立、可撤销的逐能力事实；用户 Grant
按插件保存权限数组，缺少逐能力状态、用途变更和统一拒绝原因；插件身份以名称为主；事件、后台任务、配置 Secret、稳定 DTO
与进程协议没有共享同一个授权判定核心。`GetUser` 等接口还可能暴露超过最小用途的字段，未知 Host API 方法也必须从兼容行为收紧为默认拒绝。

因此 v1.0 的问题不是“增加更多权限开关”，而是把既有能力收敛成一个可证明的授权系统：

```text
有效权限 = Manifest 声明
         ∩ 管理员授予
         ∩ 用户同意（仅 consent_required 能力）
         ∩ 插件身份与版本
         ∩ 资源 Scope
         ∩ 运行状态
         ∩ 系统安全策略
```

## 3. 版本目标与成功标准

### 3.1 核心目标

1. 建立统一 Capability Catalog 和单一 `AuthorizationService`，所有插件敏感操作通过同一判定入口。
2. 完成“声明、管理员授予、用户同意”三层授权；任何一层不能扩大上一层能力。
3. 建立稳定插件身份、版本、发布者、包摘要和权限指纹，新增或扩权不自动继承旧授权。
4. 把 Host API、受管数据/文件、事件、后台任务、配置和 Secret 纳入相同安全边界。
5. 以 Manifest v3、Host API v3 和稳定 DTO 推进新合同，同时为 v1/v2 提供有期限的兼容适配。
6. 提供管理员和用户可理解的授权界面、机器可读拒绝原因、审计、诊断和应急停用。
7. 完善 SDK、CLI、Harness、参考插件和 Conformance Suite，使第三方插件能够在不接触宿主内部结构的前提下开发。
8. 以 clean baseline 重建全部测试数据库；基线冻结后从 `000004` 起恢复追加 migration、checksum 和受控 reset 规范。

### 3.2 可量化成功标准

| 维度 | v1.0 Final 门槛 |
| --- | --- |
| 授权覆盖 | 插件可调用的 Host API、事件订阅、后台任务、Secret、受管记录/文件入口 100% 绑定 Capability 和判定测试 |
| 默认拒绝 | 未知方法、未知 Capability、版本不匹配、未授予、未同意、Scope 不匹配、停用/隔离均稳定拒绝 |
| 撤销 | 管理员撤销、用户撤销或紧急停用提交成功后，下一次敏感调用不得继续命中旧的允许结果 |
| 升级 | Added/Expanded/Purpose Changed 必须重新审批；Removed/Reduced 可收缩但不得暗中恢复 |
| 数据 | 空库 up、checksum drift、逐步 down/up、全链 reset、Schema/审计/冗余合同均有自动证据 |
| 契约 | Manifest/Host API/事件/错误/Capability 均有版本化机器合同和 drift check |
| 工具链 | 参考插件可完成 init、build、test、verify、pack、install、授权、撤销、升级和诊断闭环 |
| 体验 | Admin 可解释“谁授予了什么”，用户可理解用途/风险/数据范围并单项撤销 |
| 性能 | G0 建立基准后，授权热路径 p95 目标不高于 5 ms、冷路径不高于 20 ms；若环境不具可比性，以批准后的基线回归阈值为准 |

## 4. 范围

- 架构与威胁模型冻结、Capability Catalog、插件身份/版本模型。

### 4.2 P1：v1.0 应完成

- required/optional 能力和 `self/system` Scope。
- 有时效、可撤销、不可扩权的后台任务 Delegation。

- 事件发布/订阅授权与 `campusos.event/v1` 稳定 Envelope。

- `runtime: process` 与 `campusos.process/v1`；历史 `runtime: grpc` 仅作兼容别名。
- 统一诊断、SDK/CLI/Harness 增强、Conformance Suite。
- 三个参考插件贯穿真实授权和生命周期流程。

### 4.3 P2：不阻塞 v1.0 Final

- OS 级完整进程沙箱、远程公共市场、插件到插件 Capability Provider。
- 标准 protobuf gRPC、标准 MCP Server、Agent Runner。
- 多节点授权缓存一致性、跨租户授权和组织级策略。
- macOS 正式发行认证、Windows 原生进程 Runtime 生产支持。

- External Plugin 直接访问 PostgreSQL、Repository、内部 Service、JWT、用户 Token 或宿主目录。
- 把 Core Module、Built-in Feature、Resource Package 重新放入插件安装生命周期。
- 用 RBAC 角色直接替代插件 Capability，或让用户同意覆盖管理员拒绝。
- 兼容 v1/v2 时继续扩大旧接口；兼容层只允许收敛、告警和迁移。
- 为已删除的 `000001-000049` 测试链重新建立原地升级兼容；当前 clean baseline 是新的唯一建库起点。

## 6. 目标架构与职责

```text
Package / Manifest v3
        │ 声明 Capability、版本、发布者、摘要
        ▼
Plugin Identity & Version Registry
        │
        ├── Admin Grant ───────┐
        ├── User Consent ──────┤
        ├── Runtime State ─────┤
        ├── Resource Context ──┤
        └── System Policy ─────┤
                               ▼
                    AuthorizationService
                     │ Allow/Deny + Reason
          ┌──────────┼───────────┬──────────┐
          ▼          ▼           ▼          ▼
       Host API   Event Bus   Job Runner   Secret/Data Ports
          │
          ▼
    Stable DTO / Core Port
```

模块职责：

| 模块 | 职责 | 不承担 |
| --- | --- | --- |
| Manifest/Package | 声明需求、校验签名/摘要、产生权限指纹和升级 diff | 授予权限 |
| Identity/Version | 稳定标识发布者、插件、版本和包 | 运行期业务访问 |
| Capability Catalog | 定义 code、scope、risk、consent、数据分类和审计级别 | 保存某个插件的实际授权 |
| Admin Grant | 记录管理员对指定插件版本的逐能力批准/拒绝 | 替用户同意个人数据用途 |
| User Consent | 记录用户对 consent-required 能力的逐项同意/撤销 | 批准系统级或管理员能力 |
| AuthorizationService | 汇总全部条件并返回机器可读判定 | 直接读写业务数据 |
| Host/Event/Job Adapter | 构造可信调用上下文、执行判定、转换 DTO | 信任插件传入的 user_id/role |
| Data/Secret Port | 受管访问、配额、加密、保留与审计 | 暴露表、路径、SQL 或明文 Secret |
| Runtime Manager | 启停、健康、令牌、资源限制和隔离 | 静默绕过授权 |

## 7. 三层授权与判定合同

### 7.1 三层事实

1. **Declaration**：插件包声明“希望使用什么”，本身不产生权限。
2. **Admin Grant**：管理员批准“这个身份的这个版本可使用什么”，不得超出 Declaration。
3. **User Consent**：当前用户同意“该插件可为所述用途处理我的什么数据”，只对 `consent_required=true` 生效。

运行状态、Scope、版本、系统策略不是第四层授权，而是每次判定必须同时满足的保护条件。

### 7.2 Capability v1 目标结构

```yaml
code: schedule.self.read
resource: schedule
action: read
scope: self
risk: medium
consent_required: true
data_classification: personal
audit_level: decision
```

Manifest v3 的声明项另含 `required`、`purpose` 和可选约束。Catalog 元数据由平台维护，插件不能降低风险级别或关闭审计。

### 7.3 判定输入与输出

输入至少包括 `plugin_id`、`version_id`、`runtime_instance_id`、`capability_code`、可信 Actor、ResourceContext、
operation、delegation_id、policy_revision 和 trace_id。输出为 `allow`、`reason_code`、匹配范围、审计级别和安全元数据，
不得返回内部策略对象。

首批稳定拒绝码：

| ReasonCode | 含义 |
| --- | --- |
| `DENY_UNKNOWN_OPERATION` | 方法或操作未纳入目录 |
| `DENY_CAPABILITY_NOT_DECLARED` | Manifest 未声明 |
| `DENY_ADMIN_GRANT_MISSING` | 管理员未授予或已撤销 |
| `DENY_USER_CONSENT_MISSING` | 用户未同意或已撤销 |
| `DENY_VERSION_MISMATCH` | 授权不属于当前版本/权限指纹 |
| `DENY_SCOPE_MISMATCH` | 资源不属于可信 self/system Scope |
| `DENY_PLUGIN_INACTIVE` | 插件停用、停止、异常或隔离 |
| `DENY_DELEGATION_INVALID` | 后台委托过期、撤销或超范围 |
| `DENY_SYSTEM_POLICY` | 系统策略或应急开关拒绝 |

用户界面展示中文建议和恢复动作；日志/合同保留稳定英文码，不把内部错误原样暴露给用户。

### 7.4 缓存与即时撤销

- 缓存键必须包含 plugin/version/actor/capability/scope/policy revision。
- Grant、Consent、版本、运行状态或系统策略变更与 revision 更新在同一事务提交。
- 高风险操作默认不使用跨请求正向缓存；其余缓存提交后主动失效，并用短 TTL 兜底。
- “即时”定义为撤销事务成功后的下一次入口判定拒绝；正在提交的业务事务按 ADR 明确原子边界。

## 8. API、运行时与数据边界

### 8.1 版本策略

- 新增 `campusos.plugin/v3` 和 Host API v3；v1/v2 保持一个主版本兼容窗口。
- 新增 `runtime: process` 与 `campusos.process/v1`；`runtime: grpc` 映射为旧进程协议兼容别名，并输出迁移告警。
- v3 外部插件不允许 `*/*`；未知 Capability、方法、事件和字段默认拒绝。
- API v3 只返回稳定 DTO。`user.public_profile.read` 与 `user.contact.read` 分开，email 不再随普通 user/read 返回。

### 8.2 可信身份与 Scope

- 用户发起调用的 Actor 来自已验证 Session；插件不得提交可信 user_id、role、permission 或 Token。
- `self` 由宿主注入当前用户；`system` 只用于明确系统资源并要求 Admin Grant。
- 插件后台任务使用短期 Delegation，绑定用户、版本、能力、资源范围、到期时间和单调 revision。
- 第一阶段不实现任意用户、组织、全租户或插件自定义 Scope。

### 8.3 数据与 Secret

- 用户/系统受管记录和文件继续由 Host 保存，插件只使用 ID 和稳定 API。
- 用户撤销、插件停用或卸载不得自动删除用户数据；保留现有卸载后导出/删除能力。
- Secret 值与普通配置分表/分接口存储，加密密钥来自部署环境；UI、日志和 API 只显示掩码。
- 插件自有 SQLite 仅能位于插件隔离目录；不得将 PostgreSQL 连接、宿主 DSN 或任意文件路径交给插件。

## 9. 数据库演进计划

### 9.1 已冻结模型

数据库基础已按项目所有者的无旧版本兼容决策实施。`plugins.id` 作为稳定插件身份，不再重复创建
`plugin_identities`；`plugins.publisher_id` 关联发布者，`plugin_versions` 保存不可变版本事实。

| 已建表 | 关键职责 |
| --- | --- |
| `plugin_publishers` | 发布者、信任状态、签名 Key 引用 |
| `plugin_versions` | plugin_id、SemVer、digest、signature、Manifest/Host API 版本、权限指纹和生命周期 |
| `plugin_capability_declarations` | version、Capability、required、purpose、risk、scope 与数据分级 |
| `plugin_admin_grants` | 管理员逐能力决策、作用域、原因和 policy revision |
| `plugin_user_consents` | 用户逐能力决策、purpose hash、作用域、撤销和 revision |
| `plugin_delegations` | 短期委托 Token 摘要、能力/资源范围、过期和撤销 |
| `plugin_secret_values` | 密文、nonce、算法、Key 版本和轮换状态 |
| `plugin_authorization_decisions` | request、version、actor、Capability、依据、结果、原因和 trace |

当前 Runtime/市场代码仍使用 `plugin_permissions`、`plugin_user_grants`、`plugin_releases` 等现行业务表。
待新服务真正切换、验证和发布后，再从 `000004+` 通过前向 migration 清理被替代模型。

### 9.2 当前 migration 顺序

```text
000001  clean current schema：76 张现行业务表，删除旧 permissions，时间统一为 TIMESTAMPTZ
000002  plugin authorization foundation：8 张 v1 插件表和 plugins.publisher_id
000003  reference data：角色、76 个 Permission Code、最小角色矩阵和身份安全策略
000004+ 后续业务实现只追加，不再改写上述基线
```

每个后续 migration 必须有 up/down、空库、当前基线 up/down/up、约束和受影响 Repository 测试。
执行器记录 SHA-256 并以数据库锁阻止并发；发现旧三列 `schema_migrations` 或 checksum 漂移即拒绝。

### 9.3 测试数据重置规则

当前测试库允许重置，跨平台执行器已经实现硬门禁：

1. `CAMPUSOS_ENV` 必须严格为 `development` 或 `test`。
2. `CAMPUSOS_RESET_CONFIRM` 必须与解析后的 `DB_NAME` 完全相同。
3. reset 明确执行 `DROP SCHEMA public CASCADE`，然后从 `000001` 全量 up。
4. production/staging 不允许使用此入口；真实数据以后只能按当前基线向前追加 migration。
5. migration 不导入用户、管理员、邮箱、密码或业务 fixture；首次管理员由安全 bootstrap/CLI 创建。

详细命令和影响见 [数据库全面重构方案](01-v1.0数据库全面重构方案.md)。

## 12. 实施节奏

### 12.1 标准 10 周排期

| 周次 | 阶段 | 主要输出 | 退出条件 |
| --- | --- | --- | --- |
| W1 | G0 冻结 | 基线、威胁模型、ADR、Capability/DB 草案 | M0 评审通过，禁止并行造多套授权逻辑 |
| W2-W3 | 授权核心 | 身份/版本、判定引擎、Grant/Consent schema 与服务 | M1 判定矩阵和 migration 隔离测试通过 |
| W4-W5 | API/撤销 | Host API v3、稳定 DTO、撤销/隔离、Admin/Web 主流程 | M2 下一调用拒绝与端到端浏览器证据通过 |
| W6 | 升级/迁移 | 五类 diff、当前模型切换、对账和前向清理方案 | M3 扩权不继承、当前基线回滚通过 |
| W7-W8 | 生态能力 | Delegation、Config/Secret、Event、Data、Process Runtime | M4 三类核心场景无绕过路径 |
| W9 | 工具链 | SDK、CLI、Harness、Conformance、参考插件 | M5 新开发者能按教程完成闭环 |
| W10 | 集成/发布 | reset 演练、全门禁、性能/恢复/安全审查、文档 | M6 Final 审查通过 |

若只有 1 名后端和 1 名前端，按 14-18 周安排；不得通过移除撤销、迁移、恢复、安全或浏览器测试压缩周期。

### 12.2 里程碑

- **M0 架构冻结**：接口、身份、表、Scope、ReasonCode 和兼容策略有 ADR。
- **M1 判定可用**：三层授权在服务层闭环，但尚不切换全部入口。
- **M2 主路径切换**：Host API/Admin/Web 真实流量经过统一判定。
- **M3 可安全升级**：权限变化、当前基线前向迁移、数据切换和回滚经过隔离演练。
- **M4 生态完整**：事件、任务、Secret、数据和进程运行时共享边界。
- **M5 开发者可用**：SDK/CLI/参考插件和 Conformance 可独立执行。
- **M6 Final 候选**：代码、合同、迁移、浏览器、恢复、性能与文档证据齐全。

## 14. 验证与发布门禁

### 14.1 自动化门禁

- 单元：Capability 解析、判定表、Scope、版本、revision、diff、Secret 脱敏。
- 集成：每个 Host API/事件/任务/数据入口的 allow/deny；未知入口默认拒绝。
- 数据库：空库 up、checksum drift、全链 down/up、并发 Grant/Consent、当前模型切换对账、reset 重建。
- 合同：Manifest v1/v2/v3、Host API v1/v2/v3、事件、ReasonCode、Capability Catalog drift。
- 安全：伪造 user_id、跨插件/跨用户数据、通配扩权、旧 Token、路径穿越、Secret 泄漏、停用绕过。
- 前端：Admin 授予/撤销/隔离/升级，Web 同意/撤销/数据导出删除，中文拒绝解释。
- 生态：三个参考插件的 Conformance 和升级矩阵。
- 性能：判定热/冷路径、审计写入、撤销失效和受管数据容量基线。

### 14.2 发布判定

以下任一项缺失，不得宣称 `v1.0 Final`：

1. P0 未全部完成或存在已知授权绕过。
2. migration 没有 checksum、当前基线 down/up、reset 和回滚证据。
3. 管理员撤销、用户撤销、停用或版本替换后仍可能复用旧允许结果。
4. 旧 v1/v2 包没有兼容/拒绝矩阵或没有弃用告警。
5. Linux 目标环境 release、浏览器、备份恢复和性能证据不完整。
6. 文档把计划能力写成已交付，或 Admin/Web 无法解释拒绝原因。

## 15. 风险与应对

| 风险 | 概率/影响 | 预防与应对 |
| --- | --- | --- |
| 三套权限事实漂移 | 中/高 | 单一判定服务、生成目录、DB 约束、reconcile 和 drift CI |
| 当前插件读写模型成为永久双轨 | 中/高 | 单一切换计划、对账、v3 默认拒绝和前向清理里程碑 |
| 当前插件名称与稳定 ID 关联错误 | 中/高 | 安装时强制稳定 ID/版本、唯一约束、冲突报告和切换对账 |
| 撤销缓存滞后 | 中/高 | transaction revision、提交后失效、高风险禁正缓存、并发测试 |
| 审计泄漏个人数据/Secret | 中/高 | allowlist 元数据、哈希/脱敏、保留期、访问权限和泄漏测试 |
| Scope 概念过度扩张 | 中/高 | v1.0 只交付 self/system；其他 Scope 进入 P2 |
| 进程 Runtime 被误认为沙箱 | 高/高 | 文档显式区分协议与 OS 沙箱；完整沙箱保持 P2 |
| reset 误伤非测试环境 | 低/极高 | 环境/数据库名双门、打印精确目标、显式 apply、生产硬拒绝 |
| 前端提示与后端 reason 漂移 | 中/中 | ReasonCode 机器合同生成映射，未知码有安全中文兜底 |
| 范围膨胀到远程市场/Agent | 中/高 | M0 锁定 P0/P1；P2 不阻塞 Final |

## 16. Stop Rules 与回滚

- 任何入口绕过 `AuthorizationService`：停止新增能力，先修复覆盖和测试。
- 为兼容旧插件需要开放数据库、JWT、任意 user_id 或宿主路径：拒绝方案，改用 Adapter/DTO。
- 迁移无法给出冲突清单或回滚：停在双读，不执行 cutover/reset。
- 撤销无法在下一调用生效：禁止上线高风险能力和后台任务。
- Secret 可能出现在 API、日志、审计、fixture 或导出：停止发布并轮换受影响值。
- 进程隔离证据不足：降级为开发/受信环境 Runtime，不宣称生产沙箱。
- 性能只能通过跳过权限或审计达标：回退设计，不能降低安全门槛。

回滚优先顺序为关闭新入口、回到 v1/v2 Adapter 只读兼容、停止新版本、保留数据并 forward-fix；不得使用 destructive down 删除用户受管数据或授权审计。

## 17. Definition of Done

每个任务完成必须同时具备：

1. 实现与必要 migration；无未声明的内部捷径。
2. 正反向测试、失败注入、并发/撤销测试和影响范围门禁。
3. 机器合同、中文 Help、Admin/Web 提示、升级与回滚说明。
4. `docs/进度/v1.0-dev/` 中的时间、变更、验证、兼容和未决证据。
5. 代码审查确认插件不能扩大 Capability、选择可信用户或取得内部对象。

v1.0 只有在 P0/P1、M6 和发布判定全部通过后才能封版。P2 可以延期，但必须明确记录为后续范围，不能用接口占位宣称完成。
