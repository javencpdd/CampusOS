# CampusOS v1.1 插件自包含与动态加载重构计划书

> 创建及更新时间：2026-09-21（Asia/Shanghai）
> 状态：新一轮重构的设计与实施计划，尚未实施；不是版本完成或发布声明。
> 决策依据：项目所有者要求插件功能、用户页面、管理员页面及配置定义统一收敛到根目录 `plugins/`，独立安装/卸载，用户添加时自动创建其专属配置目录；允许破坏性重构，不要求旧插件合同兼容。
> 现状基线：`djw-window`；开始核对时为 `505d3e8` 加工作区，收尾时 HEAD 已推进到 `cbb19b6`，本任务未执行提交；前轮证据为 [v1.1.19-dev](../../进度/v1.1-dev/v1.1.19-dev.md)。
> 本计划成为本轮 v1.1 的实施范围权威。[旧版计划](00-v1.1版本计划书.md)保留作背景，[旧实现审查](01-v1.1代码完成情况审查与项目回顾.md)不代表本计划已经完成。

## 1. 结论、目标与范围变更

可以把插件完整收敛到 `plugins/`。但仅将 Vue 文件搬进去再让 Web 静态 import，仍然需要重建宿主，不能称为独立安装。
本次采用“自包含插件包 + 通用宿主 + 隔离前端运行环境 + 受控后端 Runtime + 用户配置服务”。

验收的核心场景：**先构建并启动不包含 PDF 插件代码的 CampusOS，再安装 PDF 插件包；用户添加后自动生成配置目录，立即可用；卸载后入口与调用失效。全过程不改宿主源码、不重建 Web/Admin/API。**

### 1.1 与旧计划冲突的明确决策

| 旧约定 | 新决定及影响 |
| --- | --- |
| PDF 页面通过 `trusted-module` 随 Web 构建 | 改为插件包独立构建的 UI；删除 PDF 专用的宿主页面、静态注册和专用 builtin 注册 |
| 第三方 UI Bundle、隔离 iframe 与 Bridge 不属于 v1.1 | 现纳入 P0；增加包校验、独立 Origin、Bridge、浏览器与供应链验收，不能沿用旧工期 |
| UI v1/v2 必须向后兼容 | 本重构不保留旧插件合同适配层；平台内置页面可保留自己的静态组件机制，不与外部插件混用 |
| 用户加入主要表现为授权记录 | 显式分离“用户安装关系、配置就绪、启用状态、能力同意”，加入不是自动授予全部能力 |
| process 与 API 同宿主运行，OS 隔离未完成 | 不再允许作为正式外部插件运行路径；采用受限 Wasm 或独立隔离容器，隔离不成立时拒绝启用 |

“不兼容旧版本”不等于放弃权限与数据完整性；不要求保留旧代码，但必须保留附件业务规则、授权边界和可恢复部署能力。
本轮只写计划，不执行迁移、删除、重置或插件安装。

### 1.2 纳入与排除

- P0：插件包规范、签名/摘要、独立构建、用户与管理员动态 UI、通用 API/Bridge、三层授权、隔离 Runtime、用户配置目录与生命周期、PDF 完整迁出、Docker 交付与负向测试。
- P1（仍属于本版验收）：升级/回退、配置变更工具、配额与恢复、可观测性、SDK/CLI/示例、独立插件 CI。
- 沿用的产品要求：图片参与正文排版；PDF/MP3/MP4/DOC(X)/XLS(X)/ZIP/RAR 为独立附件；本版仅 PDF 在线预览。20 MiB/文件、10 个/文、40 MiB/文，用户文件默认 50 MiB 且管理员可调整；业务权限不能因插件重构而放宽。
- 不纳入：远程公共市场、付费/评价、跨站联合、多节点调度、Office 转换、音视频转码、任意后端 SQL、让未经审核插件获得全部用户文件、DRM。
- “新增插件无需改核心”限定为使用已发布的 SDK、Capability、资源类型及扩展点；新的平台业务能力仍需核心演进，不提供任意代码/SQL逃生接口。

## 2. 现有代码事实与改造边界

| 核对位置（仓库根相对路径） | 当前事实 | 改造方向 |
| --- | --- | --- |
| `web/src/campus-ui/trustedModules.ts` | `core.pdf-viewer` 静态导入 `web/src/modules/pdf-viewer/pages/PdfViewerView.vue` | 移除 PDF 项；核心页面留在平台，不把所有 `modules` 都误当插件 |

| `internal/plugin/builtin_pdf_viewer.go` | Manifest/Capability/Surface 由 Go 专用代码构造 | 转成插件包内声明，不再编译进服务端 |
| `internal/plugin/manager.go`、`package.go` | 已有目录安装、包导入、生命周期、快照和 UI 注册 | 改造为校验后的不可变安装包与持久状态机，不扫描目录即自动执行 |
| `internal/plugin/storage_layout.go` | 系统级 `data/plugin_data/<plugin>/plugin.db`、`config.json` | 保留私有运行数据概念，增加用户级配置服务；现有代码不能视为已实现用户自动建目录 |
| `internal/plugin/market.go` 的 `Grant/Revoke` | 已有用户关系与权限处理 | 拆开加入、启停、Consent 和配置 provisioning |
| `internal/platform/pluginui`、RichText、Personal Documents | 宿主签发上下文并执行业务 ACL、对象版本与字节读取 | 保留为通用平台能力，去掉 PDF 插件名称/类型的硬编码特权 |
| `plugin_versions/admin_grants/user_consents/records/secret_values` 等现有表 | 平台拥有插件治理与受控数据事实 | 按需重构现有通用表；插件不得自行新增平台表 |

PDF 的翻页、缩放、搜索、目录、阅读位置交互属于插件；文章可见性、附件绑定、Object、身份、Grant/Consent 属于宿主。
插件自包含不是复制用户系统、数据库访问或文件鉴权到每个插件。

## 3. 标准目录、产物与配置所有权

### 3.1 单个插件源码（拟定规范）

```text
plugins/
  campusos.pdf-viewer/
    plugin.yaml                 # 唯一包入口：身份、版本、合同、能力、UI/Runtime
    README.md                   # 中文功能/权限/配置/安装/恢复说明
    LICENSE
    config/
      system.schema.json        # 管理员配置字段与验证规则
      system.defaults.json      # 非敏感默认值
      user.schema.json          # 用户配置字段与验证规则
      user.defaults.json
      migrations/               # 有界声明式配置转换，不是平台 SQL
    frontend/
      user/                     # 用户页面、组件及入口
      admin/                    # 可选管理员专属页面及入口
      shared/                   # 此插件内部共享代码
      assets/                   # 图标、字体、PDF.js Worker 等
      package.json
      pnpm-lock.yaml
      vite.config.ts
    backend/                    # 可选；PDF 允许纯 UI，无空壳后端要求
      src/
      runtime.yaml              # 构建目标；不能自行提高宿主容器权限
    storage/
      sqlite/                   # 插件自身 SQLite schema/迁移，禁止平台 DDL
    tests/                      # 单元/合同/集成/浏览器/安全样例
    dist/                       # 构建生成，不手工修改
    checksums.json              # 打包生成，覆盖实际发布文件
    signature.json              # 发布签名，签名对象绑定规范化摘要清单
  .installed/                   # 已安装不可变包，忽略提交
    <plugin-key>/<version>-<digest>/
  .staging/                     # 校验及原子安装暂存，忽略提交
```

仓库维护的插件源码与安装产物都归 `plugins/`，但不混用；下载第三方包进入 `.installed`，不覆盖源码。
发行包只需 Manifest、编译后的 UI/后端产物、配置定义、许可证/说明/校验签名；不要求在用户服务器安装 Node/Go 或编译源码。
插件第三方依赖在插件构建时锁定并打包；不导入 `web/src`、`admin/src`、Go `internal` 或宿主 `node_modules`。

Plugin key 使用稳定小写 ASCII 命名空间，长度不超过 128；拒绝 `..`、路径分隔符、Windows 保留名及大小写碰撞。
display name 可中文；所有跨前后端 bigint ID 传十进制字符串。版本 SemVer，已发布的 `(key,version)` 不允许对应另一个摘要。
所有路径必须为包内相对路径；拒绝绝对路径、符号/硬链接、设备文件、压缩炸弹和解压越界。

### 3.2 代码、定义、实际值分离

| 内容 | 唯一权威位置 | 写入者 |
| --- | --- | --- |
| 插件实现、页面、管理员配置定义/默认值 | `plugins/<key>/`；运行时是 `.installed` 不可变发布包 | 插件开发与构建 |
| 系统非敏感实际配置 | 现有 `plugins.config`，增加 revision/schemaVersion | 宿主配置服务；不回写包默认值 |
| 系统私有业务数据 | `data/plugin_data/<installation-id>/plugin.db` 等 | 受限 Runtime/Host API，不能越过此安装根 |
| 用户非敏感实际配置 | `data/personal-space/<user-id>/plugins/<key>/config/user.json` | 用户配置服务，不直接挂载给共享插件进程 |
| 用户安装与状态、配置摘要/revision | 平台通用关系表 | 平台服务 |
| 密钥/Token/密码 | 现有 Secret 服务的加密存储 | 宿主；不放包、JSON 默认值或普通 config |

因此“管理员相关配置文件放进插件”包括 schema、默认值、管理页面和文案；不包括管理员运行时填写的秘密。
管理页面可以只声明 schema，宿主自动生成配置表单；复杂业务管理页面才需要 `frontend/admin`。

## 4. Manifest 与平台扩展合同

新合同拟命名 `campusos.plugin/v4`、`campusos.ui/v3`、`campusos.bridge/v1`；为设计名称，不是现有 API。
Manifest 最少声明：

| 字段组 | 内容与约束 |
| --- | --- |
| identity | key、version、publisher、显示名、许可证、host/SDK 兼容范围 |
| artifacts | UI 的 entry/file list/digest、后端 wasm 或容器内容摘要；不接受浏览器任意远端 URL |
| backend | `none`、`wasm`、`container`；后端命令/事件/健康合同、资源预算 |
| ui | user/admin surfaces、相对 route、navigation、固定 slot、modal/drawer/fullscreen/new-tab |
| previewProviders | 支持 MIME、资源类型、Surface；由宿主选用户默认/明确选择，不硬编码 PDF 插件 ID |
| capabilities | 必需/可选能力、用途、风险说明、数据使用及声明 scope；宿主目录校验，不接受自定义提权能力 |
| configuration | system/user schema、defaults、版本、可编辑键、允许的声明式转换 |
| data | 通用记录 collection、私有 SQLite 需要、用户配置上限；不得声明平台表 DDL |
| compatibility | contract/schemaVersion、宿主版本、CPU/OS、依赖清单与许可证/SBOM |

首版不支持强制依赖其他插件或自动链式安装；共享代码以开发依赖打包。以后扩展插件间通信必须走具名合同和双方授权。
未知合同 major、未知必需 Capability、重复 Surface、保留路径冲突、缺失构建文件均在安装前阻断。

## 5. 前端：真正动态安装与隔离加载

### 5.1 选择方案

Web/Admin 只内置通用 `PluginHost`、路由注册器、消息 Bridge、配置表单、授权界面及宿主能力客户端。
插件自行打包自己的 Vue/其他前端框架，不要求向宿主交付可直接 import 的 `.vue` 源文件。

默认采用**独立 Origin 的 sandbox iframe**，不采用主站内动态 import、eval、全局脚本注入或把 Module Federation 当作安全边界。
每个安装版本、user/admin audience 分配独立 UI Origin，由静态网关映射到已校验的包目录。
生产使用与主站不同的注册域及 HTTPS；开发使用隔离域名/端口。所有域名必须由部署配置生成，不由 Manifest 指定。

同源内容同时开启 `allow-scripts` 与 `allow-same-origin` 会破坏预期隔离，因此本方案仅在确实跨 Origin 时允许这两个权限，且启动前检查 Origin 不重合。
该限制依据 [MDN iframe 说明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)。

### 5.2 路由和页面流程

1. 登录后请求宿主的有效 UI 清单：按用户安装状态、管理员身份、Grant/Consent、插件版本及健康过滤；响应带 revision。
2. 宿主根据声明动态注册 `/extensions/<key>/<route>`；Admin 使用独立路由空间和 audience，拒绝覆盖平台保留路由。
3. 路由组件始终是通用 Host；它向服务端创建用户/插件/版本/Surface 绑定的短期 UI 会话，再加载指定包入口。
4. 浏览器只下载需要的页面产物；宿主与插件握手建立 MessageChannel。加载中、超时、崩溃、合同不兼容均有中文状态和重试。
5. 停用、撤权、升级和卸载提高服务端 revision，撤销会话并通知前端；前端销毁 iframe/Worker/监听/路由。通知丢失不影响服务端即时拒绝后续调用。
6. 深链接刷新须先恢复登录态及 UI 清单，再解析插件路由；登出清除旧身份的路由、上下文和待处理请求。
7. 弹窗/抽屉/全屏由宿主拥有，ESC、焦点返回、移动端适配为统一责任。新标签先由用户点击打开同源 Host 壳页，重新认证后再嵌入隔离插件；URL 不带 Token/秘密。

`addRoute/removeRoute` 能实现动态路由，但不会自动解决当前页面重新匹配和清理问题；这些纳入宿主测试。[Vue Router 官方说明](https://router.vuejs.org/guide/advanced/dynamic-routing.html)。

### 5.3 Bridge 与浏览器安全合同

- 握手核对精确 `event.origin`、`event.source === iframe.contentWindow`、随机 challenge、插件/版本/Surface/audience；随后只使用转交的 MessagePort。
- 消息必须有协议版本、requestId、方法、参数，执行 schema/大小/频率/超时校验；iframe reload 后旧 Port 失效。不能把消息中的 userId、pluginKey 当作认证事实。
- `targetOrigin` 使用确定值，不使用通配符传递敏感数据。[MDN postMessage 安全说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)。
- 允许 `config.read/update`、`resource.describe/readRange`、具名 `backend.invoke`、`ui.requestSurface`、受控 `records.*`；不提供任意 fetch、SQL、文件路径或通用管理员代理。
- JWT、管理员会话、平台凭据仅在宿主；Bridge 服务端再次执行认证、版本、安装、Declaration∩Grant∩Consent、资源 ACL。前端 Bridge 校验不是最终权限边界。
- UI 打开请求需真实用户操作：涉及新标签或敏感动作时使用宿主按钮/确认框，不能相信插件自报 `userGesture=true`。
- Admin iframe 也不获得管理员万能令牌；平台安装/卸载/授予权限的最终确认 UI 在宿主，插件自定义页面只能调用声明且获批的管理业务方法。

静态网关设置 CSP/Permissions-Policy：默认拒绝资源与连接，脚本/Worker 仅版本包来源，图片/字体仅受限来源，禁止 object、表单提交、嵌套 frame 和任意跳转；frame-ancestors 只允许 Web/Admin。
不依赖实验性 iframe `csp` 属性；Worker 响应同样配置 CSP。PDF.js 必要的 blob Worker 权限须单独验证，不顺带开放网络。
参考 [CSP 响应头文档](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)。

安全边界必须诚实：iframe/CSP 不能承诺插件拿到内容后绝无泄露可能，也不能提供可靠的每 iframe CPU/内存硬隔离。
不把已授权 PDF 字节视为仍对插件保密；包审核/发布者信任、最小授权、恶意导航测试、用户风险提示仍为发布门禁。
未审核插件不得获得敏感文件能力；不宣称浏览器沙箱是 DRM 或完整恶意代码执行平台。

### 5.4 缓存和 PDF 字节

包静态资源 URL 绑定 digest，可用长期 immutable HTTP 缓存；UI 清单及会话 no-store，资产/用户配置私有且不缓存到共享层。
不缓存用户 PDF 到 Service Worker/IndexedDB；不允许插件注册 Service Worker。网关拒绝 Service Worker 脚本请求，校验已批准 Worker 文件清单，独立版本 Origin 不复用旧活动上下文；必须补充实际浏览器拒绝注册测试，不能仅靠“不写注册代码”成立。
浏览器可能驱逐 HTTP 缓存，所以承诺“未变更且缓存仍在时可复用”，不承诺永不重新下载。
已缓存 JS 不代表仍有访问资格，卸载/撤权后服务端必须拒绝调用。

PDF 插件通过 Bridge 的有限 `readRange(offset,length)` 获取 ArrayBuffer，宿主转发原有认证 Range，逐次校验资源状态。
使用 Transferable 和背压，不把整份 PDF base64 化；拟定单块最多 1 MiB、每会话最多 4 个并发，受现有更严格全局限额约束。
PDF.js 用自定义 Range Transport 接入，API 依据 [PDFDataRangeTransport](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFDataRangeTransport.html)，必须先做真实 Worker/跨 Origin 原型验收。
普通认证下载由宿主按钮完成；插件失败或被移除时仍可按业务权限下载，不能把下载依赖于插件是否安装。

## 6. 后端发现、注册、运行与隔离

### 6.1 通用组件

| 组件 | 职责 |
| --- | --- |
| PackageService | 接收包、限制解压、验证签名/摘要/合同、暂存、原子发布、版本快照 |
| Catalog/Registry | 已安装事实、不可变版本、UI/命令/预览 Provider 索引，向用户返回过滤清单 |
| LifecycleService | 幂等操作、启停/升级/卸载协调、代次 fencing、健康和重试 |
| RuntimeAdapter | `none/wasm/container` 统一 Start/Stop/Invoke/Health；不含 PDF 特例 |
| AuthorizationService | 继续拥有三层授权、Scope、版本、撤销、Secret 和审计 |
| UserPluginService | 用户加入/退出、启停、配置 provisioning 和恢复 |
| ConfigService | system/user schema 验证、默认值、CAS 更新、秘密分流、配置转换 |
| UIAssetGateway/Bridge | 已校验静态资源与受限会话调用；不是插件目录通用文件服务器 |
| Host Resource Ports | 文章/资产/文档 ACL、Object、Range、受管记录和配置；插件不访问平台仓储 |

发现只识别候选包，不能因为目录存在就安装/启用/执行。启动时以已安装数据库记录为准校验对应磁盘摘要；缺包或不一致置 unavailable，不执行未知文件。
开发提供显式 `watch`：重新构建、校验并通过同一升级流程发布开发包，不直接执行工作区任意改动。

后端 HTTP 统一通过 `/api/v1/plugins/<key>/actions/<action>` 等通用网关；路径为拟定合同。
插件处理其内部命令和事件，不向 Gin 直接注册任意路由，不以 Go plugin 动态链接宿主，不要求向 bootstrap 添加插件专用 import。
事件由宿主以签名/认证的运行实例身份派送；用户事件有受限 Delegation，不允许系统实例伪造用户身份。

### 6.2 Runtime 安全底线

- `none`：纯 UI 插件无需后端进程；PDF 默认选择此模式，授权判断仍由宿主执行。
- `wasm`：无默认网络/文件目录，显式 Host imports；限制内存、执行时间/取消、并发；读写只经已授权能力。
- `container`：每插件安装实例独立非 root 身份、只读包/根文件系统、专属数据目录、受限 tmpfs、PID/CPU/内存限制、drop capabilities、no-new-privileges，禁止特权/host network/宿主根挂载。
- 后端不能连接 PostgreSQL/Redis/NATS 或读取平台环境。网络只到 Host API 网关；不共享基础设施网络，按需外连必须受批准的出口策略约束。
- 独立 Runner 控制器只接受平台签发的有界运行请求；部署使用专属受限/rootless Engine 或隔离 Runner 主机。API 和插件容器均不得挂载主 Docker socket，插件不得提供 Compose/任意容器启动参数。
- Runner 是敏感控制面，需双向认证、请求审计、固定模板、安装代次校验和重启恢复。仅凭“运行在 Docker 中”不能通过隔离验收。[Docker 安全文档](https://docs.docker.com/engine/security/)。
- 没有合格 Runner 的环境禁止 container 插件启动，不退回同宿主 `exec`；Windows 开发使用 Linux Containers，与 Linux 目标合同一致。

## 7. 用户添加与配置目录：完整一致性设计

### 7.1 创建时机和目录

管理员全局安装只安装一次代码；每个用户点击“添加到我的插件”才创建该用户目录。
不能注册账号时为所有插件预建目录，也不能等待首次写配置才建。就算插件没有可配置字段，也建立带版本信息的空配置。

```text
data/personal-space/<user-id>/plugins/<plugin-key>/
  config/
    user.json             # 非敏感配置数据，唯一配置值事实源
    meta.json             # 配置 schema/revision/hash、安装代次，非授权凭证
  .pending/               # 宿主暂存/事务恢复；不对用户文件列表暴露
  .snapshots/             # 配置升级快照，有限保留
```

此目录逻辑上属于用户空间，但由宿主配置服务管理，普通“我的文档”不会列出内部 config/meta。
插件用户页通过 `config.*` API 修改；用户可在插件设置中查看/重置/导出自己的非敏感配置。
插件共享后端不挂载整个 `personal-space`，也不直接遍历该插件所有用户配置；每次调用由认证/Delegation 确定 owner。

### 7.2 “加入”不等于授权或启用

```text
用户确认添加 -> installing -> 配置目录就绪 -> installed（已加入）
                                         -> enabled（必需权限满足且用户请求启用）
                                         -> awaiting-consent / blocked（可保留配置）
```

平台未安装/未发布的插件，用户只能申请管理员安装，不能上传任意代码并执行；申请不创建用户插件目录。
用户同意可选能力不得被默认勾选；必需能力不满足时明确说明为何不能启用。用户无需自行生成 Token/密钥。

### 7.3 文件系统与数据库不能假装同一事务

1. 认证 owner，锁定用户安装关系；检查发布状态、用户配置预算；用 Idempotency-Key 创建 operation 与 `installing` 关系，同事务写 Outbox。
2. 配置 Worker 读取已校验 defaults/schema，在同一文件系统的暂存目录写入 user/meta，校验、fsync、原子 rename；所有路径由宿主生成。
3. 用 operation generation/fencing 完成 CAS：写配置摘要/revision、关系 `installed`、审计，释放预算预约。重放发现同一代次已就绪则直接收敛。
4. 崩溃恢复：关系存在而目录缺失则重试；目录存在而关系未完成则核对 operation 后补记；未知目录仅隔离报告，绝不直接当作已授权。
5. 失败返回明确中文原因/operationId，允许重试或撤销；接口在完成前返回 202/pending，不能显示“添加成功”。磁盘满、并发添加、停用/卸载竞争必须测试。

路径防护包含每级根约束、禁止符号链接/Windows junction/reparse point、避免检查后替换竞态；Linux 使用可信目录句柄下的安全操作。
默认目录 0700、文件 0600；Windows/Docker bind mount 权限不能仅靠 chmod 宣称安全，发行使用经验证的命名卷/ACL。
用户 ID 来自登录态，plugin key 来自已安装注册表；API 不接受根路径、文件名或替代 owner。

### 7.4 配置语义、并发和预算

- schema/defaults 随不可变插件版本发布；只允许有界 JSON Schema 子集，本地 `$ref`，禁止远程引用和可执行验证器。
- 系统配置与用户配置使用不同 schema。某些系统字段可声明“允许用户覆盖”，不允许用户覆盖网络/安全/容量等管理员策略。
- 读取优先级：用户显式值 > 允许覆盖的系统默认值 > 包默认值；策略上限始终由宿主最终裁决。默认值不是授权事实。
- `PUT/PATCH` 使用 `If-Match`/revision，409 要求重新加载；同用户/插件串行化可靠写入，文件更新与元数据在 operation 下恢复，禁止双向 JSONB/文件双写事实源。
- 设计默认：单插件用户配置 256 KiB、每用户总配置 2 MiB、单份默认值最多 8 KiB；纳入独立、可调的配置预算，不占用原始附件的 50 MiB Object 配额。快照另设有限预算与保留数，不能绕过限额。
- 原文件、插件产生的用户业务附件继续走 Object/用户文件配额；不能塞入 user.json 或 SQLite 绕过文件治理。SQLite 的系统业务数据另受插件运行存储预算约束。
- 密钥使用 Secret API，由宿主保存；配置只保存不具备访问权限的 secret 引用，前端不会回显明文。
- 用户自己通过宿主设置页修改其配置受 owner 规则；插件主动读写配置则需要声明并获批的 `plugin_config.self.read/write`（拟新增平台通用能力）。

## 8. 数据模型与平台数据库约束

本节是目标设计，不更改当前 Schema。插件不可自行建平台表、修改表、提交 SQL 或获取连接串。
重构由平台 migration 一次性完成；优先改造现有通用表，不建立 PDF 或每插件一张专用表。

| 现有结构 | 拟调整 | 约束/影响 |
| --- | --- | --- |
| `plugins` | runtime none/wasm/container、active_version_id、installation_generation、desired/actual state、config_revision、可诊断错误码 | 统一控制面，不再把 builtin 当外部插件特殊权限；active version 有明确 FK |
| `plugin_versions` / `plugin_releases` | 统一不可变身份/包摘要引用，versions 管完整声明与产物，releases 只管发布频道状态 | `(plugin_key,version)` 唯一且摘要不可换包；不保留两套冲突的有效版本 |
| `plugin_user_grants` | 重构并可直接重命名为 `plugin_user_installations`；用户 FK、安装状态、desired_enabled、generation、config_schema/revision/hash、last_operation_id | `(user_id,plugin_key)` 唯一；关系不能再作为另一套能力授权事实；旧 permissions 字段移除 |
| `plugin_capability_declarations/admin_grants/user_consents` | 绑定不可变版本及 scope，加入 config/Bridge 所需通用能力 | Consent 与用户安装关系分离；升级能力变化需重新批准，不能沿用旧 granted 布尔值 |
| `plugin_ui_invocations` | 明确 UI session 与资源 invocation 的类型、audience、版本/安装代次、过期/撤销；普通设置页允许无资源，资源页保留现有 FK 互斥约束 | 不改成无验证任意 JSON resource ID；每次读仍走业务 Port |
| `platform_operation_runs/platform_outbox` | 承载安装、用户配置准备、升级、删除与修复 | 复用幂等、重试、fencing、审计，不再新建插件专用任务系统 |
| `plugin_records/secret_values` | 继续提供受控记录/加密秘密 | 不与用户 JSON 配置重复存储同一字段；阅读页是业务记录，不是授权令牌 |

索引按明确访问模式：用户插件列表 `(user_id,state,updated_at,id)`，全局停用扫描 `(plugin_key,state,user_id)`，
后台收敛 `(state,updated_at,id)`，会话清理 `(expires_at,id)`、版本撤销 `(plugin_version_id,revoked_at)`；唯一键与 FK 覆盖按数据库演练确认，避免重复前缀索引。
用户删除后配置目录使用可靠清理任务；不能只依赖 FK cascade 删除数据库而留下可访问文件。

当前数据可丢弃，不要求旧插件原地迁移；实施时先列出精确库/卷/目录及影响，保存代码快照并执行受控测试重建。
不得把“可重写文件”理解成删除整个仓库或真实环境。schema、ER PNG/SVG/说明、Admin 架构页及生成合同要一起更新。

## 9. 安装、启停、退出、升级、卸载

| 操作 | 必须执行 | 数据处理 |
| --- | --- | --- |
| 管理员安装 | 上传/选择发布包→验证信任/摘要/合同/配额→staging→记录版本→原子发布→installed-disabled | 不自动给用户建目录，不执行 npm/postinstall/shell 安装脚本 |
| 管理员启用 | 配置验证、Admin Grant、Runtime 隔离检查、健康探测→原子切换 effective 状态→发布 UI revision | 用户仍需自己的安装关系和 Consent |
| 用户添加 | 明确确认→可靠建立关系和目录→installed→按用户选择申请启用 | 用户配置从已验证默认值初始化；重复请求幂等 |
| 用户禁用 | 立即拒绝该用户新调用、撤销会话/Delegation、关闭 UI；后台清理在途任务 | 保留配置与业务数据，不影响其他用户 |
| 管理员禁用 | 先将有效状态置 disabled、提高 generation、撤销所有会话，再停事件订阅/Runtime | 保留包、配置、用户关系和数据；不能仅等待前端刷新 |
| 用户退出/移除 | 撤销个人 Consent/会话、移除有效关系；提示是否保留或删除插件配置/业务记录 | 默认保留为 detached；清除需明确确认；不删除原始 PDF/文章附件 |
| 升级 | 暂存新版本、能力/配置差异、审核、健康与配置快照→切换代次；配置转换失败的用户进入 repair-required | 新增/扩大能力重新 Grant/Consent；不自动扩大权限；不能同版本换包 |
| 回退 | 停用新版本，选择已验证旧包及兼容配置快照；重建会话，不复活旧 Token | 不兼容 SQLite 变更先恢复一致快照或前向修复，不承诺任意降级 |
| 全局卸载 | 先禁用、撤销、停 Runtime/Worker/路由/Provider，再移除安装产物；记录操作及审计 | 默认保留私有数据和用户配置为 detached；可选择另行受控清除，列出影响用户和字节 |
| 清除持久数据 | 精确目标、权限、原因、二次确认、后台分批删除/对账 | 只删该安装的 config/SQLite/记录；Object 必须检查引用，不能连带删除用户原文件 |

安装/启用/配置迁移/卸载均有 desired 与 observed 状态，不用长数据库事务包住进程启停/磁盘 IO。
同插件操作串行化、代次 fencing，崩溃后 reconciler 收敛；Runner 不可达时先拒绝业务访问，显示 stopping/error，不谎报已停止。
旧运行实例在权限撤销后不再获准 Host API；直接外连禁止/被出口策略关闭，避免“后端仍活着就继续有权限”。
重新安装同 key 但不同发布者不能继承保留数据；只有发布者身份连续、用户明确选择恢复且 schema 兼容时才可重新关联。

## 11. Docker、开发工具、配置与交付

拟提供统一 CLI 子命令 `campusosctl plugin scaffold/build/validate/pack/install/dev/uninstall`；这些命令及参数在合同阶段落实，不声称当前已经可用。
插件 build 在隔离构建容器执行，签名/信任在发布或安装阶段执行；插件包安装不在 API 容器运行构建脚本。
宿主、SDK 和插件分别 CI；插件测试依赖发布 SDK，不通过相对路径偷偷依赖宿主源码。

拟新增部署配置：`PLUGIN_SOURCE_ROOT`、`PLUGIN_INSTALL_ROOT`、`PLUGIN_UI_ORIGIN_TEMPLATE`、`PLUGIN_UI_ALLOWED_PARENTS`、
`PLUGIN_RUNNER_ENDPOINT`、发布者信任根、用户配置预算；默认目录按第 3/7 节。每项有启动校验、中文诊断和示例，秘密不写默认文件。
Docker 开发增加 UI 静态网关与可选隔离 Runner；宿主源码热加载与插件打包热更新分开。
`plugins` 包根只读挂载给服务端/静态网关；仅安装服务写安装根；用户空间不暴露给静态网关或插件容器。

开发域名必须能从浏览器解析到开发机；局域网客户端不能使用指向自己机器的 localhost，需 DNS/hosts 与端口防火墙说明。
生产单独插件域名、证书和反代路由是部署前置条件；不能因配置困难退回主站同源执行插件 JS。
Windows Docker 与 Linux 需覆盖路径/换行、原子替换、volume 权限、域名、Worker 和缓存行为。

| 用户目录 | 首次添加、无 schema 插件、重复点击、两用户同插件、两插件同用户、写满/并发/崩溃恢复；每次 owner 隔离 |
| 生命周期 | 全局与个人启停相互独立；升级扩大能力需同意；清除与卸载分开；缓存旧页面不能继续调用 |
| 内容 | 原有文章附件/个人资产/个人文档 PDF 三入口、非作者有权文章、owner-only、下架/隔离/删除、下载降级 |
| 后端隔离 | 进程身份、挂载、跨插件目录、平台 DB 网络、环境秘密、资源限制、Runner 故障、Host API 撤权证据 |
| 数据与恢复 | PostgreSQL+包摘要+系统配置+用户 JSON+SQLite/WAL+Secret 密钥版本的一致备份恢复；孤儿目录仅报告 |
| 容量 | 冻结硬件、PDF 样本/页数、20 路 Range、冷/热包缓存、RSS/p95、慢客户端和配置并发预算后实测 |
| 工程 | Go、组件、真实浏览器、包 Conformance、合同/ER/架构/链接/换行检查，扫描不存在插件到宿主源码的导入 |

G0 必须填写容量阈值和目标机规格，否则容量门禁保持未完成；本计划不编造实测数字。
所有 P0/P1 和保留的附件规则均完成、负向测试通过、独立目标恢复成功、风险批准后才允许 Final。
不能把“文件已搬迁”“构建通过”“iframe 能显示”当作整版验收。

## 14. 风险、停止条件与回退

- Bridge 成为通用越权代理：固定方法/资源句柄/身份和每次授权；发现可指定任意 owner/URL/SQL 立即停止发布。
- iframe 安全或 PDF.js Worker 不兼容：先原型；不得悄悄换回主站动态执行，必须修正隔离方案并重审。
- Runtime 控制面权限过大：独立受限 Runner，禁止主 socket；隔离测试失败时只保留 ui-only/合格 Wasm，不把 container 标为完成。
- 配置文件/数据库不一致：operation+Outbox+代次+原子文件替换、重试与对账；禁止静默重置用户配置掩盖故障。
- 恶意包/发布者更换/依赖漏洞：签名信任根、不可变摘要、SBOM/锁定依赖、撤销与紧急禁用；签名不能证明代码无害。
- 域名与 LAN 环境复杂：预检、可复制 Docker 示例和中文诊断；缺独立 Origin 必须阻止插件 UI，不能降低安全默认值。
- 不兼容重构：只在明确测试目标重建；保留代码与一致数据快照作为环境回退，不建立永久旧合同兼容层。
- 主程序出错时可关闭全部插件，基础登录、文章和有权下载仍可用；不得让 PDF 插件卸载破坏核心业务。
