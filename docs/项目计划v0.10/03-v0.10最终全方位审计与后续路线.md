# CampusOS v0.10 最终全方位审计与后续路线

> 审计日期：2026-07-16  
> 审计基线：`v0.10.0`、A0-A15 及封版后边界收口 A16-A18
> 当前结论：A0-A18 全部实现，并通过包含联合恢复、Chrome 业务流和七视口检查的最终统一门禁。
> 证据记录：`docs/进度/v0.10-dev/v0.10.22-dev.md` 至 `v0.10.27-dev.md`

## 1. 审计结论

本次没有只按计划书中的“已完成”标记作结，而是重新核对了代码、追加迁移、路由和 OpenAPI 生成物、Go/Web/Admin/docs-site/SDK 测试入口、数据库检查、恢复流程、浏览器工作流及 A0-A15 进度证据。

v0.10 的十项最终成功标准均有对应实现和历史统一门禁证据。第一次封版复核修复了角色写接口默认拒绝、最后管理员并发保护、进程插件生命周期和文档版本漂移；后续目录审查又确认 Built-in 描述符、External Plugin 和风格资源虽然已有逻辑分类，仍残留在 `data/plugins`/`data/plugin_data` 的历史物理布局。A16-A18 将该问题纳入 v0.10 封版补强，以渐进迁移、兼容投影和可回滚工具完成收口，而不是重写系统。

## 3. 本轮发现与修复

### 3.1 权限写接口默认拒绝

- `RoleHandler.AssignRole` 和 `RevokeRole` 现在必须从认证中间件上下文取得操作者 ID；缺失时返回 `401`。
- HTTP 路径不再降级到供受信任内部调用方使用的 `AssignRole`/`RevokeRole`，避免未来路由装配或中间件漂移形成 fail-open。
- 保留内部兼容方法，不破坏现有模块测试和渐进迁移边界。

### 3.2 最后管理员并发原子保护

- PostgreSQL Adapter 新增事务内 `RevokeRoleUnlessLastGlobal`，使用按角色的 transaction advisory lock 串行化“检查并撤销”。
- Memory Adapter 在同一互斥区完成计数和撤销，保持开发/生产语义一致。
- 新增双管理员并发互相撤销测试，断言只允许一次撤销且至少保留一个全局管理员。
- 旧 Repository Adapter 继续走兼容检查；生产 PostgreSQL 和内存实现使用原子路径。

### 3.3 外部进程插件生命周期与事件端点

- 插件进程只由监控协程调用一次 `cmd.Wait()`；停止流程等待同一完成信号，消除 double-Wait 和误标记错误状态。
- 旧进程退出时不会删除同 ID 的新进程注册，主动停止不会把插件写成 `error`。
- 删除由启动时间推导随机本机端口的事件探测。只有显式 `event_url` 且目标通过 loopback 校验时才投递；旧 Manifest 未声明时保持“仅记录”兼容行为。
- `extension_url` 与 `event_url` 共用严格的 `http + loopback + 无 userinfo/fragment` 校验。

### 3.4 契约和文档治理

- 新增 `internal/platform/version` 作为应用版本唯一代码事实源；启动日志、健康接口、API Index 和 OpenAPI 不再各自硬编码版本。
- OpenAPI 信息版本改为代码常量 `0.10.0-experimental`，API Index 增加 `application_version: v0.10.0`。
- docs-site、TypeScript SDK、Go SDK、CLI 新建插件的兼容范围和三个官方模板同步到 v0.10；`version-check` 已进入 release-check，防止再次漂移。
- 校正权限帮助中的实际 API 路径，并补充 fail-closed 与并发最后管理员说明。
- README、`docs/README.md` 和官方文档站同步到 v0.10；明确兼容文件名和 `runtime: grpc` 的真实边界。
- `make readme-check` 纳入 release-check，并要求根 README、docs 入口和 docs-site 入口与服务启动版本一致。
- release-check 现在执行 v2 示例插件独立模块测试，而不只验证其编译结果。

### 3.5 模块、External Plugin 与 Resource Package 物理隔离

- 编译期描述符统一为 `modules/{core,features}/*/module.yaml`，实现统一进入 `internal/modules/{core,features}`；`modules` 不是安装目录。
- Feature Registry 从嵌入的 `campusos.module/v1` Catalog 注册状态、依赖、配置和 UI；Plugin Manager 不再注册 Built-in Runtime。
- `/api/v1/features` 管理 Core/Built-in Feature，`/api/v1/plugins` 只列 External Plugin；旧 Built-in 别名仅保留单项兼容投影。
- `data/plugins`/`data/plugin_data` 只服务 External Plugin，`data/module_data` 保存 Built-in Feature 本地数据，`data/resources` 保存无 Runtime 资源包。
- 包导入、CLI、扫描器和市场拒绝 `runtime: builtin` 及模块/Feature/兼容别名冲突；架构检查阻止 External Plugin 导入 `internal/*`。
- `campusosctl resource adopt/inspect`、资源 checksum、布局迁移/逆向回滚、数据库 up/down/up 和备份恢复 v2 共同提供迁移证据。

## 4. 兼容与回滚结论

- 未删除旧 API、`threads.status`、旧 `permissions`、route alias、`user_space_contents` 或历史 Manifest；旧 Built-in 文件布局通过显式迁移脚本而不是静默读取保留回滚能力。
- migration `000001` 至 `000022` 未改写；v0.10 顺序追加 `000023` 至 `000026`。
- Built-in Feature 停用、External Plugin 停止和内容下架都不删除用户数据。
- `000026` 的 down migration 可恢复历史 Built-in 活跃投影；当前 Feature Store 状态和用户数据保持不删。文件布局由 `layout-moves.tsv` 逆序回滚，冲突时停止而不覆盖。
- 权限和 Runtime 修改可按代码版本回退；若回退原子撤销实现，必须同时回退调用方接口，不能留下不完整类型断言。
- 生产数据库结构回退仍优先 forward-fix；任何 down migration 只允许在有备份和恢复演练的开发环境执行。

## 5. 已完成能力回顾

- 内容：普通文本与 RichText 的草稿、发布、私密、审核、下架、整改重提、直接恢复、回收站和永久清除边界。
- 查询：Community 统一公开可见性、作者视图、标签/版块筛选和个人主页内容装配。
- 权限：稳定 Permission Code、Operation、全局/板块作用域、自定义角色、权限矩阵、越权防护和授权审计。
- 扩展：Manifest v2、本地 Catalog、用户 Grant、受管记录/文件、签名检查，以及 Core/Built-in Feature/External Plugin/Resource Package 在代码、Runtime、API 和数据上的独立边界。
- 多端：Web/Admin 共享布局策略及重点工作流的桌面、平板、手机横竖屏回归。
- 治理：API/路由生成合同、架构边界、数据目录、生成物、数据库审计、联合备份恢复和统一发布门禁。

## 6. 后续版本应单独规划的工作

以下项目没有被伪装成 v0.10 已实现功能，也不阻断 v0.10 关闭：

1. 为高风险业务写操作和 `authorization_audits` 设计同一事务或可靠 outbox；当前跨表审计是尽力记录，不是不可丢失的合规账本。
2. 根据真实容量、法规和恢复目标定义内容修订、审核动作、插件日志、Webhook 投递及授权审计的保留时长和清理任务。
3. 建立独立版本的 protobuf gRPC 扩展协议和 SDK；当前历史 `runtime: grpc` 是受管进程加 loopback HTTP。
4. 实现标准 MCP Server 和真实第三方消息 Adapter；当前 MCP-like/Message Local 只代表受控实验能力。
5. 为 `user_space_contents` 收集读写和差异统计，再决定停写、弃用和物理删除时间。
6. 在现有 `resource adopt/inspect`、Appearance 导入/应用和布局回滚基础上，继续建设通用资源包签名发布、版本比较和跨实例分发；仓库内 Legacy style-pack 物理迁移已完成。
7. 生产多实例仍需共享 User Storage Provider、插件 Runtime 协调和本地 SQLite/KV 迁移，不得通过共享宿主目录绕过单写保护。

## 8. 封版后入口与入门补验

2026-07-16 的后续可用性审查确认，后端四类模块边界和生命周期实现没有回退，但 v0.10 Admin 信息架构把 `/features`、`/plugins` 和风格资源入口收进“扩展总览”的二级跳转，导致课表与风格包难以发现；Extension Hub 还把 `/plugins` 兼容投影当作原生 Feature DTO，可能显示空名称和空状态。

本轮恢复了内置功能、外观与风格包、外部插件和插件中心的直接侧栏入口，新增独立 `/appearance` 页面，并以共享映射修复 Built-in Feature 兼容展示。`localhost:3002` 同时新增完整入门路径与课表插件教程；配套 `schedule-helper` 严格使用 Manifest v2 用户受管数据，不读取内置课表或内部 Service。

这属于封版后可发现性、兼容投影和文档闭环补强，不改变 v0.10 的数据库、API 或产品范围。完整实现、回滚和当次统一门禁证据见 `docs/进度/v0.10-dev/v0.10.23-dev.md`。

## 9. 模块、插件与资源边界收口

A16-A18 完成了上一轮审计尚未覆盖的物理隔离：Core/Built-in Feature 描述符和实现进入 `modules`/`internal/modules`；Plugin Manager 与 `data/plugins`/`data/plugin_data` 只管理 External Plugin；Built-in Feature 本地数据进入 `data/module_data`；Theme、Homepage、Space Style 等资源统一进入 `data/resources`。

最终验收还验证了：`runtime: builtin` 和保留名称不能导入；`/plugins` 与 `/features` 不再混列；Runtime Manifest 保持 `modules[]/plugins[]` 双通道；旧布局可 apply/rollback；`000026` 可 up/down/up；备份格式 v2 可恢复模块、插件、资源和用户文件。完整证据分别见 `v0.10.25-dev.md`、`v0.10.26-dev.md` 和 `v0.10.27-dev.md`。
