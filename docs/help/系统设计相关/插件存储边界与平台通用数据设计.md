## 1. 强制约束

插件持久数据仅允许使用平台预先定义并开放的现有表、插件自己的 SQLite 数据库、插件自己的文件型 config。
“开放表”意味着平台通过受控接口开放部分操作，不能解释为把表名、SQL 或数据库连接交给插件。

- 外部插件安装、启动、升级、卸载均不得执行平台 PostgreSQL 的建表、改表、建索引、建 schema 或任意 SQL。
- 不允许为每个插件新增 `pdf_*`、`plugin_某名称_*` 等平台专用表，也不按插件数量复制通用表。
- 插件不能因为获得文件读取、记录写入或管理员 Grant，就获得平台数据库连接、其他插件 SQLite 或其他用户文件权限。
- 平台通用结构不足时，由平台开发修改现有通用表及服务合同，随 CampusOS 版本交付；插件包不能自行执行该迁移。
- 第一方受管插件也遵守数据所有权边界；编译进平台不构成增加私有平台表的理由。
- 当前测试数据允许清空或重建。具体执行应先确定数据库、卷、目录和影响范围；授权允许清理，并不要求每次设计更新都清理。

## 2. 存储选型与现有接口

| 数据 | 允许的存储位置 | 现状与访问边界 |
| --- | --- | --- |
| 插件结构化业务记录 | 现有 `plugin_records` | `MarketService` 按插件、owner、collection、record key 隔离，校验声明字段及版本；插件不提供 SQL |
| 插件私有 KV | 插件自己的 SQLite | Host API `StorageGet/Set/Delete` 由 `SQLiteKVStore` 实现，要求插件身份匹配；路径统一为专属 `plugin.db` |
| 插件非敏感配置 | 现有 `plugins.config`、旧插件 config，或 v4 用户空间 `plugins/<key>/config/` | `GetConfig/SetConfig` 仍使用宿主配置合同；v4 已提供用户 JSON 的 defaults/schema、CAS、快照与 pending 恢复工具，不与 `plugins.config` 双向同步；自动 provisioning 仍待用户安装状态机 |
| 用户文件及附件 | 已开放的文件/内容服务 | 平台通过 `storage_objects`、资产/文档和文章绑定表保存事实；插件只能使用获准的内容接口 |
| 插件受管文件元数据 | 现有 `plugin_file_metadata` 及受管文件接口 | 表由平台拥有，数据仍受插件命名空间、owner 和配额约束 |
| 声明、Grant、Consent、Secret | 现有插件授权与秘密管理表 | 平台维护；插件不能向普通记录或 SQLite 写入“已授权”来替代平台判定 |
| 打开预览的短期上下文 | 现有 `plugin_ui_invocations` | 平台签发与读取，插件不能自行写入并获得内容权限 |

源码依据：

- [Host API 方法分发](../../../internal/plugin/hostapi/grpc_server.go)：Storage、Record、Config 等有界方法；当前 Host API Record 方法调用系统记录接口，不能声称它们已提供代任意用户写记录的能力。
- [通用记录服务](../../../internal/plugin/market.go)、[记录 PostgreSQL 适配器](../../../internal/plugin/market_pg.go)：用户记录另由已认证用户接口确定 owner。
- [SQLite KV](../../../internal/plugin/hostapi/sqlite_store.go)：默认路径 `data/plugin_data/<plugin-name>/plugin.db`，根目录配置为 `PLUGIN_DATA_DIR`。
- [配置校验](../../../internal/plugin/config.go)：配置字段类型/限制与 Secret 分流。

## 3. SQLite 与文件型 config 的约定

现有 `plugin.db` 由 Host API 管理，当前只提供固定 `plugin_kv` 表。插件通过该接口使用 KV 时不能任意修改它的内部表。
`PreparePluginStorage` 统一生成 `data/plugin_data/<plugin-name>/`、`plugin.db` 与 `config.json`；目录、数据库和配置文件
按最小权限创建，并拒绝目录穿越与 config 符号链接。插件名称允许 Manifest 中已有的点号，例如 `campusos.pdf-viewer`。
需要复杂本地关系的插件可在这个专属目录使用另一个 SQLite 文件（如 `private.db`），自行维护本地 schema 版本；它仍不是平台
PostgreSQL，也不会被 Host API 当作任意 SQL 接口。

文件型 config 适合语言、显示偏好、非敏感运行参数。当前平台提供 JSON 约定：专属数据目录下的 `config.json`，最大 256 KiB、
必须为合法 JSON，以临时文件原子替换并拒绝符号链接；推荐包含 `config_version`。`ReadPluginFileConfig` / `WritePluginFileConfig`
是平台侧工具，不会自动把配置同步到 `plugins.config`，也不允许保存密码、SMTP 授权码或第三方 Token。

同一配置键只选择一个权威来源：宿主管理配置走 `plugins.config`；插件本地配置走文件。不要双向同步并制造冲突。
密码、SMTP 授权码、第三方 Token 等继续使用既有 Secret 服务，普通 config、JSONB 记录和 SQLite 均不得保存明文 Secret。

备份覆盖插件 SQLite/config 的一致快照；SQLite 存在 WAL 时采用 SQLite 备份接口或停写后的完整快照，不能只复制正在写入的主文件。
插件升级保留数据目录；卸载与删除持久数据是分开的操作。插件私有存储不得成为用户原文件的第二套账本。

## 4. 如何理解 v1.1 基线中的预览上下文

[v1.1 基线](../../../migrations/000001_v1_1_schema_baseline.up.sql) 已在现有
`plugin_ui_invocations` 中包含 `personal_document_id`、外键、三类上下文互斥检查及索引，没有创建 PDF 插件私有表。
它只由平台 migration 执行器应用，插件不读取或执行 SQL 文件。因此其数据边界符合本次约束。

当前由 [通用平台上下文服务](../../../internal/platform/pluginui/context.go) 签发并校验，
[业务资源适配器](../../../internal/modules/features/richtext/resource_contexts.go) 和
[个人文档适配器](../../../internal/server/personal_document_pdf_viewer.go) 复用原有业务 ACL。
插件 Surface/Action 的注册与版本验证在 [server 装配](../../../internal/server/plugin_resource_surface.go) 完成。
只支持三种固定资源类型的 PDF；插件不能新增可执行资源解析器、任意 SQL 或路径。

保留现有三个资源引用列及 FK，避免为了改名丢失数据库完整性。新 PDF 插件应复用这三类平台资源合同，不能再增加
`某插件_document_id`。只有平台本身新增资源类型、已有合同确实无法表达时，才评估修改通用表。

补充更正：数据库记录并非实现即时撤销和实时权限检查的唯一方法。当前项目选择短期服务端记录；PDF.js 的 Range 请求
会重复使用它，不能描述成一次性字节令牌。授权状态始终在每次读取时重新检查。

## 5. 通用预览服务（2026-09-20 已实现）

签发与校验已从 PDF 专用入口提取为宿主通用服务，沿用 `plugin_ui_invocations`；既有 `context_digest` 保存插件版本/Surface 与资源对象版本摘要。
输入使用宿主定义的资源类型、资源 ID、操作、Surface 和展示方式；当前支持类型只限文章附件、个人资产、个人文档。

1. 宿主认证当前用户，解析注册的插件版本、Surface 与操作白名单。
2. 平台资源解析器按类型调用业务模块：文章附件检查文章阅读权及绑定，个人资产/文档检查 owner。
3. 平台执行 Capability、Grant、Consent 和资源状态检查，保存短期上下文，返回不透明 Invocation ID。
4. 插件请求内容时，宿主根据上下文重新执行相同授权及资源检查，返回认证文件流。
5. 插件升级、撤权、资源回收/删除或上下文过期时拒绝后续读取；后台任务清理过期上下文。

插件只消费此接口，不注册 SQL 查询、表名、文件路径或可执行解析器。新增插件复用既有资源类型不需要 migration。
通用 HTTP 请求沿用 `POST /api/v1/plugin-ui/invocations`，接受 `plugin_key/surface_id/presentation/resource_type/resource_id`，
文章附件另需 `thread_id`，声明式动作另需 `action_id`。Web 类型为 `UIResourceContext`，执行器为 `uiRuntimeApi.openSurface`。
旧 PDF 三入口仍复用同一服务；不让外部进程持有浏览器 JWT。请求示例见 [官方 UI v2 文档](../../../docs-site/plugins/ui-v2.md)。

暂不把三个资源外键改为任意 `resource_type + resource_id + JSONB`：无约束的多态 ID 会失去数据库 FK。
如果以后确需这种结构，必须由平台登记类型，并补齐资源存在性、删除联动、索引、事务与一致性检查，不能用 JSONB 绕过业务鉴权。

## 7. 验收标准

- 安装、升级、启动、卸载一个外部插件前后，平台业务表/列/索引清单不因插件动作变化。
- 插件无法调用 SQL/DDL、选择平台表名或取得 PostgreSQL 凭据；Manifest 增加 collection 只影响通用记录合同。
- 两个插件同名 key、两个用户同名记录、多个资源类型同 ID 均保持隔离；非法 owner、collection、字段与路径被拒绝。
- 本地 SQLite/config 升级及恢复不影响平台 Schema；配额和文件权限可验证。
- PDF 的文章附件、个人资产、个人文档入口与认证下载均通过原有授权回归。
- 当前测试环境若重建，先列出准确目标与影响，再验证平台 migration、插件配置及三入口；2026-09-16 已对确认可丢弃的 Docker `campusos` 开发库执行 reset 并应用单一 v1.1 baseline。
