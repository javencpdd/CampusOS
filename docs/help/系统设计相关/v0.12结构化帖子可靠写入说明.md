# v0.12 结构化帖子可靠写入说明

> 适用阶段：v0.12 C0  
> 面向对象：开发者、维护者和排查内容写入问题的管理员

## 1. 为什么要有这层设计

一篇内容不只是一行帖子。普通帖子至少要同时保存帖子本身和它的历史 Revision；图文文章还要保存
Article Detail。系统还需要留下可靠命令审计，并在提交后投递事件。

这些记录如果分开提交，就会出现“页面上有帖子但没有正文详情”或“内容已改但历史没有记录”的状态。
v0.12 先把这一类问题收敛成一个规则：一次内容操作要么全部成功，要么全部不留下。

## 2. 普通帖子如何工作

用户创建、编辑或删除自己的普通帖子时，Community 会在一个可靠命令中完成：

```text
检查作者和帖子状态
-> 写 Thread
-> 写 Content Revision
-> 写命令审计
-> 写 Outbox 事件
-> 提交
```

任一步失败，数据库会回滚，用户不会看到部分完成的帖子。缓存刷新和兼容 EventBus 事件不会抢在提交前发生。

## 3. 图文文章如何工作

图文文章仍使用原有 `/richtext/articles` API。创建、保存草稿、发布、下线、作者删除，以及管理员的
下线、恢复、删除都在一个外层可靠命令中同时处理：

```text
Community Thread / Revision / 治理状态
             +
RichText Article Detail
             +
command audit / Outbox
```

因此，Article Detail 保存失败时，系统不会再创建一个“已经被放进回收站”的空帖子。它会直接回滚整个请求。

图片上传仍是例外：文件系统不能和 PostgreSQL 做同一个原子提交。上传文件先经过 User Storage 的路径、
配额和安全检查；尚未绑定到文章的文件由后续清理策略处理。不要为了追求表面上的原子性，在事务中上传文件或
调用外部网络服务。

## 4. 开发 Built-in Feature 时的规则

新 Built-in Feature 不应直接访问 `ThreadRepository` 或拿数据库连接。它应调用 Community 的
`ContentGateway`，并由 Feature 自己的可靠命令协调自己的 Detail Store。这样 Community 保持 Thread、
Revision 和治理状态的所有权，Feature 保持自己的业务详情所有权。

下一阶段会提供正式的 Structured Thread Participant 合同。当前不要自行复制 RichText 的内部函数，也不要
把事务、AppContext 或 Repository 传给 External Plugin、MCP、Agent Runner。

## 5. 如何验证和排查

运行以下检查会模拟 Revision 或 Article Detail 写入失败：

```bash
make v12-failure-injection-check
```

检查会确认失败后没有残留 Thread、Article、command audit 或 Outbox。需要看已经提交的命令时，管理员使用
“可靠任务”页面读取审计与事件摘要；该页面不展示敏感 payload、Token 或 HTML 正文。

如果线上发现旧版本遗留的补偿回收帖子，不要直接删除。先通过正常回收站或治理流程确认归属，再使用
forward-fix 或经过验证的恢复方案处理。
