# CampusOS v0.6 数据库体检与模型决策

## 1. 可重复检查

```bash
make migrate-up
make database-check
python3 skills/campusos-data-architecture-sync/scripts/check_architecture_sync.py --root .
```

`database-check` 检查核心孤儿、重复、非法状态和负计数，并核对关键表、列、已验证约束和索引；任一违规都会返回非零状态。

2026-07-11 本地基线：30 张表，migration `000001` 至 `000016`，14 组数据检查均为 0 violations，core schema contract 通过。

## 2. `000016` 决策

| 领域 | 决策 |
| --- | --- |
| 内部 ID | 用户、社区、RBAC 和富文本继续以 BIGINT 为内部标识；字符串只用于外部平台 ID。 |
| 稳定关系 | accounts/sessions、threads/posts、RBAC、personal space、richtext 和 webhook delivery 增加已验证 FK。 |
| 删除 | 当前业务使用软删除；稳定 FK 使用 `ON DELETE RESTRICT`，防止维护脚本物理删除造成静默级联。 |
| 状态 | users、threads、posts、plugins 增加与代码常量一致的 CHECK。 |
| 计数 | 社区计数、回复楼层、插件包大小禁止负数。 |
| 索引 | 增加 session 过期、回复 thread/floor、API key 过期和 webhook status/time 索引。 |

Migration 在增加约束前执行 preflight。回滚文件只撤销本次约束和索引，不修改业务数据。

## 3. 暂未强制的模型

1. `mcp_audit_logs`、`message_bindings` 和 `user_space_style_snapshots` 仍存在字符串 user ID，需先区分内部与外部 ID，再补标准列和回填。
2. tags 表与 thread/category 数组并存。v0.6 保持数组为当前查询模型，不宣称规范化已完成。
3. likes 使用 `target_type + target_id`。已限制 target_type，目标存在性继续由定期检查器负责。
4. plugin_name 仍是部分日志和权限表的可变引用。版本快照已隔离，immutable package ID 仍需后续 migration。

## 4. 架构页边界

管理端静态架构图由 migration 和同步 Skill 防漂移。实线关系应表示数据库 FK，逻辑关系必须明确标注。Web 端只能读取白名单元数据，不能执行任意 SQL。
