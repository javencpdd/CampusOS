# CampusOS 数据库管理指南

> 当前基线：v1.0 clean database baseline
> 更新时间：2026-09-01
> PostgreSQL：16+
> 详细设计：[数据库全面重构方案](../../项目计划书v1/项目计划v1.0/01-v1.0数据库全面重构方案.md)

## 1. 事实来源

判断当前数据库时按以下顺序：

```text
migrations/*.up.sql
  > scripts/schema-contract.sql / database-audit.sql / migration-hygiene.sql
  > Admin /architecture
  > 本指南
  > v0.x 历史架构与进度快照
```

当前只有三组 migration：业务 Schema、v1 插件授权基础、稳定参考数据。旧 `000001-000049` 已删除，
不能用历史文件名或历史表数量判断新数据库。

## 2. 连接配置

本机/PostgreSQL Client 常用环境变量：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DB_HOST` | `localhost` | 数据库主机 |
| `DB_PORT` / `POSTGRES_PORT` | `5432` | 端口 |
| `DB_USER` | `campusos` | 数据库用户 |
| `DB_NAME` | `campusos` | 数据库名 |
| `DB_PASSWORD` / `POSTGRES_PASSWORD` | 开发默认值 | 不应提交真实凭据 |
| `PSQL_MODE` | `auto` | `host`、`docker` 或自动选择 |
| `POSTGRES_CONTAINER` | `campusos-postgres` | Docker 模式容器名 |
| `CAMPUSOS_SKIP_DOTENV` | `false` | 测试或显式环境下可跳过仓库 `.env` |

Docker 开发通常从 `deploy/docker/.env.dev.local` 启动服务；独立运行 migration 时，应显式传入实际容器名和数据库名，
避免脚本读取了另一套 `.env`。

## 3. migration 命令

Linux / Git Bash：

```bash
./scripts/migrate.sh status
./scripts/migrate.sh check
./scripts/migrate.sh up
./scripts/migrate.sh down
```

Windows PowerShell：

```powershell
.\scripts\migrate.ps1 status
.\scripts\migrate.ps1 check
.\scripts\migrate.ps1 up
.\scripts\migrate.ps1 down
```

| 动作 | 行为 |
| --- | --- |
| `status` | 显示版本、名称、checksum 前缀、耗时、执行者与时间，并检查漂移 |
| `check` | 检查六位版本、up/down 配对、重复版本和已执行 checksum |
| `up` | 顺序执行全部未应用版本；SQL 与版本记录同一事务 |
| `down` | 只回滚最高的一个已执行版本 |
| `reset` | 删除整个 public schema 后从零 up；仅 development/test + DB 名确认 |

不要手工修改 `schema_migrations`。检测到旧格式时，应确认数据可丢弃后 reset；真实数据环境需要单独设计前向迁移。

## 4. 当前数据库规模和领域

- 84 张业务表；
- 2 张执行器系统表；
- 76 个稳定 Permission Code；
- 4 个系统角色；
- migration 不创建任何用户、账号、管理员准入记录或默认密码。

主要领域：

| 领域 | 代表表 |
| --- | --- |
| Identity/RBAC | `users`、`accounts`、`sessions`、`roles`、`permission_definitions` |
| 管理员与 MFA | `identity_admin_accounts`、`identity_mfa_*`、`identity_*challenge*` |
| Community | `categories`、`threads`、`posts`、`mutual_aid_details`、`secondhand_details` |
| 内容治理 | `content_revisions`、`content_moderation_*`、`richtext_article_*` |
| 存储/文档 | `storage_objects`、`user_storage_*`、`personal_document_*` |
| 学期/课表 | `academic_terms`、`user_schedule_terms`、`user_schedule_preferences` |
| 插件当前模型 | `plugins`、`plugin_permissions`、`plugin_records`、`plugin_user_grants` 等 |
| 插件 v1 基础 | `plugin_publishers`、`plugin_versions`、`plugin_*grants/consents/delegations/secrets/decisions` |
| Reliability | `platform_outbox`、`platform_outbox_attempts`、`platform_worker_leases` |
| Integration | `webhook_*`、`message_*`、`mcp_audit_logs`、`ai_call_logs` |

完整表清单以 Admin `/architecture` 和重构方案为准。

## 5. 初始管理员

migration 不携带默认管理员。首次启动通过应用安全 bootstrap 或受控 CLI 创建：

- 凭据由 Identity `accounts` 保存；
- 管理平面准入由 `identity_admin_accounts` 保存；
- 全局 admin RBAC 由 `user_roles` 保存；
- 密钥/密码不得写入 migration、日志或文档。

部署时检查 `AUTH_BOOTSTRAP_ADMIN_SECRET` 等当前配置，不要恢复历史默认密码。

## 6. reset 旧开发库

确认所有数据可删除后，Windows Docker 示例：

```powershell
$env:CAMPUSOS_SKIP_DOTENV = "true"
$env:PSQL_MODE = "docker"
$env:POSTGRES_CONTAINER = "campusos-dev-postgres-1"
$env:DB_USER = "campusos"
$env:DB_NAME = "campusos"
$env:CAMPUSOS_ENV = "development"
$env:CAMPUSOS_RESET_CONFIRM = "campusos"
.\scripts\migrate.ps1 reset
```

Linux/Git Bash 使用同名环境变量执行 `./scripts/migrate.sh reset`。

reset 后：

1. 启动/重启 API；
2. 通过 bootstrap 创建首个管理员；
3. 运行 schema、audit、hygiene；
4. 验证登录、帖子、上传、学期、文档和插件基础路径；
5. 如需要测试数据，使用独立且可审计的 fixture，不放回 migration。

## 7. 审计与维护

```bash
./scripts/database-check.sh audit
./scripts/database-check.sh schema
./scripts/database-check.sh hygiene
./scripts/database-check.sh all
```

- audit：重复、孤儿、非法状态、负数计数和业务一致性；
- schema：必需表、列、约束和索引；
- hygiene：重复/冗余索引和重复约束；
- 任一违规返回非零。

综合门禁：

```bash
POSTGRES_CONTAINER=campusos-dev-postgres-1 make v1-database-baseline-check
make architecture-check
make database-check
```

## 8. 备份与恢复

数据库备份不能替代 `data/`、对象文件、插件数据和环境配置备份。恢复点至少包含：

1. PostgreSQL；
2. `data/personal-space` 和对象实际文件；
3. `data/plugins`、`data/plugin_data`、`data/module_data`；
4. 不提交到 Git 的环境配置和密钥引用；
5. Git revision、migration version/checksum。

恢复到隔离环境后先运行 `migrate check`、database-check，再启动 Worker/插件 Runtime，防止旧进程在未验证数据上产生副作用。

## 10. 常见故障

### `legacy schema_migrations detected`

目标数据库仍使用旧格式。开发/测试数据可删除时按第 6 节 reset；不要补假 checksum。

### `migration lock is held`

先检查是否真的有另一个脚本/CI 在执行。只有确认异常遗留后，才能临时设置
`CAMPUSOS_MIGRATION_LOCK_FORCE=true` 并执行一次 `up` 或 `down`，随后立即清除变量。`check` 不获取迁移锁，
因此不会清理遗留锁。

### `migration drift`

仓库 SQL 与数据库记录 checksum 不同。恢复正确 Git revision，或为新变化新增 migration；不要改数据库记录绕过。

### Docker 中连接了错误数据库

打印并核对 `POSTGRES_CONTAINER`、`DB_NAME`、`DB_USER`，必要时设置
`CAMPUSOS_SKIP_DOTENV=true` 防止根 `.env` 覆盖显式测试值。
