# 插件自包含、动态加载与用户配置设计

> 更新时间：2026-09-21（Asia/Shanghai）
> 状态：R11-01、R11-03 和用户端 PDF 的隔离 UI/Host Bridge/Docker 网关已实现；用户安装状态机、Admin 动态 Host、Runner 与升级/卸载仍是目标设计，不能作为当前可执行操作说明。
> 范围权威：[新 v1.1 重构计划](../../项目计划书v1/项目计划v1.1/02-v1.1插件自包含与动态加载重构计划书.md)。

## 1. 为什么不能只把页面移动到 plugins

PDF 页面已迁至 `plugins/campusos.pdf-viewer/frontend`，不再通过 `trustedModules.ts` 编译进 Web；Docker 开发环境把它打包为
校验后的 `.installed` release，由 3003 隔离网关服务。当前仍不能把“用户添加”和用户配置目录的完整生命周期视为完成，
因此本次目标仍包含安装、加载、运行、授权与配置管理方式的继续重构。

重构完成后，平台只拥有通用插件 Host，插件页面独立构建成可安装产物；后端按通用 Runtime 合同运行。
内置登录、文章、文件鉴权等平台功能不必迁成插件。插件自包含不表示每个插件复制核心身份或直接连接平台数据库。

## 2. 四种东西不要混在一起

| 分类 | 目标位置 | 说明 |
| --- | --- | --- |
| 插件源码及定义 | `plugins/<key>/` | 用户页面、管理员页面、后端实现、config schema/defaults、测试和文档 |
| 已安装可运行版本 | `plugins/.installed/<key>/<version>-<digest>/` | 校验过的不可变包；运行不依赖源码目录或 Node/Go 编译环境 |
| 系统级实际数据 | 平台 `plugins.config` 与 `data/plugin_data/<installation-id>/` | 系统配置有唯一权威；专属 SQLite 只能保存插件自己的业务数据 |
| 用户级实际配置 | `data/personal-space/<uid>/plugins/<key>/config/` | 每人每插件独立，由宿主管理，不能被另一用户或插件访问 |

管理员配置字段、默认值和配置界面随插件放在 `plugins`；管理员填入的密码等秘密不属于源码，继续使用加密 Secret 服务。
用户 JSON 配置同样禁止密码、Token 和可替代权限的字段。`meta.json` 的版本和摘要不是授权凭证。

## 3. 页面如何出现

管理员安装并启用包 → 用户添加并满足必需权限 → 宿主返回有效 UI 清单 → 注册通用 Host 路由 → 隔离 iframe 加载包内页面。

用户和管理员拥有不同 audience/Surface，不能因为打开 Admin 页面就获得管理万能权限。
插件通过有界 Bridge 调用配置、记录、资源 Range 等能力；JWT 和平台凭据留在宿主，每次服务端复查权限。
消息来源、窗口、版本、方法、参数、大小和频率都校验。新标签打开宿主壳页，不允许插件自行跳任意地址。

目标使用与主站隔离的 UI Origin，不在主站动态执行上传的 JavaScript。
具体 iframe/CSP/Worker/路由及浏览器安全边界见计划第 5 节；不能仅靠 iframe 宣称插件拿到的文件绝不会泄露。

## 4. 用户配置目录何时建立

用户明确点击“添加到我的插件”后建立，不在账号创建时批量建立，也不等到第一次保存配置。

```text
data/personal-space/12345/plugins/campusos.pdf-viewer/
  config/
    user.json
    meta.json
  .pending/
  .snapshots/
```

没有配置项的插件也创建空配置及版本元信息。“我的文档”不列出这些内部文件；用户从插件设置查看/重置/导出。
插件共享后端不挂载用户空间；通过带当前用户或受限委托上下文的配置接口访问，不接收客户端伪造的 owner。

“添加成功”的必要条件是关系和目录均已就绪。文件系统不与 PostgreSQL 共事务，宿主用 operation、Outbox、幂等重试和原子替换收敛。
磁盘满时显示准备失败及重试，不伪装成功；未知目录不自动转成安装关系或授权。

拟定默认预算：每插件每用户 256 KiB、每用户配置总量 2 MiB；与用户原文件默认 50 MiB 配额分开管理。
快照也有限额，不能把 PDF 或其他大文件藏在配置里。生成的用户附件仍走 Object 和正常文件配额。

## 5. 权限如何判断

```text
插件调用可执行 = 全局安装/启用有效
              ∩ 当前用户已添加且启用（用户调用）
              ∩ 当前版本 Manifest 声明
              ∩ 管理员 Grant
              ∩ 用户 Consent（涉及个人数据）
              ∩ 本次资源/操作的业务权限
              ∩ 有效会话、Scope、版本、限额
```

用户不需要生成密钥或 Token。“添加”创建关系与目录；“同意”才是能力级授权；“启用”决定是否实际可运行。
三者可以在一个向导中展示，但数据与状态必须分离。拒绝可选读取能力不应阻止不需要它的基本功能。
管理员禁用覆盖用户启用；用户只能下载自己空间的文件，其他人的附件仍只能经有权访问的文章入口读取。

## 6. 常见场景

| 场景 | 目标行为 |
| --- | --- |
| 管理员安装 PDF 插件 | 装一次包，不预建所有用户目录；包未启用时不能调用 |
| 用户第一次添加 | 从已验证默认值创建自己的配置，显示权限说明，必需权限满足后启用 |
| 用户更改缩放偏好 | 配置按 revision 更新；并发冲突提示重新加载，不悄悄覆盖 |
| 用户不同意保存阅读位置 | 可按其他必需授权预览，仅保留本次会话状态，不写个人阅读记录 |
| 管理员禁用/用户撤权 | 服务端立即拒绝后续调用，前端移除界面；已传到浏览器的数据不能追溯收回 |
| 用户退出插件 | 停用、撤销个人调用；默认保留 detached 配置，用户可另行确认删除 |
| 全局卸载 | 所有人失去入口和调用，移除可执行包；持久数据保留或清除明确分开 |
| 插件坏了或不存在 | 核心文章/文件仍可用，PDF 仍可按业务权限认证下载 |

## 7. 数据库与后端边界

插件只通过平台开放的受控通用 API 使用现有表，或使用自己的 SQLite/config；不能自行创建平台表或运行 DDL。
目标把现有 `plugin_user_grants` 重构为用户安装关系，与 `plugin_user_consents` 的能力授权分开，具体字段及索引见计划第 8 节。
这是平台负责的 Schema 变更，不是插件安装脚本。纯 UI 插件不需要后端；有后端的插件使用受限 Wasm 或独立隔离容器。

容器需要目录/身份/网络/资源限制；API 和插件不能获得主 Docker socket。
当前 process 运行方式不等于目标安全隔离，也不能因为已有 env 白名单就将新方案标为完成。
