# v1.0 插件三层授权与运行安全说明

> 文档状态：v1.0 目标设计，尚未全部实现
> 当前可用基线：Manifest v1/v2、Host API v1/v2、本地插件目录、版本绑定用户 Grant、运行时令牌和受管数据
> 正式计划：[v1.0 插件生态与三层授权体系正式项目计划](../../项目计划书v1/项目计划v1.0/00-v1.0版本计划书.md)
> 创建/更新时间：2026-09-01

本文面向插件开发者、管理员和维护人员，解释 v1.0 为什么引入三层授权、各模块负责什么、如何配置，以及常见操作会发生什么。
在 v1.0 代码和 migration 完成前，本文中的 Manifest v3、Capability code、Admin Grant 和 ReasonCode 属于目标合同，不能据此认为当前实例已经支持。

## 1. 先理解两个不同的权限系统

CampusOS 的平台 RBAC 与插件授权解决不同问题：

| 系统 | 回答的问题 | 典型主体 |
| --- | --- | --- |
| 平台 RBAC | 某个用户或管理员能否执行 CampusOS 操作 | 用户、版主、管理员 |
| 插件三层授权 | 某个插件版本能否代表当前用户或系统使用某项受控能力 | 插件身份、插件版本、当前用户、后台委托 |

例如，用户本身能查看自己的课表，不等于任意插件都能读取；插件必须声明能力、管理员批准，并获得该用户同意。反过来，用户同意也不能让插件绕过管理员拒绝或系统策略。

## 2. 核心公式

```text
最终允许
  = 插件已声明该 Capability
  AND 管理员已为当前插件版本授予
  AND 当前用户已同意（该能力要求同意时）
  AND 插件身份、版本和包摘要匹配
  AND 资源属于可信 Scope
  AND 插件处于可运行状态
  AND 系统策略允许
```

任何一项不满足都拒绝。Manifest 只是申请单，不是通行证；管理员和用户也不能授予 Manifest 未声明的能力。

## 3. 核心概念

### 3.1 Capability

Capability 是平台维护的稳定能力标识，不是插件随意编写的字符串。目标元数据包括：

- `code`：例如 `schedule.self.read`。
- `resource/action`：资源和动作。
- `scope`：v1.0 只支持 `self` 或 `system`。
- `risk`：low/medium/high。
- `consent_required`：是否需要当前用户同意。
- `data_classification`：公开、个人、敏感等分类。
- `audit_level`：是否记录判定和业务结果。

插件可声明用途和 required/optional，但不能自行降低平台风险等级、扩大 Scope 或关闭审计。

### 3.2 三层授权

| 层 | 谁提供 | 作用 | 失效场景 |
| --- | --- | --- | --- |
| Declaration | 插件包发布者 | 声明该版本希望使用的能力和用途 | 新包移除、版本替换、Manifest 无效 |
| Admin Grant | 有权管理员 | 批准该插件版本可在本实例使用哪些能力 | 管理员撤销、版本/权限指纹变化、紧急隔离 |
| User Consent | 当前用户 | 同意该插件按说明处理自己的数据 | 用户撤销、用途变化、版本扩权、账号状态变化 |

### 3.3 插件身份与版本

`plugin_name` 便于阅读，但不能独自承担长期身份。v1.0 目标使用稳定 `plugin_id`、`publisher_id` 和 `version_id`，并绑定包 digest、签名状态和权限指纹。这样同名恶意包、旧版本授权复用和扩权升级都能被识别。

### 3.4 Scope

- `self`：资源所有者由已验证 Session 注入。插件提交的 `user_id` 不可信。
- `system`：访问明确的系统级资源，通常不需要用户同意，但必须有 Admin Grant。

v1.0 不提供“任意用户”“全租户”或插件自定义 Scope。后台任务如需代表用户执行，必须持有受限 Delegation。

### 3.5 Delegation

Delegation 是宿主为后台任务签发的短期委托，绑定用户、插件版本、Capability、Scope、到期时间和策略 revision。
它不能增加权限；用户撤销、管理员撤销、插件停用、版本替换或委托到期后，下一次任务调用被拒绝。

## 4. 模块职责

| 模块 | 主要职责 | 安全边界 |
| --- | --- | --- |
| Manifest/Package Validator | 校验声明、签名、摘要、兼容性和权限 diff | 不做授权决定 |
| Plugin Identity Registry | 保存发布者、插件、版本和包事实 | 不暴露内部数据库给插件 |
| Capability Catalog | 提供机器可读能力定义和中文展示元数据 | 插件不能自定义风险等级 |
| Admin Grant Service | 记录逐能力批准、拒绝、理由和 revision | 不代替用户 Consent |
| User Consent Service | 记录逐用户逐能力同意/撤销 | 不批准系统能力 |
| AuthorizationService | 汇总全部事实，返回 allow/deny 与稳定原因码 | 所有敏感入口只依赖这一判定核心 |
| Host API/Event/Job Adapter | 构造可信 Actor/ResourceContext 并调用判定 | 不信任插件传入用户身份 |
| Runtime Manager | 启停、健康、运行时令牌、超时和隔离 | 停用状态优先于所有 Grant |
| Managed Data/Secret Port | 受管数据、配额、保留、加密和脱敏 | 不返回路径、SQL、DSN、JWT 或明文 Secret |

## 5. Manifest v3 目标配置

以下是目标格式示意，不是当前 Manifest v1/v2 可直接使用的配置：

```yaml
api_version: campusos.plugin/v3
host_api_version: v3
name: schedule-reminder
version: 1.0.0
runtime: process

capability_requests:
  - code: schedule.self.read
    required: true
    purpose: 读取本人课表以生成上课提醒
  - code: notification.self.send
    required: false
    purpose: 在 CampusOS 内发送提醒
```

规则：

1. `required` 被拒绝时，插件不能启用依赖该能力的核心功能。
2. `optional` 被拒绝时，插件必须提供明确降级，不能反复诱导授权。
3. `purpose` 发生实质变化视为权限变化，需要重新审批/同意。
4. v3 External Plugin 禁止 `*/*` 通配扩权。
5. 旧 v1/v2 Manifest 在兼容期由 Adapter 映射到保守 Capability；映射结果必须可见、可测试。

## 6. 一次调用如何判定

以“课表提醒插件读取当前用户课表”为例：

```text
已登录用户触发插件操作
  -> Host 注入 user/session/trace，不接受插件自报 user_id
  -> Runtime Token 验证 plugin_id/version/runtime instance
  -> Host API v3 把方法映射为 schedule.self.read
  -> AuthorizationService 检查声明、Admin Grant、User Consent、版本、Scope、状态、策略
  -> Allow：调用稳定 Schedule ReadPort，并返回最小 DTO
  -> Deny：返回 ReasonCode，写低敏审计，前端显示中文修复建议
```

Host API 不返回内部 Domain Entity。用户公开资料与邮箱等联系信息使用不同 Capability，避免普通资料读取顺带获得敏感字段。

## 7. 管理员如何使用

### 7.1 安装或升级

1. 导入包后查看发布者、签名、digest、版本和权限指纹。
2. 检查 Capability diff：Added、Expanded、Removed、Reduced、Purpose Changed。
3. 对每项 Capability 选择授予或拒绝，并填写高风险操作理由。
4. required 能力未授予时，系统明确显示插件不可启用的原因。
5. Added、Expanded、Purpose Changed 不继承旧授权；Removed/Reduced 只能缩权。

### 7.2 撤销与紧急处置

- 撤销单项 Admin Grant：该能力在事务提交后的下一次调用被拒绝。
- 停用插件：所有运行能力停止，但用户数据不自动删除。
- 隔离插件：阻断 Host API、事件、后台任务并轮换/吊销运行令牌，用于安全事件。
- 卸载插件：实现可移除，受管用户数据继续允许原用户导出或删除。

### 7.3 诊断

管理员应看到插件、版本、Capability、判定、ReasonCode、trace、时间和低敏 Scope 摘要；不应看到 Secret、JWT、完整个人内容或明文外部凭据。

## 8. 用户如何使用

用户同意页按 Capability 展示：

- 插件要做什么、为什么需要。
- 将访问哪类本人数据、风险等级和是否为必要能力。
- 不同意时哪些功能不可用，哪些仍可降级使用。
- 当前同意属于哪个插件版本，以及用途是否发生变化。

用户可逐项撤销。撤销后系统不自动删除数据；用户仍可在受控路径导出或删除本人受管数据。重新同意必须是明确操作，不能由插件后台自动恢复。

## 9. 稳定拒绝码与中文提示

| ReasonCode | 建议用户/管理员提示 | 修复方式 |
| --- | --- | --- |
| `DENY_CAPABILITY_NOT_DECLARED` | 插件未声明此能力，平台已阻止调用 | 更新合法插件包；不能在后台强行放行 |
| `DENY_ADMIN_GRANT_MISSING` | 管理员尚未授权此能力或已撤销 | 联系有权管理员审查该版本 |
| `DENY_USER_CONSENT_MISSING` | 你尚未同意此项数据用途或已撤销 | 在插件授权页查看用途并自主选择 |
| `DENY_VERSION_MISMATCH` | 插件已升级，旧授权不能继续使用 | 审查权限变化后重新授权 |
| `DENY_SCOPE_MISMATCH` | 插件请求的数据不属于允许范围 | 返回本人范围；如仍出现请报告插件问题 |
| `DENY_PLUGIN_INACTIVE` | 插件已停用、异常或被安全隔离 | 管理员检查运行状态和审计 |
| `DENY_DELEGATION_INVALID` | 后台任务授权已过期或撤销 | 重新发起显式任务/授权，不复用旧委托 |
| `DENY_SYSTEM_POLICY` | 系统安全策略阻止了该操作 | 管理员查看策略和 trace；不要绕过保护 |
| `DENY_UNKNOWN_OPERATION` | 当前插件或平台不支持该操作 | 更新兼容版本或修复插件调用 |

前端不得直接展示 SQL、堆栈或 `internal server error`。未知 ReasonCode 使用“操作未获授权，请检查插件权限或联系管理员，并提供追踪编号”的安全兜底。

## 10. 常见场景

### 场景 A：安装一个只读课表插件

管理员批准 `schedule.self.read`；用户首次启用时同意读取本人课表。插件只能获得宿主注入的当前用户 DTO，不能查询其他用户。

### 场景 B：用户不同意可选通知

课表读取为 required、站内通知为 optional。用户拒绝通知后，插件仍可展示提醒列表，但不能发送通知；不能把 optional 拒绝误报为插件整体故障。

### 场景 C：插件升级新增邮箱读取

diff 标记 Added/Expanded；旧 Admin Grant 和 User Consent 不覆盖新能力。插件旧能力是否继续运行由版本切换 ADR 决定，新邮箱能力一定在重新批准和同意前拒绝。

### 场景 D：后台定时提醒

宿主签发短期 Delegation。用户撤销课表读取或插件被停用后，待执行任务即使已入队也必须在消费前重新判定并拒绝。

### 场景 E：插件卸载后处理文件

Runtime 不再运行，但用户仍可通过 CampusOS 自身的保留路径查看用量、导出或删除本人数据；插件不能借此重新获得运行权限。

## 11. 当前版本使用提示

在 v1.0 实现完成前：

- 当前 Host API 仍以 Manifest 声明检查为主，管理员逐能力 Grant 尚未形成独立事实。
- 当前用户授权按插件和版本保存权限数组，已支持显式选择、撤销和版本失效，但不是目标逐 Capability Consent 表。
- 当前 `runtime: grpc` 实际是 loopback HTTP 管理进程，不是标准 protobuf gRPC。
- 当前 SDK/CLI 已有基础开发闭环；不要重复创建已有的 init/build/test/verify/dev 命令。

现行插件开发请同时阅读 [插件体系](../../../docs-site/plugins/overview.md)、
[SDK、CLI 与测试](../../../docs-site/plugins/sdk-cli.md) 和
[插件市场与受管数据](../插件相关/插件市场与受管数据-v0.9.md)。
