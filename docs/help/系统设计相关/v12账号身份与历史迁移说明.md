# v12 账号身份与历史迁移说明

> 适用阶段：v0.12 A2  
> 状态：已实施。邮箱验证码、密码重置和会话轮换在后续 A3-A7 阶段实现。

## 1. 这次改动解决什么问题

过去用户邮箱会同时出现在用户资料和登录账号中。两处内容如果不一致，或者只差大小写，
登录和后续验证可能得到不同结果。v12 先把“用于登录的邮箱”收敛到账号记录，再安全地
保留旧资料字段，避免破坏已有用户。

这一步不是给历史账号自动完成邮箱验证。它只是让系统能清楚地区分：哪些用户是新注册后
真正验证过邮箱，哪些用户只是为了兼容历史登录而被保留。

## 2. 邮箱和状态的含义

| 数据 | 用途 | 谁可以写 |
| --- | --- | --- |
| `accounts.identifier_normalized` | 登录邮箱的权威规范化值 | Identity Service |
| `users.email` | 旧接口和资料读取的兼容投影 | Identity Service 同步，不应单独写入 |
| `verification_state` | 邮箱拥有权和账号兼容状态 | Identity Service |
| `auth_version` | 后续 Session / Token 撤销版本 | Identity Service |

系统只做两种安全且可预期的规范化：去除首尾空格、转为小写。例如
` Student@Example.Test ` 会保存为 `student@example.test`。系统不会猜测 QQ、Gmail 等服务
商对点号、加号别名或其他规则的处理方式。

验证状态如下：

| 状态 | 当前能否登录 | 是否等于邮箱已验证 | 说明 |
| --- | ---: | ---: | --- |
| `unverified` | 后续验证流程启用后否 | 否 | 已创建但还未消费验证 Ticket 的新账号。 |
| `legacy_accepted` | 是 | 否 | 历史账号的兼容状态；不能被当作找回邮箱。 |
| `verified` | 是 | 是 | 用户完成目标用途的邮箱验证。 |
| `system_managed` | 是 | 不适用 | 系统管理员等部署管理账号；不走公网邮箱找回。 |

## 3. 历史数据升级前应做什么

1. 先备份 PostgreSQL 和 `data/`，并确认备份可恢复。
2. 在预发布数据库运行 migration。若发现邮箱冲突、同一用户多个邮箱账号、用户资料与账号
   不一致、孤儿账号或空邮箱，migration 会停止并输出相关 ID。
3. 人工决定真实邮箱归属后修复数据，再重新运行 migration。不要用 SQL 批量把所有账号改
   为已验证，也不要通过删除唯一索引绕过冲突。
4. 完成升级后运行检查命令，确认结构和状态映射正确。

```bash
make identity-email-check
make database-check
```

正常的历史普通账号会进入 `legacy_accepted`，仍可使用原密码登录。新注册、密码找回和
更换邮箱尚未在 A2 打开，因此不会在本阶段突然改变普通用户的网页流程。

## 4. 历史共享邮箱占位

如果历史导入曾使用共享邮箱，例如 `1904650862@qq.com`，它不能变成多个用户的登录邮箱。
系统用两类独立数据记录它：

- `identity_legacy_email_placeholders`：仅记录某位用户曾带有历史占位标记；它不是账号。
- `identity_reserved_identifiers`：阻止这个标识被新注册、绑定或找回流程当作个人邮箱。

管理员界面和导出物应显示“历史占位标记”，不能把它显示成“已绑定邮箱”。占位标记不用于
发送邮件、登录、验证码或 Session。

## 5. 开发者边界

- Handler、插件、风格包和前端不得直接更新 `users.email`、`accounts.identifier` 或
  `verification_state`。
- 需要读取当前账号状态时，使用公开的 `identity.account-reader` Port；它只返回账号 ID、
  用户 ID、规范化标识、验证状态和时间，不返回 password hash、JWT、验证码或 Ticket。
- 邮件模块只能在后续阶段调用最小 Dispatch Port，不可导入 Identity 的 PostgreSQL
  Repository。
- 不要把邮箱地址、验证码、Ticket、Token、Secret 或 hash 写进日志、Outbox payload、
  插件数据或浏览器缓存。

## 6. 回退边界

生产故障优先使用 forward-fix。`000028` 的 down migration 只用于隔离演练：它会删除 v12
状态列和策略表，不能安全地还原历史大小写、验证含义或冲突数据。回退前应暂停新账号写入，
保留备份和故障证据，再按受控恢复流程操作。
