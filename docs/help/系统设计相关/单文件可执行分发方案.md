# 单文件可执行分发方案（Windows / Linux）

> 评估日期：2026-08-03 · 基线：v0.13.41-dev（迁移 000001–000043）
> 目标：不具备技术背景的用户下载后解压即可运行整个 CampusOS，无需编译环境、无需 Docker。

---

## 1. 总体结论

**可行。** CampusOS 的技术栈对单文件分发非常友好：

| 检查项 | 现状 | 结论 |
|--------|------|------|
| 后端形态 | Go 单体服务，单一入口 `cmd/server` | 交叉编译即得单个 exe / 二进制 |
| CGO 依赖 | 全部依赖为纯 Go（pgx v0.5、nats.go、go-redis、wazero、modernc.org/sqlite） | `CGO_ENABLED=0` 可静态编译，跨平台无坑 |
| Redis | 有 `REDIS_ENABLED` 开关，仅作缓存 | 单文件模式关闭即可 |
| NATS | 连接失败自动回退内存事件总线（`platform_modules.go:66`） | 单文件模式无需部署 |
| 前端 | web / admin / docs-site 三个 Vite 静态产物 | 构建一次后用 `go:embed` 打进二进制 |
| 迁移 | 3 组 clean baseline SQL + checksum/lock 治理表 | embed 后按顺序执行；已应用文件禁止漂移 |
| 文件存储 | `data/` 目录磁盘存储 | 单文件模式天然兼容 |
| **PostgreSQL** | 唯一的硬外部依赖 | 见第 3 节专项方案 |

唯一的实质性工作是：**数据库内嵌 + 前端内嵌 + 启动自举**。

## 2. 当前代码中与分发相关的事实（已核实）

1. `pkg/config/config.go:155`：`DATABASE_DSN` 环境变量驱动，默认指向 `localhost:5432`；`.env` 文件可选加载。
2. `internal/server/bootstrap.go:56-63`：PG 连接失败时回退内存 Adapter（`ProfileMemory`）——**数据不落盘，重启即丢**，只能用于演示，不能作为正式方案。
3. `internal/server/platform_modules.go:64-72`：NATS 失败回退内存总线。
4. `internal/server/bootstrap.go:71`：Redis 由 `Enabled && addr != ""` 控制，可完全关闭。
5. Go server **目前不伺服任何前端页面**（无 `go:embed`、无 `FileServer`），三前端依赖独立 dev server / Nginx。
6. 迁移由 `scripts/migrate.sh` 外部触发，版本表 `schema_migrations` 按版本号幂等跳过。
7. `modernc.org/sqlite` 已在依赖中，但仅用于插件 HostAPI 的本地存储（`internal/plugin/hostapi/sqlite_store.go`），与主业务库无关。

## 3. 数据库专项：是否必须依赖本地/云端？

**是的，主业务库必须是 PostgreSQL。** 84 个迁移大量使用 PG 方言（PL/pgSQL 触发器与约束、pgcrypto、CTE、部分索引），仓储层基于 pgx 连接池，改造成其他数据库等于重写数据层，不现实。

在此前提下，有四种部署方式：

### 3.1 方案对比

| 方案 | 原理 | 用户操作 | 优点 | 缺点 | 适用场景 |
|------|------|----------|------|------|----------|
| **A. 内嵌 PostgreSQL** | 随包携带 PG 二进制（embedded-postgres-go 或官方 EDB zip），首次启动自动解压 + initdb 到 `./data/pg`，作为子进程拉起 | 解压、双击 | 零外部依赖；数据落盘持久化；SQL/迁移零改动 | 包体积 +60~80MB；需按 OS 分别打包 PG 二进制；杀软可能误报子进程行为 | **个人体验、演示、小团队（推荐默认）** |
| **B. 本地数据库服务** | 用户自行安装 PostgreSQL 16，exe 通过 `DATABASE_DSN` 连接 | 装 PG、建库、配 DSN | exe 体积小；数据独立于应用 | 需要技术背景，违背"最简单"目标 | 有运维能力的部署者 |
| **C. 云端数据库托管** | DSN 指向 RDS / Neon / Supabase 等托管 PG | 注册云服务、配 DSN | 无需本地 DB；天然多机共享、自动备份 | 依赖网络与厂商；有费用；数据离校 | 正式运营、多节点接入 |
| **D. SQLite 改造** | 数据层换 SQLite | 解压即用 | 真·单文件，体积最小 | **不可行**：迁移全是 PG 方言，工作量≈重写数据层，且丧失并发写能力 | 不推荐 |

### 3.2 推荐：A + B/C 双模式自动切换

启动时自动判断：

```
DATABASE_DSN 已设置  →  模式 B/C：直连外部 PG（本地服务或云端托管）
DATABASE_DSN 未设置  →  模式 A：拉起内嵌 PG（数据存 ./data/pg）
```

- **默认零配置**：小白用户下载解压双击，走模式 A，数据就在 exe 旁边的 `data/` 目录。
- **进阶可升级**：正式部署时设一个环境变量即切换到外置 PG，数据层代码完全一致，无需两个版本。
- 这也回答了"数据库是否怎么看都需要本地或云端"——内嵌模式本质上就是"把本地数据库服务一起打包，并自动管好它的生命周期"。

## 4. 实施要点（五项改造）

### 4.1 前端产物内嵌（约 1 天）

- 三个前端先 `pnpm build` 产出 `dist`（构建只在发布机做一次，最终用户不需要 Node）。
- 新增 `internal/server/static.go`：`go:embed` 三份 dist，挂载 `/`（web）、`/admin`、`/docs`，带 SPA history fallback 与 `Cache-Control`。
- 前端 API baseURL 已是相对路径 `/api`，同源伺服后天然免 CORS。

### 4.2 启动自动迁移（约半天）

- `go:embed migrations/*.up.sql`，启动时在 `database.New` 成功后按 `migrate.sh` 同逻辑执行（读 `schema_migrations`，按版本号顺序补跑）。
- 与现有 shell 流程共用同一版本表，CI / Docker 部署不受影响。

### 4.3 内嵌 PostgreSQL 引导（约 1 天）

- 引入 `fergusstrange/embedded-postgres` 或自行打包 EDB 官方二进制（离线场景必须**随包携带**，不能运行时下载）。
- 数据目录 `./data/pg`，监听 `127.0.0.1:15432`（避开常见端口冲突），首次启动 initdb 并写入 `data/pg.password`（0600）。
- 进程生命周期随主进程：启动时拉起、退出时 `pg_ctl stop`；异常退出后用锁文件/端口探测自愈。
- Windows 包用 EDB win-x64 zip，Linux 包用对应 x64 二进制；arm64 可后续补。

### 4.4 配置自举（约半天）

- `.env` 完全可选化；首次启动自动生成 JWT 密钥等随机配置，持久化到 `data/config.local.json`，二次启动复用。
- 单文件模式默认：`REDIS_ENABLED=false`、`NATS_URL` 留空（自动内存总线）、`DEPLOY_ENV=standalone`。

### 4.5 发布流水线（约半天）

- GoReleaser 或 Makefile 目标一条命令产出：
  - `campusos-windows-amd64.zip`（`campusos.exe` + `data/` + `README.txt`）
  - `campusos-linux-amd64.tar.gz`（`campusos` + `data/` + `README`）
- `CGO_ENABLED=0 go build -trimpath -ldflags "-s -w"`，UPX 可选（注意杀软误报率上升）。
- 挂到 GitHub Actions 的 tag 发布，CI 里已有 Go/Node 环境可直接复用。

**总工作量估算：3~4 天**出第一个可分发版本。

## 5. 风险与注意事项

| 风险 | 说明 | 缓解 |
|------|------|------|
| 杀软误报 | exe 释放并启动 `postgres.exe` 子进程是典型可疑行为 | 代码签名；README 说明；避免 UPX |
| 端口冲突 | 8080 被占用 | 启动时探测并提示，或支持 `PORT` 环境变量 |
| 数据迁移 | 用户换机器需拷贝整个 `data/` 目录 | README 写明备份=拷贝 data；后续可加一键导出 |
| 多用户并发 | 内嵌 PG 性能足够百人级校园社区；超出后切外置 PG | 双模式设计天然支持升级 |
| 升级路径 | 新版 exe 替换旧版，启动自动跑增量迁移 | 迁移版本表幂等已保证 |

## 6. 交付形态（最终用户体验）

**小白用户（模式 A）：**

1. 下载 `campusos-windows-amd64.zip`，解压到任意目录。
2. 双击 `campusos.exe`，等待约 10 秒（首次 initdb）。
3. 浏览器自动打开 `http://localhost:8080`，注册即可使用。
4. 关机前关闭窗口即可；数据保存在 `data/` 目录，下次启动原样恢复。

**正式部署（模式 B/C）：**

1. 准备 PostgreSQL 16（本地服务或云托管），建库。
2. 设 `DATABASE_DSN` 环境变量（或 `.env`），双击 / `./campusos`。
3. 启动时自动完成全部迁移，直接可用。

## 7. 决策建议

1. **先做 4.1 + 4.2 + 4.4 + 4.5（约 2 天）**：交付"外置 DSN 模式"的单 exe，有 PG 环境的用户立即可用，且改造全部向后兼容（Docker/CI 流程不受影响）。
2. **再做 4.3 内嵌 PG（约 1 天）**：补上零配置体验，达成"不具备技术背景也能部署"的最终目标。
3. SQLite 路线明确放弃；内存降级模式仅用于 `campusos --demo` 演示开关，不作为分发方案。
