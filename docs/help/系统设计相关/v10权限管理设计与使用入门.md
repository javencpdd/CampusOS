# CampusOS v10 权限管理设计与使用入门

> 状态：`v0.10-dev` 已实现；需先应用 migration `000025_v10_authorization_catalog` 才能使用权限目录、权限矩阵和授权记录。  
> 适用读者：平台管理员、板块版主、后端/前端开发者、External Plugin 开发者。  
> 最后核验：2026-07-16。本文描述当前代码与迁移的真实行为，不把后续规划当成已实现功能。

## 1. 用一句话理解

CampusOS 的授权判断是：**已登录的谁，凭哪个角色中的稳定权限 Code，在服务端确认的真实资源范围内，是否可以执行某个操作，并留下审计记录。**

“user1 是版主”并不足以放行操作。例如对帖子 `823` 置顶时，后端必须确认：

```text
主体：user1
角色：moderator
权限：community.thread.pin
作用域：category=编程交流
资源：帖子 823（后端从数据库得到所属板块）
结果：允许或拒绝
审计：谁、何时、在哪个请求中、对什么资源做了什么
```

客户端传来的 `category_id`、操作者 ID、审核状态或资源所有者都不是可信授权依据。

## 2. 先完成部署前置条件

1. 执行 `make migrate-up`，再用 `make migrate-status` 确认 `000025` 已应用。
2. 启动服务后，管理员进入 Admin 的“用户与权限 -> 角色与权限”（`/permissions`）。
3. 若 `/api/v1/permissions` 返回“权限目录迁移尚未完成”，不要绕过接口或手工修改旧表；先检查数据库迁移和服务连接。

`000025` 是追加迁移。它保留旧的 `permissions(role_id, resource, action)` 表，回填新的权限目录和角色绑定，供兼容读路径使用。历史 migration 不会被改写。

## 3. 三套授权不要混淆

| 体系 | 解决的问题 | 保存位置/边界 |
| --- | --- | --- |
| 管理员 RBAC | 谁能管理用户、帖子、角色、集成与平台功能 | Identity 的角色、作用域、权限目录与审计表 |
| External Plugin Host 权限 | 外部插件可以调用哪些宿主 API | Plugin Platform 的 manifest、审批和 Host API 边界 |
| 用户对插件的数据授权 | 某个用户是否同意插件读取其个人数据或文件 | Plugin 用户授权/受管数据边界 |

管理员批准插件不等于用户授权个人数据；用户同意某个插件也不会获得管理后台权限。External Plugin 不能直接访问 CampusOS 核心数据库、内部 Service、JWT 私钥或 CampusOS 用户 Token。

## 4. 当前数据模型

### 4.1 角色与作用域

现有基础表继续生效：

```text
roles
user_roles(user_id, role_id, scope_type, scope_id)
permissions(role_id, resource, action)          # 兼容期旧模型
```

`user_roles` 目前只使用两种范围：

- `global`：全站范围。
- `category`：指定板块范围；版主只能在被分配的板块内执行受支持的治理操作。

基础角色 `member`、`guest` 不能通过普通分配/撤销接口变更。`moderator` 不能作为全局角色分配，必须通过版主管理选择至少一个板块。系统角色在权限矩阵中只读；自定义角色才可以组合和更新权限。

### 4.2 v10 权限目录

迁移新增：

```text
permission_definitions
role_permissions
route_operations
route_permission_bindings
authorization_audits
```

| 表 | 用途 |
| --- | --- |
| `permission_definitions` | 稳定权限 Code、所属领域、风险等级、允许的作用域类型与审计等级。 |
| `role_permissions` | 角色和权限定义的多对多关系；`deleted_at` 让历史绑定可软删除。 |
| `route_operations` | 服务实际注册的路由操作、所有者、HTTP 方法、路径、受众与 legacy alias。 |
| `route_permission_bindings` | 路由操作与权限目录的绑定。一个权限可保护多个路由。 |
| `authorization_audits` | 路由门禁、角色调整和资源作用域判断的结构化授权记录。 |

权限 Code 格式固定为：

```text
<domain>.<resource>.<action>
```

例如：

```text
community.thread.take_down
community.thread.review
community.thread.direct_restore
community.thread.restore
community.thread.purge
identity.role.create
identity.role.update_permissions
identity.role.read_audit
```

Code 是跨环境的稳定名称；数字 ID 只用于数据库关联。新代码不能用 URL、HTTP Method、数据库 ID、通配符或界面文案作为权限 Code。

## 5. 一次请求如何被允许或拒绝

```text
认证（JWT/Session）
  -> 路由权限门禁
  -> 需要范围时，仅确认调用者拥有某个候选范围
  -> 应用服务读取持久化资源
  -> 用资源真实 category/owner/state 做最终授权
  -> 状态机与业务不变量检查
  -> 执行并记录审计
```

### 5.1 路由操作和权限不是一回事

路由操作 ID 描述传输层动作；权限 Code 描述业务能力。例如：

| 路由 | Operation | Permission Code | 最终范围判断 |
| --- | --- | --- | --- |
| `POST /admin/threads/:id/take-down` | `http.community.thread.take_down` | `community.thread.take_down` | 服务端读取该帖的 `category_id` |
| `POST /admin/threads/:id/review/approve` | `http.community.thread.review_approve` | `community.thread.review` | 服务端读取该帖的 `category_id` |
| `POST /admin/threads/:id/review/reject` | `http.community.thread.review_reject` | `community.thread.review` | 服务端读取该帖的 `category_id` |
| `POST /admin/threads/:id/direct-restore` | `http.community.thread.direct_restore` | `community.thread.direct_restore` | 全局高风险权限 |
| `DELETE /admin/threads/:id/purge` | `http.community.thread.purge` | `community.thread.purge` | 全局高风险权限 |
| `POST /admin/roles` | `http.identity.role.create` | `identity.role.create` | 管理员自身权限上限 |
| `PUT /admin/roles/:id/permissions` | `http.identity.role.update_permissions` | `identity.role.update_permissions` | 管理员自身权限上限 |

普通历史路由仍可使用 `resource:action`，并通过 `permissioncode.FromLegacy` 得到兼容 Code。高风险新增路由必须显式声明 `PermissionCode(...).Operation(...)`。

### 5.2 为什么版主能先通过路由门禁

请求进入带 `Scoped("category")` 的路由时，中间件只能知道“该用户在某个板块拥有候选权限”。它不能信任请求参数来决定板块，因此会让候选版主进入应用服务。应用服务随后读取帖子实际所属板块，并执行 `CheckCodeScoped`。不匹配就拒绝。

这不是放宽权限：候选检查只避免全局门禁把合法版主提前挡住，最终决定仍由资源事实完成。

## 6. 管理员实际操作指南

### 6.1 查看权限目录、角色矩阵和授权记录

1. 打开 Admin 的“用户与权限 -> 角色与权限”。
2. 左侧选择角色，右侧查看按领域分组的权限 Code、风险等级、审计等级和允许范围。
3. 系统角色显示为只读。选择自定义角色后，可以勾选或取消权限。
4. 保存前界面会展示新增/移除的 Code 差异；高风险权限有明显标记。
5. 页面下方的“授权记录”可查看路由决定、角色权限变更、角色授予/撤销与版主范围更新。记录不保存 Token 或 Secret。

管理 API：

```text
GET  /api/v1/permissions
GET  /api/v1/roles/:id/permissions
GET  /api/v1/authorization-audits?limit=100
POST /api/v1/roles
PUT  /api/v1/roles/:id/permissions
```

### 6.2 创建和调整自定义角色

创建自定义角色需要 `identity.role.create`。更新自定义角色权限需要 `identity.role.update_permissions`。两种操作都遵循最小权限原则：操作者只能把自己当前实际拥有的 Code 授予新角色或目标角色，不能借角色编辑给自己制造更高权限。

当前版本支持：

- 创建自定义角色；
- 为自定义角色设置权限 Code；
- 查看系统角色，但不能直接改写它们的权限矩阵；
- 为用户分配/撤销可分配的全局角色；
- 通过版主管理为用户配置 `moderator` 的 category 作用域。

当前版本没有提供系统角色的自由编辑、任意 ABAC 条件表达式或跨租户策略引擎。新增这些能力必须先扩展权限目录、审计和负向测试，不能绕过 Service 直接写表。

### 6.3 给用户分配或撤销角色

管理 API 保留：

```text
GET    /api/v1/users/:id/roles
POST   /api/v1/users/:id/roles
DELETE /api/v1/users/:id/roles
```

服务端额外保护：

- 不允许给自己分配或撤销角色；
- HTTP Handler 必须从认证上下文取得真实操作者；上下文缺失时返回 `401`，不会降级调用受信任的内部接口；
- 分配需要 `identity.role.assign`，撤销需要 `identity.role.revoke`；
- 操作者必须拥有目标角色中每一个有效权限；
- 不能撤销最后一个有效的全局 `admin`。PostgreSQL 使用事务和按角色加锁完成“检查并撤销”，内存实现使用同一互斥区，两个管理员并发互相撤销时也至少保留一人；
- `member`、`guest` 是保护角色；`moderator` 必须走板块范围配置；
- 成功的分配和撤销写入 `authorization_audits`。

### 6.4 配置板块版主

在 Admin 的版主管理页面为用户选择板块。对应接口为：

```text
GET /api/v1/moderation/admin/moderators
GET /api/v1/moderation/admin/moderators/:id
PUT /api/v1/moderation/admin/moderators/:id
```

更新范围时，服务端验证用户、角色和每个板块 ID，并要求操作者拥有 `identity.role.assign` 以及 `moderator` 当前有效的所有权限。范围更新写入授权审计和 Moderation 审计。

版主治理能力受系统功能配置控制：`allow_pin`、`allow_lock`、`allow_delete_post`。这些配置关闭时，已分配的版主范围不会被删除，但对应动作被拒绝。内容下架、审核、直接恢复、回收站恢复和永久清除是独立的内容治理权限，不应默认假定所有版主都拥有。

## 7. 对开发者的接入规则

### 7.1 新增权限或高风险路由

1. 先定义稳定 Code，使用 `internal/core/identity/permissioncode` 的格式规则。
2. 通过追加 migration 新增 `permission_definitions` 和必要的角色绑定；不得改历史 migration。
3. 在路由中显式声明 `PermissionCode(code).Operation(operation)`；对资源范围操作再声明 `.Scoped("category")`。
4. 中间件只是第一道门禁。Service 必须从数据库读取资源并做 `CheckCodeScoped`、所有者、状态和不变量检查。
5. 通过 `AuthorizationRepository` 记录授权与高风险业务审计；不要从业务模块直接依赖 Identity 的 PostgreSQL Repository。
6. 增加正向、拒绝、跨板块、越权授权、操作者上下文缺失、最后管理员并发撤销和兼容回退测试。

示意代码：

```go
admin.
    PermissionCode("community.thread.take_down").
    Scoped("category").
    Operation("http.community.thread.take_down").
    POST("/threads/:id/take-down", handler)

// Service 内：先查 thread，再用 thread.CategoryID 做最终检查。
allowed, err := permissionService.CheckCodeScoped(
    ctx, actorID, "community.thread.take_down", "category", threadCategoryID,
)
```

不要把请求体中的 `category_id` 传给最终授权函数，也不要只因为前端隐藏了按钮就省略服务端检查。

### 7.2 External Plugin 的边界

External Plugin 不获得 `AppContext`，不能注册 Core Module，也不能导入 CampusOS `internal/*`。它只能通过公开 Host API、Extension Gateway、MCP 或公开 HTTP API 访问被授权能力。插件 manifest 权限、用户数据 Grant 和管理员 RBAC 是三套独立合同。

## 8. 审计、兼容和恢复

授权记录至少包含操作者、权限 Code、操作 ID、结果、原因、请求 ID/IP（可用时）、作用域与资源摘要。它不记录 Session、Access/Refresh Token、JWT 私钥、Webhook Secret 或第三方 Token 明文。

兼容期内：

- 旧 `permissions` 仍保留；目录读取不可用时，`CheckCode` 会保守回退到可映射的 `resource:action`，未知 Code 不会被放宽。
- `runtime: builtin`、旧路由 ID 和旧 URL 的其他兼容规则不因权限迁移被删除。
- `000025` 的 down migration 会删除 v10 权限目录和授权审计表，因此只可在可恢复的开发/演练环境使用。生产回退优先采用前向修复；执行前先运行 `make backup` 并验证恢复演练。

当前审计写入采用可用的 Authorization Repository；请求门禁和角色/范围变更有记录路径，但业务事务与跨表审计不是同一个原子提交单元。高风险操作的严格事务性需要在后续版本单独设计，不能把“尽力记录”当成不可丢失的合规保证。

## 9. 常见问题

**为什么给 user1 分配版主时没有选择板块？**  
`moderator` 不能走普通全局角色分配。请在版主管理中选择板块；普通接口会返回“版主角色必须通过版主配置选择至少一个板块”。

**为什么版主能打开下架请求，但最终仍被拒绝？**  
路由层只确认其拥有某个 category 的候选权限。帖子属于另一个板块、动作配置被关闭或帖子状态不允许转换时，Service 会拒绝。

**为什么不能编辑 admin 或 moderator 的权限矩阵？**  
系统角色是平台不变量的一部分，当前 UI 故意只读。用自定义角色组合额外权限；对系统角色的变更必须走受审计的迁移/功能配置流程。

**权限页加载失败怎么办？**  
先检查 `make migrate-status` 是否包含 `000025`，再检查当前管理员是否拥有 `role:read`、`identity.role.read_audit` 等所需权限。不要通过直接写数据库临时绕过。
