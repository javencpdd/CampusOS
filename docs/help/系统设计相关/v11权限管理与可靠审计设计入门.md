# CampusOS v0.11 权限管理与可靠审计设计入门

> 文档状态：v0.11 运行时已实施并通过 v0.11.0 验收。
>
> 当前可用行为：v0.10 权限模型继续有效；v0.11 已为高风险命令增加事务、Outbox、可靠
> 命令审计、Worker 和后台可靠任务入口。
>
> 适用读者：平台管理员、版主、后端/前端开发者、External Plugin 开发者。
>
> 对应计划：[CampusOS v0.11 可靠命令与持久事件实施计划书](../../项目计划v0.11/00-v0.11版本计划书.md)。

## 1. 先看结论

v0.11 没有推翻现有权限系统。管理员仍然配置角色和板块范围，服务端仍然使用稳定
Permission Code 判断权限。v0.11 已解决的是另一个问题：

> 权限判断通过以后，如果业务写入成功，但审计或事件写入失败，系统怎样保证不
> 留下一半成功、一半失败的状态？

v0.10 已经能回答“谁能做什么”；v0.11 进一步保证“做了什么、业务结果、审计和后续
事件能够一起可靠提交，并在故障后恢复”。

## 2. 四个概念不要混淆

| 概念 | 回答的问题 | CampusOS 示例 |
| --- | --- | --- |
| 认证 Authentication | 你是谁 | JWT/Session 解析出 `user1` |
| 授权 Authorization | 你能不能做 | `user1` 是否有 `community.thread.take_down` |
| 业务规则 Invariant | 当前状态允许不允许做 | 已删除帖子不能再次下架 |
| 审计 Audit | 谁在何时做了什么，结果如何 | 记录 actor、命令、资源、结果和 request ID |

前端隐藏按钮只改善操作体验，不等于授权。客户端传来的 `actor_id`、`category_id`、
角色名和资源状态也不能作为最终事实；后端必须从认证上下文和数据库读取。

## 3. 当前 v0.10 权限模型

### 3.1 一次授权判断

```text
已登录用户
  -> 路由 Operation
  -> Permission Code 候选检查
  -> 应用服务读取真实资源
  -> global/category scope 最终检查
  -> 业务状态机检查
  -> 执行或拒绝
  -> 记录授权审计
```

例如 user1 要下架帖子 823：

```text
actor          = user1
operation      = http.community.thread.take_down
permission     = community.thread.take_down
resource       = thread:823
resource scope = 后端查询得到的 category:编程交流
actor scope    = 管理员分配给 user1 的 category:编程交流
```

只有权限和范围同时匹配，帖子状态也允许下架，操作才会继续。

### 3.2 当前数据结构

```text
roles
user_roles                 # 用户、角色和 global/category 范围
permissions                # 兼容期 resource:action
permission_definitions     # 稳定 Permission Code
role_permissions           # 角色拥有的 Permission Code
route_operations           # 路由 Operation 和 Owner
route_permission_bindings  # Operation 到 Permission Code
authorization_audits       # 允许、拒绝和错误记录
```

当前稳定 Permission Code 使用：

```text
<domain>.<resource>.<action>
```

例如：

```text
identity.role.assign
identity.role.update_permissions
community.thread.take_down
community.thread.review
platform.feature.lifecycle
```

数字 ID 可以随数据库环境不同，Permission Code 不能随页面文案或 URL 改名。

### 3.3 三套权限仍然独立

| 体系 | 管理对象 | 不能替代什么 |
| --- | --- | --- |
| 管理员 RBAC | 用户、角色、板块、后台操作 | 不能自动授权插件读取个人数据 |
| Plugin Host 权限 | External Plugin 可调用的 Host API | 不能获得后台管理员权限 |
| 用户 Grant | 用户是否同意插件访问自己的受管数据/文件 | 不能让插件直连数据库 |

管理员安装插件不等于每个用户都同意数据访问。用户授权插件也不等于插件可以管理
角色、帖子或系统功能。

## 4. v0.11 为什么需要“可靠命令”

以“给 user1 分配角色”为例。这个动作至少包含：

1. 确认操作者已登录。
2. 确认操作者有 `identity.role.assign`。
3. 确认目标角色的权限没有超过操作者自己的权限。
4. 防止操作者给自己提权。
5. 写入 `user_roles`。
6. 写入 required audit。
7. 产生角色变化事件，供其他受控模块刷新状态。

如果第 5 步成功、第 6 步失败，角色已经生效，但审计中没有证据。v0.10 对部分操作
仍可能出现这种跨写入失败窗口。v0.11 的目标是让数据库内高风险命令满足：

```text
业务事实 + required audit + outbox event = 同一个数据库事务
```

任一部分失败，全部回滚。

## 5. v0.11 的三个稳定标识

### 5.1 Permission Code

描述“需要什么权限”。

```text
identity.role.assign
```

### 5.2 Operation Code

描述“从哪个入口调用”。同一个权限可以保护多个 HTTP、CLI 或内部入口。

```text
http.identity.role.assign
```

### 5.3 Command Code

描述“正在执行哪个业务写命令”，用于事务、幂等、审计和事件关联。

```text
identity.role.assign
```

Code 文本有时相同，但含义和所属目录不同。实现中不能因为名字相同就省略任何一层。

## 6. v0.11 已实现执行流程

### 6.1 允许的高风险写操作

```text
请求进入
  -> 认证
  -> 路由权限候选检查
  -> 创建 command_id / transaction_id
  -> 开启 TxKernel
       -> 重新读取操作者有效权限
       -> 读取资源真实 owner/category/state
       -> 锁定需要保护的数据行或版本
       -> 写业务事实
       -> 写 required audit
       -> 写 Outbox Event
  -> COMMIT
  -> Worker 在提交后处理事件
```

权限必须在高风险事务内复核。否则管理员刚撤销某人权限，而旧请求仍可能在检查后
继续写入，这就是典型的 TOCTOU（检查与使用之间发生变化）问题。

### 6.2 被拒绝的操作

```text
权限不足
  -> 返回 401/403
  -> 记录 deny audit
  -> 审计写入失败则告警
```

deny audit 失败也必须继续拒绝请求，绝不能因为审计系统故障而放行。

### 6.3 外部副作用

数据库事务不能把 HTTP、NATS、文件替换或插件进程一起“锁进事务”。正确顺序是：

```text
事务内写 Outbox -> 提交 -> Worker 处理 -> 保存结果/重试/dead-letter
```

Webhook 采用至少一次投递。接收方必须按事件 ID 幂等，CampusOS 不承诺 HTTP
exactly-once。

## 7. 风险等级与审计规则

当前可靠命令按以下风险分级：

| 等级 | 示例 | 默认要求 |
| --- | --- | --- |
| low | 读取普通目录 | 标准授权记录，可采样业务日志 |
| medium | 修改普通配置 | 完整 actor/resource/result 审计 |
| high | 分配角色、下架内容 | 事务内 required audit 和幂等键 |
| critical | 最后管理员、永久清除、dead-letter 重放 | required audit、二次确认、严格权限和并发保护 |

审计允许保存：

- request ID、transaction ID、command ID、event ID；
- actor、Permission/Operation/Command Code；
- scope、资源类型/ID、结果、受控原因；
- 必要的 before/after 摘要和时间。

审计禁止保存：

- 密码和密码哈希；
- Session、Access Token、Refresh Token；
- JWT 私钥、API key、Webhook Secret；
- 邮箱验证码、第三方 Token；
- 未经过字段 allowlist 的整个请求体或 Outbox payload。

## 8. 管理员现在如何配置权限

以下步骤是当前 v0.10 已实现行为，不需要等待 v0.11。

### 8.1 查看角色和权限

1. 登录 `http://localhost:3001`。
2. 打开“用户与权限 -> 角色与权限”。
3. 选择角色，查看按领域分组的 Permission Code、风险等级和允许范围。
4. 系统角色只读；自定义角色可以在操作者自身权限上限内调整。
5. 页面下方查看授权记录。

### 8.2 创建自定义角色

1. 点击“创建自定义角色”。
2. 填写稳定、可理解的角色名称和说明。
3. 只勾选完成职责所需的最小权限。
4. 保存前核对新增和移除的 Code，特别关注高风险权限。
5. 保存后重新打开角色，确认后端返回的权限矩阵与预期一致。

管理员不能把自己没有的权限转授给新角色，不能通过角色编辑给自己提权。

### 8.3 分配普通角色

1. 打开“用户管理”。
2. 选择目标用户和可分配角色。
3. 确认不是给自己修改角色。
4. 提交后检查用户角色和授权记录。

系统会保护 `member`、`guest` 等基础角色，并防止撤销最后一个有效全局管理员。

### 8.4 分配版主

`moderator` 不能当作全局角色直接分配。

1. 打开“版主管理”，或在用户角色窗口选择版主。
2. 明确选择一个或多个板块。
3. 保存并核对显示的板块范围。
4. 使用普通用户端进入对应帖子，验证置顶、锁定等受配置允许的动作。
5. 再进入未分配板块，确认动作被拒绝。

版主只能管理分配给自己的板块。客户端提交的板块 ID 不会替代帖子在数据库中的
真实板块。

## 9. 管理端如何使用可靠任务

管理员可打开 `http://localhost:3001/reliability`。页面已展示：

- Outbox 待处理数量和最老任务时间；
- Worker 健康、lease 和冲突；
- dead-letter 与失败原因摘要；
- Webhook 失败和重试状态；
- 可靠命令与 request/event 关联（不显示 payload、details 或 Secret）；
- 保留策略 dry-run 和执行历史。

“查看”和“重放”使用不同权限。拥有 `platform.reliability.read` 不代表可以重放
外部副作用；重放还需要 `platform.reliability.replay`，必须二次确认、带
`Idempotency-Key` 并留下 required command audit。保留预演需要
`platform.retention.preview`，v0.11 只保存 dry-run，不物理删除数据。

具体的逐步操作见 [v0.11 可靠任务与 Webhook 安全运维](./v11可靠任务与Webhook安全运维.md)。

## 10. 开发者新增权限和命令的步骤

### 第一步：确定 Owner 和业务事实

先明确哪个模块拥有被修改的表和规则。Identity 的角色命令不能由 Plugin 模块直接
写 `user_roles`；插件只能调用公开 Host/Gateway/API。

### 第二步：定义三个 Code

```text
permission_code = community.thread.take_down
operation_code  = http.community.thread.take_down
command_code    = community.thread.take_down
```

Code 必须稳定、可迁移、可生成文档，不能用中文按钮、数据库数字 ID 或完整 URL。

### 第三步：评估风险和原子边界

回答：

- 修改哪些业务表？
- 哪些审计不可丢？
- 产生哪些事件？
- 幂等键是什么？
- 重复执行会发生什么？
- 是纯数据库事务，还是需要文件/进程补偿？
- 哪些字段属于敏感信息？

### 第四步：在服务端读取真实资源

路由中声明 Permission/Operation，应用服务再读取资源真实板块、所有者和状态。
不能信任请求体中的 scope，也不能仅依赖前端隐藏按钮。

### 第五步：通过 TxKernel 写入

纯数据库高风险命令在同一事务中写：

```text
business state
required audit
outbox event
```

Service 不直接 `pool.Begin`，不接收 `pgx.Tx`。External Plugin 不得访问 TxKernel。

### 第六步：设计幂等

Idempotency Key 至少绑定 actor、command、目标资源和请求语义。相同 key、相同请求
应返回已有结果；相同 key、不同 payload 应返回稳定冲突，不能执行第二次。

### 第七步：补齐测试

至少包括：

- 允许、拒绝、未登录；
- 跨板块、越权转授、自助提权；
- 业务失败、审计失败、Outbox 失败全部回滚；
- 并发重复请求和版本冲突；
- 最后管理员并发撤销；
- Worker 崩溃接管和重复消费；
- 审计/日志中不存在 Secret。

## 11. External Plugin 的权限边界

External Plugin 只能通过公开 Host API、Extension Gateway、MCP 或 HTTP 合同访问
被授权能力。它不能：

- 导入 CampusOS `internal/*`；
- 获取 PostgreSQL 连接、TxKernel 或内部 Repository；
- 获取 JWT 私钥、CampusOS 用户 Token 或宿主完整文件系统；
- 伪造 actor、scope、command ID 或 required audit；
- 直接写 Outbox 表来冒充 Core 事件。

插件发起受支持的高风险动作时，由 Host 验证插件身份、用户 Grant 和管理员 RBAC，
再由 Core Command Handler 创建真实命令和审计。

## 13. 故障时应该看到什么

| 故障 | 预期行为 |
| --- | --- |
| 账号写入失败 | 用户、审计和事件全部回滚 |
| required audit 写入失败 | 高风险业务回滚并返回错误 |
| Outbox 写入失败 | 业务和审计一起回滚 |
| 提交后进程退出 | Outbox 保留，重启后 Worker 继续处理 |
| Worker 处理中崩溃 | lease 到期后其他 Worker 接管 |
| 重复投递 | 内部消费者和 Webhook 接收方用幂等键去重 |
| deny audit 写入失败 | 请求仍被拒绝；若拒绝发生在一个回滚事务内，回滚后独立保留 deny/error evidence |
| Webhook 指向私网 | 投递被拒绝，不因“测试”按钮绕过生产策略 |

## 14. 发布与回滚

1. v0.10 migration `000001` 至 `000026` 冻结。
2. v0.11 新能力以 Adapter 和开关逐步接管，旧 API 先保留。
3. 回退 producer 前先停止新命令进入，排空或冻结 Outbox。
4. 回退 Worker 前释放 lease 或等待过期，不能把处理中任务直接改成功。
5. 数据库生产回退优先 forward-fix；down 只在有备份的隔离环境演练。
6. 旧权限回退、旧 Built-in API 和旧 Manifest 只有在兼容遥测证明无调用后才可另行
   提出删除计划。

## 16. 常见问题

**v0.11 会改变我现在给用户分配角色的方法吗？**

基本操作不变。主要变化是后端提交更可靠，Admin 已提供 command/request/event 关联和
可靠任务入口。

**为什么不直接换成一个通用权限框架？**

当前 Permission Code、作用域和资源事实判断已经覆盖现阶段需求。v0.11 的真实缺口是
事务、审计和事件一致性，替换权限引擎会扩大风险但不能自动解决这些问题。

**审计失败时是不是所有请求都不能用？**

只读和低风险操作按 A1 的审计策略处理；required audit 失败时，高风险写操作必须
fail closed。权限拒绝永远保持拒绝。

**为什么 Webhook 不能保证 exactly-once？**

HTTP 请求可能已被对方处理，但 CampusOS 在保存成功状态前崩溃。系统只能可靠重试，
接收方必须用事件 ID 幂等。

**版主以后会自动管理子板块吗？**

不会在 v0.11 改变。多级板块和 `self/subtree` 作用域属于 v0.12，实施前必须单独评审，
默认不能静默扩大现有版主权限。
