# v1.2 细粒度授权与资源策略设计

> 状态：设计方案，尚未实现；当前配置仍以 [权限配置入门](../../../docs-site/guide/permission-configuration.md) 和 [v0.11 权限与审计](v0.11权限管理与可靠审计设计入门.md)为准。
> 日期：2026-09-25
> 对应计划：[v1.2 优化计划](../../项目计划书v1/项目计划v1.2/00-v1.2版本优化计划书.md)

## 1. 为什么不是再加几个角色

WeKnora 本机快照 `e2433b12` 的 `internal/router/rbac.go` 将空间角色、资源创建者、子资源归属和平台级配置分开选守卫；`internal/middleware/kb_access.go` 再核对知识库共享；`internal/middleware/api_key_gate.go` 对机器凭据采取显式路由白名单。这个分层值得借鉴，但 CampusOS 目前没有多租户工作区，不应照搬 `Owner > Admin > Contributor > Viewer` 的单轴等级，也不能复制其 RBAC 关闭时记录而放行的过渡行为。

CampusOS 已有 `permission_definitions`、`role_permissions`、`user_roles(global/category)`、独立 `identity_admin_accounts`、稳定 Operation Code、版主管理和插件三层授权。当前 `PermissionService.CheckCode[Scoped]` 主要回答“用户是否拥有权限码和版块范围”；帖子治理由服务端额外读取真实版块。目标是把这套资源复核变成跨模块一致的公开 Policy Port，同时保留各业务模块对自己资源状态的最终解释权。

## 2. 基本名词与边界

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| Principal | 调用身份及可信凭据上下文；匿名访问另有显式策略 | 用户、后台账号、Integration Principal、插件实例、Worker；Session/Key 是凭据而非角色 |
| Capability | 稳定 Permission Code；只表达动作 | `community.thread.take_down`、`knowledge.collection.query` |
| Role | 可管理的能力组合，不是所有资源的万能通行证 | member、category moderator、后台自定义角色 |
| Scope | 角色或凭据获准的范围 | global、精确 category ID、允许的知识库 ID |
| Resource Fact | 业务模块提供的当前事实 | 帖子作者、真实版块、是否私密/下架/删除 |
| Condition | 风险和生命周期约束 | 功能启用、后台准入、MFA、用户明确同意 |

**授权决策 = 可信身份上下文 ∩ 已声明动作 ∩ 可用授予/所有者规则 ∩ 实际资源范围 ∩ 当前资源状态 ∩ 调用通道约束。** 同一授权层的有效角色授予可合并，不同安全层的上限取交集；显式禁止优先。 各层缺失、查库失败或不认识的权限码都拒绝；不能因“管理员”称谓跳过私有资源保护。授权和业务状态是两道门：有 `take_down` 能力也不能下架一个已经永久清除的帖子。

## 3. 身份、角色和委托不能混淆

| 主体 | 获取权限的方式 | 严格边界 |
| --- | --- | --- |
| 访客 | 公开内容的显式匿名读策略 | 不拥有 member 角色；不读私密/未审核内容 |
| 用户 | Session + 隐式 member + 显式角色 | 自己资源的操作仍按具体动作和状态判定 |
| 后台管理员 | 独立后台准入 + MFA 策略 + Permission Code | 管治理动作，不默认读取个人文档或课表原文 |
| 拥有版主角色的用户 | `category` 作用域角色 + Core 动作上限 | 只作用于明确分配的版块；默认不继承子版块 |
| Integration Principal | 命名凭据 + 端点/动作/知识库白名单 | 不复用用户 JWT、后台 Session 或插件 Host Token |
| External Plugin | 包声明 ∩ Admin Grant ∩ User Consent（需要时）∩ 当前安装/运行状态 | 只走 Host API；不能使用后台权限或读核心表 |
| Worker | 固定服务身份 + 单一任务类型 + 事件来源 | 不继承触发者的长期用户 Token；副作用前复核授权事实 |

版主是用户的角色绑定，作者是用户与资源的关系，都不是新的 Principal 类型。插件代用户调用同时记录 `actor=插件实例` 与 `effective_subject=被委托用户`；用户必须来自宿主验证的短期委托，不能信任插件传来的 `user_id`。委托记录限制动作、资源范围、有效期、audience 与认证强度，审计同时保留两方。

不设置“跨全部个人文件的超级管理员”。确需合规介入时另设计有期限、双人确认、原因和 required audit 的 break-glass 流程；v1.2 不提供这个默认入口。

## 4. 资源策略矩阵

下表是目标策略的**默认值**，不是现有 API 行为；业务模块可进一步收紧，不能自行放宽 Core 安全下限。

| 资源/动作 | 自己 | 同版块版主 | 后台治理员 | 其他用户/机器 |
| --- | --- | --- | --- | --- |
| 已发布公开帖子读 | 允许 | 允许 | 允许 | 访客可读；机器仍需端点白名单 |
| 草稿/私密帖子读、编辑 | 作者按状态和动作允许 | 不允许 | 不默认允许 | 不允许 |
| 帖子置顶、锁定、下架 | 作者无治理权 | 对**实际所属**版块按各动作授予 | 有相应治理权限且后台准入 | 默认拒绝 |
| 回复删除 | 作者只能执行本人内容的自删规则 | 对父帖子实际版块按动作授予 | 有相应治理权限 | 默认拒绝 |
| 个人文档/课表原文读 | 仅本人，经功能策略 | 不允许 | 不默认允许 | 插件需专门 Host API + 本人同意；Integration Key 默认拒绝 |
| 知识库检索 | 集合可见且来源当前可见 | 不因版主身份扩张 | 仅已授予集合/来源，私有资料不默认可读 | 机器需端点和集合范围，返回前逐来源复核 |
| 角色/插件授予、模型密钥配置 | 无 | 无 | 专门高风险 Permission Code + MFA/审计 | 一般 Integration Key 与插件拒绝 |

`owner` 不是通用越权开关：作者能编辑自己未下架的帖子，不代表能审核自己帖子、管理私有文件的系统副本或发布他人知识库。子资源必须追溯父资源：回复 → 帖子 → 版块；知识片段 → 来源 → 集合，再核对原业务资源。

## 5. 决策接口与执行时机

建议在 Identity/Authorization Core 暴露小 Port；G1 冻结合同，V12-02a 实现。以下是语义示意，不是当前可调用 SDK：

```go
type ResourceRef struct { Kind, ID string }
type ResourceFacts struct {
    Ref ResourceRef
    OwnerID string
    CategoryID string
    State string
    Revision int64
}
type Decision struct { Allowed bool; ReasonCode string; PolicyRevision int64 }
type Authorizer interface {
    CheckRouteCandidate(ctx context.Context, principal Principal, operation, code string) (Decision, error)
    Evaluate(ctx context.Context, principal Principal, code string, facts ResourceFacts) (Decision, error)
}
```

资源拥有模块的应用服务先读取真实资源/父级关系，再将最小只读事实传给 `Evaluate`。核心只依赖自己的策略与授予 Port，不反向导入 Community/Knowledge/Storage、不自行查找任意业务 Fact Port；由调用方负责明确装配。跨模块事实查询也只走公开 Port，不导入 PostgreSQL Repository。事实 DTO 使用明确类型与必填规则，不能让插件或浏览器直接构造可信事实，也不使用任意 `map[string]any` 扩展成万能规则引擎。

`CheckRouteCandidate` 只做预筛选，不能成为写操作或私密详情的最终放行。高风险命令在事务内通过资源版本、授权版本及锁策略复核，再与 required audit、Outbox 一起提交；审计不含私密正文。撤销与写入按提交顺序生效，不能承诺撤销能逆转已提交操作。

列表、批量、分页、计数、导出与详情采用同一策略。数据库查询先限制可见候选，返回敏感摘要前复核；不得由前端过滤越权结果。批量请求逐项鉴权，明确部分成功或全事务语义，不能以首项授权替代整批检查。

不存在的资源与无权查看的私有资源可统一对外返回 `404`，但内部审计区分原因；普通能力不足返回 `403`，未登录为 `401`，授权依赖故障为失败关闭的 `503`。任何错误都不回落到 legacy 角色或“默认管理员”。

## 6. 数据与后台配置

继续以 `permission_definitions` 为动作目录，以 `role_permissions` 和 `user_roles` 为角色授予事实；必须验证 `allowed_scope_types`、风险级别和角色可授予上限。`user_roles` 仍只承载 `global/category`，不要把每份知识库分享都塞入角色表。v1.2 个人知识库只供本人使用，不实现协作分享表。未来新增合作范围时，可用独立 `knowledge_collection_grants` 表表示主体、集合、动作及有效期；它只能**缩小**来源原始权限，不能把私密帖子或他人文档变公开。Integration Principal 的凭据和 Scope 独立建模，原始 Token 不入库。

能力目录由拥有资源的模块注册，条目至少包含稳定 code、所属模块、可用 Principal/audience、资源类型、允许 Scope、风险、审计要求和是否可委托。外部插件只能申请已公开的 Host 能力，不能自定义一个同名 code 获得核心权限；自有配置动作也必须处于包命名空间并经宿主校验。新增动作默认不授予旧角色，禁止用持久化 `*` 在升级后自动扩权；UI 从目录生成可选项，不能独立维护另一份权限含义。

例如：`community.thread.take_down` 的后台/版主策略与 `knowledge.collection.query` 的用户读策略分开；模型 Profile 管理、Secret 写入和知识资料模型出站分别授权，不能用一个“AI 管理员”布尔值包办。Scope 的类型、ID 和包含关系由目录明确规定，未知类型或不存在的板块拒绝；以后加入组织/群组范围时新增类型与测试，不依赖角色名称字符串。

管理端目标流程：先选择人和角色，预览实际 Permission Code；再选明确版块或集合范围，显示可操作资源样例和高风险提示；保存前验证独立的“授予权”，并检查新授予的动作、Scope、期限和认证要求均不超出操作者可委托上限；有执行权不等于有转授权权，category A 不能扩成 global、期限不能变长、MFA 不能降级；保存后显示有效权限/来源、策略版本和最近拒绝原因。权限预览只是排错工具，不替代后端每次实时判定。系统角色安全核心只读；自定义角色可调但不能绕过后台准入和 MFA。

## 7. 迁移、检查和验收

用户允许清理当前测试数据，v1.2 可在隔离 development/test 库重新规划授权表，但不允许因重建取消审计或正反权限测试。V12-02a 建立纯 Policy Core 和表驱动正反测试；V12-02b 将业务服务接到唯一的新授权路径。无需保留旧新策略双路径、历史角色兜底或旧数据库兼容；未接入目标合同的路由必须关闭并报错，不能静默放行。历史测试可重写为目标合同测试，但不得丢失跨用户/跨版块的安全断言。任何新增路由必须声明 Principal 类型、Operation、Permission Code、Scope Resolver 和审计级别，启动/CI 对照 Gin 路由表检查缺项。机器凭据只允许显式列出的入口，缺失规则默认拒绝。

验收至少覆盖：跨用户私密帖子和个人文档、版主跨版块/子版块、帖子移动版块后旧版主、知识来源下架后旧索引、授权撤销并发写、角色扩权拦截、缺省路由、插件和机器凭据冒充后台、MFA 失效、策略仓储故障、审计脱敏；PostgreSQL 与 Memory/本地测试 Profile 的判定一致。评审每条拒绝路径时同时检查 API、服务、列表、文件代理、MCP 和模型上下文，不能只测按钮是否隐藏。

扩展接口、依赖方向与授权并发决策见 [v1.2 架构审查](../../项目计划书v1/项目计划v1.2/01-v1.2架构审查与扩展合同决策.md)。

具体知识库与外接模型设计见 [v1.2 校园知识库与 RAG 接入](v1.2校园知识库与RAG接入设计.md)。
