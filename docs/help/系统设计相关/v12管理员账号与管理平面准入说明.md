# v12 管理员账号与管理平面准入说明

> 更新日期：2026-07-22
> 适用迁移：`000038_v12_admin_accounts`；v13 操作扩展见 `000039_v13_admin_admission_operations`
> 适用入口：Admin `http://localhost:3001`、API `POST /api/v1/auth/admin/login`

> v13 已提供管理员准入的独立列表、暂停、恢复、Session 撤销、版本冲突保护和本地恢复。日常操作请改读
> [v13 管理员准入管理与本地恢复](./v13管理员准入管理与本地恢复.md)；本文保留 v12 的数据模型与迁移背景。

## 1. 为什么不能只给用户加一个 admin 角色

早期 CampusOS 把管理员表示为普通 `users` 记录加一条全局 `admin` 角色。这样可以复用登录、会话和
个人资料，但“能否进入管理后台”和“进入后能做什么”混在了同一个角色判断里。角色数据误配时，管理
平面的边界也会跟着变得模糊。

v12 将它拆成三层：

```text
users / accounts       身份主体与登录凭据：你是谁、如何验证密码
identity_admin_accounts 管理平面准入：该身份现在能否进入 Admin
roles / permissions     操作授权：进入以后可以执行哪些动作
```

一个请求进入管理端 API 时必须同时满足：有效 Session、`identity_admin_accounts.status=active`、
对应 Permission Code。缺少任意一项都会被后端拒绝，前端隐藏按钮不能替代这些检查。

## 2. 为什么不复制管理员密码

独立管理员表不复制密码哈希。`identity_admin_accounts.credential_account_id` 通过外键引用 Identity Core
已有的 `accounts` 凭据，原因是：

- 同一密码哈希不应在两个表中形成双写和轮换漂移。
- 密码验证、Session 轮换、`auth_version` 和账号状态仍由一套 Identity Core 规则负责。
- 管理员准入可以立即撤销，而不需要删除用户资料或改写凭据。

因此，“独立账号表”指独立的管理平面账号生命周期和准入事实，不表示另建一套容易失控的密码、JWT 或
Session 系统。未来若需要强制 MFA 或独立凭据域，应在新的安全方案中增量设计，不能直接复制
`accounts.credential`。

## 3. 表结构和状态

关键字段：

| 字段 | 作用 |
| --- | --- |
| `user_id` | 指向唯一 CampusOS 用户主体。 |
| `credential_account_id` | 指向该管理员使用的有效邮箱凭据。 |
| `status` | `active`、`suspended` 或 `revoked`。 |
| `activation_source` | 记录由迁移、角色分配或 Bootstrap 创建。 |
| `last_authenticated_at` | 最近一次通过管理员专用登录入口的时间。 |
| `version` | 管理员账号状态版本，必须大于等于 1。 |

状态含义：

| 状态 | 能否登录 Admin | 角色数据 |
| --- | --- | --- |
| `active` | 可以；仍需密码、Session 和具体权限。 | 保留全局 admin 角色。 |
| `suspended` | 不可以。 | 可以保留，用于独立暂停管理平面访问。 |
| `revoked` | 不可以。 | 全局 admin 角色已撤销或不存在。 |

## 4. 角色分配和撤销如何同步

`000038` 会把升级前所有有效的全局 admin 角色回填到独立表。之后：

1. 管理员通过现有角色管理服务给用户分配全局 `admin`。
2. 服务和数据库触发器共同确保 `identity_admin_accounts` 存在并处于可用状态。
3. 撤销全局 `admin` 时，对应管理员账号变成 `revoked`，但用户资料、普通登录凭据和历史审计不会删除。
4. 数据库仍保护“不能撤销最后一个有效系统管理员”的既有规则。
5. `suspended` 不会因普通角色记录刷新而被静默改回 `active`。

数据库触发器是防止脚本或旧代码只改 `user_roles` 而造成漂移的最后一道完整性保护；正常操作仍应调用
Admin 角色管理 API，不应直接修改表。

## 5. 登录和请求流程

Admin 前端使用专用入口：

```http
POST /api/v1/auth/admin/login
```

后端按以下顺序处理：

1. 使用 `accounts` 验证规范化邮箱、密码、验证状态和用户状态。
2. 检查 `identity_admin_accounts` 是否为 `active`，并确认关联用户及凭据仍有效。
3. 记录最近管理员认证时间。
4. 由 Session Service 签发短期 Access Token 和 HttpOnly Refresh Cookie。
5. 每次管理端 API 请求再次检查 Session、管理员准入和具体权限。

普通用户入口 `POST /api/v1/auth/login` 为兼容保持不变。即使用户持有有效普通 Session，没有活动管理员
账号也不能访问管理平面 API。

版主不是管理员。少量声明了 `category` scope 的治理路由允许版主通过明确的板块权限进入，但这不会创建
管理员账号，也不会允许其登录 Admin 或访问插件、用户、系统配置等全局管理能力。

## 6. 运维查询

只查看非敏感状态：

```sql
SELECT
  aa.user_id,
  u.username,
  aa.status,
  aa.activation_source,
  aa.last_authenticated_at,
  aa.version
FROM identity_admin_accounts aa
JOIN users u ON u.id = aa.user_id
ORDER BY aa.updated_at DESC;
```

检查角色和准入是否一致：

```bash
make database-check
```

该检查会拒绝管理员账号孤立、凭据所有者不一致、非法状态、活动准入缺少全局 admin 角色等问题。不要查询
或导出 `accounts.credential`、Refresh Token 摘要、JWT Secret 和 SMTP Secret。

## 7. 迁移、回滚和故障处理

升级前执行：

```bash
make migrate-up
make migrate-status
make identity-admin-account-check
```

迁移预检要求每个现有全局管理员恰好有一个有效邮箱凭据。遇到冲突时迁移会在建表前中止并列出用户 ID，
不会猜测应绑定哪个账号。

生产事故优先 forward-fix。`000038.down.sql` 只用于隔离 up/down/up 演练；它会删除管理平面准入表和同步
触发器，但不会删除 `users`、`accounts`、`user_roles` 或管理员业务数据。回退旧二进制前必须进入维护
窗口，并确认旧版本不依赖新准入合同。
