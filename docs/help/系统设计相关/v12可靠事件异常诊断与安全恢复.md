# v12 可靠事件异常诊断与安全恢复

> 适用范围：消费者已经成功，但 Outbox 仍长期 processing、attempts 越界或最终化失败。
> 原则：只读排查、保留 Receipt、单事件受控 Replay、继续执行 lease generation fencing。

## 1. 先判断现象

管理后台打开 `http://localhost:3001/reliability`，筛选 processing、retry 和 dead。以下组合
通常表示消费者副作用已经完成，但主事件最终化失败：

- 同一事件每隔一个 lease 周期重新出现；
- attempts 已达到或超过 max attempts；
- 消费者 Attempt 为 `skipped`，说明 Consumer Receipt 已存在；
- `system:outbox-finalize` 为 `failed`，或消费者均完成但没有成功 finalize 记录。

`attempts` 是 Claim 次数。不要按消费者数量解释，也不要因为 `skipped` 删除 Receipt。

## 2. 安全只读查询

以下查询不读取 payload、headers、idempotency key、邮箱、验证码、Token 或 Secret。只在经过
授权的只读会话中执行，并按事件 ID 缩小范围。

查询异常事件：

```sql
SELECT id, event_type, status, attempts, max_attempts,
       available_at, lease_owner, lease_until, lease_generation,
       dead_lettered_at, updated_at
FROM platform_outbox
WHERE attempts > max_attempts
   OR (status = 'processing' AND lease_until < NOW())
   OR (attempts >= max_attempts AND status IN ('pending', 'retry'))
ORDER BY updated_at DESC
LIMIT 100;
```

查询一个事件的 Consumer Receipt：

```sql
SELECT consumer_name, event_id, attempt, delivered_at
FROM outbox_consumer_receipts
WHERE event_id = '<event-id>'
ORDER BY delivered_at, consumer_name;
```

查询最近 Attempt。`has_error` 只说明存在错误证据，不输出可能来自旧版本的原始错误文本：

```sql
SELECT id, event_id, consumer_name, worker_id, lease_generation,
       attempt, status, (error_message IS NOT NULL) AS has_error,
       started_at, finished_at
FROM platform_outbox_attempts
WHERE event_id = '<event-id>'
ORDER BY started_at DESC
LIMIT 50;
```

查询 Worker 心跳：

```sql
SELECT worker_id, last_heartbeat_at, updated_at
FROM platform_worker_leases
ORDER BY last_heartbeat_at DESC
LIMIT 50;
```

优先使用管理端 API，因为它会对 `last_error` 和 Attempt `error` 做 allowlist 脱敏。不要把上述
查询扩展为 `SELECT *`，也不要把数据库输出粘贴到公开工单。

## 3. 部署修复后的收敛步骤

1. 先完成 migration `000037_v12_outbox_worker_convergence`，再启动新 Worker。
2. 确认 Worker 有新心跳，日志中的 `component=reliability_worker` 不包含业务 payload 或凭据。
3. 等待至少一个 Poll 周期。attempts 已耗尽的 pending、retry 和租约已过期 processing 会自动
   进入 dead；历史 `103/8` 仍保留 103，不会再次增加。
4. attempts 尚未耗尽的过期 processing 可以被重新领取。已有 Receipt 的消费者会 skipped，
   `system:outbox-finalize=succeeded` 后事件进入 published。
5. 如果 finalize 仍为 failed，核对 operation、lease owner/generation、数据库健康和迁移状态。
   租约丢失是 fencing 生效，不应覆盖当前合法 Worker。

## 4. 单事件受控 Replay

只有事件已经是 dead、根因已修复、Receipt 与消费者集合已经人工核对后，才能重放：

1. 使用管理后台“可靠任务 -> 事件队列 -> 失败队列”。
2. 打开消费尝试，确认已成功消费者、失败阶段和最新 lease generation。
3. 确认外部接收方按 CampusOS Event ID 幂等处理。
4. 点击该事件的重放按钮并完成确认。系统通过权限、命令审计和 `Idempotency-Key` 执行。
5. 刷新详情。已有 Receipt 的消费者应为 skipped，finalize 应为 succeeded，事件应为 published。

Replay 只重置主事件 attempts 和可用时间，不删除 Consumer Receipt。这正是避免验证码邮件、
Webhook 或 EventBus 副作用重复执行的恢复机制。

## 5. 禁止操作

- 不要删除 `outbox_consumer_receipts`。
- 不要把 processing 直接更新为 published。
- 不要批量把事件改成 pending 或无限重置 attempts。
- 不要提高 MaxAttempts 来掩盖状态转换错误。
- 不要绕过 lease owner 和 lease generation 条件。
- 不要自动按 Receipt 数量推断“所有消费者完成”，运行时消费者集合可能已经变化。
- 不要批量删除 Outbox、Attempt、审计或 Worker 证据。
