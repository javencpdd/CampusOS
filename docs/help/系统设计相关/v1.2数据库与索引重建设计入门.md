> 对应计划：[CampusOS v1.2 版本优化计划](../../项目计划书v1/项目计划v1.2/00-v1.2版本优化计划书.md)

## 1. 现在的数据库是什么

CampusOS 当前使用 PostgreSQL 16+。可执行 migration 依次是 `000001_v1_1_schema_baseline`、`000002_v1_1_ui_only_plugin_runtime`、`000003_v1_1_trusted_market_sources`。`storage_objects` 管实际字节事实，`user_assets` 管用户资产身份，文章附件绑定另有表；`platform_outbox` 与消费者回执支持事务提交后的可靠工作。当前 `api_keys` 表仍有原始 `key` 字段，主要属于旧插件凭据模型，不能直接当作安全的外部 MCP 密钥库。

本页解释**计划中的改造**。今天开发或排查数据库仍须看 [当前数据库管理指南](数据库管理指南.md)与 [migration 规则](../../../migrations/README.md)；不能把下方目标表名当成已经存在的表。

## 2. 一份资料的几个不同事实

| 事实 | 所有者 | 例子 | 删除/更新规则 |
| --- | --- | --- | --- |
| 原始文件字节 | User Storage | 官方 PDF 或附件对应的 `storage_objects` | 有引用时不能擅自清除；走配额和对象生命周期 |
| 来源与发布状态 | 自有官方资料由 Knowledge Feature 管；帖子由 Community、私有文档由 Personal Documents 管 | “学生证补办指南”的 `published`、帖子的当前可见性或文件的 owner | 原业务模块是检索授权的权威；撤回立即不可读 |
| 内容修订 | Knowledge Feature | 第 3 版指南的摘要和校验和 | 乐观并发控制，保留可追溯历史 |
| 检索块/索引 | Knowledge Feature 的派生投影 | 片段、词项、向量引用、索引代次 | 可以重建；失败不可冒充 `ready` |
| 搜索权限 | Identity + 来源拥有者 | 哪个 Principal 能读哪个来源 | 不复制到索引作为最终许可 |

**字节、业务引用、索引和权限不能混作一张万能表。** 例如从检索索引删除一条资料，不等于从用户空间删除文件；资料下架也不意味着立即硬删除历史修订。

## 3. v1.2 目标表和约束

| 归属 | 候选表/现有表 | 必需约束 |
| --- | --- | --- |
| Identity | `integration_principals`、`integration_credentials` | 凭据只存摘要/前缀；唯一主体、明确作用域、到期与撤销；不得关联万能 Admin Session |
| Plugin Platform | `plugin_packages`、`plugin_versions`、`plugin_user_installations`、`plugin_operations`、`plugin_admin_grants`、`plugin_user_consents` | 包摘要不可变；安装状态与能力授权分离；操作唯一代次/幂等键；授权按插件版本和能力收口 |
| Knowledge Feature | `knowledge_collections`、`knowledge_source_selections`、`knowledge_collection_sources` | 集合 owner、订阅规则、显式成员与选择代次分开；首版私有集合仅本人，协作 grants 表留后续 |
| Knowledge Feature | `knowledge_sources`、`knowledge_revisions`、`knowledge_chunks`、`knowledge_index_generations` | 来源/修订唯一；索引代次绑定来源版本；状态有 CHECK；受限 owner/版块引用有 FK 或应用级存在校验 |
| Knowledge Feature | `knowledge_index_tasks`、`knowledge_backfill_runs` | 持久任务去重键、来源修订/选择代次、租约、重试和分页检查点；撤回不可被旧任务恢复 |
| Security / AI | 受管 Secret 仓储、`ai_provider_profiles` | Secret 与普通配置分开；Profile 保存引用、用途/端点/策略修订，无普通查询可回显的原始密钥 |
| Core/Platform 复用 | `storage_objects`、`platform_outbox`、`outbox_consumer_receipts` | 不建第二套字节库或后台队列；副作用可重试、可对账 |

G0 冻结所有权与不变量，G1 确定公开合同；具体字段、索引和 FK 在所属阶段编写 migration 前确定。V12-01a 的 P0 Schema 与仓储同步切换，知识结构在 09a/09b、模型 Profile 在 14a 前向追加。建议检索维度至少能按集合、来源状态、owner/版块、修订、索引代次过滤；这些列只作候选过滤，返回前仍向原模块复核权限。私有文档的片段/向量/临时解析物有独立清理和备份边界；不要在没有 `EXPLAIN ANALYZE` 和黄金问题集时预建大量 JSONB/向量索引。对于中文，先比较参数化词法、`pg_trgm` 或受限外部 Provider 的真实效果。

### 索引状态示例

```text
管理员发布修订 4
  -> 来源 current_revision = 4，发布状态 = published
  -> 同事务写 Outbox(index, source_id, revision=4)
  -> 常驻消费者幂等保存持久索引任务，再完成 Outbox 回执
  -> Worker 领取任务，检查当前选择与来源修订，索引代次变为 processing
  -> 成功：ready(revision=4)
  -> 失败：failed(revision=4, reason_code)，可重试
```

当修订 5 已发布而修订 4 的 Worker 后到，代次检查阻止旧结果覆盖新索引。下架或删除首先更新权威状态，搜索立即排除该来源；索引清除可以稍后由可靠事件完成。用户看到“发布成功”与“索引完成”两个独立状态。这个方法借鉴 WeKnora 的修订/索引状态设计，同时复用 CampusOS 已有 Outbox；它不是永久事件日志。事件生成 ID 不代表提交顺序，不能以最大 ID 回放保证无遗漏。历史分页回填、周期权威对账与删除清理要独立验收，覆盖事件过期、晚提交和长期停机。

## 4. 为什么允许重建，又为什么只能受控执行

项目所有者确认**当前数据库和持久化目录均为测试数据**，因此 v1.2 可以不提供旧测试数据的兼容迁移。计划允许受控的 P0 clean baseline 和测试文件清理，但编写这份文档本身不会删除任何数据。

实施顺序：

1. G0 先确认 Git 基线、`DB_NAME`、`CAMPUSOS_ENV`、Compose Project、对象目录和插件包目录，列出将被清理的对象；把任何非测试实例排除。
2. 在隔离库证明新基线 `up/down/up`、checksum、权限参考数据、ER/Admin 架构和启动可重复；将旧 `000001`～`000003` 的历史留在 Git。
3. 停止应用写入后，使用带环境限制和数据库名确认的开发 reset 流程，重建**明确指定的**测试库/测试目录。生产或无法判定的路径必须拒绝。
4. 同步重建 API/SDK 合同和测试夹具；验证登录、帖子、附件、插件和知识检索的正反路径，冻结 P0 基线校验和；知识/模型功能随所属阶段追加迁移和回归。
5. 之后每次结构变化恢复前向追加 migration；不要每开发一个功能就重写 `000001`。

“测试数据可删”不包括随意删除自动化测试源码、运行时安全校验或审计。若发现任何需要保留的数据，停止重建并另行设计导出与前向迁移。

## 5. 开发者日常操作与验收

当前环境可用 `./scripts/migrate.sh status`、`check`；Windows 使用 `.\scripts\migrate.ps1 status`、`check`。v1.2 新基线尚不存在，**现在不要执行 reset 试图获得 v1.2 表**。

实施阶段应逐项验证：

- 只有被标记为 development/test 的隔离库能 reset；误指生产库、空数据库名或不匹配确认值必须失败。
- 迁移无默认管理员账号、密码、原始 API key、插件 Secret 或用户文档内容。
- 目标表归属、FK、唯一性、状态 CHECK、必要索引和敏感字段脱敏符合 Schema ADR。
- 同一索引事件重复投递、Worker 崩溃/恢复、晚提交、保留期过后回填、旧代次后到及来源撤回均不会泄露旧片段。
- 词法片段、向量、临时解析物、任务载荷与备份同样视为私人派生数据；保护不足必须禁用私人索引，不能改用词法便视为安全。
- `make database-check`、`python migrations/tools/generate_er.py --check`、架构同步检查、API 合同、隔离库恢复以及 Web/Admin 构建均留下实际执行记录。

权限判定和管理员配置路径见 [v1.2 权限与知识访问入门](v1.2权限与知识访问设计入门.md)；集合、帖子和个人文档的来源/撤权规则见 [校园知识库与 RAG 接入](v1.2校园知识库与RAG接入设计.md)。
