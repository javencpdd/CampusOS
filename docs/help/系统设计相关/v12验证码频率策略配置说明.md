# v12 验证码频率策略配置说明

> 适用范围：注册、密码找回、邮箱绑定和管理员辅助恢复产生的邮件验证码请求  
> 实现归属：`core.identity`，始终启用，不是插件或可停用功能模块

## 1. 默认规则

CampusOS 同时检查邮箱和来源 IP。默认值如下：

| 对象 | 连续统计窗口 | 最多发送 |
| --- | ---: | ---: |
| 同一个规范化邮箱 | 10 分钟 | 5 次 |
| 同一个来源 IP | 60 分钟 | 10 次 |

两个条件都通过才会创建新的 Challenge。计数使用带部署 Secret 的 HMAC 摘要，限流表不会保存原始
邮箱或 IP。窗口是滑动窗口：例如 10:03 到 10:13 之间已发送 5 次，第 6 次会被拒绝，而不是等固定
整点窗口重置。

邮箱限制对所有验证码用途合并计算。这样攻击者不能通过在“注册、找回密码、绑定邮箱”之间切换来
绕过同一收件箱的发送上限。

## 2. 在管理端修改

1. 使用拥有策略权限的管理员登录 `http://localhost:3001`。
2. 进入“用户与权限 -> 验证码策略”。
3. 修改邮箱或 IP 的“统计窗口（分钟）”和“最多发送（次）”。
4. 点击“应用策略”。保存成功后，新请求立即使用新值，不需要重启 API、Web 或 Admin。

例如要改为“每个邮箱 5 分钟最多 2 条”，填写：

```text
邮箱统计窗口（分钟） = 5
邮箱最多发送（次）   = 2
```

IP 规则仍会同时生效。若 IP 上限比邮箱上限更早耗尽，请求仍会被拒绝。

## 3. 不可关闭的安全边界

管理端只能在以下范围内修改：

| 字段 | 最小值 | 最大值 |
| --- | ---: | ---: |
| 邮箱/IP 窗口 | 1 分钟 | 1440 分钟 |
| 邮箱次数 | 1 | 100 |
| IP 次数 | 1 | 1000 |

次数不能设置为 `0`，也没有“关闭限流”开关。数据库 CHECK、Service 校验和管理端输入范围会共同拒绝
越界值。修改使用 `expected_version` 做并发检查；两个管理员同时编辑时，旧版本保存会返回冲突并重新
加载当前策略。

## 4. 权限与审计

| Permission Code | 作用 |
| --- | --- |
| `identity.challenge_policy.read` | 读取当前策略。 |
| `identity.challenge_policy.update` | 修改策略，属于高风险 required audit 操作。 |

更新成功会写入 `identity.challenge_policy.updated.v1` 可靠事件和命令审计。事件只包含策略 ID 和版本，
不包含邮箱、IP、验证码、Ticket 或 SMTP Secret。默认只有内置 `admin` 角色拥有这两个权限。

## 5. 密码找回为何不再手填请求编号

普通“邮箱找回”仍使用 `challenge_id` 作为 API 内部关联字段，但发送验证码后由浏览器页面内存自动
保存。用户只输入邮箱、六位验证码和新密码。刷新或关闭页面会丢失内存状态，此时重新发送即可。

“辅助恢复”由管理员在另一工作流发起，用户设备没有创建 Challenge 时的页面状态，因此仍需填写
邮件中的请求编号。两种流程共用安全的 Challenge/Ticket 协议，但交互不同。

## 6. 部署和排障

首次升级必须应用 `000036_v12_identity_challenge_policy`。可执行：

```bash
make migrate-up
make migrate-status
./scripts/test-v12-identity-challenge-policy-migration.sh
```

修改限流不会让 Fake Provider 发送真实邮件。用户收不到验证码时，还要检查 `.env` 中的 SMTP 配置、
`core.email-delivery` 健康状态和可靠任务；参见[邮件投递与 SMTP 部署说明](v12邮件投递与SMTP部署说明.md)。

生产环境不应直接更新 `identity_challenge_policies` 或删除 `identity_challenge_rate_limits`。误配时从
管理端恢复合理值，并依据命令审计和 trace ID 排查；数据库 down 只用于隔离演练。
