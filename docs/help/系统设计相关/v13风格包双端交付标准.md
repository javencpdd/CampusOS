# v0.13 风格包双端交付标准

> 适用版本：v0.13-dev
> 适用对象：用户前台系统主题、首页风格包、个人主页风格包

## 1. 这份标准解决什么问题

过去的风格包只要能被读取，就可能被选择。这样会出现一个实际问题：电脑端看起来正常，手机端的文字、背景图或按钮却重叠、裁切或看不清。

v0.13 将风格包当作 Resource Package 管理，并把“桌面端和移动端都能使用”变成后端和 CLI 会检查的合同。风格包不是 External Plugin：它不能启动进程、访问数据库、读取登录 Token 或调用任意系统接口。

目录归属保持明确：

```text
data/resources/themes/<name>/              # target: web，管理员提供，用户选择
data/resources/homepage-packs/<name>/      # target: homepage，管理员统一应用
data/resources/space-style-packs/<name>/   # target: personal-space，主页所有者应用
data/plugins/                               # 只放 External Plugin 实现，不放风格包
data/plugin_data/                           # 只放 External Plugin 运行数据，不放内置风格包
```

## 2. 新包必须包含的交付声明

历史包仍能读取和导出，但会得到 `legacy-readonly` 状态，不能再次选择、上传应用或发布。新包和修改后的包必须在 `style.yaml` 中声明：

```yaml
schema_version: page-style-pack.v1
target: personal-space
name: my-space-style
version: 0.1.0
delivery_contract: campusos.appearance-delivery/v1
viewport_support:
  desktop: true
  mobile: true
  mobile_breakpoint: 720px
preview_image: preview.png # 旧客户端缩略图，可保留
preview_images:
  desktop: preview-desktop.png
  mobile: preview-mobile.png
entry: templates/page.html
styles:
  - styles/theme.css
```

标准目录示例：

```text
my-space-style/
  style.yaml
  resource.json
  README.md
  preview.png
  preview-desktop.png
  preview-mobile.png
  templates/
    page.html
    card.html
  styles/
    theme.css
  assets/
    cover.webp
  config.schema.json
```

`preview-desktop.png` 和 `preview-mobile.png` 是两张面向不同设备的真实预览，不是只改文件名的占位图片。它们用于选择界面和发布审查；源模板和 CSS 不要求复制两份。

## 3. 必须通过的静态检查

系统会在目录扫描、ZIP 上传、源码目录选择和 `resource adopt` 中使用同一套严格检查。`resource inspect` 会复验资源清单和基础安全规则，并返回 `delivery_status`；为发布前硬失败可加 `--strict`。它至少检查：

1. `desktop`、`mobile` 都为 `true`，断点是受限的像素值。
2. CSS 包含对应的响应式宽度媒体查询。
3. 两张预览都存在，且是包内允许的图片格式。
4. HTML、CSS、路径、资源声明、配置 schema 和目标根选择器安全。
5. 文字与页面/卡片背景的常规对比度至少为 `4.5:1`。
6. 有 `effect` 的包必须包含 `prefers-reduced-motion: reduce` 降级规则。
7. 可配置的文字色、背景色、遮罩、页边距和背景资源仍受 schema 值域与对比度校验约束。

失败结果会返回 `errors` 和安全的 `issues`。`issues` 只包含稳定规则代码、包内相对文件和端侧，例如 `appearance.preview_mobile_missing`；不会返回宿主机绝对路径。

常见状态：

| 状态 | 含义 | 可否应用 |
| --- | --- | --- |
| `valid` | 满足严格合同 | 可以 |
| `invalid` | 任一安全或双端硬门失败 | 不可以 |
| `legacy-readonly` | 旧包只满足兼容读取 | 不可以重新选择；可继续读取/导出 |

## 4. 开发与检查流程

1. 从当前页面导出示例 ZIP，或复制一个已有资源包目录。
2. 在本地修改模板、CSS、图片和 `config.schema.json`。
3. 在 1440 x 1000、390 x 844 和 768 x 1024 下检查内容、长文本、空状态和背景可读性。
4. 使用 CLI 生成或刷新资源清单：

```bash
GOCACHE=/tmp/campusos-go-cache go run ./cmd/campusosctl resource adopt \
  data/resources/space-style-packs/my-space-style \
  --type space-style-pack \
  --version 0.1.0 \
  --compatibility '>=0.13.0 <0.14.0' \
  --source campusos-builtin \
  --force
```

5. 用同一 CLI 再检查一次：

```bash
GOCACHE=/tmp/campusos-go-cache go run ./cmd/campusosctl resource inspect \
  data/resources/space-style-packs/my-space-style --strict
make appearance-delivery-check
```

`scripts/migrate-v10-module-plugin-layout.sh` 遇到安全但缺少双端合同的旧包时，会使用内部的
`resource adopt-legacy` 路径写入可校验的资源清单。该包仍是 `legacy-readonly`，不能在前端重新选择、
应用或发布；补齐本章的合同、预览和响应式规则后，再执行普通的 `resource adopt --force` 才能变为
`valid`。不要把 `adopt-legacy` 当成新包导入或发布的绕过方式。

6. 在用户端使用 Desktop/Mobile 分段预览确认后，再应用。上传 ZIP 时必须先点击“筛查”；后端即使收到直接应用请求也会再次严格验证。

## 5. 选择和回滚边界

- 系统主题由管理员放入 `data/resources/themes/`，用户在 `/appearance` 只选择通过检查的主题。选择保存于该用户本机，不影响其他用户，也不影响 Admin。
- 个人主页风格包由主页所有者在个人主页设置中应用。任何访问者打开 `/u/:username` 时都看到该主页所有者保存的风格。
- 首页包由管理员统一应用，影响用户前台首页，不影响 Admin。
- 个人主页和首页都在应用前保存快照。严格检查失败不会覆盖当前风格；已应用的旧风格不会因升级被删除。

## 6. 动效、背景图和可读性

动效只能使用 `sandbox-worker.v1` 和 CampusStyleSDK 的声明式只读能力。它不能读 DOM、Cookie、JWT、浏览器存储或任意网络；动效层不得拦截点击。

背景图不能成为文字的唯一背景。推荐做法是为正文提供不透明或高透明度的内容表面，或者通过可配置遮罩提高对比度。修改颜色配置后，前端会即时提示低对比度，后端也会拒绝不合法配置。

## 7. 发布前浏览器矩阵

`web/tests/style-pack-responsive.mjs` 会遍历内置系统主题和个人主页包，在以下尺寸记录截图与失败诊断：

```text
desktop  1440 x 1000
mobile    390 x 844
bridge    768 x 1024
```

脚本检查水平溢出和可见控件越界。失败时会在 `STYLE_PACK_SCREENSHOT_DIR` 保存端侧、包 ID、页面状态、页面 URL、HTTP 失败响应和截图。发布检查通过 `scripts/smoke/browser-smoke.sh` 调用该矩阵；它需要已启动的受控 API、Web 和测试账号环境。
