## 1. 这项能力解决什么问题

CampusOS 的 MFA 是 Identity Core 的内置安全能力，不是插件，也不能被资源包、外部插件或 Agent 调用。它在密码之外要求认证器生成的六位 TOTP 验证码，用于：

- 管理员登录后的第二步验证；
- 管理员已登录后访问管理 API 时的近期 Step-up；
- 用户主动保护自己的账号；
- 普通 User 丢失设备时使用本域一次性恢复码恢复控制权。

普通 User 的 TOTP/一次性恢复码与独立 Admin 的 TOTP、MFA 票据和会话分别存储和验证。User 的恢复码、邮件找回、辅助恢复 Case、全局角色或同号 ID 都不能替代独立 Admin 证明。当前独立 Admin 的公网恢复票据消费 HTTP 尚未开放，不能从恢复票据仓储推断远程恢复入口。邮箱验证码不作为第二因子；这里不提供 Passkey、短信或 OAuth 登录。

## 2. 部署前配置

MFA 密钥只存在部署环境变量中。它不能写入前端、插件 Manifest、资源包、数据库普通字段、日志、备份说明或配置导出包。

```dotenv
# 当前用于写入新 TOTP Secret 的密钥 ID。
AUTH_MFA_ACTIVE_KEY_ID=v1

# key-id:secret 形式，可保留旧密钥以读取历史记录。
AUTH_MFA_ENCRYPTION_KEYS=v1:<new-random-secret>,v0:<previous-random-secret>

# 认证器中显示的签发方名称。
AUTH_MFA_ISSUER=CampusOS

# 本机紧急恢复所需；生产环境也要求设置。
AUTH_BOOTSTRAP_ADMIN_SECRET=<deployment-secret>
```

要求：

1. 每个密钥使用独立、高熵、至少 16 字符的部署 Secret；生产环境不能使用 `.env.example` 中的开发值。
2. `AUTH_MFA_ACTIVE_KEY_ID` 必须在 `AUTH_MFA_ENCRYPTION_KEYS` 中存在。
3. 先部署新旧两把密钥并切换 active ID，再逐步让用户重新写入 MFA Secret；确认没有旧记录后才能删除旧密钥。
4. 未配置可用密钥时，未强制 MFA 的普通登录保持可用；已有 MFA 因子或强制管理员策略会安全失败，而不是降级绕过。

## 3. 普通 User 如何启用

在 PC 或手机端登录后，打开“账号安全 -> 多因素认证”。

1. 点击“启用认证器”，输入当前密码。
2. 在认证器 App 中扫描二维码；不能扫码时复制页面给出的手工密钥。
3. 输入认证器生成的六位验证码并确认。
4. 页面只显示一次恢复码。离线保存它们，不要截图上传、发送到聊天群、写进浏览器笔记或交给他人。
5. 下次登录时，密码验证成功后再输入认证器验证码。

关闭 MFA 需要同时证明当前密码和一个 TOTP 验证码或未使用的恢复码。关闭成功会撤销该账号的全部 Session，必须重新登录。

## 4. 独立 Admin 的注册与近期 Step-up

管理端的本人 MFA 入口使用当前独立 Admin 会话和 Admin CSRF。对应接口为：

```text
POST /api/v1/admin/identity/mfa/enroll
POST /api/v1/admin/identity/mfa/confirm
POST /api/v1/admin/identity/mfa/step-up
```

注册需在认证器保存当前本域的 TOTP Secret，并用有效 TOTP 确认。确认步骤不直接提升会话认证强度，后续应使用新的 TOTP 时间步完成 Step-up；具体管理 API 继续按当前角色、资源权限与 MFA 事实复核。

`/mfa-policy` 的 `off`、`enrollment_grace`、`required` 和覆盖率保留的是旧 User 关联管理员策略兼容能力，不表示独立 Admin 的 MFA 已注册或可以绕过本域门禁。User 登录取得的会话也不能调用独立 Admin 本人或管理接口。

## 5. 丢失设备时的恢复

普通 User 可使用自己的未用恢复码，随后轮换恢复码并检查登录设备。该 User 流程不恢复独立 Admin。

独立 Admin 丢失 TOTP 时，在可信服务器的真实交互式 TTY 中执行：

```bash
campusosctl identity reset-mfa --account-id adm.example --reason "lost independent Admin authenticator"
```

`adm.example` 仅为示例，应替换为受控创建回执或运维记录中的实际不透明 Admin `account_id`。旧 `--user-id` 参数已退役，不能使用旧准入兼容页里的 User ID。

命令要求：

1. 目标是现有、活跃、有有效本域密码凭据且存在待确认或已启用 TOTP 因子的独立 Admin。
2. `--reason` 非空、单行、不超过 500 字符，不包含敏感证明原文。
3. 部署配置中已设置 `AUTH_BOOTSTRAP_ADMIN_SECRET`。
4. 逐字确认 `RESET-MFA adm.example`，再隐藏输入该部署 Secret；不能用参数、管道、CI 或配置存在本身替代操作者终端证明。
5. 当前实例数据库及必需事务审计可用。

成功后关闭目标 Admin 的 TOTP，消费所有旧 Admin MFA/恢复票据，撤销其全部会话及刷新凭据；已有 Admin 角色绑定保持，不新授权限。账号、凭据和 TOTP 当前事实会在事务前后复核，相关 CAS、票据消费、会话撤销、必需审计和 Outbox 任一步失败都会整体回滚。不会清除或修改同号 User 的 TOTP、恢复码、凭据、角色或会话，也不承诺触发 User 域安全邮件。

重新登录后应立即注册新的认证器。已 `revoked` 的 Admin 不能被本机恢复重新激活；`suspended` 的 Admin 应先按[管理员准入与本机恢复](v0.13管理员准入管理与本地恢复.md)执行带 `--account-id` 的 `restore-admin-admission`，该操作也不授予角色。只有固定系统 Admin 邮箱可使用 `identity reset-password` 恢复密码，并需 Bootstrap 证明及两次隐藏输入新密码。

## 6. 受控验证

任何会启用、关闭或恢复 MFA 的演练都只针对独占测试实例与可变更账号。验证独立 Admin 时必须使用本域账号、会话、CSRF 和实际 TOTP；旧 User/关联准入的浏览器脚本或恢复码不能作为本域验收证据。演练失败应保留原始日志和清理记录，再按对应身份域处理，不能通过直接改安全表或删除审计绕过恢复。

## 7. 安全与排错

- 手机和服务器时间应自动同步。系统只容忍有限时间窗口，重复使用同一 30 秒时间步会被拒绝。
- 普通 User 的 MFA Ticket 在密码验证后产生，短期、单用途、只保存摘要。Admin 的 MFA/恢复票据是独立仓储；当前没有开放 Admin 公网恢复票据消费 HTTP。两域票据都不能写入 URL、Local Storage 或日志。
- TOTP Secret 只以带 key ID 的加密信封保存。普通 User 恢复码只保存不可逆摘要和使用状态，不能据此假设独立 Admin 存在同样的恢复码入口。
- `identity.mfa.ticket_invalid`、`identity.mfa.factor_invalid`、`identity.mfa.replay` 和 `identity.mfa.step_up_required` 都是稳定机器错误码。不要把用户输入的验证码写入工单或日志。
- `identity.mfa.unavailable` 表示部署侧密钥、策略或依赖无法安全评估，应先检查环境配置和服务健康，而不是关闭权限检查。

当前限制：没有 Passkey、硬件密钥、跨节点密钥托管或自动化身份验证器迁移。密钥轮换和本机恢复须由具备服务器管理权限的运维人员执行。
