# CampusOS 插件三层授权与 Manifest v3 开发指南

> 适用版本：v1.0-dev  
> 更新时间：2026-09-11

## 1. 先理解授权模型

外部插件不需要用户手工生成永久 API Key，也不得接触用户 JWT、数据库连接或宿主目录。插件安装后由宿主签发仅供本地运行时使用的短期运行令牌；涉及个人数据的前台调用使用当前登录会话，后台调用只能使用用户主动签发、最长 24 小时且可随时撤销的 Delegation。

一次敏感操作只有同时满足以下条件才允许：

```text
Manifest v3 声明 ∩ 当前版本管理员 Grant ∩ 用户 Consent（需要时）
∩ self/system Scope ∩ 插件正在运行 ∩ 有效 Delegation（后台任务时）
```

任一条件缺失都会返回稳定 `DENY_*` 原因码；未知方法和未知 Capability 默认拒绝。撤销不依赖正向缓存，事务成功后的下一次调用即按新状态判定。

## 2. 管理员和用户怎么操作

- 管理员进入“插件管理”，对外部插件点击“授权”，查看当前版本声明、用途、风险、现有决策和最近判定记录；填写原因后逐项授予、拒绝或撤销。
- 用户进入“插件中心”，点击“精细授权”；只有管理员已授予且 Catalog 标记 `consent_required=true` 的能力才可开启。
- 用户可在“精细授权 → 短期后台委托”生成一次显示的 15 分钟 Delegation；API/SDK 允许设置更短时长且上限 24 小时。令牌只交给对应插件运行时，撤销、过期、版本变化或插件停用都会使其失效。
- 管理员在插件“授权 → 系统 Secret”管理实例级凭据；用户在“精细授权 → 我的插件 Secret”管理个人凭据。保存同名项会轮换旧值，列表只返回 `••••••••`，数据库保存 AES-256-GCM 密文；插件只能通过已授权的 Host API 在运行时解析。

部署端必须配置 `CAMPUSOS_PLUGIN_SECRET_KEY`（32 字节，使用 64 位十六进制或 Base64）及 `CAMPUSOS_PLUGIN_SECRET_KEY_VERSION`。Docker 初始化脚本会为正式部署生成随机值；开发 Compose 提供仅限本机测试的默认值。

## 3. Manifest v3 最小示例

```yaml
name: my-process-plugin
api_version: campusos.plugin/v3
host_api_version: v3
type: external
version: 1.0.0
runtime: process
scope: user
capability_declarations:
  - code: schedule.self.read
    required: true
    purpose: 读取当前用户课表并生成提醒
    scope: self
config:
  command: ./plugin
  process_contract: campusos.process/v1
  health_url: http://127.0.0.1:39090/health
  extension_url: http://127.0.0.1:39090/events
storage: { type: none }
```

Capability 风险、数据分类、是否需要 Consent 和审计级别由平台 Catalog 决定，插件不能降低。v3 禁止通配权限。同一插件的同一语义版本必须保持包摘要和权限指纹不变；修改代码、用途或范围后必须提升版本。启动扫描发现同版本内容冲突时，CampusOS 会在插件启动前将其隔离并继续启动 API，日志会明确提示提升版本，防止旧授权被新内容继承。

## 4. 稳定合同

- Capability：`docs/api/plugin-capabilities-v1.json`，执行 `make contracts-check` 检查漂移。
- Event：`campusos.event/v1`，包含 `spec_version/id/time/trace_id/actor/data_schema/data`。
- Process：`campusos.process/v1`。健康端点必须只监听 loopback，校验宿主运行令牌，并回传 `X-CampusOS-Process-Contract: campusos.process/v1`。
- Host API：v3 通过方法到 Capability 的完整映射调用统一 `AuthorizationService`；`GetUser` 不再携带邮箱，联系信息改用 `GetUserContact` 和独立高风险能力。

## 5. 开发、诊断和一致性检查

```bash
go run ./cmd/campusosctl plugin init my-plugin --runtime process
go run ./cmd/campusosctl plugin doctor ./my-plugin
go run ./cmd/campusosctl plugin watch ./my-plugin
go run ./cmd/campusosctl plugin conformance ./my-plugin --json
```

`doctor` 检查 Manifest、Capability Catalog、配置 Schema 和进程合同；`watch` 在文件变化后重跑 test/build/verify；`conformance` 形成测试、构建、包安全和合同一致性证据。仓库的三个 v1 参考插件位于 `examples/plugins/v1-*`。

常见拒绝处理：

| 原因码 | 处理方式 |
| --- | --- |
| `DENY_CAPABILITY_NOT_DECLARED` | 修改 Manifest、提升版本并重新导入 |
| `DENY_ADMIN_GRANT_MISSING` | 管理员在插件管理中逐项审查 |
| `DENY_USER_CONSENT_MISSING` | 用户确认当前用途后开启；用途变化必须重新确认 |
| `DENY_VERSION_MISMATCH` | 停止使用旧版本令牌或旧 Delegation |
| `DENY_SCOPE_MISMATCH` | 只请求宿主注入的当前用户或声明的系统范围 |
| `DENY_PLUGIN_INACTIVE` | 检查停用、隔离、进程握手和健康状态 |
| `DENY_DELEGATION_INVALID` | 重新签发最小能力、短时 Delegation |

若 Docker 曾显示 `dependency api failed to start`，先执行
`docker logs --tail 200 campusos-dev-api-1`。看到 “plugin version ... is immutable” 表示开发目录中的插件代码或声明已改变但版本号未变；提升其 Manifest 版本并重新安装。新版本会隔离问题插件而不会拖垮 API；修复后再次执行 `docker-dev.* up` 启动等待中的 Web/Admin 容器。

## 6. 数据和卸载边界

受管记录、受管文件和搜索均由宿主确定 owner；Manifest v3 请求会进入统一授权服务。停用、隐藏或卸载插件不会自动删除个人数据，用户仍可通过保留数据通道导出或显式删除。普通配置禁止写入 Secret 字段，防止明文进入配置、日志或导出。
