> 当前统一版本：`v1.1.0-dev`（`v1.1-dev` 主线）；开发容器与默认部署镜像使用同一版本号，运行配置仍有区别

本指南收拢本地开发、Docker 开发、任务归属、常用验证和贡献脚本。命令默认在仓库根目录执行。
第一次接触项目时，先走 [开发者递进入门路线](../开发者递进入门路线.md)，不要把带旧版本号的历史快照
当作当前教程。

当前源码、开发容器中运行的应用及单主机部署模板统一采用 `v1.1.0-dev`。这只是同一代码阶段的标识：
开发容器会热重载源码，部署容器使用构建后的固定镜像；`CAMPUSOS_ENV=production` 还要求正式密钥、
真实邮件投递等安全配置。相同版本号不等于已完成正式发布验收，具体差异见
[Docker 单主机部署与迁移](../../../docs-site/deployment/docker.md#版本号与运行方式)。

## 1. 第一次运行

无论使用哪种模式，都先在宿主机克隆源码并在宿主 IDE 中编辑：

```bash
git clone https://github.com/javencpdd/CampusOS.git
cd CampusOS
```

开发 Compose 把这份工作区绑定挂载进容器；它不会自行 clone 或向 GitHub 同步。容器内 shell 用于诊断，
不能作为源码的唯一保存位置。

### 1.1 只安装 Git 和 Docker

Windows 10/11 使用 Docker Desktop 的 WSL2/Linux Containers，现代 Linux 使用 Docker Engine + Compose v2：

```bash
./scripts/docker-dev.sh setup
# 编辑 deploy/docker/.env.dev.local
./scripts/docker-dev.sh setup --start
```

PowerShell：

```powershell
.\scripts\docker-dev.ps1 setup
# 编辑 deploy/docker/.env.dev.local
.\scripts\docker-dev.ps1 setup -Start
```

开发栈包含 PostgreSQL、Redis、NATS、API、Web、Admin 和 Docs 七个服务。源码以宿主 UID/GID 运行，
不会用 root 所有权污染 Vite/VitePress 缓存；`node_modules` 和 Go cache 使用独立命名卷。
详细命令和 Windows 文件共享设置见 [Docker 跨平台开发环境](../../../docs-site/deployment/docker-development.md)。

首次 `setup` 只创建被 Git 忽略的本地配置，不启动容器。填写完成后再次运行，脚本会检查：

- 根 `.env` 已存在时，按白名单迁移数据库账号、JWT/认证和邮件字段，但不复制旧 DSN/端口或打印值；
- 所有宿主端口都在有效范围内且互不冲突；
- 开发栈保持 `127.0.0.1` 绑定，避免固定开发凭据暴露到局域网；
- `EMAIL_PROVIDER` 是 `fake` 或 `smtp`；
- SMTP host、from、认证字段配对和 STARTTLS 开关有效；
- Docker Compose 能正确解析最终配置。

`fake` 不会发送或打印验证码。需要完整验证注册、找回密码或邮箱绑定时必须配置真实/隔离测试 SMTP；
SMTP 密码只写入 `deploy/docker/.env.dev.local`，不能提交到 Git。后续日常启动使用
`./scripts/docker-dev.sh up` 或 `.\scripts\docker-dev.ps1 up`。

容器运行期间，Go 源码、`go.mod`/`go.sum`、新 migration 和 module YAML 由 API 轮询构建并自动切换；
Web/Admin/Docs 源码由 Vite/VitePress HMR 自动加载，普通源码修改不需要重启。

修改 `.env.dev.local` 或 Compose 运行参数后执行 `docker-dev.* up`；它使用已有开发镜像并带
`--no-build` 启动/更新容器，不会因普通源码改动访问 Docker Hub。修改前端 package/lockfile、
`Dockerfile.dev`、Compose 构建项或 `deploy/docker/dev-*.sh` 后才执行 `docker-dev.* rebuild`。
两条命令都无需先 `down`；`build` 只构建不启动，`docker restart` 不会重读环境文件。

### 1.1.1 `/api/v1/health` 的检查间隔

开发栈中每隔 5 秒出现一次 `GET /api/v1/health`，通常是 **API 容器的 Docker healthcheck**，不是 3001
管理端页面在轮询，也不是 `CAMPUSOS_DEV_POLL_INTERVAL`。该接口只报告 API 进程存活状态；容器会在内部请求
`127.0.0.1:8080/api/v1/health`，以决定 API 是否健康。

如需调整开发环境的检查频率，在被 Git 忽略的 `deploy/docker/.env.dev.local` 增加或修改：

```dotenv
# Compose duration，例如 5s、30s、1m；默认 5s
CAMPUSOS_DEV_API_HEALTHCHECK_INTERVAL=30s
```

然后执行 `./scripts/docker-dev.sh up` 或 `.\scripts\docker-dev.ps1 up` 让 Compose 按新运行配置重建受影响容器；
不需要 `rebuild`，也不需要重启 Docker Desktop。`CAMPUSOS_DEV_POLL_INTERVAL` 仍只控制 API 源码热重载的
扫描周期，调大它会让 Go 源码变更生效更慢，不能改变 healthcheck。

执行完整 Go 回归时使用 `./scripts/docker-dev.sh test` 或 `.\scripts\docker-dev.ps1 test`。测试运行数据只存在于
一次性 API 容器的 `/tmp/campusos-go-test`，不会写入源码包内的 `.campusos/`；若历史测试已留下该被 Git 忽略目录，
它不是源码，也不会被 API 热重载指纹扫描。不要手工删除来源或所有权不明的被忽略目录；先确认产生进程和数据是否仍需保留。

切换分支或拉取代码后先判断是否包含镜像构建输入：普通源码继续热更新或执行 `up`，构建输入变化使用
`rebuild`。详细决策表见
[Docker 跨平台开发环境](../../../docs-site/deployment/docker-development.md#修改代码后会发生什么)。

### 1.1.1 跨平台代理辅助脚本

`sh/proxy.sh` 面向 Linux、WSL2、Git Bash，必须用 `source sh/proxy.sh on` / `off`；它会同时管理当前
Bash 环境、Git 全局代理和带标记的 SSH 配置。Windows 原生 PowerShell 使用：

```powershell
. .\sh\proxy.ps1 on
# Docker Desktop 需要读取 Windows System proxy 时：
. .\sh\proxy.ps1 on -SystemProxy
.\sh\proxy.ps1 status
.\sh\proxy.ps1 test
. .\sh\proxy.ps1 off
```

PowerShell 开头的 `. ` 不能省略，否则环境变量只在脚本进程内有效。默认地址为
`http://127.0.0.1:7897`；可通过 `-ProxyHost`、`-Port` 覆盖。修改 Windows 系统代理后，已运行的
Docker Desktop 还需执行 `docker desktop restart`；普通源代码或项目 `.env.dev.local` 变化不需要重启
Docker Desktop。

### 1.2 本机 Go/Node 开发并共享 Docker 数据

安装 Go、Node.js 与 pnpm，并先完成上面的 `docker-dev.* setup`。然后执行：

```bash
STOP_EXISTING=true make dev-all
```

启动器会停止 Docker 中的 API/Web/Admin/Docs，但保留同一个 `campusos-dev` PostgreSQL、Redis、NATS
项目及命名卷。原生 API 从 `deploy/docker/.env.dev.local` 读取相同的数据库、SMTP、JWT、Challenge、
Session 和 MFA 配置，并与容器 API 共用宿主 `data/`。因此用户、帖子、会话、个人文件和资源在切换后
保持一致。

切回完整 Docker 模式：

```bash
./scripts/docker-dev.sh up
```

该命令会核验 `.campusos/run/native-dev.pid`，优雅停止本项目的原生服务，再启动应用容器。默认端口相同，
所以这是单写入者交接，不能让两套 API 同时写同一份数据。只有显式设置
`CAMPUSOS_DEV_INFRA_MODE=legacy` 时才继续使用旧 `docker-compose.yml` 的独立数据源。

常用地址：

| 服务 | 地址 |
| --- | --- |
| 用户端 | `http://localhost:3000` |
| 管理端 | `http://localhost:3001` |
| 官方文档 | `http://localhost:3002` |
| API | `http://localhost:8080/api/v1` |
| pgAdmin | `http://localhost:5050`（需要启动 tools profile 或本地基础设施） |

环境变量见 [环境配置与 Host API 端口](环境配置与HostAPI端口说明.md) 和
[官方配置指南](../../../docs-site/deployment/configuration.md)。数据库关系以 Admin `/architecture`、当前
`migrations/` 和 `make database-check` 为准；[数据库管理指南](数据库管理指南.md) 已同步当前
单一 `000001_v1_1_schema_baseline`、checksum/lock 治理与显式 reset 边界。

## 2. `STOP_EXISTING=true make dev-all`

开发机上遗留的 API、Vite、管理端或文档站进程可能占用默认端口。带上 `STOP_EXISTING=true` 后，启动脚本
先停止 Docker 应用容器和已登记的 CampusOS 原生进程，再处理剩余端口监听者：

```bash
STOP_EXISTING=true make dev-all
```

不加该变量时，脚本保留已有进程并提示端口冲突。切换脚本不会按 PID 文件误杀其他进程：只有命令行仍匹配
`scripts/start-dev.sh` 才会停止；状态不可信时会拒绝继续。共享关系如下：

| 内容 | 是否共享 |
| --- | --- |
| PostgreSQL、Redis、NATS | 同一个 `campusos-dev` 容器和命名卷 |
| 用户文件、插件数据、模块数据、资源包 | 同一个宿主仓库 `data/` |
| 源码 | 同一个宿主 Git 工作区 |
| Go/pnpm cache、`node_modules` | 分开保存，不属于业务数据 |

本节是启动脚本的唯一当前 Help 入口。早期“一键启动”短说明已合并到这里，不再单独维护。

## 3. 先确定改动归属

| 要做的事情 | 代码和数据位置 | 不能做什么 |
| --- | --- | --- |
| 平台完整性、安全或数据所有权 | `modules/core/`、`internal/modules/core/` | 不能做成可卸载插件 |
| 随主程序编译、可启停的产品功能 | `modules/features/`、`internal/modules/features/`、`data/module_data/` | 不能进入普通插件安装流程 |
| 可独立安装的第三方扩展 | `data/plugins/<id>/`、`data/plugin_data/<id>/` | 不能导入 `internal/*` 或直连数据库 |
| 主题、首页、个人主页风格、Skill/Prompt | `data/resources/<type>/<id>/` | 不能注册业务进程、migration 或后台路由 |
| 用户拥有的附件和课表 | User Storage 下 `data/personal-space/<user-id>/` | 不能让调用方提供任意宿主路径 |

详细决策见 [模块、插件与资源生命周期](../插件相关/插件分级与生命周期说明.md) 和
[模块与插件边界](../../../docs-site/guide/module-plugin-resource-boundaries.md)。

## 4. 日常验证

后端改动：

```bash
GOCACHE=/tmp/campusos-go-cache go test ./... -count=1
```

用户端改动：

```bash
cd web && pnpm lint && pnpm format:check && pnpm build
```

管理端改动：

```bash
cd admin && pnpm test:component && pnpm build
```

Web/Admin 的 `@/*` TypeScript 路径映射不再使用已弃用的 `baseUrl`，而是相对各自 `tsconfig.json` 显式写为
`"@/*": ["./src/*"]`；Vite 中的 `@` alias 仍负责运行时构建解析。TypeScript 6 会对 `baseUrl` 报弃用，
TypeScript 7 将不再支持它，因此不要用 `"ignoreDeprecations": "6.0"` 代替迁移。详见
[TypeScript 6.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html#deprecated---baseurl)。

官方文档改动：

```bash
cd docs-site && pnpm build
```

数据库迁移改动：

```bash
make migrate-up
make migrate-status
```

文档或整体改动完成前：

```bash
git diff --check
python scripts/check-line-endings.py --include-untracked
make readme-check
make docs-links
make architecture-check
```

Docker 交付改动：

```bash
make docker-deploy-check
```

数据库、迁移或数据所有权改动：

```bash
make database-check
make data-governance-check
```

`make docs-links` 检查 README、Help/API/架构/Skill、所有版本计划与进度、官方文档站、插件和 SDK
文档中的仓库内链接。最终验收统一执行：

```bash
RUN_RESTORE_DRILL=true RUN_BROWSER_SMOKE=true make release-check
```

该门禁包含合同、版本和文档同步、全量 Go、数据库 migration/schema/audit、可靠性和故障注入、插件模板、
Web/Admin 组件测试与构建、docs-site/SDK、恢复演练、认证业务流、风格包双端和七视口真实 Chrome 工作流。

旧 v0.5 Smoke 快照已移除；当前验收以 `release-check` 和受影响模块的定向测试为准。

## 5. 验证选择

## 6. 提交和 PR 脚本

提交前请先确认 `git status --short`，不要把本地密钥、构建产物或其他开发者未关联的改动混入提交。

创建提交：

```bash
./sh/git_commit.sh "feat: describe the change"
```

脚本会检查当前改动、要求提交信息，并按脚本内配置执行基础检查。它不会代替你对改动范围和测试结果的判断。

创建 Pull Request：

```bash
./sh/git_pr.sh -t "feat: describe the change"
```

`git_pr.sh` 使用 GitHub CLI 创建 PR；运行前需要安装并登录 `gh`，并确认当前分支已推送。可用选项见
[PR 提交脚本使用说明](../github使用相关/PR提交脚本使用说明.md)。
