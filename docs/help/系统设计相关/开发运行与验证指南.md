# 开发、验证与贡献指南

> 当前基线：`v0.13.0`
> 最近核验：2026-07-29

本指南收拢本地开发、Docker 开发、任务归属、常用验证和贡献脚本。命令默认在仓库根目录执行。
第一次接触项目时，先走 [开发者递进入门路线](../开发者递进入门路线.md)，不要把带旧版本号的历史快照
当作当前教程。

## 1. 第一次运行

### 1.1 本机 Go/Node 开发

```bash
cp .env.example .env
make docker-up
make migrate-up
STOP_EXISTING=true make dev-all
```

`make docker-up` 启动 PostgreSQL、Redis、NATS 等开发期依赖；`make migrate-up` 将数据库迁移到当前版本；`make dev-all` 启动 API、用户端、管理端和独立官方文档站。

### 1.2 只安装 Git 和 Docker

Windows 10/11 使用 Docker Desktop 的 WSL2/Linux Containers，现代 Linux 使用 Docker Engine + Compose v2：

```bash
./scripts/docker-dev.sh up
```

PowerShell：

```powershell
.\scripts\docker-dev.ps1 up
```

开发栈包含 PostgreSQL、Redis、NATS、API、Web、Admin 和 Docs 七个服务。源码以宿主 UID/GID 运行，
不会用 root 所有权污染 Vite/VitePress 缓存；`node_modules` 和 Go cache 使用独立命名卷。
详细命令和 Windows 文件共享设置见 [Docker 跨平台开发环境](../../../docs-site/deployment/docker-development.md)。

常用地址：

| 服务 | 地址 |
| --- | --- |
| 用户端 | `http://localhost:3000` |
| 管理端 | `http://localhost:3001` |
| 官方文档 | `http://localhost:3002` |
| API | `http://localhost:8080/api/v1` |
| pgAdmin | `http://localhost:5050`（需要启动 tools profile 或本地基础设施） |

环境变量见 [环境配置与 Host API 端口](环境配置与HostAPI端口说明.md) 和
[官方配置指南](../../../docs-site/deployment/configuration.md)。数据库关系以 Admin `/architecture`、当前
`migrations/` 和 `make database-check` 为准；[数据库管理指南](数据库管理指南.md) 的 migration
`000001-000018` 表清单只保留为历史快照。

## 2. `STOP_EXISTING=true make dev-all`

开发机上遗留的 API、Vite、管理端或文档站进程可能占用默认端口。带上 `STOP_EXISTING=true` 后，启动脚本会先停止占用 CampusOS 开发端口的旧进程，再启动当前工作区的服务：

```bash
STOP_EXISTING=true make dev-all
```

不加该变量时，脚本会保留已有进程并提示端口冲突，适合你明确知道现有服务应继续运行的场景。
本节是启动脚本的唯一当前 Help 入口。早期“一键启动”短说明已合并到这里，不再单独维护。

## 3. 先确定改动归属

| 要做的事情 | 代码和数据位置 | 不能做什么 |
| --- | --- | --- |
| 平台完整性、安全或数据所有权 | `modules/core/`、`internal/modules/core/` | 不能做成可卸载插件 |
| 随主程序编译、可启停的产品功能 | `modules/features/`、`internal/modules/features/`、`data/module_data/` | 不能进入普通插件安装流程 |
| 可独立安装的第三方扩展 | `data/plugins/<id>/`、`data/plugin_data/<id>/` | 不能导入 `internal/*` 或直连数据库 |
| 主题、首页、个人主页风格、Skill/Prompt | `data/resources/<type>/<id>/` | 不能注册业务进程、migration 或后台路由 |
| 用户拥有的附件和课表 | User Storage 下 `data/personal-space/<user-id>/` | 不能让调用方提供任意宿主路径 |

详细决策见 [模块、插件与资源生命周期](../插件相关/插件分级与生命周期说明.md) 和
[模块与插件边界](../../../docs-site/guide/module-plugin-resource-boundaries.md)。

## 4. 日常验证

后端改动：

```bash
GOCACHE=/tmp/campusos-go-cache go test ./... -count=1
```

用户端改动：

```bash
cd web && pnpm lint && pnpm format:check && pnpm build
```

管理端改动：

```bash
cd admin && pnpm test:component && pnpm build
```

官方文档改动：

```bash
cd docs-site && pnpm build
```

数据库迁移改动：

```bash
make migrate-up
make migrate-status
```

文档或整体改动完成前：

```bash
git diff --check
make readme-check
make docs-links
make architecture-check
```

Docker 交付改动：

```bash
make docker-deploy-check
```

数据库、迁移或数据所有权改动：

```bash
make database-check
make data-governance-check
```

`make docs-links` 检查 README、Help/API/架构/Skill、所有版本计划与进度、官方文档站、插件和 SDK
文档中的仓库内链接。最终验收统一执行：

```bash
RUN_RESTORE_DRILL=true RUN_BROWSER_SMOKE=true make release-check
```

该门禁包含合同、版本和文档同步、全量 Go、数据库 migration/schema/audit、可靠性和故障注入、插件模板、
Web/Admin 组件测试与构建、docs-site/SDK、恢复演练、认证业务流、风格包双端和七视口真实 Chrome 工作流。

[v0.5 回归 Smoke 测试说明](v0.5回归Smoke测试说明.md) 只用于理解早期检查方式，不再替代当前
`release-check`。

## 5. 验证选择

| 改动范围 | 最小验证 | 合并/封版前追加 |
| --- | --- | --- |
| 纯文档 | `make readme-check`、`make docs-links`、docs-site build、`git diff --check` | 涉及命令声明时运行对应命令 |
| Go/模块 | 定向测试、全量 `go test`、`architecture-check` | 数据库或浏览器门禁按影响追加 |
| Web/Admin | lint/组件测试/build | 受影响视口或完整浏览器矩阵 |
| migration/可靠写入 | 定向 migration drill、`database-check`、故障注入 | 恢复演练和完整发布门禁 |
| Plugin/Resource | CLI inspect、模板测试、架构检查 | 导入/回滚、权限负向和真实渲染矩阵 |
| Docker | 配置合同、隔离栈健康、镜像构建 | 备份恢复、目标平台和完整发布门禁 |

不要用旧进度文档中的一次成功结果替代当前工作树的验收。

## 6. 提交和 PR 脚本

提交前请先确认 `git status --short`，不要把本地密钥、构建产物或其他开发者未关联的改动混入提交。

创建提交：

```bash
./sh/git_commit.sh "feat: describe the change"
```

脚本会检查当前改动、要求提交信息，并按脚本内配置执行基础检查。它不会代替你对改动范围和测试结果的判断。

创建 Pull Request：

```bash
./sh/git_pr.sh -t "feat: describe the change"
```

`git_pr.sh` 使用 GitHub CLI 创建 PR；运行前需要安装并登录 `gh`，并确认当前分支已推送。可用选项见
[PR 提交脚本使用说明](../github使用相关/PR提交脚本使用说明.md)。

## 7. 当前 CI/CD

Pull Request 和受支持分支的 CI 使用：

```text
.github/workflows/ci_test.yml
```

它执行：

- PostgreSQL migration、schema/data audit 和数据库合同检查。
- 全量 Go 测试、后端构建、API/授权合同、文档链接和模块边界检查。
- Web lint、格式、组件测试和构建。
- Admin 组件测试和构建。
- docs-site 与 TypeScript Plugin SDK 构建。

发布工作流使用 `.github/workflows/deploy.yml`。推送 `v*` 标签或手动触发时，它会重新执行关键测试，
构建 Linux `amd64` 后端和三个前端/SDK，并生成发布包；配置 production Environment 后才执行 SSH 部署。
GitHub CI 是合并门禁，不替代本地按改动范围验证。完整流程见
[官方贡献与 CI 工作流](../../../docs-site/contributing/workflow.md)。

## 8. 工作原则

1. 插件、样式包和用户文件分别放在其职责目录中；不要把风格包源码放回 `data/plugins/`。
2. 不要用 scope 推断生效方式；按 `lifecycle.backend.activation_mode` 判断整站重启、插件重启或热更新，所有插件前端均热加载。详见 [插件分级与生命周期说明](../插件相关/插件分级与生命周期说明.md)。
3. 每个可验收任务都应新增对应的 `docs/进度/` 记录，并列出实际运行过的验证命令。
4. README 只保留当前基线和入口；操作细节应写入 `docs/help`、`docs/api` 或架构文档。
5. 历史计划和帮助文档保留当时事实；当前有效性由 [版本计划总结](../../计划书总结/README.md) 和
   [Help 生命周期索引](../README.md) 说明。
