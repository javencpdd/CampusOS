# v1.0 插件平台数据模型与开发库重置说明

> 文档状态：v1 clean baseline 已实施；插件授权业务服务仍在后续计划中  
> 当前数据库基线：migration `000001-000003`  
> 更新时间：2026-09-01  
> 详细方案：[v1.0 数据库全面重构方案](../../项目计划书v1/项目计划v1.0/01-v1.0数据库全面重构方案.md)

## 1. 当前结论

CampusOS 已不再使用旧 `000001-000049` migration 链，也不支持旧开发库原地升级。三段新基线从空库创建：

- `000001`：76 张当前业务表；
- `000002`：8 张插件身份、版本与三层授权基础表；
- `000003`：角色、Permission Code、最小授权矩阵和身份安全策略。

最终为 84 张业务表，加执行器管理的 `schema_migrations`、`schema_migration_locks`。migration 不创建用户、
邮箱、默认管理员凭据或默认版块。

## 2. 插件数据职责

### 当前仍在运行的模型

`plugins`、`plugin_permissions`、`plugin_logs`、`plugin_records`、
`plugin_file_metadata`、`plugin_user_grants`、`plugin_catalog_entries`、
`plugin_install_requests`、`plugin_releases`、`plugin_market_audits` 仍被当前 Runtime/市场代码使用。

它们进入 clean baseline 是因为属于当前业务，不是为了兼容旧数据库。后续服务完成切换前不能提前删除。

### v1 授权基础

| 表 | 模块职责 |
| --- | --- |
| `plugin_publishers` | 发布者身份、信任状态、签名 Key 引用 |
| `plugin_versions` | 不可变版本、包摘要、签名状态、API 版本、权限指纹 |
| `plugin_capability_declarations` | 插件版本声明的逐项能力、用途、风险、数据范围 |
| `plugin_admin_grants` | 管理员逐能力批准/拒绝/撤销 |
| `plugin_user_consents` | 用户逐能力同意/拒绝/撤销 |
| `plugin_delegations` | 有时效的后台任务委托，只保存 Token 摘要 |
| `plugin_secret_values` | Host 托管密文、nonce 和 Key 版本 |
| `plugin_authorization_decisions` | 判定结果、依据、原因和 trace 证据 |

表已建立只代表数据库准备完成。Host API、事件、后台任务、Secret 和 UI 仍需按正式计划接入统一
AuthorizationService 后，才能宣称三层授权功能完成。

## 3. 用户如何授权

用户不需要自行生成长期 Key 或 Token。

1. 插件包在 Manifest 中声明能力。
2. 管理员在 Admin 中批准该版本允许使用的能力。
3. 对涉及个人数据的能力，用户在 Web 中阅读用途并逐项 Consent。
4. 每次调用由 Host 根据可信登录用户、插件身份/版本、资源 Scope、运行状态和三层事实判定。
5. 后台任务需要时由 Host 签发短期 Delegation；数据库只保存摘要，可过期、撤销且不能扩权。

用户手工创建的 API Key 不是三层授权的替代品，也不能让插件绕过 Grant/Consent。

## 4. Secret 与普通配置

- 普通配置可保存普通字符串、数字、布尔或非敏感 JSON。
- 密码、SMTP 授权码、第三方 Token 等必须进入 Secret Service。
- 数据库只保存密文、nonce、算法和 key version；API、日志和审计只能返回掩码或引用。
- 插件停用后不可读取 Secret；轮换或卸载按明确策略吊销，不把明文放进备份 fixture。

## 5. 重置旧开发库

重置会删除目标数据库的整个 `public` schema。只允许已确认可丢弃的 development/test 数据。

Windows PowerShell：

```powershell
$env:CAMPUSOS_SKIP_DOTENV = "true"
$env:PSQL_MODE = "docker"
$env:POSTGRES_CONTAINER = "campusos-dev-postgres-1"
$env:DB_NAME = "campusos"
$env:CAMPUSOS_ENV = "development"
$env:CAMPUSOS_RESET_CONFIRM = "campusos"
.\scripts\migrate.ps1 reset
```

Linux / Git Bash：

```bash
CAMPUSOS_SKIP_DOTENV=true \
PSQL_MODE=docker \
POSTGRES_CONTAINER=campusos-dev-postgres-1 \
DB_NAME=campusos \
CAMPUSOS_ENV=development \
CAMPUSOS_RESET_CONFIRM=campusos \
./scripts/migrate.sh reset
```

安全门禁：

- `CAMPUSOS_ENV` 只能是 `development` 或 `test`；
- `CAMPUSOS_RESET_CONFIRM` 必须和解析后的 `DB_NAME` 完全相同；
- 旧 `schema_migrations` 会被明确拒绝，不会自动猜测或迁移；
- 生产/staging 不允许调用 reset；
- reset 后由安全 bootstrap/CLI 创建首个管理员，不存在 migration 默认密码。

重置并重新启动 API 后，再执行登录和业务测试。源码热更新和数据库 Schema 更新是两条不同路径：改 Go/Vue 源码按
Docker 开发指南 reload/rebuild；新增 migration 则先 `migrate up`。

## 6. migration 日常命令

Windows：

```powershell
.\scripts\migrate.ps1 status
.\scripts\migrate.ps1 check
.\scripts\migrate.ps1 up
.\scripts\migrate.ps1 down
```

Linux / Git Bash：

```bash
./scripts/migrate.sh status
./scripts/migrate.sh check
./scripts/migrate.sh up
./scripts/migrate.sh down
```

- `check`：检查 up/down 配对、版本格式和已执行文件 checksum。
- `up`：按顺序应用未执行版本；每个 SQL 与版本记录同事务提交。
- `down`：只回滚最新一个版本。
- `reset`：经过双确认后清空并从零 up。
- 数据库互斥锁阻止两个 migration 进程并行改 Schema；只有确认没有真实执行进程时，才能用
  `CAMPUSOS_MIGRATION_LOCK_FORCE=true` 配合一次 `up`/`down` 清理异常遗留锁；只读 `check` 不处理锁。

## 8. 常见问题

### 为什么 `up` 提示 legacy schema_migrations？

旧表缺少 checksum，说明目标仍是 49 段历史链构建的开发库。确认数据可删除后按第 5 节 reset；不要手工补列伪装成新基线。

### 为什么表已经有 Grant/Consent，界面还没有完整功能？

数据库基础先于业务服务和 UI。只有写入、判定、撤销、升级 diff、审计和浏览器测试全部接通后，功能才算完成。

### 插件卸载会删除用户文件吗？

默认不会。停用/卸载移除运行权限，用户受管数据仍由 CampusOS 保存，并通过明确导出/删除流程处理。

### 可以直接改 `000001` 吗？

仅本次 owner 明确批准的 reset 重构允许形成 clean baseline。该基线进入共享分支后即冻结，后续必须从 `000004` 追加。
