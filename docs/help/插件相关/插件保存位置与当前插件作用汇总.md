# 插件保存位置与当前插件作用汇总

本文只说明 CampusOS 当前插件保存位置、Admin 管理入口，以及现有插件的作用。具体安装、打包、配置和运行方法，以各插件目录中的 README 或项目已有插件教程为准。

## 1. 当前结论

- 插件文件默认保存在 `data/plugins/<插件名>/`。
- 后端启动时默认扫描 `data/plugins`，也可以通过环境变量 `PLUGINS_DIR` 改成其他插件目录。
- 如果本地 `.env` 仍保留旧值，实际扫描目录以 `.env` 或 shell 环境变量为准，需要手动同步。
- Admin 后台已有 `插件管理` 页面，可以查看已安装插件、启用状态、运行时、版本、描述，并执行导入、导出、配置、启用、禁用、卸载和查看日志。
- 目前没有独立命名为 `插件仓库` 或 `插件市场` 的完整界面；现有 `插件管理` 更接近“已安装插件管理页”，不是远程下载市场。
- PostgreSQL 中保存的是插件元数据、状态、配置、权限和日志；插件代码或 Wasm 文件本身仍保存在插件目录中。

## 2. 插件保存位置

| 内容 | 默认位置或表 | 说明 |
| --- | --- | --- |
| 插件目录 | `data/plugins/<插件名>/` | 每个插件一个目录，目录内需要有 `plugin.yaml`。 |
| 插件 manifest | `data/plugins/<插件名>/plugin.yaml` | 记录插件名称、版本、运行时、订阅事件、权限、配置等信息。 |
| Wasm 插件文件 | `data/plugins/<插件名>/*.wasm` | Wasm Runtime 会根据 `plugin.yaml` 中的配置加载模块，例如 `plugin.wasm`。 |
| 页面拓展风格包源码目录 | `data/plugin_data/<插件名>/style-packs/<风格包名>/` | `page-style-pack.v1` 文件夹风格包，标准包含 `style.yaml`、`README.md`、`preview.png`、`templates/`、`assets/`、`styles/` 和 `config.schema.json`，可编辑源码后打包为 zip 导入，或由特定接口按目录应用。 |
| CLI 安装目标 | `data/plugins` | `campusosctl plugin install` 默认把插件包解压到该目录下的插件名子目录；该目录只应保存插件实现代码、manifest 和运行入口。 |
| 可覆盖插件目录 | `PLUGINS_DIR` | 后端启动时如果设置了该环境变量，会改为扫描指定目录。 |
| 插件运行数据 | `data/plugin_data/<插件名>/` | SQLite-backed 插件 KV、页面拓展风格包源码目录等插件运行/配置数据，默认根目录可由 `PLUGIN_DATA_DIR` 调整。 |
| 个人空间文件 | `data/personal-space/<用户ID>/` | `personal-space` 内置插件使用的本地个人空间文件目录，默认每用户 10MB；按 `file`、`img`、`excel`、`word`、`pdf` 分类。 |
| 插件元数据 | PostgreSQL `plugins` 表 | 保存插件名称、显示名称、版本、运行时、状态、配置、错误信息等。 |
| 插件权限声明 | PostgreSQL `plugin_permissions` 表 | 保存插件声明或同步后的 Host API 权限。 |
| 插件运行日志 | PostgreSQL `plugin_logs` 表 | 保存插件运行、事件处理、Host API 日志等记录。 |
| API Key | PostgreSQL `api_keys` 表 | 保存插件或用户相关 API Key 信息。 |

补充说明：

- `internal/plugin/` 是插件框架源码，包括 Manager、Runtime、Host API、仓储接口等，不是插件保存目录。
- `admin/src/views/PluginManageView.vue` 是 Admin 插件管理页面源码，不是插件保存目录。
- 如果项目未启用 PostgreSQL 仓储，插件 Manager 仍会在内存中维护本次进程加载到的插件状态。

## 3. 后端如何发现插件

后端启动时会创建 Plugin Manager，并注册当前支持的运行时：

- `grpc`
- `wasm`
- `builtin`

随后后端扫描插件目录：

- 默认目录：`data/plugins`
- 覆盖目录：`PLUGINS_DIR`

扫描规则比较简单：

- 只扫描插件目录下的一级子目录。
- 子目录中存在 `plugin.yaml` 才会被视为插件。
- manifest 解析成功后，插件会被安装到 Plugin Manager 的内存列表中。
- 如果配置了 PostgreSQL 插件仓储，插件元数据会同步到 `plugins` 表。

因此，一个插件被“安装”至少包含两层含义：

- 文件层：插件目录存在，并且有合法的 `plugin.yaml` 和必要运行文件。
- 运行层：后端启动或 CLI 安装后，Plugin Manager 能识别并加载该插件。

## 4. Admin 是否有插件仓库界面

当前 Admin 端已有 `插件管理` 页面：

- 前端路由：`/plugins`
- 页面源码：`admin/src/views/PluginManageView.vue`
- 后端接口前缀：`/api/v1/plugins`
- 权限要求：需要通过 JWT 登录，并按操作具备 `plugin:read`、`plugin:configure`、`plugin:lifecycle`、`plugin:install` 或 `plugin:uninstall`。

页面当前能力：

| 能力 | 当前状态 |
| --- | --- |
| 查看已安装插件列表 | 已支持 |
| 查看插件名称、显示名称、版本、描述 | 已支持 |
| 查看运行时类型 | 已支持 |
| 查看插件级别和生效方式 | 已支持，scope 与 restart/plugin-restart/hot 分开显示 |
| 查看启用/禁用状态 | 已支持，同时显示 BackendState、FrontendState、Health 和待重启状态 |
| 启用/禁用 restart 插件 | 已支持，记录目标状态，重启 API 服务后生效 |
| 加载/重载 plugin-restart 或 hot 插件 | 已支持，无需重启 API 服务 |
| 覆盖更新用户级插件 | 已支持；已加载插件会停止旧 Runtime 并加载新包 |
| 卸载插件 | 仅用户级插件支持；系统级插件随服务代码部署 |
| 查看插件日志 | 已支持 |
| 按 `config_schema` 编辑插件配置 | 已支持 |
| 导入标准插件包 | 已支持 |
| 导出标准插件包 | 已支持 |
| 在线下载插件 | 暂未支持 |
| 插件市场搜索 | 暂未支持 |
| 插件版本回滚 | 暂未支持 |

所以，当前可以理解为：

- 有 Admin 插件管理界面，可管理已安装插件并导入/导出标准用户级插件包。
- 还没有完整的“插件仓库/插件市场”界面。
- 如果后续要做“插件仓库”，建议在现有 `插件管理` 基础上扩展“本地已安装”和“远程可安装”两个视图。

## 5. 当前插件作用汇总

### 5.1 `data/plugins/hello-plugin`

作用：

- 作为 gRPC Runtime 插件的示例 manifest。
- `scope: user`，可在管理端手动加载、重载或通过覆盖包更新。
- 说明 gRPC 插件如何声明基础元数据、事件订阅、API 权限和 SQLite 存储。
- 当前订阅了用户、帖子、回复、版块等核心事件，设计目标是“接收并记录核心事件”。
- 适合作为后续开发 gRPC 插件时的 manifest 参考。

注意：

- 当前该目录只有 `plugin.yaml`，没有独立 README。
- 如果后续补充实际 gRPC 服务端实现，应以该插件自己的 README 为准。

### 5.2 `data/plugins/hello-wasm`

作用：

- 作为 Wasm Runtime 的最小可运行示例插件。
- `scope: user`，用于验证无需重启 API 的 Runtime 加载与重载流程。
- 用于验证 `runtime: wasm` 插件可以被安装、启动并接收事件。
- 当前订阅 `thread.created` 和 `post.created` 事件。
- 当前 Wasm 入口函数固定返回允许事件继续，用于验证事件派发链路。
- 可用于测试 Manager、Wasm Runtime、事件处理结果和 `plugin_logs` 写入链路。

使用说明：

- 具体 ABI、文件说明、重新生成 `plugin.wasm` 和测试命令，请参考 `data/plugins/hello-wasm/README.md`。

### 5.3 `data/plugins/personal-space`

作用：

- 作为个人主页和默认风格包的内置插件元数据目录。
- `scope: system`，启用或停用需要重启 API 服务后才会影响用户侧 Space API。
- 统一承载个人主页、默认风格包、受限 HTML 风格片段和个人空间文件能力的默认插件配置。
- 使用 `runtime: builtin`，不启动外部进程，主要用于让内置能力和随项目分发的静态资产在插件目录中有明确归属。
- 当前 4 个默认 JSON 风格包位于 `data/plugin_data/personal-space/styles/`；`data/plugins/personal-space/` 只保留实现清单和说明。
- 文件夹/zip 页面拓展风格包源码示例位于 `data/plugin_data/personal-space/style-packs/clean-blog/` 和 `kinetic-journal/`，标准为 `page-style-pack.v1`，`target` 必须是 `personal-space`。
- 头像上传等个人空间文件默认写入 `data/personal-space/<用户ID>/img/avatars/`，默认每用户 10MB、保留最近 3 个头像源文件；课表 JSON 保存到 `file/schedule/`。
- 个人主页、风格包导入导出、HTML 风格片段检测与应用、内容同步、个人空间文件等主要实现仍在 `internal/space/`。
- 该插件被管理员禁用后，用户侧公开主页、主页设置、风格包操作、头像上传和内容同步都会返回不可用或暂停执行。

使用说明：

- 具体目录说明请参考 `data/plugins/personal-space/README.md`。

### 5.4 `data/plugins/homepage-customizer`

作用：

- 作为用户前台首页 `http://localhost:3000/` 的内置配置插件。
- `scope: system`，启用或停用需要重启 API 服务后生效。
- 使用 `runtime: builtin`，由后端公开接口 `GET /api/v1/home/config` 输出安全后的首页配置。
- 管理员可在 Admin `插件管理` 页面打开该插件的“配置”弹窗，修改首页标题、副标题、背景图、背景遮罩、版块检索标签显示数量、受限 HTML/CSS 片段，并导入首页拓展风格包 zip。
- 文件夹/zip 页面拓展风格包源码示例位于 `data/plugin_data/homepage-customizer/style-packs/campus-hero/`，标准为 `page-style-pack.v1`，`target` 必须是 `homepage`。
- `custom_html` 和 `custom_css` 会在写入前执行后端安全检查，脚本、事件处理器、不安全 URL 和危险 CSS 会被拒绝；任意 JS/未审查 HTML 仍不开放。

使用说明：

- 具体目录说明请参考 `data/plugins/homepage-customizer/README.md`。

### 5.4.1 `data/plugins/web-theme`

作用：

- 作为完整用户前台系统主题的内置提供插件，`target` 必须是 `web`，不会进入 Admin 管理端。
- `scope: system`，插件启停需要重启 API；主题 CSS、特效和用户本地选择可以立即切换。
- 管理员提供的源码包位于 `data/plugin_data/web-theme/style-packs/`，用户只能从筛查通过的目录中选择，不能在用户端安装系统主题。
- 当前示例 `campus-canvas/` 可以调整所有用户前台页面的字体、背景、页边距、卡片和响应式布局，并运行隔离的活动背景特效。
- JavaScript 只允许以 `sandbox-worker.v1` 执行；TypeScript 只作为开发源码，必须先编译为 JavaScript。
- 系统包可声明 `community.threads.read`、`categories.read` 和需用户授权的 `schedule.me.read`，但不能获得 JWT、任意 API 或写操作。

相关说明：

- `data/plugins/web-theme/README.md`
- `docs/help/系统设计相关/风格包能力边界与CampusStyleSDK说明.md`

### 5.5 `data/plugins/controlled-richtext-article`

作用：

- 作为受控富文本图文文章的内置插件，提供图片上传、草稿、预览、发布和管理端治理能力。
- `scope: system`，启用或停用需要重启 API 服务后生效。
- 每个用户的图文图片写入 `data/personal-space/<用户ID>/img/richtext/`，与头像、课表共享 `personal-space` 的本地配额。
- 对外仍使用 `/api/v1/richtext/assets/<user_id>/<filename>` 访问图片，迁移不会改变已写入 HTML 或数据库的 URL。
- 旧的 `data/images/richtext/users/` 默认目录会在后端启动时自动迁移。

使用说明：

- 具体接口和安全边界请参考 `data/plugins/controlled-richtext-article/README.md`。

### 5.6 `data/plugins/personal-schedule`

作用：

- 作为用户个人课表的内置插件，可在管理端启用、禁用和配置导入限制。
- `scope: system`，启用或停用需要重启 API 服务后生效。
- 每个学期课表保存到 `data/personal-space/<用户ID>/file/schedule/terms/<年份>-<spring|fall>.json`；`index.json` 仅记录最近选择的课表。它们与头像和图文文章图片共同计入个人空间配额。
- 用户可选择已保存课表，或选择年份和春季/秋季后新建课表；通过“设置第一周”按钮修改当前学期第一周的开始日期。
- 用户端同时提供按周的节次课表和可浏览过去、未来月份的日历视图；日历根据第一周、星期和课程周次计算课程日期。

使用说明：

- 导入格式、文件位置和配置项请参考 `data/plugins/personal-schedule/README.md`。

### 5.7 `data/plugins/category-moderation`

作用：

- 作为版块版主管理的内置系统级插件，提供管理端独立配置页和用户端治理入口。
- 管理员可为一个用户选择一个或多个版块；版主只能在这些版块中置顶/取消置顶、锁定/解锁主题和删除回复。
- 插件配置可全局关闭任一治理动作，但不能扩大用户的版块范围，也不能授予角色、用户、插件或系统管理权限；治理审计强制保留。
- 后端从主题或回复所属主题读取实际 `category_id`，再匹配 `user_roles` 的 `category` scope，跨版块请求返回 `403`。
- `scope: system`，插件整体启用和禁用在重启 API 后生效；置顶、锁定、删除回复的动作开关支持热更新。
- 停用不会删除版主与版块分配或历史审计；停用后的用户侧治理接口返回不可用，管理员仍可维护分配。

使用说明：

- 权限、配置和生命周期请参考 `data/plugins/category-moderation/README.md` 和 [RBAC 权限与版主管理说明](../系统设计相关/RBAC权限与版主管理说明.md)。

## 6. 与个人主页内置实现的关系

`personal-space` 现在是“内置默认插件目录”，用于保存 manifest、默认风格包和个人空间文件配置。它的启用/禁用状态会影响用户侧 Space API，但不表示个人主页能力已经完全从核心模块迁移为外部插件。

当前可通过 `data/plugins/personal-space/plugin.yaml` 调整：

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `file_root` | `data/personal-space` | 本地个人空间文件根目录 |
| `file_url_prefix` | `/api/v1/spaces/files` | 文件公开访问 API 前缀 |
| `default_quota_mb` | `10` | 每个用户初始本地空间大小 |
| `avatar_keep_limit` | `3` | 每个用户保留的头像源文件数量 |
| `max_avatar_mb` | `2` | 单个头像文件大小上限 |
| `future_storage_provider` | `local` | 后续个人云盘接入预留配置 |

后续如果要把“博客园式个人主页”或“风格切换”做成完全外部化插件，还需要补齐：

- 插件运行时实现。
- 与个人主页数据模型的 Host API 或后端接口边界。
- Admin 或用户侧的插件配置入口。
- 插件安装、启用、禁用、卸载后的数据保留策略。

## 7. 建议后续演进方向

如果要把现有 `插件管理` 升级为真正的 `插件仓库`，建议按以下顺序推进：

1. 保留现有 `插件管理`，作为“已安装插件”视图。
2. 新增“本地插件包安装”能力，支持上传或指定插件包。
3. 新增“插件仓库”视图，展示远程可安装插件。
4. 增加插件签名、版本校验、兼容版本校验。
5. 增加插件安装前权限预览。
6. 增加插件升级、回滚和数据迁移策略。

当前阶段更建议先稳定：

- 插件目录规范。
- manifest schema。
- Admin 已安装插件管理。
- Host API 权限控制。
- 插件日志和故障定位能力。
