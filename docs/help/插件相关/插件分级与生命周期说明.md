# 插件分级与生命周期说明

CampusOS 使用 `plugin.yaml` 的 `scope` 区分两类插件：

```yaml
scope: system # 或 user
```

未填写 `scope` 时，`runtime: builtin` 默认是系统级，gRPC 和 Wasm 插件默认是用户级。这让旧 manifest 可以继续使用。

## 1. 两类插件

| 类型 | `scope` | 适用场景 | 生效方式 |
| --- | --- | --- | --- |
| 系统级插件 | `system` | 随 CampusOS 服务代码发布的核心能力，例如个人空间、首页配置、富文本和个人课表 | 管理端启用或停用只记录目标状态；重启 API 服务后生效 |
| 用户级插件 | `user` | 可独立安装、维护的 gRPC 或 Wasm 扩展 | 在管理端手动加载、重载或覆盖更新后立即生效，不需要重启 API 服务 |

这里的“用户级”表示运行时可热加载的扩展级别，并不表示普通登录用户可以安装插件。当前安装、配置、加载和卸载仍由具备 `role:manage` 权限的管理员操作；终端用户插件市场和每用户私有安装尚未实现。

## 2. 管理端操作

进入 Admin 的“插件管理”页面后，列表会显示“级别”“生效方式”和“状态”。

| 操作 | 系统级插件 | 用户级插件 |
| --- | --- | --- |
| 启用 | 显示“待重启启用”；重启 API 后加载 | 立即加载 Runtime |
| 禁用 | 显示“待重启停用”；当前进程保持原状态直到重启 | 立即停止 Runtime |
| 加载/重载 | 不提供，改为部署并重启 | 点击“加载”或“重载”即可应用当前目录中的 Runtime 文件和已保存配置 |
| 覆盖更新包 | 不允许通过网页导入 | 选择“覆盖”导入同名包；若旧插件已加载，系统会停止旧 Runtime 并加载新包 |
| 卸载 | 不允许；需要通过服务代码发布流程处理 | 可在管理端卸载 |

系统级开关不会在当前进程中改变个人主页、富文本、课表等接口的可用性。这是有意的行为，避免核心服务在运行中切换依赖和配置。

## 3. 用户级插件开发示例

```yaml
name: attendance-helper
display_name: "Attendance Helper"
version: "0.1.0"
runtime: wasm
scope: user
events:
  subscribe:
    - thread.created
config:
  module: "plugin.wasm"
  entrypoint: "handle_event"
```

开发时修改 `plugin.wasm` 或 gRPC 插件的运行文件后，可在管理端点击“重载”。若修改了 `plugin.yaml`、事件订阅或包内文件结构，应重新打包并以“覆盖”方式导入，使 Manager 重新读取 manifest 和事件订阅。

## 4. API 生命周期字段

`GET /api/v1/plugins` 和 `GET /api/v1/plugins/:name` 会返回：

| 字段 | 含义 |
| --- | --- |
| `scope` | `system` 或 `user` |
| `activation_mode` | `restart` 或 `hot` |
| `desired_enabled` | 管理端请求的目标开关状态 |
| `pending_restart` | 系统级插件的当前运行状态与目标状态不一致时为 `true` |

管理员还可使用 `POST /api/v1/plugins/:name/reload` 重载用户级插件。系统级插件调用该接口会被拒绝。

## 5. 安全边界

- 网页插件包导入只接受用户级插件；声明为 `scope: system` 的包会在预检阶段被拒绝。
- 系统级插件仍从服务部署目录 `data/plugins/` 随代码加载，避免管理员在运行中替换核心能力。
- 热更新不绕过现有插件包路径、权限、Checksum、大小和风险预检。
- 用户级插件在重启后仅会自动恢复此前已加载的状态；未手动加载的新插件保持未启用。
