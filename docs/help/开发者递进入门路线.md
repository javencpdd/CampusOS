# CampusOS 开发者递进入门路线

> 当前基线：`v0.13.0`  
> 目标读者：第一次接触仓库、准备贡献代码或开发插件的开发者  
> 建议用时：首次浏览约 90 分钟，后续按任务深入

本路线只安排当前仍有效的入口。带旧版本号的设计记录、事故复盘和兼容说明不会出现在必读路径中。
遇到具体问题后，再从 [Help 文档审计与整理说明](文档审计与整理说明.md) 查找专项或历史材料。

## 阶段 0：先知道应该相信什么

CampusOS 文档数量较多，当前事实按以下顺序判断：

```text
代码和 migration
  > 生成的 OpenAPI、路由、数据库和资源合同
  > 最新进度验收证据
  > 当前架构与 Help
  > 已封版计划和历史说明
```

先读：

1. [仓库 README](../../README.md)
2. [文档门户](../README.md)
3. [当前架构概览](../architecture/当前架构概览.md)

完成标志：能够说明 CampusOS 是模块化单体，并区分 Core Module、Built-in Feature、External Plugin 和
Resource Package。

## 阶段 1：选择开发方式并启动系统

### 只安装 Git 和 Docker

Windows 10/11 使用 Docker Desktop 的 WSL2/Linux Containers；Linux 使用 Docker Engine 和 Compose v2：

```bash
git clone https://github.com/javencpdd/CampusOS.git
cd CampusOS
./scripts/docker-dev.sh setup
# 编辑脚本生成的 deploy/docker/.env.dev.local
./scripts/docker-dev.sh setup --start
```

PowerShell：

```powershell
.\scripts\docker-dev.ps1 setup
# 编辑脚本生成的 deploy/docker/.env.dev.local
.\scripts\docker-dev.ps1 setup -Start
```

`EMAIL_PROVIDER=fake` 可以启动系统，但不会发送或显示验证码；需要从页面完成真实注册时，应在本地配置中
填写 SMTP。脚本会校验端口冲突、开发栈只能绑定 loopback、邮件 Provider、SMTP 必填字段和 Compose
语法，并且不会输出 SMTP 密码。

Docker 不会替开发者下载或长期保存源码。仓库是宿主机的 Git 工作区，Compose 只把它绑定挂载到容器；
平时在宿主 IDE 中编辑，Git 提交和推送也在宿主完成。

阅读 [Docker 跨平台开发](../../docs-site/deployment/docker-development.md)。

### 已安装 Go、Node.js 和 pnpm

```bash
STOP_EXISTING=true make dev-all
```

先完成一次 `docker-dev.* setup`。原生模式会停止 Docker 的四个应用容器，但继续使用同一个 PostgreSQL、
Redis、NATS 项目、命名卷和宿主 `data/`；运行 `./scripts/docker-dev.sh up` 可以交接回完整 Docker 模式。
不要同时启动两套 API。

阅读 [开发、验证与贡献指南](系统设计相关/开发运行与验证指南.md) 和
[环境配置与 Host API 端口](系统设计相关/环境配置与HostAPI端口说明.md)。

### 启动检查

| 服务 | 地址 |
| --- | --- |
| 用户前台 | `http://localhost:3000` |
| 管理后台 | `http://localhost:3001` |
| 官方文档 | `http://localhost:3002` |
| 后端 API | `http://localhost:8080/api/v1` |

```bash
curl -fsS http://localhost:8080/api/v1/health
```

完成标志：四个应用可访问，API 健康检查成功，并且能在 `.campusos/logs/` 找到对应日志。

## 阶段 2：理解代码和数据归属

按顺序阅读：

1. [模块、插件与资源生命周期](插件相关/插件分级与生命周期说明.md)
2. [模块、插件与资源保存位置](插件相关/插件保存位置与当前插件作用汇总.md)
3. [官方模块与插件边界](../../docs-site/guide/module-plugin-resource-boundaries.md)
4. [数据目录](../../docs-site/reference/data-layout.md)

第一次修改前先回答：

| 问题 | 判断 |
| --- | --- |
| 平台没有它就不完整吗 | 是：Core Module |
| 随主程序编译，但允许停用吗 | 是：Built-in Feature |
| 需要独立安装、升级和卸载吗 | 是：External Plugin |
| 只包含主题、风格、Skill 或 Prompt 吗 | 是：Resource Package |

完成标志：能够为改动选择 `internal/modules/core`、`internal/modules/features`、`data/plugins` 或
`data/resources`，且不会把运行数据写进实现目录。

## 阶段 3：跟踪一次请求

选择一个只读请求，例如：

```text
GET /api/v1/categories
```

依次找到：

1. `internal/transport/httpapi/` 中的路由注册。
2. 对应模块 Handler。
3. Service 或公开 Port。
4. Repository 与数据库表所有权。
5. Web/Admin 中的调用点。
6. [API 与机器合同](../api/README.md) 和生成的
   [HTTP 路由与授权矩阵](../api/HTTP路由与授权矩阵-v0.6.md)。

不要从前端按钮是否显示推断权限。服务端仍会校验身份、Permission Code、资源所有权或板块作用域。

完成标志：能够从浏览器调用追踪到路由、Service、数据所有者和返回合同。

## 阶段 4：完成第一次小改动

开始前：

```bash
git status --short
```

优先选择不含 migration 的小改动，例如补充错误处理、增加一个组件测试或修正文档。完成后按范围验证：

```bash
GOCACHE=/tmp/campusos-go-cache go test ./... -count=1
make docs-links
make architecture-check
git diff --check
```

前端改动追加：

```bash
cd web && pnpm lint && pnpm format:check && pnpm build
cd ../admin && pnpm test:component && pnpm build
```

文档站改动追加：

```bash
cd docs-site && pnpm build
```

完成标志：改动有定向测试、全量基础验证和清晰回滚方式，不通过删除权限或安全校验来换取测试成功。

## 阶段 6：提交贡献

提交前按 [开发、验证与贡献指南](系统设计相关/开发运行与验证指南.md) 选择验证范围。

可选辅助脚本：

```bash
./sh/git_commit.sh "feat: describe the change"
./sh/git_pr.sh -t "feat: describe the change"
```

Web/Admin/Docs 和 TypeScript SDK。完整贡献流程见
[官方贡献与 CI 工作流](../../docs-site/contributing/workflow.md)。
