# CampusOS 当前项目状态与未来规划

> 规划基线：`v0.13.0`  
> 状态：版本间候选路线，不是正式 v14 承诺

## 1. 当前已经形成的能力

CampusOS 当前是可运行、可验证、可容器化交付的模块化单体：

- Core Module 覆盖 Identity、Community、Moderation、User Storage、Reliability、Observability、
  Email Delivery、Feature Registry 和 Plugin Platform 安全边界。
- Built-in Feature 覆盖 Personal Space、RichText、Schedule、Appearance、Webhook、AI、MCP-like、
  Message、Mutual Aid 和 Secondhand 等可启停功能。
- External Plugin 支持 Manifest v1/v2、Wasm 或受管进程、Host API/Extension Gateway、Catalog、
  用户 Grant 及受管记录/文件。
- Resource Package 覆盖主题、首页包、个人主页风格、Skill、Prompt、Persona 和知识元数据。
- API、Web、Admin、Docs 可以分别构建镜像，也可以通过 Compose 一键启动。

当前尚未交付生产级高可用、标准 MCP Server、真实 protobuf gRPC 扩展、远程公共插件市场或完整 Agent
产品。这些能力不能从早期计划愿景中推断为已经实现。

## 2. P0：下一阶段优先候选

### 生产交付认证

- 在真实 Windows 10/11 Docker Desktop 和 Linux `arm64` Runner 复验镜像、脚本、备份和恢复。
- 提供独立反向代理/TLS 参考方案。
- 增加镜像 SBOM、漏洞扫描、签名、来源证明和依赖升级策略。
- 在目标环境验证 SMTP、Prometheus 告警、备份保留和持续运行。

### 文档与发布治理

- 为官方文档增加版本选择和 release notes。
- 持续同步 OpenAPI、路由授权矩阵、Admin 只读架构和资源 checksum。
- 把真实平台验证结果接入 release runner，而不是只依赖人工说明。

### 安全与运维

- 为 TOTP、SMTP、插件签名和第三方 Secret 接入可替换 Secret Provider。
- 建立可靠 Worker、邮件、Webhook、数据库和 User Storage 的 SLO 与告警接收闭环。
- 保持最后管理员、Step-up、板块作用域、required audit 和事务 Outbox 的默认拒绝语义。

## 3. P1：架构和生态候选

| 方向 | 目标 | 前置条件 |
| --- | --- | --- |
| 标准 MCP | 正式协议 Server 和版本化 Tool/Resource | 权限、确认、审计、限流和敏感字段投影 |
| 进程扩展协议 | 真实 protobuf gRPC 或明确的新协议名 | 兼容、健康、超时、签名和迁移 |
| 远程插件目录 | 下载、版本索引、审核和签名吊销 | 供应链扫描、透明审计和失败回滚 |
| 共享 User Storage | S3/OSS/WebDAV Provider | 所有权、配额、幂等、加密和多实例一致性 |
| 身份增强 | OAuth/OIDC、Passkey 或更多邮件 Provider | 账号合并、恢复、Step-up 和历史兼容 |
| 通知增强 | SSE/WebSocket 或外部邮件通知 | 轮询兼容、离线状态、用户偏好和限流 |
| 第三方 Adapter | Discord、OneBot 等生产适配器 | 独立插件、最小权限、重试和审计 |

## 4. P2：高风险或长期候选

- 多节点 API/Worker、高可用 PostgreSQL 和分布式 Session/限流。
- 隔离 Agent Runner、Knowledge Provider、Prompt/Persona 管理和代码执行审批。
- 公共插件市场的社区审核、评分、支付、恶意包分析和跨实例 Secret envelope。
- 个人云盘、跨插件统一搜索、向量检索和大规模内容索引。

没有威胁模型、隔离、资源配额、审计和恢复方案时，不得提前开放这些能力。

## 5. 下一版正式立项条件

1. 冻结当前代码、42 个 migration、路由/OpenAPI、Module/Runtime Manifest 和数据目录。
2. 运行完整发布门禁，记录操作系统、CPU 架构、Docker/Compose、浏览器和数据库版本。
3. 从 P0/P1 中只选择有限主线，并明确非目标。
4. 为每阶段定义代码目录、数据迁移、兼容、回滚、负向测试和进度证据。
5. 创建正式版本计划后才形成新版本承诺。

## 6. 不能回退的边界

- 不把模块化单体拆成无必要的微服务。
- 不把 Built-in Feature 或 Resource Package 放回普通插件生命周期。
- 不允许 External Plugin 或 Agent Runner 获取核心数据库、JWT 私钥、用户 Token 或完整宿主文件系统。
- 不在 Feature 停用、Plugin 卸载或资源切换时删除用户数据。
- 不为了通过测试移除权限、审计、清洗、路径、配额、事务或数据库约束。
- 不默认明文导出任何 CampusOS 或第三方 Secret。
