# v12 账号恢复与邮箱绑定流程

> 阶段：A7 找回、绑定与恢复  
> 权威路由合同：[openapi-v0.6-current.yaml](openapi-v0.6-current.yaml)

## 1. 端点

| 方法 | 路径 | 认证 / 权限 | 说明 |
| --- | --- | --- | --- |
| `POST` | `/auth/password-reset/challenge` | 无 | 统一受理密码重置 Challenge 请求。 |
| `POST` | `/auth/password-reset/verify` | 无 | 校验六位验证码，返回短期一次性 Ticket。 |
| `POST` | `/auth/password-reset/complete` | 无 | 消费 Ticket，更新密码并撤销全部会话。 |
| `POST` | `/auth/email-binding/challenge` | Access JWT + CSRF | 为当前用户的新邮箱创建 Challenge。 |
| `POST` | `/auth/email-binding/verify` | Access JWT + CSRF | 校验绑定验证码。 |
| `POST` | `/auth/email-binding/complete` | Access JWT + CSRF | 原子替换已验证邮箱并撤销全部会话。 |
| `POST` | `/auth/recovery/complete` | 无 | 完成管理员创建的辅助恢复 Case。 |
| `GET/POST` | `/identity/recovery-cases` | `identity.account.recovery.override` | 列出或创建辅助恢复 Case。 |
| `POST` | `/identity/recovery-cases/:id/cancel` | `identity.account.recovery.override` | 取消未完成 Case。 |
| `GET` | `/identity/users/:id/sessions` | `identity.session.read` | 读取目标用户脱敏会话。 |
| `POST` | `/identity/users/:id/sessions/revoke-all` | `identity.session.revoke` | 撤销目标用户全部会话。 |
| `GET` | `/identity/challenge-policy` | `identity.challenge_policy.read` | 读取邮箱/IP 验证码滑动窗口策略。 |
| `PUT` | `/identity/challenge-policy` | `identity.challenge_policy.update` | 按版本热更新窗口和次数上限。 |

所有端点均使用 `{ code, msg, data, request_id }` 包络。具体 request/response schema 由生成的
OpenAPI 为准；新增客户端不应从文档示例推断或存储未声明字段。

## 2. 公共密码重置

请求：

```json
POST /api/v1/auth/password-reset/challenge
{"email":"student@example.edu"}
```

无论邮箱是否存在、是否验证、是否停用或是否被限流，响应都保持 `accepted: true` 的统一形状。真正
可用的请求编号只会关联到已验证且可恢复的账号，客户端不得把返回编号当作“账号存在”的证据。官方
Web 会把响应中的 `challenge_id` 暂存在页面内存，普通用户只填写验证码，不手动输入请求编号。

验证码校验成功后，响应中会有短期 `ticket`。完成请求需要同时提供与 Ticket 绑定的规范化邮箱、
`challenge_id`、`ticket` 和新密码。Ticket 只能使用一次；用途、邮箱、有效期、摘要和消费状态都在
事务中校验。

## 3. 邮箱绑定

绑定 API 只接受当前 JWT 所代表的用户。三个写请求均需要 `X-CSRF-Token`，前端从同源
`campusos_csrf` Cookie 读取并传递相同值。服务端不信任请求体中的用户 ID。

完成绑定后，会同步写入权威 `accounts` 邮箱和兼容 `users.email`，把账号状态置为 `verified`，增加
`auth_version` 并撤销所有 Session。因此完成接口成功后客户端应清空内存 Access Token，回到登录页。

## 4. 管理员辅助恢复

创建 Case 的请求包含 `user_id`、新邮箱和线下核验编号。HTTP 响应和后续列表不会返回线下编号、
原始邮箱、验证码、Ticket、密码或 hash；管理员只看到 Case 公共 ID、用户 ID、脱敏邮箱、状态和时限。

用户使用邮件中的 Challenge 编号和验证码取得 Ticket，再调用 `/auth/recovery/complete` 设置新密码。
该命令锁定 Case 与 Challenge，确认账号仍符合历史恢复条件后原子完成账号转正、密码更新、会话撤销和
Case 完成状态。取消、过期或已完成 Case 都不能再次使用。

## 5. 错误与安全语义

- 公共找回不返回“邮箱不存在”“历史账号不可恢复”等差异化错误，避免账号枚举。
- Code、Ticket、Challenge 用途错误、过期、已消费或已取消均返回稳定的无效语义。
- 管理员 Case 不能用于 `verified`、`system_managed` 或停用账号；系统管理员只能本机交互式恢复。
- 所有密码变更、邮箱绑定、管理员完成恢复和管理员会话撤销都写 Reliability required command audit
  和最小 Outbox 事件；payload 不含邮件、Code、Ticket、密码或证明材料。
- Refresh Token 只存在于 HttpOnly Cookie，数据库只保存摘要；会话列表也不返回摘要或原始 IP。

## 6. 兼容与回退

`users.email` 继续作为旧 API 的兼容投影，但只能由 Identity Service 与权威 Account 在同一命令中更新。
历史 `legacy_accepted` 用户可继续用原密码登录；只有其主动绑定并验证新邮箱，或完成管理员辅助恢复，
才会转为可走邮件找回的 `verified` 账号。

生产回退采用 forward-fix，不恢复旧 Access/Refresh Token，也不删除 Challenge、Case、Session、Outbox
或审计证据。`000031` 的 down migration 只供隔离数据库演练使用。
