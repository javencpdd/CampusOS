> 状态：本切片实现、自动化与 Linux PG 目标三态通过

POST `/richtext/articles/:id/attachments/upload` 使用固定 `http.feature.richtext.attachment.upload` operation。入口在解析 multipart 前校验当前实际 User Session，仅接收一个 file，不接收 actor/owner/action/scope/facts。Core 先按同一实际作者 edit Policy 判定；独立 Admin 不可代理 User。

内容探测前后与 byte I/O 后复核完整 Core/Article20/Asset-Binding22、当前完整 Principal 和 enable 状态。保留 20 MiB/10 个/40 MiB、格式/魔数与 OOXML 条目限制；实际容量由当前持久化 quota 决定。Object 暂存后，真实命令事务锁定完整资源与 Object receipt，Asset/Binding 和必需 audit/outbox 原子，最终证明只允许预期新增项。时间规范为 UTC，仍比较所有 Object 字段。

201 成功只返回 thread_id、attachment_id；事件 richtext.attachment.updated 同样只含 IDs。当前 Web 消费者重新请求附件列表。401 当前凭据不可用；403 非作者/跨域；404 资源不存在；409 当前事实变化/库存总量或容量冲突；413 单文件/数量限制；503 校验不可用或补偿未完成。写成功回执不推出后续读取权限。

业务失败使用五秒、取消独立的清理上下文，先核对完整 staged receipt，再按精确 owner/ID/version 删除。已变化 receipt 不删除，删除或 provider Abort 失败明确返回 compensation pending，不能报告成功或容量已释放；现有持久化 receipt 与 reconcile 边界保留，不新建通用清理 registry。

仅接受真实上传路径；个人文档复制仍需可信来源和源版本最终 proof。无 DDL，current22/next23。详见[进度 .88](../进度/v1.2-dev/v1.2.88-dev.md)。
