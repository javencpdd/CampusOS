# CampusOS v9 插件数据存储与前端适配修订方案

## 一、最终决策

v9阶段采用以下数据原则：

```text
插件代码由管理员安装
插件运行状态由CampusOS管理
插件结构化数据由CampusOS托管
插件用户文件保存到CampusOS用户空间
插件通过Host API执行数据增删查改
插件不能直接访问CampusOS主数据库
SQLite和外部云存储暂时后置
```

这意味着，v9不同时实现以下复杂能力：

- 每个插件独立数据库。
- 每个用户独立SQLite。
- 插件自行配置云数据库。
- 插件直接管理对象存储凭证。
- CampusOS跨外部数据源统一检索。
- 插件任意SQL查询。
- 插件自定义数据库管理界面生成器。

v9先完成一个稳定、可权限控制、可备份和可迁移的系统托管存储闭环。

# 二、当前存储现状审查

当前插件Manifest已经允许声明：

```yaml
storage:
  type: sqlite | postgresql | none
```



当前Host API中也已经实现本地SQLite KV：

```text
data/plugin_data/{plugin_name}/plugin.db
```

每个插件拥有一个本地SQLite文件，表结构主要是：

```text
plugin_kv
- key
- value
- updated_at
```

它目前只提供：

- 读取单个Key。
- 写入单个Key。
- 删除单个Key。

不支持：

- 分页列表。
- 条件查询。
- 按用户自动隔离。
- 全文检索。
- 字段索引。
- 多实例共享。
- 统一备份策略。

 

因此，当前SQLite实现可以作为开发和兼容能力保留，但不适合作为v9用户插件数据主方案。

# 三、v9插件数据主路径

## 3.1 系统托管的结构化数据

v9中，插件默认通过CampusOS提供的统一存储服务保存数据。

建议定义：

```text
Plugin Data Service
```

底层优先使用CampusOS PostgreSQL，但插件不直接获得数据库连接。

推荐逻辑模型：

```text
plugin_records
- id
- plugin_id
- owner_type
- owner_id
- collection
- record_key
- data_json
- search_text
- created_at
- updated_at
- version
```

字段含义：

| 字段 | 说明 |
|---|---|
| `plugin_id` | 插件标识 |
| `owner_type` | `system`、`user`、`space` |
| `owner_id` | 用户ID、空间ID或系统范围 |
| `collection` | 插件内部数据集合 |
| `record_key` | 插件定义的唯一Key |
| `data_json` | JSON结构化数据 |
| `search_text` | 可选的系统检索文本 |
| `version` | 乐观锁版本 |

用户级数据命名空间：

```text
plugin/{plugin_id}/user/{user_id}/{collection}/{record_key}
```

平台级数据命名空间：

```text
plugin/{plugin_id}/system/{collection}/{record_key}
```

插件无法指定其他用户的命名空间，Host API根据当前身份自动注入用户ID。

---

## 3.2 系统托管的用户文件

插件生成或上传的用户文件，统一进入CampusOS用户空间。

建议路径：

```text
users/{user_id}/plugins/{plugin_id}/
```

例如：

```text
users/10001/plugins/calendar-assistant/export.ics
users/10001/plugins/note-tool/images/cover.png
```

插件不能直接拼接服务器绝对路径，只能调用文件Host API：

```text
CreateFile
ReadFile
ListFiles
DeleteFile
GetFileMetadata
CreateTemporaryURL
```

现有权限目录已经区分了：

- `storage:read/write/delete`
- `space_file:read/write`



v9应进一步规定：

- `storage`：插件内部结构化数据。
- `space_file`：用户可见的个人空间文件。
- `plugin_file`：插件私有但属于用户的文件。

建议新增：

```text
plugin_file:read
plugin_file:write
plugin_file:delete
plugin_file:list
```

# 四、插件如何进行数据增删查改

## 4.1 系统提供通用Host Storage API

插件不需要为每一种底层存储自行实现数据库连接，只需要调用统一接口。

建议接口：

```go
type PluginDataStore interface {
    Create(ctx context.Context, request CreateRecordRequest) (*Record, error)
    Get(ctx context.Context, request GetRecordRequest) (*Record, error)
    Update(ctx context.Context, request UpdateRecordRequest) (*Record, error)
    Delete(ctx context.Context, request DeleteRecordRequest) error
    List(ctx context.Context, request ListRecordsRequest) (*RecordPage, error)
}
```

基础查询能力包括：

- 按插件。
- 按当前用户。
- 按Collection。
- 按Record Key。
- 分页。
- 创建时间排序。
- 更新时间排序。
- 标签筛选。
- 有限的已声明字段筛选。

插件负责定义业务含义，CampusOS负责：

- 身份注入。
- 权限检查。
- 用户隔离。
- 数据保存。
- 配额。
- 审计。
- 备份。
- 并发控制。

## 4.2 插件仍负责业务接口

CampusOS提供通用数据能力，但不理解所有插件业务。

例如“记账插件”可能提供：

```text
POST /extensions/accounting/records
GET  /extensions/accounting/monthly-summary
DELETE /extensions/accounting/records/:id
```

记账插件内部再调用Host Storage API保存数据。

因此职责划分是：

```text
用户前端
→ 插件业务API
→ 插件业务逻辑
→ CampusOS Host Storage API
→ CampusOS托管数据库
```

CampusOS不需要为每个插件自动生成完整业务接口。

# 五、系统是否提供插件数据检索

## 5.1 v9提供基础检索，但不提供任意业务查询

只要插件数据保存在CampusOS托管存储中，系统可以提供基础检索：

- 根据Key查询。
- 根据Collection查询。
- 分页查询。
- 根据标签查询。
- 根据时间范围查询。
- 根据已声明索引字段查询。
- 根据用户空间文件名和元数据查询。

系统不应该允许插件直接提交：

```sql
SELECT * FROM ...
```

也不应该允许任意JSON路径查询，因为这会带来：

- 性能不可控。
- 索引不可控。
- 数据越权。
- 查询注入风险。
- 数据结构强耦合。

## 5.2 全文检索采用显式声明

需要系统检索的插件，应在Manifest声明可索引内容：

```yaml
data:
  collections:
    - name: notes
      searchable: true
      searchable_fields:
        - title
        - summary
        - tags
      filterable_fields:
        - category
        - status
```

CampusOS只索引声明字段。

插件未声明时：

```text
数据可以CRUD
但不进入系统全局搜索
```

## 5.3 全局搜索结果需要插件提供展示合同

即使系统索引了数据，也不能直接把内部JSON展示给用户。

插件应声明：

```yaml
search:
  provider: host-index
  result_contract:
    title_field: title
    summary_field: summary
    route_template: /extensions/note-tool/notes/{id}
```

这样系统搜索才能显示：

- 标题。
- 摘要。
- 插件名称。
- 跳转地址。
- 权限状态。

# 六、SQLite和云端数据后置后的规则

## 6.1 SQLite

SQLite保留为兼容和开发能力，v9不继续扩展为用户级正式存储体系。

适用范围：

- 插件开发。
- 单机部署。
- 临时缓存。
- 示例插件。
- 离线插件实验。
- 现有插件兼容。

不推荐用于：

- 多实例CampusOS。
- 多用户共享业务。
- 大量数据。
- 需要统一检索的数据。
- 需要高可用的数据。
- 需要跨节点灰度的数据。

v9规则：

```text
新插件默认不得选择SQLite
现有SQLite插件继续兼容
生产环境显示单实例警告
多实例模式可以阻止启用SQLite插件
```

现有SQLiteKV可以在后续提供迁移工具：

```text
SQLite plugin.db
→ CampusOS Plugin Data Service
```

## 6.2 外部云存储或云数据库

云端存储后置到v10或独立版本。

未来可以支持：

```yaml
storage:
  provider: external
  adapter: plugin-defined
```

但外部数据一旦不经过CampusOS托管，CampusOS默认只能知道：

- 插件使用了外部存储。
- 存储服务状态。
- 数据大致规模。
- 插件声明的同步状态。

CampusOS无法直接知道：

- 外部数据具体内容。
- 外部数据库表结构。
- 数据是否完整。
- 数据是否被插件外部修改。
- 如何执行全局检索。

因此未来外部存储要接入系统搜索，必须实现标准接口：

```go
type PluginSearchProvider interface {
    Search(ctx context.Context, request SearchRequest) (*SearchResultPage, error)
}
```

或者将索引摘要同步到CampusOS：

```text
外部数据保留在云端
索引元数据同步到CampusOS
```

该能力不进入v9硬性范围。

# 七、插件数据可见性和用户控制

用户可以在用户插件中心查看：

- 插件保存了多少条记录。
- 插件占用了多少存储空间。
- 插件保存了多少文件。
- 数据最后更新时间。
- 是否进入系统搜索。
- 是否使用外部服务。
- 数据保留策略。
- 停用插件后是否保留数据。

用户可以执行：

```text
导出个人插件数据
删除个人插件数据
清除插件缓存
撤销个人权限
停止插件继续写入数据
```

但用户不能：

- 直接进入插件数据库。
- 执行SQL。
- 修改插件内部系统记录。
- 访问其他用户数据。
- 删除管理员要求保留的审计记录。

# 八、插件卸载和数据生命周期

插件代码状态与数据状态必须分离：

```text
插件停用 ≠ 删除数据
插件卸载 ≠ 删除用户数据
```

建议卸载流程：

```text
管理员停用插件
→ 停止新数据写入
→ 导出或创建数据快照
→ 卸载插件代码
→ 插件数据进入保留状态
```

数据删除必须是独立操作：

```text
保留
归档
导出后删除
立即删除
```

用户个人数据可以由用户删除，但系统审计和平台治理数据按管理员策略保留。

# 十二、v9最终存储定义

v9对插件数据能力的正式定义应为：

> CampusOS v9中的插件数据默认由系统统一托管。结构化数据通过受控Host Storage API保存到CampusOS管理的数据库，用户文件通过受控文件API保存到用户在系统中的个人空间。插件负责业务逻辑和面向用户的操作界面，CampusOS负责权限、隔离、存储、配额、审计、备份和基础检索。SQLite、插件自有数据库及外部云存储作为兼容或未来扩展能力，不作为v9主交付范围。

最终闭环：

```text
管理员安装插件
→ 管理员批准数据和文件权限
→ 用户启用插件
→ 用户授权个人数据
→ 插件调用Host API
→ CampusOS保存到用户命名空间
→ 用户通过插件界面CRUD
→ CampusOS执行权限、审计和基础索引
→ 用户可导出或删除个人插件数据
```

这一方案可以显著降低v9实现复杂度，同时保留未来扩展SQLite、云数据库、对象存储和远程Search Provider的接口空间。

本次调整后，SQLite和云端插件数据从原P0/P1范围下调为P2，系统托管结构化数据、用户空间文件、基础检索以及PC/移动端响应式适配成为v9主路径。
