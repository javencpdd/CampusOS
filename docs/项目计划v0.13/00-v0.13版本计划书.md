## 1. 计划结论

v0.13 不继续横向增加大量业务模块，也不重写已经形成的模块化单体。该版本只承担一条主线：

> 将 v0.12 已建立的可信账号、分层社区、结构化内容和可靠任务，从“功能可用”推进到
> “性能有边界、故障可定位、外观资源强制双端交付、管理平面可运营、高风险登录可加强”。

实施顺序为：

```text
v0.12 Final 闭环
  -> v0.13 基线与容量画像
  -> 结构化列表批量读取
  -> 统一错误合同
  -> Observability Core 与 Prometheus 导出
  -> 可靠任务运营闭环
  -> 系统主题和个人主页风格包强制双端交付
  -> 管理员准入生命周期
  -> TOTP MFA 与受控恢复
  -> 容量回归和 Final
```

标准 MCP Server、标准 protobuf gRPC、OAuth/OIDC、Passkey、分布式 Session/限流、
多节点 Worker、完整 Agent 产品和真实第三方消息 Adapter 不进入 v0.13 承诺。它们需要独立威胁模型、
协议版本和部署验证，不能借本次可运营性改造顺带开放。

## 2. 输入审查与当前事实

### 2.1 思路文件的适用边界

`CampusOS v0.13 产品计划思路.md` 的正文实际是 2026-07-17 对 v0.12 计划的审查对话，标题、迁移规划、
阶段和验收内容均指向 v0.12。该文件作为需求来源和历史推理保留，不覆盖、不重命名，也不直接当作 v0.13
执行清单。

本计划从该材料中继承三项原则：

1. 先解决既有链路的一致性和安全缺口，再增加新产品能力。
2. 任何高风险写入都必须有权限、审计、事务、恢复和负向测试。
3. 计划状态必须以当前代码、迁移、生成合同和可复验证据为准。

v0.13 的实际范围来自当前仓库和 v0.12 回顾中明确后置的候选项，而不是把已经完成的 v0.12 工作重新计入。

### 2.3 当前架构不需要推倒重写

v0.7-v0.12 已形成以下稳定边界：

```text
Core Modules
  Identity / Community / Moderation / User Storage / Reliability / Email Delivery / Platform

Built-in Features
  Personal Space / RichText / Schedule / Appearance / Mutual Aid / Secondhand / Integrations

External Plugin
  Manifest / Runtime / Host API / Gateway / Managed Data / Grant

Resource Package
  Theme / Homepage Pack / Space Style / Skill / Prompt / Persona Metadata
```

v0.13 只新增公开 Port、Adapter、指标和受控安全状态。External Plugin、MCP、Agent Runner 和浏览器仍不能
获得 `AppContext`、TxKernel、数据库连接、内部 Repository、JWT 私钥、CampusOS Token 或宿主完整文件系统。

## 3. 版本目标、优先级与非目标

### 3.1 P0 必须完成

1. 封闭 v0.12 Final，形成真正的 `v0.12.0` 可回退发布基线。
2. 冻结可重复的 v0.13 性能、故障和容量画像。
3. 消除 Mutual Aid、Secondhand 列表的 N+1 Detail 读取，并建立查询预算测试。
4. 建立统一错误分类、HTTP 映射、脱敏和兼容包络合同。
5. 建立始终启用的 Observability Core、低基数指标和可选 Prometheus 导出。
6. 为 HTTP、数据库连接池、Reliability Worker、Email Delivery、Session 和 Challenge 提供核心指标。
7. 让 Admin 能看到队列积压、最老事件、重试、dead-letter 和最终化失败，并有明确处置文档。
8. 将系统主题和个人主页风格包统一到机器可检查的 PC/移动端强制交付合同。
9. 新导入、采用、应用或发布的风格包未通过双端静态与浏览器验证时必须拒绝，不能只显示警告。

11. 提供 Windows/Linux 共用的 Docker 开发栈，源码热更新不依赖 Ubuntu 22.04 宿主工具链。
12. 提供单主机 Compose 镜像、随机密钥初始化、自动 migration、备份、显式确认恢复和跨主机迁移教程。

### 3.2 P1 本版应完成

1. 为独立管理员准入账号提供列表、暂停、恢复、版本冲突、原因、会话撤销和 required audit。
2. 防止暂停或撤销最后一个可用管理员，并保留受控 CLI 恢复路径。
3. 增加可选 TOTP MFA、一次性恢复码和 Session 级 MFA 状态。
4. 为管理员提供分阶段 MFA 强制策略，不在未完成注册和恢复准备时直接锁死全部管理员。
5. 完成 PC/移动端账号安全、Admin 登录和管理员账号管理流程。
6. 建立可重复容量测试和最终回归预算，防止后续版本重新引入查询放大和指标高基数。

### 3.3 P2 后续候选

## 4. 目标架构

### 4.1 可观测性边界

新增 `core.observability` 语义边界。采集始终启用，导出可配置：

```text
HTTP / Core / Feature / Runtime
  -> Observability Port
       -> bounded in-process collector
       -> Admin summary projection
       -> optional Prometheus exporter on a dedicated loopback listener
```

要求：

- Module 通过显式 `Meter`/`Tracer` Port 记录指标，不读取全局变量或注册任意回调。
- 默认仍保留 `/api/v1/metrics/summary`，其权限继续使用 `platform.metrics.read`。
- Prometheus exporter 默认关闭；开启时默认只绑定 loopback，不能复用公开业务 API 作为匿名端点。
- 指标标签只允许固定枚举、HTTP method、稳定 route operation、status class、module、consumer、provider、result。
- 禁止 user ID、email、IP、thread ID、plugin record key、完整 URL、原始错误、Token 或任意配置值成为标签。
- External Plugin 不能直接注册 Prometheus Collector；后续如开放，只能走 Host API 的固定 metric descriptor 和配额。

### 4.2 统一错误边界

保持现有成功和错误包络：

```json
{
  "code": 10004,
  "msg": "resource conflict",
  "error": {
    "code": "resource.conflict",
    "message": "resource conflict",
    "details": {},
    "request_id": "...",
    "retryable": false
  },
  "request_id": "..."
}
```

新增统一 `AppError`/`ErrorDescriptor` 和 Translator，但采用模块逐步接入：

```text
Domain/Port error
  -> module translator
  -> stable machine code + HTTP status + safe message + retry policy
  -> existing response envelope
```

规则：

1. 顶层数字 `code`、`msg`、`data` 和现有 HTTP status 在兼容期保留。
2. 未分类错误只返回 `internal.error` 和 request ID；原始错误只进入脱敏服务端日志。
3. `retryable` 由错误描述符决定，不能简单把所有 5xx 都标为可安全重试。
4. Validation details 只能包含字段名、规则和稳定原因，不包含 SQL、路径、Secret 或用户敏感数据。
5. Panic Recovery 使用同一包络，但不能把 panic 文本返回客户端。
6. SDK 增加统一错误类型，旧客户端按顶层字段处理仍可工作。

### 4.3 批量结构化读取

Mutual Aid 和 Secondhand 各自拥有 Detail 表，因此不把业务字段搬进 Community。新增模块内批量 Port：

```go
type Store interface {
    Create(context.Context, *Detail) error
    Get(context.Context, string) (*Detail, error)
    GetMany(context.Context, []string) (map[string]*Detail, error)
    Update(context.Context, *Detail, int64) error
}
```

`ListPublic` 先取得排序稳定的 Thread 页，再一次读取对应 Detail，并按 Thread 顺序组装。任何可见的类型化
Thread 缺少 Detail 时继续整页失败并记录完整性指标，不能静默返回半条记录。

查询预算至少满足：

```text
Q(max_page_size) <= Q(1) + 1
```

即查询数量不能随页面条数线性增长。列表字段、分页总数、顺序、可见性和 Feature Gate 行为保持不变。

### 4.4 管理员准入生命周期

继续保持三层模型：

```text
users/accounts                身份和凭据
identity_admin_accounts       管理平面准入
roles/permission_definitions  操作授权
```

v0.13 增加：

- 管理员账号只读列表和详情。
- `active -> suspended -> active` 的受控命令。
- 全局 admin 角色撤销继续产生 `revoked`；恢复角色后仅 `revoked` 可按策略重新激活，`suspended` 不自动恢复。
- 每次状态变更要求期望版本、非空原因、操作者、时间、required audit 和 Outbox。
- 暂停成功后在同一 Identity 可靠命令中撤销该管理员的全部 Session。
- 并发检查最后一个可用管理员；不能只在前端计数。
- CLI 恢复要求本机操作、显式确认、Bootstrap Secret 或等价部署凭据，并写 required audit；不提供匿名远程后门。

建议新增 Permission Code：

| Code | 作用 | 风险 |
| --- | --- | --- |
| `identity.admin_account.read` | 查看准入状态和非敏感认证时间 | medium |
| `identity.admin_account.suspend` | 暂停准入并撤销 Session | critical |
| `identity.admin_account.restore` | 恢复非 revoked 准入 | critical |
| `identity.admin_account.read_audit` | 查看准入状态变更审计 | high |

admin 角色默认获得这些权限；自定义角色不自动获得。操作者不能通过该页面给自己绕过角色或 MFA 策略。

### 4.5 TOTP MFA 与 Step-up

v0.13 只支持标准 TOTP 和高熵一次性恢复码。安全合同：

- TOTP Secret 使用带 key ID 的 AEAD envelope 加密，密钥只来自部署 Secret Provider，不写入数据库、日志、
  API、资源包或插件配置。
- 恢复码只显示一次，数据库只保存不可逆摘要和使用时间。
- enrollment 必须先通过现有密码/Session，再验证一次 TOTP 才进入 `active`。
- 登录密码通过后，如策略要求 MFA，只签发短期、单用途、摘要存储的 MFA Ticket；第二因子成功前不签发
  Access Token 和 Refresh Cookie。
- Session 保存 `mfa_verified_at` 和认证强度；高风险命令可要求最近一次 Step-up，而不是只相信 JWT 声明。
- TOTP 校验允许受控时钟漂移，拒绝同一时间步重放，并有独立尝试次数和速率限制。
- 关闭 MFA 需要当前密码加 TOTP/恢复码；管理员代恢复必须有独立权限、原因、required audit 和强制 Session 撤销。
- MFA 初始为可选。管理员强制策略采用 `off -> enrollment_grace -> required`，只有至少两个可恢复管理员或
  已验证的 CLI 恢复路径时才允许进入 `required`。

不允许把邮箱验证码当作第二因子，也不允许 External Plugin、Agent 或 Resource Package读取 MFA Secret。

### 4.6 Appearance 强制双端交付边界

“双端”在本计划中明确指用户前台的 PC 与移动 Web，不表示同一主题进入 Admin。系统主题仍只作用于
`target: web`，个人主页风格仍只作用于 `/u/:username` 的主页根节点。

| 包类型 | 作用范围 | 供给与选择 | 双端验收重点 |
| --- | --- | --- | --- |
| 系统主题 | 除 Admin 外的完整用户前台 App Shell 和页面内容 | 管理员提供；用户从已通过筛查的目录中选择 | Shell、导航、首页、列表、详情、表单、课表、个人主页外壳、弹层和错误状态 |
| 个人主页风格包 | 主页所有者的资料区、头像、元信息、介绍、帖子列表、标签和空状态 | 管理员提供内置包或用户上传个人包；访问者始终看到主页所有者应用的风格 | 所有者/访客、长昵称、长标签、有帖/空状态、加载/错误、公开可见性和头像 |

#### 4.6.1 交付合同

现有 `page-style-pack.v1`、`campusos.app-style-pack.v2` 和 `viewport_support` 继续兼容读取。A5 新增与
业务 schema 解耦的交付合同，建议结构如下，最终字段名由合同测试确定：

```yaml
delivery_contract: campusos.appearance-delivery/v1
viewport_support:
  desktop: true
  mobile: true
  mobile_breakpoint: 720px
preview_images:
  desktop: preview-desktop.png
  mobile: preview-mobile.png
```

强制规则：

1. `desktop` 和 `mobile` 必须同时为 `true`，断点必须是受限像素值。
2. 可以用同一套响应式 HTML/CSS，也可以提供端侧覆盖文件；双端交付不强制复制两套源码。
3. CSS 必须有宽度媒体查询或等价的容器查询，并继续满足目标根选择器、安全 CSS 和资源声明规则。
4. 必须提供 PC 与移动端两张真实预览；单张旧 `preview.png` 只作为兼容别名，不能满足 v0.13 新发布要求。
5. 动效包必须提供 `prefers-reduced-motion` 降级；关闭动态效果后页面仍完整可用。
6. 文字、背景、图片遮罩和内容表面必须满足正文 4.5:1、大字和必要 UI 3:1 的最低对比度。
7. 用户可配置背景、文字、字距、页边距和宽度时，每次应用配置都重新执行值域、资源和对比度检查。

#### 4.6.2 静态与渲染双门禁

静态校验负责 manifest、路径、大小、checksum、HTML/CSS/JS 安全、能力、响应式声明、预览、配置 schema、
对比度 token 和 reduced-motion 规则。渲染校验使用真实 Web App Shell 和个人主页组件验证：

```text
PC hard profile       1440 x 1000
Mobile narrow         320 x 568
Mobile hard profile    390 x 844
Mobile landscape       852 x 393
Bridge regression      768 x 1024
```

PC 和 Mobile 是所有新包的发布硬门；仓库内置包进一步固定执行 320 窄屏、852 横屏和 768 过渡宽度，
用于发现断点两侧及低高度触控设备的破损。至少检查：

- 无横向溢出、文字裁切、控件重叠、不可达内容或动态内容导致的布局跳变。
- Header、Navigation、PageOutlet、Safety、登录/用户菜单和必要错误提示没有被隐藏或遮挡。
- 键盘焦点可见，移动端主要触控目标不小于 44px，安全区域和软键盘场景不遮挡操作。
- 默认配置、背景图开启/关闭、高风险文字背景组合、长文本、空/错/加载和弹层状态可用。
- 动效层不接收点击、不覆盖正文；reduced-motion 下不创建特效运行环境。
- 系统主题覆盖代表性页面矩阵，个人主页包覆盖所有者和访客矩阵，而不是只验证设置页。

v0.13 实际交付的受控渲染门禁是 `release-check` 调用的固定 Playwright 矩阵：只遍历仓库内置包，只连接
loopback 候选服务，使用受控测试账号和固定页面/视口，不接受任意包路径、外部 URL、数据库连接、JWT 私钥
或用户 Token。矩阵证据与当前仓库资源 checksum、版本和截图目录共同复核，源包变化必须重新运行门禁。

早期方案中的“服务端按每个第三方上传包启动通用浏览器 Runner、持久化 checksum 证明并产生
`pending-validation`”未在 v0.13 实现。没有进程/容器隔离、资源配额和可信证明存储前，将浏览器执行器嵌入 API
进程会扩大宿主文件系统和代码执行风险，因此 Final 审计将其明确后置。v0.13 对动态上传包执行严格静态安全、
双端声明、双预览、对比度和 reduced-motion 硬门，但不得把该结果描述为已完成真实双端渲染认证。

#### 4.6.3 导入、应用与兼容状态

严格静态验证必须进入 `campusosctl resource inspect/adopt`、目录扫描、zip 导入、个人主页上传、应用、导出
和发布门禁；仓库内置包还必须进入真实浏览器发布矩阵。v0.13 实际提供的状态包括：

```text
valid            严格静态合同通过，可以选择和应用
invalid          任一硬门失败，不进入可应用目录
legacy-readonly  历史包可继续读取/导出，不能新发布或重新选择
```

`pending-validation` 保留为未来通用隔离 Runner 的候选状态，v0.13 API 不返回该状态。只有仓库发布门禁同时
通过真实 PC/Mobile/窄屏/横屏/Bridge 浏览器矩阵时，才能在发布文档中声明该内置包具有双端实渲染证据。

- 已经应用的历史包不得在升级瞬间导致用户页面不可访问；运行失败时回退 Core 默认主题并保留诊断证据。
- 新导入、新采用、新应用和新发布从 v0.13 起全部使用严格模式，不允许以兼容 warning 绕过。
- `aurora-campus`、`campus-canvas`、`campus-hero`、`clean-blog`、`kinetic-journal` 必须在 Final 前迁移到严格合同并生成
  两张预览；仓库内置包不能使用 `legacy-readonly` 通过发布。
- 管理员提供的源包继续只保存于 `data/resources/themes/` 和 `data/resources/space-style-packs/`；用户上传包
  只能通过 Personal Space/User Storage 保存其受控编译结果和归属数据。两者都不得进入 `data/plugins/`
  或 `data/plugin_data/` 伪装成业务插件。

## 5. 数据、API 和兼容规划

### 5.1 Migration 规划

| Migration | 计划内容 | 兼容原则 |
| --- | --- | --- |
| `000039_v13_admin_admission_operations` | 管理员准入原因、状态变更操作者/时间、必要索引和新增权限定义 | 旧二进制忽略新增列；不复制凭据，不删除角色 |
| `000040_v13_identity_mfa` | MFA method、MFA challenge、恢复码摘要、Session MFA 时间和策略 | 默认不强制；旧账号和旧 Session 在策略未开启时保持可用 |

批量查询、统一错误、指标和 Appearance 双端合同不要求 migration。资源包 manifest、预览和 checksum
使用文件级兼容迁移；不得为了指标建立无界明细日志表，Prometheus 时序数据属于外部监控系统，不写入
CampusOS 核心数据库。

### 5.2 API 变化

所有 API 采用加法变更。预计新增：

```text
GET  /api/v1/identity/admin-accounts
GET  /api/v1/identity/admin-accounts/:user_id
POST /api/v1/identity/admin-accounts/:user_id/suspend
POST /api/v1/identity/admin-accounts/:user_id/restore

GET    /api/v1/auth/mfa
POST   /api/v1/auth/mfa/totp/enrollment
POST   /api/v1/auth/mfa/totp/confirm
DELETE /api/v1/auth/mfa/totp
POST   /api/v1/auth/mfa/recovery-codes/rotate
POST   /api/v1/auth/mfa/login/complete
POST   /api/v1/auth/mfa/step-up
```

路径可在实现阶段按现有路由所有权调整，但必须满足：

- 生成 Route Operation、Permission Code、OpenAPI schema 和 SDK 类型。
- 管理员准入写入只在 Admin audience 下开放。
- 用户 MFA 管理要求登录、CSRF 和重新认证；登录完成端点只接受短期 MFA Ticket。
- 旧 `/auth/login` 和 `/auth/admin/login` 请求结构保持兼容。需要 MFA 时返回稳定的 challenge 状态，而不是
  先签发完整 Session 再提示。
- 不删除现有 `/metrics/summary`；Prometheus scrape 不进入公开 `/api/v1` 产品合同。
- Appearance 校验、目录和运行包 API 只增加交付状态、双端预览及验证报告字段；旧客户端忽略新字段仍可读取。

### 5.3 指标目录

首批指标必须有稳定名称、类型、单位和标签白名单：

| 领域 | 最小指标 |
| --- | --- |
| HTTP | request total、duration histogram、in-flight、response size、panic total |
| PostgreSQL | pool acquired/idle/max、acquire duration、acquire error、query budget violation |
| Reliability | pending、processing、retry、dead、oldest age、claim、complete、finalize error、lease conflict |
| Email | queued、delivered、retry、dead、provider error class、delivery duration |
| Identity | challenge accepted/limited/consumed、login result、refresh reuse、session revoke、MFA result |
| Structured Content | list duration、batch size、missing detail、query count budget |
| External Runtime | start/stop/error、gateway request duration；标签只使用受校验 plugin ID 和固定结果 |

不把请求路径参数、邮箱域名、用户 ID、错误文本或第三方 endpoint 放入标签。

### 5.4 SLI 与初始 SLO

A0.5 在固定测试环境冻结基线，A3 形成以下 SLI：

- HTTP 可用性和按 Route Operation 的 p50/p95/p99 延迟。
- 注册 Challenge 接受率、限流率和邮件投递延迟。
- Outbox 最老待处理年龄、成功率、重试率和 dead-letter 数量。
- 数据库连接池等待和耗尽率。
- 结构化列表查询数、延迟和 Detail 完整性。

v0.13 不在计划书中凭空写生产阈值。A0.5 必须记录参考硬件、数据规模和流量模型；A3 再冻结具体阈值，
Final 在同一环境上要求：

1. 查询预算无回归。
2. 关键路径 p95 不比其阶段验收基线恶化超过 20%。
3. 压测期间错误率不超过已冻结预算，且没有连接池耗尽、goroutine 持续增长或队列无法收敛。
4. 每个告警都有可执行 Runbook 和一次故障注入证据。

- 保留 `legacy-readonly`，但新导入、重新选择和发布不能使用 warning 绕过。
- 出口：Go 合同测试、CLI fixture、危险 CSS/HTML/JS、缺端、缺预览和对比度负向测试全部通过。

### A6：内置风格包迁移与双端闭环

- 迁移 `aurora-campus`、`campus-canvas`、`campus-hero`、`clean-blog`、`kinetic-journal` 的交付合同、双预览和 checksum。
- 系统主题设置和个人主页风格选择提供 Desktop/Mobile 分段预览及验证结果，失败包不显示应用操作。
- Playwright 遍历全部内置包；系统主题使用代表性 App Shell 页面矩阵，个人包使用所有者/访客和内容状态矩阵。
- 固定 PC `1440x1000`、Mobile `390x844` 硬门，并对内置包增加 `320x568`、`852x393`、`768x1024`
  边界回归；检测溢出、重叠、裁切、焦点、
  触控、背景可读性、配置变体、reduced-motion 和失败回退。
- 将全包检查接入 `make release-check`，并在截图失败时保存端侧、包 ID、页面状态和 request ID。
- 出口：仓库内置系统主题和个人主页包均为 `valid`，不得以 legacy 状态发布。

### A6.3：Docker 跨平台开发、部署与迁移

- `compose.dev.yml` 支持 Windows Docker Desktop Linux Containers 与现代 Linux Docker Engine；
  Go/Node/PostgreSQL/Redis/NATS 不要求安装到宿主机。
- API 源码变化采用先构建、再 migration、成功后替换进程；Web/Admin/Docs 使用独立锁定依赖卷和轮询 HMR。
- `compose.deploy.yml` 产出 API/Web/Admin/Docs 四类镜像，API 非 root、无 privileged、无 Docker socket，
  数据库和消息服务不直接暴露公网。
- `infra/api/web/admin/docs` 各有独立 Compose 与 env 覆盖，四个 CampusOS 镜像可单独构建和启动；整体
  Compose 通过 `extends` 复用同一服务定义，不能复制形成漂移实现。
- Bash 与 PowerShell 均提供 init/build/up/logs/backup/restore/down 入口；恢复要求归档位于受控
  `backups/`、checksum 通过和显式确认。
- `.dockerignore` 不把个人空间、插件/模块数据、配置、图片或日志打入镜像；内置插件实现和资源包只作为
  缺失文件种子，不覆盖运行卷。
- 出口：开发/部署 Compose 静态合同、四镜像构建、隔离整栈健康、migration 数、API 代理、备份校验、
  docs-site 和完整 `release-check` 均通过。

### B1：管理员准入管理

- 新增 `000039`、Repository/Service Port、可靠命令、API、权限目录、Admin 独立页面和筛选。
- 暂停/恢复要求期望版本和原因；冲突返回稳定 409，不覆盖其他管理员的新状态。
- 暂停在同一命令中撤销目标管理员全部 Session，并记录 required audit、command audit 和 Outbox。
- 数据库事务内锁定并检查最后可用管理员；自我暂停也受相同保护。
- CLI 恢复有本机确认、部署凭据、审计和恢复后强制改密/MFA 提示。
- 出口：角色、准入、Session 和权限四者组合测试通过；版主 scope 不受影响。

### B2：TOTP MFA Core

- 新增 `000040` 和独立 Identity Port，不把 Secret 放进 `accounts` credential 文本或普通配置。
- 实现 enrollment、confirm、login complete、step-up、disable 和 recovery code rotate/consume。
- MFA Ticket 单用途、短期、摘要存储；并发只能消费一次，错误尝试和重放受限。
- Secret Protector 支持 key ID 和轮换读取；缺少部署密钥时 MFA 功能 fail closed，但普通未强制账号保持可登录。
- 管理员恢复命令必须撤销 Session 并通知账号所有者，不返回旧 Secret 或恢复码。
- 出口：时钟漂移、重放、并发、恢复码一次性、密钥缺失、轮换和日志泄露负向测试通过。

### B3：MFA 产品闭环

- Web 账号安全页提供启用、二维码/手工密钥确认、恢复码一次显示、轮换和关闭。
- Admin 登录页支持密码成功后的第二步，不把 MFA Ticket 存入长期 Local Storage。
- Admin 提供策略状态、enrollment 覆盖率和 grace 配置；不显示 Secret、恢复码或完整个人标识。
- `required` 切换前执行影响预览和最后管理员恢复检查；有版本冲突和 required audit。
- PC、手机、键盘操作、超时、刷新、返回、错误码和网络重试均有回归。
- 文档说明时间同步、丢失设备、恢复码、CLI 恢复和禁用后的 Session 处理。

### C0：容量与回归门禁

- 将 A0.5 负载画像固化为可重复命令和 CI 可执行的轻量预算检查；长稳测试在发布环境执行。
- 覆盖公开列表、结构化列表、登录/Refresh、Challenge 限流、可靠 Worker、Admin 查询和指标导出。
- 增加 SQL 查询预算、连接池等待、队列年龄、内存/goroutine 和前端 bundle 预算。
- 不以提高默认连接数、关闭限流、缩短审计或删除安全校验作为优化手段。
- 出口：同环境关键 p95 回归不超过 20%，无查询预算、高基数、资源泄露或可靠性收敛失败。

### Final：v0.13 全链路验收

- 空库安装、v0.12.0 历史副本升级、`000039-000040` up/down/up、备份恢复和冷启动通过。
- 运行完整 Go、Web、Admin、docs-site、SDK、合同、架构、可靠性、数据库和发布门禁。
- 浏览器完成结构化列表、错误展示、指标页、管理员暂停/恢复、MFA enrollment/login/recovery 的 PC/移动端流程。
- 浏览器遍历全部内置系统主题和个人主页包的 PC/移动硬门、过渡视口、配置变体和回退流程。
- 演练 Worker 停止、SMTP 失败、Prometheus exporter 关闭/开启、最后管理员保护、MFA key 缺失和 Ticket 重放。
- 完整 `make release-check` 通过后才切换版本并撰写 v0.13 回顾与 v0.14 进入条件。

## 8. Definition of Done

每个阶段必须同时满足：

1. 定向单元、合同、集成、并发和负向测试通过。
2. `GOCACHE=/tmp/campusos-go-cache go test ./... -count=1` 通过。
3. `make contracts-check`、`make architecture-check`、`make reliability-check`、`make docs-links` 和
   `git diff --check` 通过。
4. 涉及前端时执行对应 lint/test/build；涉及 SDK 时执行 Go/TypeScript SDK 测试或构建。
5. 涉及数据库时执行 preflight、schema contract、数据 audit、up/down/up、历史升级和恢复验证。
6. API、Route Operation、Permission Code、错误码、指标、配置、Secret 和数据变化均已记录。
7. 兼容路径和回滚/forward-fix 路径经过实际验证，不只写在文档中。
8. 对应 `docs/进度/v0.13-dev/v0.13.X-dev.md` 已新增，计划中的实现状态和验收状态分别同步。
9. 涉及系统主题或个人主页风格包时，全包双端静态/渲染门禁和双预览生成通过；单端 smoke 不算完成。
10. 涉及 Docker 时，Windows/Linux 共用 Compose 可渲染，开发/部署镜像可构建，隔离整栈健康和主机迁移
    文档可复验；仅 `docker compose config` 通过不算完成。

证据不完整时只能标记“实现中”或“待验收”。单元测试通过不等于数据库、浏览器、恢复或发布验收通过。

## 10. 兼容、发布与回滚

1. v0.12 Final 是硬前置。v0.13 分支可以编写计划和测试工具，但不能在未发布 v0.12 时宣称 v0.13 功能完成。
2. 所有数据库变化只追加。生产优先 forward-fix，down migration 只用于隔离演练。
3. 批量 Detail 读取不改变 API DTO、顺序、分页和错误语义。
4. 统一错误合同保留顶层旧字段；machine code 只做加法和稳定化，不静默复用为不同含义。
5. Prometheus exporter 默认关闭；回滚时可关闭导出但保留核心计数，不影响业务请求。
6. 已应用旧风格包可在兼容期继续读取；新选择严格失败时回退 Core 默认主题，不删除用户偏好或源包。
7. 双端合同只改变资源校验和发布状态，不把资源包变成插件，也不移动到 `data/plugins`/`plugin_data`。
8. 管理员暂停/恢复回滚时保留状态和审计；不能通过删表或直接改 `user_roles` 恢复访问。
9. MFA 强制策略可先回退到 `off`/grace，但已存 Secret 和恢复码不删除；回退旧二进制前撤销强制用户的
   相关 Session 并进入维护窗口。
10. 任何回滚都不得恢复明文 Secret、放宽 Session 校验、删除 required audit、跳过最后管理员保护或自动重放
   dead-letter。
11. Docker 日常 `down` 不删除命名卷；迁移时 PostgreSQL/`data/` 归档和 `.env.docker` 分开保存，源实例保留
    到恢复验收完成。

## 12. 风险登记

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| v0.12 未封版就开始 v0.13 | 基线漂移、修复归属不清 | G0 硬阻断，版本和证据分目录 |
| 指标标签高基数 | 内存/时序存储爆炸，泄露用户信息 | 固定标签白名单、负向测试、运行时拒绝未知标签 |
| Prometheus 端点暴露 | 泄露内部拓扑和流量 | 默认关闭、独立 loopback、部署层认证/代理、无业务明细 |
| 统一错误造成兼容破坏 | 旧前端错误提示失效 | 保留旧顶层字段，按模块迁移，合同快照和 SDK fallback |
| 批量查询掩盖缺 Detail | 返回半条业务记录 | 缺失即整页稳定失败、完整性指标和数据 audit |
| 暂停最后管理员 | 管理平面锁死 | 事务锁、最后可用管理员检查、受控 CLI 恢复和演练 |
| MFA Secret 泄露 | 管理员账号接管 | AEAD envelope、key ID、日志扫描、API 永不回读 Secret |
| MFA 强制过早 | 所有管理员被锁定 | grace、覆盖率预览、至少两个恢复主体或 CLI 恢复门禁 |
| TOTP 重放/暴力尝试 | 第二因子被绕过 | last accepted step、短期 Ticket、限流、一次性恢复码 |
| 只声明双端但实际单端破损 | 导入成功后在手机或 PC 无法使用 | 静态加真实渲染双门禁，全包而非单示例遍历 |
| 背景与文字配置产生低对比度 | 内容不可读、无障碍失败 | token 和每次用户配置复验、遮罩/表面要求、浏览器状态矩阵 |
| 严格模式使历史主页失效 | 用户页面突然回退或不可访问 | `legacy-readonly`、保留偏好、Core 默认回退、内置包先迁移 |
| 压测伤害开发/生产数据 | 数据污染或服务不可用 | 隔离数据库、生成数据、显式环境保护和清理核对 |
| 为性能移除安全校验 | 越权、审计缺失、数据损坏 | 查询/指标优化不得改变权限、事务和内容安全路径 |
| 把可变数据或 Secret 打进镜像 | 镜像泄露、迁移覆盖用户数据 | `.dockerignore`、缺失文件种子、命名卷和独立 `.env.docker` |
| 把单主机 Compose 误称高可用 | 故障恢复预期错误 | 明确单 API/单主机边界，TLS、HA、异机监控由部署层完成 |
| Windows 绑定挂载或换行不兼容 | HMR/脚本失败 | Linux Containers、轮询监听、锁定依赖卷和 `.gitattributes` |

## 13. 禁止事项

- 禁止一次性重写 Identity、Reliability、Community、Router 或所有 Handler。
- 禁止把模块化单体拆成大量微服务，或引入反射式自动装配和全局 Service Locator。
- 禁止修改 `000001-000038` 历史 migration，删除旧 API、旧错误字段、旧数据或兼容 Manifest。
- 禁止用缓存掩盖 N+1，却不建立查询预算和失效规则。
- 禁止把用户 ID、邮箱、IP、资源 ID、URL、错误文本、Token 或 Secret 放入指标标签。
- 禁止公开匿名 Prometheus 端点，或让 External Plugin 注册任意指标和标签。
- 禁止以 `viewport_support: true` 的自我声明代替真实 PC/移动渲染验收。
- 禁止新导入、重新应用或发布单端风格包，也禁止用 legacy warning 绕过严格门禁。
- 禁止让系统主题进入 Admin，或让个人主页包逃出 `.public-space[data-campusos-space]` 修改全局页面。
- 禁止把管理员资源包或用户上传风格数据保存到 `data/plugins` 或 `data/plugin_data`；前者属于
  `data/resources`，后者必须通过 Personal Space/User Storage 管理。
- 禁止通过前端按钮隐藏代替后端管理员准入、Permission、MFA 或最后管理员检查。
- 禁止明文保存或导出 TOTP Secret、恢复码、CampusOS Session/Access/Refresh Token、JWT 私钥。
- 禁止把邮箱验证码当 MFA，或让 Agent/Plugin/MCP 读取 MFA/Session 内部状态。
- 禁止自动删除、自动重放或静默修复 dead-letter；恢复必须有权限、原因和审计。
- 禁止为了压测结果提高无限连接数、关闭限流、跳过审计、弱化路径/配额/内容清洗。
- 禁止把 MCP-like、`runtime: grpc` 或 Message Local 宣称为标准生产协议。
- 禁止把 Docker socket、privileged、宿主根目录或数据库凭据交给 API、插件和开发前端容器。
- 禁止将 `compose.dev.yml`、固定开发密钥或开发管理员用于公网和共享生产环境。
- 禁止把单主机 Docker 交付描述为自动 TLS、高可用、多节点或跨区域容灾。

## 14. 最终验收定义

6. 可靠任务故障能够被指标和 Admin 页面定位，恢复后队列可收敛且不破坏 Receipt/审计。

10. 最后可用管理员不能被并发暂停；CLI 恢复已在隔离环境演练。
11. TOTP MFA、恢复码、MFA Ticket 和 Step-up 满足加密、一次性、限流、重放和恢复合同。
12. 普通用户兼容登录不被默认强制 MFA 破坏；管理员强制策略有 grace 和防锁死门禁。
13. migration、数据库审计、恢复、冷启动、PC/移动端浏览器、容量和完整 `make release-check` 通过。
14. 应用、SDK、OpenAPI、docs-site、README、架构、帮助和进度文档统一到 `v0.13.0`。
