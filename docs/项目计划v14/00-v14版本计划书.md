## 0. 执行摘要

v0.14.0 的版本主题确定为：

> **学期治理与个人工作区基础。**

本版不再横向堆叠互不相关的功能，而是围绕一条连续的数据主线交付三项能力升级：

1. 将个人课表从“用户任意输入年份和学期”改为“管理员维护 AcademicTerm 目录，用户在受管学期内创建、
   导入、编辑和查看自己的课表”。
2. 将当前以安全目录、目录遍历计量和进程内互斥为主的 User Storage，提升为具有对象元数据、所有权、
   配额预留、故障恢复和 Provider 边界的对象服务。
3. 在对象服务之上新增 Built-in Feature `feature.personal-documents`，交付私有文档、不可变版本、安全下载、
   TXT/Markdown/CampusDoc 编辑以及受条件约束的 PDF/DOCX 预览。

这三项并不是平行的三个孤立项目。Storage Object Layer 是课表存储迁移和 Personal Documents 的共同基础；
AcademicTerm 负责业务治理；Personal Documents 用于验证对象服务是否真正能承载高价值用户数据。

v14 仍保持模块化单体、PostgreSQL、Local Provider 和单主机 Docker 的现行边界。本版不实现远程对象存储、
跨用户文件共享、完整 Office 在线编辑、标准 MCP、远程插件市场、多节点高可用或 Agent Runner。

### 0.1 v0.14-dev 实施快照（2026-08-29 13:47）

- `000044-000049` 已实际追加：AcademicTerm、对象/账户/Reservation、用户课表学期引用、个人文档/版本/预览状态、早期开发库对象约束名称兼容，以及课表对象绑定/查看偏好。
- 管理员学期管理、受管课表 Guard、兼容 JSON + immutable Object 双写、对象原子写与并发预留、个人文档 Web/API MVP、历史课表采用和对象对账 CLI 已实现并有定向 Go/迁移证据。
- Converter 示例部署只提供强制隔离合同；没有经审查 Runner 时 API 明确降级为 `converter_unavailable`。Windows Docker Desktop 已完成实际全量 Go、隔离 migration/DB+文件恢复和认证浏览器工作流验证；Linux 目标环境 release-check、跨主机浏览器证据和正式发布审查仍待完成，不得将本开发阶段写成 v0.14 Final。

### 1.1 当前已经具备的能力

| 范围 | 当前实现 | v14 的处理原则 |
| --- | --- | --- |
| 版本 | 应用版本为 `v0.13.0` | G0 冻结 v14 起点，不提前修改运行版本 |
| 数据库 | migration 已到 `000043_v13_post_parent_floor` | 新 migration 从 `000044` 顺序追加，不改写历史文件 |
| User Storage | `core.user-storage` 提供 `Root/EnsureLayout/Path/Usage` 和配额接口 | 保留为兼容 Adapter，新业务只依赖 Object Port |
| 配额 | 默认 50 MiB；`000042` 已提供管理员逐用户配额覆盖 | 不重复建设配额授权；补充持久用量、Reservation 和并发一致性 |
| 图片 | 头像和内容图片已有压缩；单进程用互斥保护部分写入 | 纳入对象登记和一致性检查，保留旧 URL 兼容 |
| 课表 | 每个用户每学期一个 JSON，另有 `index.json` 记录激活学期 | 历史 JSON 保留并登记；新写入通过 AcademicTerm 和 Object Port |
| 富文本 | RichText Article 有 ContentJSON、Sanitizer、Render、资产和 Community Thread 生命周期 | 抽取通用编辑/清洗能力，不让个人文档变成帖子 |
| Reliability | 事务命令、Outbox、lease/fencing、receipt、retry、dead-letter 已存在 | 预览只发布对象 ID/版本 ID 事件，转换器不进入 API 主进程 |
| Personal Space | 已有主页、内容、头像历史、样式和存储状态 | 新增“我的文档”入口，不重写现有个人主页 |
| Docker | Windows/Linux 共用 Linux Container 开发和单主机交付 | 可选 Converter 也必须遵守无网络、非特权、资源限制合同 |

### 1.2 已确认的实现缺口

| 缺口 | 代码事实 | 风险 |
| --- | --- | --- |
| 用户可自由创建学期 | `ScheduleView.vue` 暴露年份输入；`ActivateTerm` 可为任意合法年份创建 JSON | 绕过平台教学周期，历史与当前学期不可治理 |
| 存在时间推断 | Schedule Service 在缺少数据时按当前日期推断 spring/fall，并用当前周一生成第一周 | 系统行为不受管理员配置控制 |
| 课表写入非原子 | 课表和激活索引最终使用直接 `os.WriteFile` | 崩溃或磁盘故障可能留下截断文件 |
| 配额是“扫描后判断” | `Usage()` 每次遍历用户目录；多数调用先检查、后写入 | 多进程并发可超额，目录规模增长后延迟不可控 |
| 业务可获取绝对路径 | 当前 Storage Port 向 Feature 暴露 `Path()` | Provider 无法替换，业务与本机目录布局耦合 |
| 文件元数据分散 | RichText 资产有数据库行；头像、内容图片、课表主要依赖目录和 URL | 无法统一 Stat/List/审计/校验，备份后难以核对一致性 |
| 富文本和帖子耦合 | RichText Article 创建、发布、下架均同步操作 Community Thread | 不能直接作为私有文档服务复用 |
| Reliability 不是任意进程沙箱 | Worker 能可靠分发事件，但当前不会限制第三方转换器 CPU/RAM/网络 | 不能把 LibreOffice 等直接塞进 API/Worker 进程 |

### 1.3 规划输入的必要修正

1. 原思路中的“42 个 migration”已过时，规划基线必须按 `000001-000043` 处理。
2. 50 MiB 默认空间和管理员逐用户调整已在 v13 后续实现，v14 不再把它列为新增功能。
3. 当前 User Storage 不是完全无并发保护：内容图片和头像有进程内互斥；真正缺口是数据库级预留、
   多进程一致性和故障后的元数据/文件对账。
4. RichText 可复用的是 ContentJSON、Sanitizer 和 Render 能力，不是 Article/Thread 生命周期。
5. Reliability 可承载预览请求、重试和 dead-letter，但外部 Converter 必须另设隔离执行边界。
6. v13 之后又产生了业务修复和 `000043`；G0 必须先修正文档、Skill 快照、架构视图和基线文件的漂移，
   不能把旧审计中的数字直接复制为 v14 证据。

## 3. 目标架构与所有权

```text
Web Schedule ───────┐
                    ├─> feature.personal-schedule ─> AcademicTerm Core
Admin Term Console ─┘                 │
                                      └─> User Storage Object Port

Web Personal Documents ─> feature.personal-documents ─┬─> Content Editor Core
                                                       ├─> User Storage Object Port
                                                       └─> Reliability Outbox
                                                               │
                                                               └─> Isolated Converter（可选）

User Storage Object Port ─> PostgreSQL metadata/quota ledger + Local Provider files
```

### 3.1 模块归属

| 能力 | 所有者 | 依赖 | 禁止依赖 |
| --- | --- | --- | --- |
| AcademicTerm | `core.academic-term` | Identity Permission、Reliability、PostgreSQL | Schedule 的 JSON Store、Web UI |
| User Storage Object | `core.user-storage` | Identity、PostgreSQL、Provider Adapter | Personal Space/RichText/Schedule 具体 Service |
| Content Editor Core | `core.content-editor` | 纯 schema/sanitize/render 能力 | Community Thread、Document Repository |
| Personal Schedule | `feature.personal-schedule` | AcademicTerm、User Storage、Feature Registry | 绝对路径、自由时间推断 |
| Personal Documents | `feature.personal-documents` | Identity、User Storage、Content Editor、Reliability、Feature Registry | Community Repository、公开静态目录 |
| Converter Runner | 独立可选进程/容器 | 受限对象输入、受限输出、任务 ID | 数据库凭据、JWT、网络、宿主目录 |

AcademicTerm 被定义为 Core，是因为它是学校级目录事实，未来可能被日历、活动或教学服务复用；Schedule 仍是
Built-in Feature。Personal Documents 第一版也是 Built-in Feature，因为其所有权、配额、版本和预览与核心
安全边界紧密耦合，不适合作为拥有宿主路径的 External Plugin。

### 3.2 不改变的边界

- 继续使用模块化单体，不为了 Converter 把所有模块拆成微服务。
- External Plugin 仍只能使用公开 Host API/Gateway，不得到 Storage Provider、数据库或文档原文。
- Feature Disable 只关闭路由和运行能力，不删除 AcademicTerm、对象、课表、文档或版本。
- 本版只实现 Local Provider；Object Port 的存在不等于 S3 已经可用。

## 5. F1：User Storage Object Layer

### 5.1 Object Port

新业务只消费稳定的对象接口，示意合同如下：

```go
type ObjectPort interface {
    Put(ctx context.Context, ownerID string, input PutRequest) (Object, error)
    Open(ctx context.Context, actorID, objectID string) (ObjectReader, Object, error)
    Stat(ctx context.Context, actorID, objectID string) (Object, error)
    Delete(ctx context.Context, actorID, objectID string, expectedVersion int64) error
    List(ctx context.Context, ownerID string, filter ObjectFilter, page PageRequest) (ObjectPage, error)
}
```

合同要求：

- DTO 只返回 Object ID、业务文件名、MIME、字节数、hash、状态和时间，不返回 `storage_key` 或绝对路径。
- Owner 检查在服务端完成；跨用户访问统一按不存在处理，避免泄露对象是否存在。
- `purpose` 和固定的 `visibility` 由受信 Built-in Feature 指定，用户不能把私有文档改成公开对象。
- Provider Adapter 才能解释 `storage_key`；Feature 不能调用 `os.*` 或拼接 User Storage 路径。
- `Put` 支持已知最大字节数和流式输入，不允许无界 `io.ReadAll`。

### 5.2 数据模型

计划追加以下表，最终字段以 migration 评审为准：

| 表 | 关键字段 | 约束与用途 |
| --- | --- | --- |
| `storage_objects` | `id`、`owner_user_id`、`namespace`、`purpose`、`provider`、`storage_key`、`original_name`、`mime_type`、`size_bytes`、`sha256`、`status`、`version`、时间 | `(provider, storage_key)` 唯一；size 非负；状态 CHECK；软删除 |
| `user_storage_accounts` | `user_id`、`used_bytes`、`reserved_bytes`、`version`、时间 | 单用户一行；两类字节非负；事务锁定 |
| `user_storage_reservations` | `id`、`user_id`、`object_id`、`reserved_bytes`、`status`、`expires_at`、时间 | 显式记录预留、提交、释放和过期回收证据 |

对象状态至少包括：

```text
pending -> ready -> deleting -> deleted
             └──> quarantined
pending/ready ───> missing（只由对账器标记，不自动伪造文件）
```

### 5.3 本地 Provider 写入协议

1. 校验 owner、namespace、purpose、原始文件名和请求上限。
2. 在数据库事务中锁定 `user_storage_accounts`，核对 `used + reserved + incoming <= quota`。
3. 建立 Reservation 和 `pending` 对象；提交后才开始物理写入。
4. 将流写入同一文件系统下不可公开的 staging 目录，同时计算真实字节数和 SHA-256。
5. 校验 MIME、扩展名、内容结构、剩余磁盘空间和真实大小；不信任客户端 Content-Type。
6. `fsync` 文件后执行同文件系统原子 rename，再把对象更新为 `ready`、Reservation 转为 `used`。
7. 任一步失败都尝试清理 staging 并释放 Reservation；进程崩溃留下的中间态由对账任务恢复。

数据库和文件系统无法组成单一 ACID 事务，因此本文不声称“绝对不会产生中间态”。正确实现是可检测、可重试、
可对账的状态机，而不是用一次 `os.WriteFile` 模拟跨介质事务。

### 5.4 对账与孤儿处理

提供只读默认的 `campusosctl storage reconcile --dry-run`，至少报告：

- `pending` 超时、Reservation 过期；
- metadata ready 但物理文件缺失；
- 物理文件存在但无 metadata；
- hash/size 不一致、非法 owner 目录、符号链接、越界路径；
- account ledger 与对象合计不一致；
- legacy 未分类文件。

修复必须使用显式 `--apply`、权限、原因和审计。未知文件移入用户目录内的 quarantine 也属于写操作，不能在
启动时自动执行。任何对账都不得沿符号链接遍历宿主其他路径。

### 5.5 旧数据采用策略

采用 `shadow -> dual -> enforce` 三阶段：

1. **Shadow**：扫描 `data/personal-space/<user_id>/`，只生成报告；目录遍历仍是配额事实来源。
2. **Dual**：为头像、内容图片、RichText 资产、课表和其他已识别文件登记对象；旧 URL/JSON 读取继续有效。
3. **Enforce**：对象账户成为新写入的配额事实；旧读路径只作为有期限兼容 Adapter。

未识别文件登记为私有 `legacy.unclassified`，仍计入配额但不暴露下载入口。v14 不批量重命名物理文件，不因
无法识别而删除。旧头像、内容图片和 RichText URL 在兼容期继续工作，并通过 Object ID 反查真实文件。

### 5.6 F1 出口

- 同一用户 50 个并发 Put/Delete 不突破配额，Reservation 最终收敛为 0。
- 上传中断、磁盘满、rename 失败、DB commit 失败和进程重启均有故障注入测试。
- 用户 A 的 Object ID 对用户 B 返回统一 404；日志、错误和指标不泄露绝对路径。
- 10 万对象的 List 有稳定分页、索引和查询预算；Usage 不再每次递归扫描目录。
- 备份恢复后 metadata、ledger、文件 size/hash 对账为 0 差异。

| `year` | `2000..2200`，数据库 CHECK |
| `semester` | 只能 `spring` 或 `fall`，数据库 CHECK |
| `display_name`（DTO） | 由服务端按“YYYY 春季/秋季学期”计算，不在数据库保存可漂移名称，也不接受任意输入 |
| `first_week_start` | ISO Date；作为新建用户课表的初始值 |
| `status` | `open` 或 `closed`，数据库 CHECK |
| `is_default` | 只能有一个处于 open 的默认学期 |
| `version` | 乐观锁，所有管理写操作必须带 expected version |
| `created_by/updated_by` | 管理员审计主体 |
| `created_at/updated_at/closed_at` | 生命周期证据 |

数据库约束：

- `UNIQUE(year, semester)`；
- 部分唯一索引保证全局最多一个 `is_default = true AND status = 'open'`；
- closed 不能保持 default；
- first week 必须是星期一；如学校确需非星期一开课，必须先形成新业务决策，而不是前端绕过。

### 6.2 生命周期规则

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| 不存在 | 创建 | 建立 open 或 closed 学期；重复 year/semester 返回 409 |
| open | 修改第一周 | 只影响之后首次创建的用户课表，不回写存量课表 |
| open | 设置默认 | 事务内取消旧默认并设置新默认 |
| open | 关闭 | 清除 default；已有用户课表继续可读 |
| closed | 重新开放 | 允许，但需要 expected version、原因和 required audit |
| 任意 | 删除 | 仅在从未产生用户课表、对象或审计引用时允许 |

系统没有 AcademicTerm 时，用户课表页显示“当前暂无可用学期，请联系管理员”，服务端返回稳定错误；不得按
月份创建隐式学期。

### 6.3 课表记录模型

新增：

| 表 | 用途 |
| --- | --- |
| `user_schedule_terms` | `(user_id, academic_term_id)` 唯一；保存当前 schedule Object ID、复制后的 `first_week_start`、版本和时间 |
| `user_schedule_preferences` | 每用户当前查看的 AcademicTerm；只能指向开放学期或该用户已有数据的关闭学期 |

课程内容仍保持 JSON 领域合同，不在 v14 拆成大量关系表。每次保存先创建新的 schedule Object，再在数据库
事务中以 expected version 切换 `current_object_id`；旧对象在提交后通过可靠清理事件处理。这样可以避免直接
覆盖导致的截断，并为故障恢复保留最近一次完整对象。

### 6.4 用户和管理 API

计划路由：

| 受众 | 方法与路由 | 语义 |
| --- | --- | --- |
| Auth | `GET /api/v1/schedule/terms` | 返回开放学期和默认项 |
| Auth | `GET /api/v1/schedule/me/terms` | 返回本人已有课表，包含 closed 历史项 |
| Auth | `GET /api/v1/schedule/me?academic_term_id=` | 读取指定课表；closed 可读 |
| Auth | `POST /api/v1/schedule/me/terms/activate` | open 可选择；closed 仅在本人已有课表时可设为查看项 |
| Auth | `PUT /api/v1/schedule/me` | 仅 open；expected version；创建时复制 first week |
| Auth | `POST /api/v1/schedule/me/import` | 仅 open；经过文件和对象安全限制 |
| Admin | `GET/POST /api/v1/admin/academic-terms` | 查询、创建学期 |
| Admin | `PUT /api/v1/admin/academic-terms/:id` | 修改第一周和受控字段 |
| Admin | `POST .../:id/open`、`.../:id/close`、`.../:id/default` | 显式状态命令 |
| Admin | `DELETE /api/v1/admin/academic-terms/:id` | 仅无任何用户数据时允许 |

旧请求中的 `term_year + semester` 在兼容期可继续接受，但只能解析为已存在的 AcademicTerm，不能创建新学期。
响应新增 `academic_term_id` 和 `term_status`；旧顶层包络继续保留。

建议 Permission Code：

```text
schedule.academic_term.read
schedule.academic_term.manage
schedule.academic_term.delete
```

管理写操作分别登记 `http.schedule.academic_term.*` Operation Code；close/reopen/default/delete 使用 required
audit。普通用户由登录身份、对象所有权和状态机授权，不给 External Plugin 隐式管理权限。

### 6.5 稳定错误

| machine code | HTTP | 条件 |
| --- | ---: | --- |
| `ACADEMIC_TERM_NOT_AVAILABLE` | 404 | 学期不存在或用户无权得知 |
| `ACADEMIC_TERM_CLOSED` | 409 | 对 closed 学期执行创建、保存或导入 |
| `ACADEMIC_TERM_DEFAULT_UNAVAILABLE` | 409 | 没有开放的默认学期且请求依赖默认值 |
| `ACADEMIC_TERM_VERSION_CONFLICT` | 409 | 管理或用户课表乐观锁冲突 |
| `ACADEMIC_TERM_HAS_SCHEDULES` | 409 | 删除仍被课表引用的学期 |
| `SCHEDULE_OBJECT_UNAVAILABLE` | 503 | metadata 存在但对象暂不可读；记录对账信号 |

错误使用现有统一响应合同并提供中文 `msg` 和安全 details，例如学期名称、状态和允许动作，不返回 SQL、路径
或内部错误文本。

### 6.6 历史课表迁移

历史迁移不能只靠 SQL，因为事实位于用户目录 JSON 中。提供独立、可重复、默认 dry-run 的采用命令：

1. 扫描 `file/schedule/terms/*.json` 和 `index.json`，校验 owner、year、semester、JSON schema 和文件 hash。
2. 对发现的合法 `(year, semester)` 建立或复用 AcademicTerm；未由管理员配置的历史组合登记为 closed，
   不自动设置默认。
3. 将 JSON 登记为 storage object，建立 `user_schedule_terms`；复制文件内 first week，不用管理员当前值覆盖。
4. 将有效 index 映射为 preference；指向缺失文件时报告并选择默认 open 学期，但不伪造课表。
5. 损坏 JSON 保持原位并登记 quarantine/report，用户看到可操作错误和下载原始文件入口。
6. 重跑命令必须幂等；同一 user/term/hash 不重复创建对象或课表记录。

切换顺序是“先可读、再双写、最后禁止自由创建”。生产开启 enforce 前必须抽样核对历史学期数、用户数、
文件数、hash 和 closed 登记结果。

### 6.7 前端变化

- Web 删除自由年份输入和前端自造学期逻辑，使用服务端下拉项。
- open 项可创建、导入和保存；closed 历史项明确显示只读原因，编辑按钮禁用但服务端仍强制拒绝。
- FirstWeekStart 继续允许用户在自己的课表内调整；管理员修改不会覆盖既有值。
- Admin 新增“系统设置 / 学期管理”，包含列表、新增、第一周、默认、关闭/开放、引用计数和版本冲突提示。
- PC 与 `320/360/390/768/852 横屏/1024/1440` 视口覆盖选择、只读、空状态、冲突和导入失败。

## 7. D1/D2：Personal Documents

### 7.1 产品边界

Personal Space 扩展为：

```text
个人空间
├── 个人主页与资料
├── 内容与样式
├── 个人课表
└── 我的文档
```

“我的文档”默认私有。v14 的管理员只能查看对象/任务运营摘要和配额，不提供浏览用户文档内容的后台入口。

### 7.2 文档与版本数据模型

| 表 | 关键字段 | 规则 |
| --- | --- | --- |
| `personal_documents` | `id`、`owner_user_id`、`name`、`document_type`、`current_version_id`、`status`、`version`、时间、`deleted_at` | status 为 active/trashed；所有写入乐观锁 |
| `personal_document_versions` | `id`、`document_id`、`version_number`、`source_object_id`、`campusdoc_object_id`、`source_type`、`size_bytes`、`sha256`、`created_by`、时间 | `(document_id, version_number)` 唯一；版本不可更新 |
| `personal_document_previews` | `id`、`document_version_id`、`preview_object_id`、`status`、`error_code`、`attempts`、时间 | pending/processing/ready/failed/unsupported |

数据库外键采用 RESTRICT/软删除，避免误删对象。对象物理清理由明确的保留策略和可靠命令负责；v14 不提供
自动永久清理任务，移入回收站和 Feature Disable 均不释放历史版本。

### 7.3 格式能力矩阵

| 格式 | 上传 | 查看/预览 | 在线编辑 | 版本策略 |
| --- | --- | --- | --- | --- |
| TXT | 是 | 同步、安全文本 | 是 | 保存生成新版本 |
| Markdown | 是 | 服务端渲染后清洗 | 是 | 保存源文本和 CampusDoc/HTML 派生对象 |
| CampusDoc v1 | 是 | 服务端渲染后清洗 | 是 | 原生不可变版本 |
| DOCX | 是 | 仅隔离 Converter 达标后启用 | 只编辑转换后的 CampusDoc | 原 DOCX 永久保留 |
| PDF | 是 | 认证、隔离只读；可异步生成缩略预览 | 否 | 原 PDF 不覆盖 |

初始上限建议：TXT/Markdown/CampusDoc 单文件 5 MiB，DOCX/PDF 单文件 25 MiB；仍受用户总配额约束。
Office 解压后总量上限 100 MiB、条目数上限 10,000、压缩比上限 100:1。实际默认值进入模块配置、错误
details 和文档，修改时必须经过合同测试，不能只改前端。

### 7.4 CampusDoc v1 与 Content Editor Core

`CampusDoc v1` 是版本化 JSON 文档，不直接把任意 HTML 当作源事实。第一版块类型只包含段落、标题、
有序/无序列表、引用、代码块、分隔线、受限表格和图片引用。图片节点只保存 Object ID、替代文本和受控尺寸，
不接受任意 URL、style 或事件属性。

计划抽取：

- Go：`internal/modules/core/contenteditor`，拥有 schema 校验、HTML Sanitizer、Markdown/CampusDoc Render；
- Web：`web/src/modules/content-editor/`，拥有可复用编辑器组件和序列化；
- RichText Adapter：保持现有 Article API、ContentFormat、Thread 状态和旧数据不变；
- Documents Adapter：只使用编辑能力，不创建 Community Thread，也不进入公开帖子列表。

抽取必须先以现有 RichText fixture 做等价回归，再迁移 Article 调用。禁止一次重写所有历史富文本行或改变已发布
文章的 SanitizedHTML 语义。

### 7.5 文档 API

| 方法与路由 | 语义 |
| --- | --- |
| `GET /api/v1/documents` | 本人文档分页、类型/状态筛选 |
| `POST /api/v1/documents` | 上传或创建 TXT/Markdown/CampusDoc |
| `GET /api/v1/documents/:id` | 文档元数据和当前版本 |
| `GET /api/v1/documents/:id/versions` | 不可变版本列表 |
| `PUT /api/v1/documents/:id` | expected version 保存，新建版本 |
| `POST /api/v1/documents/:id/versions/:version_id/restore` | 从历史版本创建新版本 |
| `GET /api/v1/documents/:id/download?version_id=` | 认证下载原对象 |
| `GET /api/v1/documents/:id/preview?version_id=` | 同步内容或异步预览状态 |
| `DELETE /api/v1/documents/:id` | 移入回收站，不物理删除对象 |
| `POST /api/v1/documents/:id/restore` | 从回收站恢复 |

所有路由按当前 JWT 用户查找；跨用户 ID、文档 ID、版本 ID 和对象 ID 一律返回统一 404。文件响应设置
`X-Content-Type-Options: nosniff`、安全 Content-Disposition、私有缓存策略和适合格式的 CSP/sandbox。

### 7.6 上传安全

必须覆盖：

- 路径穿越、控制字符、保留设备名、双扩展名和 Unicode 混淆；
- MIME sniff 与允许列表，拒绝 HTML/SVG 伪装、可执行文件和未知 Office 容器；
- ZIP Bomb、过多条目、嵌套压缩、宏、外部关系、远程模板和嵌入对象；
- 超大 PDF、加密/损坏 PDF、JavaScript/Launch Action 等主动内容；
- 上传中断、慢速流、磁盘空间耗尽、hash 不一致、Reservation 过期；
- Markdown/HTML XSS、危险链接协议、图片跨用户引用；
- 同一文档并发保存和恢复冲突。

用户错误必须使用中文并给出可操作 details，例如“允许 25 MiB、文件实际 31.4 MiB、剩余个人空间 18 MiB”，
不能只返回 `space file exceeds allowed size` 或底层解析器文本。

## 8. D3/D4：预览与 Converter

### 8.1 Reliability 事件

文档版本提交成功后，在同一数据库事务写入：

```text
document.preview.requested.v1
```

事件只包含 document ID、version ID、source Object ID 和目标预览类型，不包含绝对路径、用户文件内容或
下载 Token。命名 consumer 使用既有 receipt 防止成功转换被重复执行；临时失败进入 retry，确定不支持进入
failed/unsupported，超过次数进入 dead-letter 并可由受权管理员查看原因类别。

### 8.2 隔离执行合同

DOCX/PDF 复杂解析只能在独立 Converter 进程或容器执行：

- 非 root、`cap_drop: ALL`、只读 rootfs、无 Docker socket；
- 默认 `network_mode: none`；
- 输入对象只读、输出目录单任务可写、tmpfs 有上限；
- 初始限制 1 CPU、512 MiB RAM、60 秒、输出 50 MiB；
- 不注入数据库、JWT、SMTP、插件签名或用户 Token；
- API/Worker 通过受限任务协议交换 Object ID 和一次性任务凭据，不共享宿主 User Storage 根目录；
- 日志只记录任务 ID、格式、耗时、结果码，不记录文件名、用户标识或内容。

如果部署无法满足以上条件，配置报告 `converter_unavailable`，DOCX 保持上传/下载，PDF 保持安全原文件查看；
不得在 API 主进程回退执行 LibreOffice 或任意外部命令。

### 8.3 可观测与运营

新增低基数指标：

```text
campusos_storage_objects{status,provider}
campusos_storage_reservations{status}
campusos_storage_reconcile_differences{kind}
campusos_document_preview_jobs{status,format}
campusos_document_preview_duration_seconds{format,result}
```

不得使用 user ID、object ID、document ID、文件名、URL 或错误文本作为标签。Admin 只显示有界摘要、
积压年龄、失败类别和 Runbook 链接；重试操作继续要求权限、原因、幂等和 required audit。

### 9.2 灰度顺序

1. 部署新表、读兼容和 dry-run 工具，`storage_object_mode=shadow`、`academic_term_guard=observe`。
2. 完成文件与课表盘点；管理员建立至少一个 open/default AcademicTerm。

4. 开启 AcademicTerm enforce；旧 year/semester 参数只解析，不创建。
5. 开启 Object enforce；新写只走 Object Port，旧读 Adapter 保留。
6. 开启 Personal Documents；Converter 继续独立开关。
7. 完成恢复、对账和浏览器门禁后发布；v14 不删除旧兼容路径。

AcademicTerm 的紧急回退只能关闭新 UI 或恢复兼容读取，不能重新允许用户创建未配置学期。Object Layer 回退时
保留 metadata/ledger 并停止新写，不能用目录扫描结果覆盖已提交的对象事实。

| Platform | Windows Docker Desktop、Linux amd64；arm64 仍需目标 Runner 证据，不能由 amd64 代替 |

计划新增聚合目标并接入 `make release-check`：

```text
make v14-baseline-check
make v14-storage-check
make v14-schedule-check
make v14-documents-check
make v14-migration-check
```

每阶段至少运行实际受影响的 Go 单测、Web/Admin test/build、合同、架构、可靠性、数据库和文档检查。Final 运行
完整 `make release-check`、恢复演练和浏览器矩阵；仅静态编译或单元测试不能替代数据迁移与恢复证据。

## 12. 性能与容量预算

G0 记录现状后冻结最终阈值，初始目标如下：

- Object Stat/Open metadata 查询 p95 不超过 100 ms（不含文件网络传输）。
- 20 项分页 List 不产生逐对象 N+1，SQL 查询数保持常数级。
- 课表 200 门课程的读取/保存不因历史学期数线性扫描整个用户目录。
- 同一用户 50 个并发配额操作最终 `used + reserved <= quota`。
- 预览队列停止后恢复，pending 能在预算窗口内收敛；failed/dead 不自动无限重试。
- 文档和对象新增索引必须经过 `EXPLAIN`/数据规模 fixture，避免重复索引和高写放大。
- 对账按批次和 checkpoint 运行，不能一次将整个 User Storage 元数据加载进内存。

这些是版本预算而非生产容量承诺；真实长稳、arm64 和外部告警通知仍需目标环境认证。

## 13. 安全、隐私与审计

1. 文档和课表默认私有；管理员拥有配额/运营权限不等于拥有内容读取权限。
2. Object ID 使用不可猜测稳定 ID，服务端仍必须检查 owner，不能把“难猜”当授权。
3. 原始文件、临时文件、预览和 Converter 输出都不得进入公开静态目录。
4. API、日志、指标、Outbox payload、审计和错误 details 不记录正文、绝对路径、Token 或 Secret。
5. 学期 close/reopen/default/delete、对象对账 apply、预览重试使用稳定 Permission/Operation Code 和审计原因。
6. 下载响应防 MIME 嗅探；Markdown/CampusDoc 先渲染再清洗；PDF/DOCX 保持受认证和隔离。
7. External Plugin 的现有 `schedule`/`space_file` Grant 不自动升级为读取 Documents；新能力另行设计最小投影。
8. Converter 镜像进入 SBOM、漏洞扫描和固定 digest；不得运行用户文档中的宏、脚本或外部链接。

## 14. 风险登记

| 风险 | 等级 | 监测信号 | 控制与回退 |
| --- | --- | --- | --- |
| 历史课表遗漏或覆盖 | 高 | dry-run 数量/hash 不一致 | 只增不删、幂等采用、closed 登记、保留原 JSON |
| 两个默认学期 | 高 | 唯一索引冲突 | 数据库部分唯一索引 + 事务 + 并发测试 |
| closed 被 API 绕过 | 高 | 非 UI 写入成功 | 所有 Save/Import/Activate 统一 Guard，负向合同测试 |
| Object metadata/file 不一致 | 高 | reconcile 差异 | pending 状态机、staging/rename、对账、禁止启动时自动删除 |
| 配额竞争 | 高 | used/reserved 超 quota | 行锁/版本、显式 Reservation、超时回收、并发测试 |
| Storage 重构破坏现有图片 URL | 高 | 头像/帖子图片 404 | dual read、兼容 Adapter、浏览器回归、v14 不删旧路径 |
| 文档版本被覆盖 | 高 | hash 或 version 重复变化 | immutable row/object、expected version、恢复生成新版本 |
| DOCX/PDF RCE/DoS | 高 | Converter 超时/OOM/外联 | 无网络容器、限额、格式预检、未达标则关闭 |
| 隐私越权 | 高 | 跨用户 Stat/Open 成功 | owner-first query、统一 404、API/对象双层测试 |
| 备份只恢复 DB 或只恢复文件 | 高 | 引用/对象/hash 差异 | 联合备份清单、恢复后强制 reconcile |
| 8 周范围过大 | 中 | F1/S2 Gate 延迟 | 优先保证 Storage/Schedule/Documents 基础；DOCX Preview 可降级 |
| 文档抽取改变旧文章 | 中 | RichText fixture/render diff | 先等价测试后迁移，保留旧表和 API |

## 15. 回滚与灾难恢复

### 15.1 AcademicTerm/Schedule

- 关闭新管理/用户 UI 时保留 AcademicTerm 和课表绑定表。
- 允许旧 JSON 兼容读取，但不能恢复未受管的新学期写入。
- 新对象写失败时继续读取最后一个 ready schedule Object；不把损坏 pending 对象设为 current。
- 管理员修改默认/关闭错误时使用新的受审计命令纠正，不直接改数据库。

### 15.2 Object Layer

- `shadow` 阶段可完全停止采用；不会改写原文件。
- `dual` 阶段停止新对象写入后保留 metadata、Reservation 和 staging 证据，由 reconcile 安全收敛。
- 已进入 enforce 后优先 forward-fix；不得 down 删除 objects/accounts/reservations。
- Feature Disable 不触发对象删除；Provider 不可用时返回可重试错误并保护 metadata。

### 15.3 Documents/Preview

- Documents Feature 可停用，表、对象和版本全部保留。
- Preview 可单独停用；列表、原文件下载和已存在的安全预览继续工作。
- 历史版本恢复永远创建新版本；不能把数据库指针直接指回旧版本而丢失恢复行为证据。
- 回收站不自动永久清理；后续版本在有保留策略、配额语义和恢复演练后再设计 purge。

## 17. Definition of Done

每个阶段同时满足：

1. 实现状态与验证状态分别记录；缺少数据库、浏览器或恢复证据时只能标记“实现中/待验收”。
2. 新 API 已进入 OpenAPI、Route Operation、Permission、错误目录和 SDK/前端统一解析合同。
3. 新表进入 schema contract、database audit、Admin `/architecture` 和数据所有权文档。
4. 新模块进入 module descriptor、依赖图、Feature 状态、README/官方文档和架构检查。
5. 定向单元、合同、集成、并发、负向、故障注入和受影响前端构建通过。
6. `go test ./... -count=1`、合同/架构/可靠性/换行/链接/差异检查通过，或明确记录平台阻断和复现证据。
7. migration 空库、历史副本、up/down/up、重复采用和恢复演练通过。
8. 对应 `docs/进度/v0.14-dev/v0.14.X-dev.md` 已新增，实际命令和结果来自当前工作树。
9. Feature Disable、Converter Disable、配额不足、磁盘故障和恢复路径经过实际验证。
10. 未经用户明确要求，不由开发流程自动 commit 或 push。

## 19. Final 验收清单

### AcademicTerm/Schedule

- [ ] 数据库和 Go 领域层都只接受 spring/fall。
- [ ] 用户不能看到或创建未配置学期；直接调用 API 同样失败。
- [ ] closed 历史可读，保存/导入/新建拒绝，重新开放和默认切换有版本及审计。
- [ ] 管理员不能删除已有课表引用的学期。
- [ ] 管理员 first week 修改只影响之后创建的用户课表。
- [ ] 历史 JSON 数、hash、学期和用户映射在采用前后相等，损坏项均有报告。

### User Storage

- [ ] 用户 A 无法 Stat/Open/Delete/List 用户 B 的对象。
- [ ] 所有新增业务只保存 Object ID，Feature 不获得绝对路径。
- [ ] 并发配额、Reservation 超时和故障恢复正确，无不可解释 orphan。
- [ ] 旧头像、内容图片、RichText 资产和课表兼容读取通过。
- [ ] 备份恢复后 metadata/file/ledger/hash 对账为 0 差异。

### Personal Documents

- [ ] 上传、列表、查看、编辑、版本、恢复、下载、回收站流程完整。
- [ ] TXT/Markdown/CampusDoc 可编辑；PDF 不可编辑。
- [ ] DOCX 原文件始终保留；Converter 不达标时明确降级。
- [ ] XSS、伪 MIME、ZIP Bomb、超限、跨用户对象引用和并发保存被拒绝。
- [ ] 中文错误包含允许上限、实际大小、剩余配额或下一步操作等安全 details。

### Reliability/Release

- [ ] Worker crash、Converter timeout/OOM、磁盘写失败、DB 错误、重复事件和 dead-letter 可定位、可收敛。
- [ ] Windows Docker Desktop 与 Linux 目标环境通过相应矩阵，平台证据不互相冒充。
- [ ] OpenAPI、Schema、Route、Permission、Admin 架构、README/Help/docs-site 和进度证据同步。
- [ ] 完整 release-check、migration、恢复、浏览器、安全和数据对账门禁通过。

## 20. 版本完成后的能力边界

v14 Final 通过后，CampusOS 可以准确宣称：

- 平台拥有管理员治理的春/秋学期目录，课表受目录状态约束并保留历史数据；
- Local User Storage 具有统一对象元数据、私有所有权、持久配额预留和可恢复对账；
- Personal Space 提供私有个人文档、不可变版本和安全预览基础；
- 复杂文档转换仅在隔离条件满足时启用。

仍不能宣称：CampusOS 已经是通用云盘、Office 在线套件、生产 S3 文件平台、多人协作平台、多节点高可用
系统或 AI 文档平台。上述边界必须同时出现在发布说明和官方文档中。
