> 编写日期：2026-07-10
> 适用范围：CampusOS 项目计划第五版、`v0.5-dev` 阶段后续收口与 v0.6 前置判断
> 基线参考：`docs/项目计划v5/00-v5版本计划书.md`、`docs/进度/v0.5-dev/v0.5.0-dev.md` 到 `v0.5.34-dev.md`、当前 README 与帮助文档

## 1. 第二版定位

第一版计划书的定位是 v0.5-dev 的任务拆分和风险边界。当前代码与文档已经推进到 `v0.5.34-dev`，实际完成范围明显超过第一版里 `v0.5.0` 到 `v0.5.7` 的初始拆分。因此第二版不再重复原始计划，而是做三件事：

| 目标 | 说明 |
| --- | --- |
| 审查第一版计划 | 标记哪些内容已经完成、哪些内容仍是边界或后续专项 |
| 固化当前基线 | 将 v0.5.34-dev 的真实系统状态写成可执行基线 |
| 优化后续路线 | 将剩余工作从“继续堆功能”改为“收口、回归、审核、版本化和生产化准备” |

第二版仍然使用 `v0.5-dev` 作为实现阶段名称，不引入产品语义版本 `v5.0.0`。

## 2. 第一版计划审查结论

第一版中多数 P0/P1 目标已经落地，但实际演进增加了几个新的设计边界。

| 第一版方向 | 当前结论 |
| --- | --- |
| 稳定化与基线确认 | 已完成，`v0.5.0-dev` 已完成迁移、登录、发帖、个人主页同步、风格应用和前后端构建回归 |
| 管理后台集成中心 | 已完成基础闭环，`/integrations` 汇总数据库、插件、AI、个人主页、Webhook、MCP-like、Message 和 Metrics |
| 个人主页与风格包运营化 | 已完成核心闭环，支持快照、回滚、恢复默认、禁用、同步状态、头像上传、本地个人空间和拓展风格包 |
| 插件包治理增强 | 已完成 v0.5 闭环，支持 checksum、包大小、预检、风险分级、版本比较、导入审计、导入导出和配置表单 |
| Webhook 基础闭环 | 已完成，支持 endpoint、事件订阅、HMAC 签名、测试投递、失败记录和后台入口 |
| MCP Server 只读实验 | 已完成内部 MCP-like 只读工具层，但不是标准 MCP 协议 Server |
| Message 协议与本地适配器 | 已完成本地闭环，支持 Message 模型、binding、local inbound 和 `ping -> pong` |
| 观测、备份和运行文档 | 已完成基础文档和平台日志入口，但生产级集中日志、告警和恢复演练仍未完成 |

第一版中“未完成或暂缓”的判断仍然有效：

| 事项 | 当前边界 |
| --- | --- |
| 完整插件市场 | 仍未完成，当前只完成本地插件包治理；公网/团队级市场还需要签名强验、审核流、版本索引和分发策略 |
| 标准 MCP 协议适配器 | 仍未完成，当前只是 CampusOS 内部 API 形态的 MCP-like 工具层 |
| 真实 IM 平台适配器 | 仍未完成，目前只有 local adapter |
| 完整 Docker 产品化封装 | 仍未完成，当前 Docker Compose 主要服务开发期依赖 |
| 原生 Windows 实机兼容 | 仍不作为主路径，推荐 WSL2 + Docker Desktop |
| 任意 JavaScript 页面风格 | 仍不开放，只允许后端筛查通过的受限 HTML/CSS |

## 5. 关键设计边界

### 5.1 插件目录边界

第二版明确插件目录和插件数据目录的职责：

| 目录 | 职责 |
| --- | --- |
| `data/plugins/<plugin>/` | 插件 manifest、运行入口、Wasm/gRPC/built-in 实现代码、插件 README |
| `data/plugin_data/<plugin>/` | 插件运行数据、SQLite KV、可编辑源码目录风格包、后续插件生成文件 |
| `data/images/` | 非个人空间的全局本地图片资源预留目录 |
| `data/personal-space/<user_id>/` | 用户个人空间文件；默认包含 `file/`、`img/`、`excel/`、`word/`、`pdf/` 分类目录 |
| `data/dist/` | 本地构建或发布产物预留 |
| `data/config/` | 本地运行配置预留，不提交 secrets |
| `data/skills/` | 本地 runtime/imported skills 预留 |

风格包目录规则：

```text
data/plugin_data/personal-space/style-packs/<name>/
data/plugin_data/homepage-customizer/style-packs/<name>/
```

当前标准源码包结构：

```text
style.yaml
README.md
preview.png
templates/page.html
templates/card.html
assets/cover.webp
assets/avatar-frame.png
styles/theme.css
config.schema.json
```

`data/plugins` 不再保存可编辑风格包源码目录。`data/style_packages/<target>/` 可作为后续跨插件共享风格仓库预留，但当前运行时读取路径仍是 `data/plugin_data/<plugin>/style-packs/<pack>/`。

### 5.2 插件分级与生命周期

插件 manifest 使用 `scope` 声明生命周期模型：

| Scope | 适用范围 | 当前行为 |
| --- | --- | --- |
| `system` | 随 CampusOS 服务代码部署的核心插件 | 管理端启用/禁用只保存目标状态；API 服务重启后加载或停止。网页不允许导入、热更新或卸载。 |
| `user` | 可独立维护的 Wasm/gRPC 扩展 | 管理端可手动加载、重载、停止、卸载；覆盖导入已加载插件会停止旧 Runtime 并加载新包。 |

`runtime: builtin` 未声明 `scope` 时兼容为 `system`；gRPC/Wasm 未声明时兼容为 `user`。这里的“用户级”是热加载扩展级别，不代表普通登录用户可安装插件；当前管理操作仍要求 `role:manage`。

### 5.3 页面风格安全边界

`page-style-pack.v1` 只开放受限 HTML/CSS，不开放任意 JavaScript。

| 风险 | 当前策略 |
| --- | --- |
| JS 执行 | 不允许 `<script>`、事件处理器、`javascript:` URL |
| 外部资源 | CSS 中不允许 `url()` 和 `@import` |
| 路径穿越 | zip 和源码目录都必须使用安全相对路径 |
| HTML 模板 | 对所有 `.html` 文件执行安全筛查，不只检查入口文件 |
| CSS 样式 | 对所有 `.css` 文件执行安全筛查，不只检查 manifest 中声明的文件 |
| 配置 Schema | `config_schema` 只能指向根目录 `config.schema.json`，且必须可解析为 JSON object |
| 图片资源 | `preview_image` 和 `assets` 只允许包内 png/jpg/jpeg/webp 相对路径 |
| 文件规模 | 限制文件数量、zip 大小、单文件大小和 CSS 大小 |
| 生效条件 | 所有文件筛查通过后才允许应用 |
| 历史数据 | 公开接口会再次过滤历史不合规 HTML/CSS |

### 5.4 MCP 与 Message 边界

| 模块 | 当前定位 | 后续方向 |
| --- | --- | --- |
| MCP-like | 内部 API 形态的只读工具层 | 后续若需要标准 MCP，需要独立协议适配器、token、审计和安全文档 |
| Message | CampusOS 内部消息协议和 local adapter | 后续通过 Adapter/Plugin 接入 Discord、NapCat、AstrBot、飞书等真实平台 |

### 5.5 首页自定义边界

`homepage-customizer` 当前是内置系统插件，支持结构化配置和受限 HTML/CSS。首页整体风格可以通过 zip 或源码目录拓展风格包应用，但尚未提供独立历史版本、审核流和回滚列表。

## 6. 第二版 v0.5-dev 后续目标

第二版后续目标不再以“补齐第一版任务”为主，而是以“让当前能力可维护、可审核、可回归”为主。

| P1 | 标准 MCP 适配预研 | 在不开放写操作的前提下设计标准 MCP Server 适配器边界 |

## 8. v0.6 前置判断

v0.6 不建议直接扩大业务范围。只有在 `v0.5.34-dev` 当前基线通过回归后，才按以下优先级推进。具体拆分见 [v1-v5 计划严格审查](../项目计划v6/00-v1-v5计划审查.md) 与 [v6 版本计划书](../项目计划v6/01-v6版本计划书.md)。

| 优先级 | 方向 | 说明 |
| --- | --- | --- |
| P0 | 接口契约 | 建立当前路由清单、OpenAPI、统一错误/分页约定和契约测试。 |
| P0 | 权限控制 | 统一身份、`resource:action`、ownership、data scope、字段裁剪、审计和越权负向测试。 |
| P0 | 数据库完整性 | 先做孤儿/重复/类型检查，再通过 `000014+` 兼容 migration 补约束、索引和稳定关系。 |
| P0 | 插件开发者生态 | 固化 Host API、权限目录、Go SDK、CLI、模板、mock/test harness 和详细帮助文档。 |
| P1 | 恢复与插件供应链 | 完成单节点恢复演练，以及插件来源、版本快照、安装后检查和回滚。 |
| P2 | 标准 MCP 或真实 IM | 在前述基础稳定后只选择一个标准外部边界实现最小闭环。 |

| 帮助文档 | 路径、接口、配置项变化必须同步到 `docs/help/` |
| 项目上手快照 | `skills/campusos-project-onboarding/references/current-project-status.md` 必须反映最新目录和边界 |

## 11. 当前明确不做

| 不做项 | 原因 |
| --- | --- |
| 任意 JS 主页和首页插件 | 安全风险高，当前只开放受限 HTML/CSS 和筛查后的风格包 |
| 标准 MCP 写操作 | 权限和审计风险高，当前只做只读内部工具层 |
| 一次性接入多个 IM 平台 | 平台差异大，容易拖慢主线 |
| 公网插件市场 | 需要签名、审核、兼容性、权限和回滚体系 |
| 完整 K8s/Helm 高可用 | 当前优先级低于稳定开发基线和备份恢复 |
| 原生 Windows 完整兼容 | 仍推荐 WSL2，原生 Windows 作为后续专项 |
| AI 自动审核强执行 | 需要人工复核、样本集和误伤处理机制 |

## 12. 总结

v5 第一版的核心目标已经基本落地：CampusOS 具备了可运营的社区核心、插件运行时、个人主页、风格包、集成中心、Webhook、MCP-like 只读工具和 Message local adapter。

第二版的重点不是继续增加大功能，而是把当前系统收口为稳定基线：

```text
统一文档和目录边界
  -> 增强风格包可发现和回滚
  -> 脚本化关键回归和富文本文章 smoke
  -> 补齐插件治理二期
  -> 做 v0.5 总体验收
  -> 再决定 v0.6 专项
```

只有当 v0.5 的核心路径可重复验证、文档不再偏离实际、目录边界稳定后，才建议进入标准 MCP、真实 IM、插件市场、风格包市场、完整 Docker 产品化或 AI 内容审核等更高风险方向。
