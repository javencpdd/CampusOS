## 1. 第二版定位

第一版计划书的定位是 v0.5-dev 的任务拆分和风险边界。当前代码与文档已经推进到 `v0.5.20-dev`，实际完成范围明显超过第一版里 `v0.5.0` 到 `v0.5.7` 的初始拆分。因此第二版不再重复原始计划，而是做三件事：

| 目标 | 说明 |
| --- | --- |
| 审查第一版计划 | 标记哪些内容已经完成、哪些内容仍是边界或后续专项 |
| 固化当前基线 | 将 v0.5.20-dev 之后的真实系统状态写成可执行基线 |
| 优化后续路线 | 将剩余工作从“继续堆功能”改为“收口、回归、审核、版本化和生产化准备” |

第二版仍然使用 `v0.5-dev` 作为实现阶段名称，不引入产品语义版本 `v5.0.0`。

## 5. 关键设计边界

### 5.1 插件目录边界

第二版明确插件目录和插件数据目录的职责：

| 目录 | 职责 |
| --- | --- |
| `data/plugins/<plugin>/` | 插件 manifest、运行入口、Wasm/gRPC/built-in 实现代码、插件 README |
| `data/plugin_data/<plugin>/` | 插件运行数据、SQLite KV、可编辑源码目录风格包、后续插件生成文件 |
| `data/images/` | 本地上传图片、头像和个人空间文件 |
| `data/dist/` | 本地构建或发布产物预留 |
| `data/config/` | 本地运行配置预留，不提交 secrets |
| `data/skills/` | 本地 runtime/imported skills 预留 |

风格包目录规则：

```text
data/plugin_data/personal-space/style-packs/<name>/
data/plugin_data/homepage-customizer/style-packs/<name>/
```

当前标准源码包结构：

```text
style.yaml
README.md
preview.png
templates/page.html
templates/card.html
assets/cover.webp
assets/avatar-frame.png
styles/theme.css
config.schema.json
```

`data/plugins` 不再保存可编辑风格包源码目录。`data/style_packages/<target>/` 可作为后续跨插件共享风格仓库预留，但当前运行时读取路径仍是 `data/plugin_data/<plugin>/style-packs/<pack>/`。

### 5.2 页面风格安全边界

`page-style-pack.v1` 只开放受限 HTML/CSS，不开放任意 JavaScript。

| 风险 | 当前策略 |
| --- | --- |
| JS 执行 | 不允许 `<script>`、事件处理器、`javascript:` URL |
| 外部资源 | CSS 中不允许 `url()` 和 `@import` |
| 路径穿越 | zip 和源码目录都必须使用安全相对路径 |
| HTML 模板 | 对所有 `.html` 文件执行安全筛查，不只检查入口文件 |
| CSS 样式 | 对所有 `.css` 文件执行安全筛查，不只检查 manifest 中声明的文件 |
| 配置 Schema | `config_schema` 只能指向根目录 `config.schema.json`，且必须可解析为 JSON object |
| 图片资源 | `preview_image` 和 `assets` 只允许包内 png/jpg/jpeg/webp 相对路径 |
| 文件规模 | 限制文件数量、zip 大小、单文件大小和 CSS 大小 |
| 生效条件 | 所有文件筛查通过后才允许应用 |
| 历史数据 | 公开接口会再次过滤历史不合规 HTML/CSS |

### 5.3 MCP 与 Message 边界

| 模块 | 当前定位 | 后续方向 |
| --- | --- | --- |
| MCP-like | 内部 API 形态的只读工具层 | 后续若需要标准 MCP，需要独立协议适配器、token、审计和安全文档 |
| Message | CampusOS 内部消息协议和 local adapter | 后续通过 Adapter/Plugin 接入 Discord、NapCat、AstrBot、飞书等真实平台 |

### 5.4 首页自定义边界

`homepage-customizer` 当前是内置系统插件，支持结构化配置和受限 HTML/CSS。首页整体风格可以通过 zip 或源码目录拓展风格包应用，但尚未提供独立历史版本、审核流和回滚列表。

| 回滚说明 | P1 | 至少形成可执行的手动回滚文档 |
| 签名预研 | P2 | 明确签名字段、信任根和验签流程，但不强制实现 |

## 8. v0.6 前置判断

v0.6 不建议直接扩大范围。只有在 v0.5.23 总体验收通过后，才建议选择下列一个或两个方向推进。

| 方向 | 前置条件 | 说明 |
| --- | --- | --- |
| 标准 MCP Server | MCP-like 工具层稳定，审计和 token 模型明确 | 不开放写操作，先做只读标准协议适配 |
| 真实 IM 适配器 | Message local adapter 和权限模型稳定 | 优先从一个平台做 adapter，不把平台协议写进核心 |
| 插件市场最小闭环 | 插件包签名、审核、版本、权限预览和回滚策略明确 | 先做本地/内网市场，不急于公网分发 |
| 风格包市场 | 风格包审核、版本、回滚和安全筛查成熟 | 可与个人主页和首页风格包体系结合 |
| Docker 产品化 | 备份恢复演练、配置管理和日志策略明确 | 再考虑完整应用镜像、systemd、反向代理和 TLS |
| AI 内容审核 | 样本、人工复核、误伤处理和配置开关成熟 | 不应只依赖模型输出直接管理内容 |

## 11. 当前明确不做

| 不做项 | 原因 |
| --- | --- |
| 任意 JS 主页和首页插件 | 安全风险高，当前只开放受限 HTML/CSS 和筛查后的风格包 |
| 标准 MCP 写操作 | 权限和审计风险高，当前只做只读内部工具层 |
| 一次性接入多个 IM 平台 | 平台差异大，容易拖慢主线 |
| 公网插件市场 | 需要签名、审核、兼容性、权限和回滚体系 |
| 完整 K8s/Helm 高可用 | 当前优先级低于稳定开发基线和备份恢复 |
| 原生 Windows 完整兼容 | 仍推荐 WSL2，原生 Windows 作为后续专项 |
| AI 自动审核强执行 | 需要人工复核、样本集和误伤处理机制 |

## 12. 总结

v5 第一版的核心目标已经基本落地：CampusOS 具备了可运营的社区核心、插件运行时、个人主页、风格包、集成中心、Webhook、MCP-like 只读工具和 Message local adapter。

第二版的重点不是继续增加大功能，而是把当前系统收口为稳定基线：

```text
统一文档和目录边界
  -> 增强风格包可发现和回滚
  -> 脚本化关键回归和富文本文章 smoke
  -> 补齐插件治理二期
  -> 做 v0.5 总体验收
  -> 再决定 v0.6 专项
```

只有当 v0.5 的核心路径可重复验证、文档不再偏离实际、目录边界稳定后，才建议进入标准 MCP、真实 IM、插件市场、风格包市场、完整 Docker 产品化或 AI 内容审核等更高风险方向。
