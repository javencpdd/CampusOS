# CampusOS v7 版本回顾与后续规划

> 审查日期：2026-07-12
>
> 审查基线：`v0.7.0`
>
> 结论：v7 计划定义的架构重构范围已完成；兼容层清理和完整 Agent 产品不属于 v7 完成条件

## 1. 审查结论

本次没有只依据计划书中的“已完成”标记作结论，而是重新核对了代码所有权、运行时接线、自动检查、测试和进度证据。复查发现首轮实现存在若干“只有接口、尚未真实接线”的问题，包括 Database 仍留在业务装配、Identity/Community Port 没有 Adapter、Feature 缺少统一静态路由 Gate、Plugin 子服务只做代理但不拥有状态、Resource 校验过弱。以上问题已经补齐后，v7 的计划内范围可以判定为完成。

v7 的“完成”不代表所有历史兼容代码都已删除。计划明确要求渐进迁移：旧 API、18 个 migration、9 个 Plugin Manifest、`runtime: builtin`、`data/plugin_data` 风格包和用户文件目录必须继续兼容。物理删除这些兼容层反而违反 v7 的禁止事项。

## 3. 当前已经具备的架构能力

### 3.1 模块化单体

- Core Module 有稳定 ID、依赖拓扑、注册、可选启动/停止和健康合同。
- Identity、Community、Moderation、User Storage 作为 Core 边界注册；Core 不允许停用。
- AppContext 只注册命名 Port，External Plugin 和 Agent Runner 不会取得 AppContext。
- Database 连接和关闭已经归入基础设施 Bootstrap；业务可在连接失败时使用既有 Memory Adapter。

### 3.2 内置功能

- Personal Space、Controlled RichText、Personal Schedule 和 Appearance 由 Feature Registry 描述。
- `restart` 功能在启动时捕获 legacy 状态，运行中变更显示待重启，不伪装成热更新。
- `hot-gated` 功能可以即时切换；Gin 路由保持静态，统一 PathGate 返回明确的 503 功能停用响应。
- 功能停用不会删除表记录、个人文件、课表 JSON、文章图片或风格偏好。

### 3.3 User Storage

- `data/personal-space/<user-id>` 仍是稳定根目录，file/img/excel/word/pdf 布局和 URL 不变。
- Core 提供路径约束、标准目录、使用量和配额检查；拒绝空段、`..`、跨用户路径。
- Space、RichText 和 Schedule 不再通过 RichText/Schedule 直接依赖 Personal Space 内部实现。
- 未来云存储 Provider 可以实现同一 Port，不需要让课表或富文本依赖完整个人主页功能。

### 3.4 Plugin Platform

- PluginCatalog 实际拥有插件索引，并分别暴露 External Plugin 和 Legacy Built-in 视图。
- RuntimeRegistry 实际拥有 gRPC、Wasm、builtin 兼容 Runtime。
- Manager 的 Lifecycle 和 Config 公开方法委托给子服务；UI revision/listener、Event subscriptions 和 Audit repository 已迁入对应 Registry/Service。
- 已知 `runtime: builtin` 映射到 Core/Built-in Feature；新外部能力仍通过 Host API、Extension Gateway 或公开合同访问系统。

### 3.5 Resource 与 Appearance

- 新资源目录为 `data/resources`，风格、Skill、Prompt、Persona 和知识元数据没有业务 Runtime。
- 新包必须提供安全 ID、类型、版本、兼容范围、入口、来源和内容 checksum。
- 校验拒绝路径逃逸、符号链接、Go 服务代码、Plugin Manifest、migration 和启动脚本。
- 旧 `data/plugin_data/*/style-packs` 保留为 Legacy Source；新资源优先，同 ID 自动去重。
- Appearance Facade 已统一 Catalog、Validator、Preference 和 Policy 边界，旧 Homepage/WebTheme/Space Style 继续通过兼容源工作。

### 3.6 Agent 安全边界

- v7 只定义 Agent Core、Runner、Knowledge Provider 和 MCP Provider 合同。
- Runner 只能使用 gRPC、Wasm 或 Remote HTTP 等隔离 Runtime。
- 数据库、JWT 私钥、CampusOS 用户 Token 和完整宿主文件系统属于禁止权限。
- CampusOS 凭据永不导出；第三方 Secret 默认不导出明文。

## 4. 兼容性结果

| 合同 | v7 结果 |
| --- | --- |
| HTTP | 仍为 148 条路由；路由 JSON、OpenAPI 和权限合同 checksum 与冻结基线一致 |
| Database | 仍为 18 个 migration、30 张架构视图表；没有改写历史 migration |
| Plugin | 9 个现有 Manifest 和 builtin/gRPC/Wasm 模板继续通过 |
| Storage | 没有移动或删除现有个人空间文件和风格包 |
| Frontend | Web、Admin、docs-site 构建和真实浏览器流程通过 |
| Recovery | 数据库和文件隔离恢复演练通过 |

## 5. 保留的技术债务

以下内容是已记录的兼容债务，不是 v7 漏项：

1. 架构检查存在 8 个 allowlist 项，其中两个是允许创建具体 Repository Adapter 的 Server composition root，其余是 MCP、Moderation、Host API、RichText 和 Space 的历史类型依赖。
2. `application.go` 仍承担兼容业务编排和静态路由。新增模块必须进入独立 assembly；后续可以继续按业务域拆文件，但不能改变路由合同。
3. Legacy builtin 仍保留在 Manager 兼容视图中。只有完成配置、Admin UI、数据和 Manifest 迁移后才能删除，不能直接卸载。
4. Appearance PreferenceStore 的权威数据仍由现有前端本地选择和旧功能配置负责；Facade 首版主要固定后端合同和资源目录边界。
5. Web/Admin 生产构建仍有大 chunk 告警，属于前端性能优化，不影响 v7 架构正确性。

## 6. 下一阶段建议

### P0：稳定运行

- 观察 Feature restart/hot-gated 状态在真实管理操作中的日志和错误提示。
- 为 Bootstrap 的 PostgreSQL fallback、Core Port 注册失败和优雅停止增加故障注入测试。
- 逐项移除非 composition-root allowlist，优先将 MCP 和 RichText 的 Community Repository 依赖替换为只读 Port。

### P1：兼容层收敛

- 为 Built-in Feature 增加独立 Admin 状态接口和配置页，再停止通过普通 Plugin 安装/卸载视图管理。
- 将 Homepage、WebTheme、StylePack 和 Space Style 的查询/应用入口逐步改为直接调用 Appearance Facade。
- 为 Resource Package 增加签名、原子导入、导出和版本回滚；确认稳定后再提供 legacy 目录迁移工具。
- 将 Appearance 用户偏好从仅本地选择扩展为可选的服务端同步，同时保留离线兼容。

### P2：v7 明确后置能力

- Agent Center、任务历史、审批流和配额。
- 独立进程或容器 Agent Runner、标准 MCP Server、Knowledge Provider。
- 第三方 Secret 加密 envelope、跨实例密钥协商和审计式迁移。
- Persona、Prompt、Skill 和知识资源的完整管理产品。

这些工作应进入独立 v8 计划。未完成威胁模型、隔离、审批、审计和回滚前，不得开放任意代码执行或明文 Secret 迁移。

## 7. 最终判断

v7 的架构重构目标已经完成：系统由集中装配的插件混合架构转为具有 Module Kernel、Core Port、Built-in Feature Registry、External Plugin Platform 和 Resource Package Repository 的模块化单体。当前剩余工作属于兼容层逐步移除、测试增强和下一版本产品能力，不应通过继续扩大 v7 范围来处理。
