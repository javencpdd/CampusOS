# CampusOS v7 架构优化计划书

> 文档状态：执行中  
> 编写日期：2026-07-12  
> 当前实现基线：`v0.6.24-dev`  
> 实施记录目录：`docs/进度/v0.6-dev/`（过渡期沿用现有编号）  
> 原则：模块化单体、渐进迁移、兼容优先、安全和数据完整性优先

## 1. 现状审查

### 1.1 已有基础

CampusOS 已有 Identity、Community、插件三类 Runtime、Host API、Extension Gateway、动态 UI、个人空间、课表、富文本、版主、风格包、集成中心、数据库契约和发布门禁。v7 不重写这些能力，而是在保持 API、表结构和前端流程的前提下重新明确归属和装配边界。

### 1.2 已确认的问题

| 问题 | 当前证据 | 影响 |
| --- | --- | --- |
| 启动装配集中 | `internal/server/server.go` 同时创建 EventBus、插件 Runtime、Repository、Service、Handler、Host API 和 148 条路由 | 依赖方向不透明，难以独立启动、停止和测试模块 |
| 系统功能与外部插件混合 | `category-moderation`、`personal-space`、`richtext`、`schedule`、`homepage-customizer`、`web-theme` 都以 `runtime: builtin` 进入 Plugin Manager | 安全核心可能被误当可卸载插件；Plugin Manager 职责膨胀 |
| Storage 归属不清 | RichText 与 Schedule 直接依赖 `internal/space` 的文件配置/路径能力 | Personal Space 停用可能错误影响独立功能，存储 Port 不稳定 |
| Appearance 重复 | Homepage、WebTheme、StylePack 和 Personal Space style 分散在多个包和配置入口 | 安全筛查、资源目录、用户偏好和导入导出规则容易漂移 |
| 跨模块依赖具体实现 | Server 直接组装 PG/Memory Repository，部分功能包直接引用其他功能包 | 无法明确 Port、表所有权和替换边界 |
| 生命周期只在插件平台完整 | 普通 Go 业务模块没有统一依赖检查、启动顺序、健康状态和逆序停止 | 启动失败回滚和优雅停止不可统一验证 |
| Agent 资源尚无正式分类 | Skills、Prompt、Persona 与插件能力没有统一包标准和权限边界 | Agent 生成插件难迁移，敏感配置可能被错误导出 |

## 2. 目标架构

```text
CampusOS Modular Monolith
├── Core Modules
│   ├── Platform Kernel / Module Registry
│   ├── Identity & Authorization
│   ├── Community Integrity & Category Moderation
│   ├── User Storage
│   └── Plugin Security Boundary
├── Built-in Feature Modules
│   ├── Personal Space
│   ├── Controlled RichText Article
│   ├── Personal Schedule
│   ├── Appearance
│   ├── Integration Center
│   └── Agent Center (later P1)
├── Plugin Platform
│   ├── Catalog / Package Governance
│   ├── Runtime Registry
│   ├── Lifecycle / Config / UI / Event Registries
│   ├── Host API / Extension Gateway
│   └── gRPC / Wasm / Remote HTTP / MCP / Agent Runner
└── Resource Packages
    ├── Theme / Homepage / Space Style Packs
    ├── Skills
    ├── Prompt Templates
    └── Persona / Knowledge Metadata
```

## 3. 四类能力合同

| 类型 | 编译与部署 | 生命周期 | 数据行为 | 访问边界 |
| --- | --- | --- | --- | --- |
| Core Module | 编译进主程序 | 必须启用，不允许卸载 | 迁移只追加；保证平台完整性 | 通过公开 Port/Facade；可发布领域事件 |
| Built-in Feature Module | 编译进主程序 | 可启停、不可普通安装/卸载 | 停用隐藏路由/UI，但不删数据 | 只依赖 Core Port，不读取外部插件内部状态 |
| External Plugin | 独立包/进程/Wasm/远程端点 | 可安装、升级、停用、卸载 | 仅拥有声明的数据目录/KV | 只能走 Host API、Gateway、MCP 或公开 HTTP API |
| Resource Package | 数据文件 | 校验、导入、应用、导出；无业务进程生命周期 | 保存到 `data/plugin_data` 或资源仓库 | 不获得 JWT、DB、Service 或任意文件系统能力 |

兼容期继续读取 `runtime: builtin`，但通过 `legacy_builtin_mapping` 将已知系统功能映射到 Core/Built-in Feature；新系统功能不得再注册成普通可卸载插件。

## 4. 模块接口与依赖规则

首版 Module Kernel 使用小接口，不引入反射式 DI 框架：

```go
type Module interface {
    ID() string
    Dependencies() []string
    Register(*AppContext) error
    Start(context.Context) error
    Stop(context.Context) error
    Health(context.Context) Health
}
```

最终接口可以按实践拆为可选生命周期能力，但必须满足：

1. ID 稳定且唯一；依赖必须存在，循环依赖启动前失败。
2. Core 不可禁用；Built-in Feature 可禁用但依赖数据保留。
3. 按拓扑顺序 Register/Start，失败时逆序 Stop 已启动模块。
4. AppContext 只保存明确注册的 Port，不作为任意全局 Service Locator。
5. 模块不得导入其他模块的 PostgreSQL Repository；跨模块写入通过 Port/应用服务，异步协作通过领域事件。
6. External Plugin 永远不能注册 Core Module 或直接取得 AppContext。

## 5. 模块与数据所有权

| 模块 | 拥有的数据/目录 | 可公开的 Port |
| --- | --- | --- |
| Identity Core | `users`、`accounts`、`sessions`、`roles`、`permissions`、`user_roles`、API keys | CurrentUser、UserReader、Authorization、RoleAdministration |
| Community Core | `categories`、`threads`、`posts`、`tags` 及关联表 | CategoryReader、ThreadReader/Writer、PostReader/Writer |
| Moderation Core | 版主作用域规则、治理审计；复用权限与社区表 | ModerationPolicy、CategoryScopeReader、ModerationAudit |
| User Storage Core | `data/personal-space/<user>/`、配额/文件元数据和 Provider 配置 | AssetStore、UserFileStore、Quota、SafePath、Provider |
| Plugin Platform | `plugins`、插件 API/事件/日志/KV、`data/plugins` | PluginCatalog、RuntimeDispatcher、Gateway、PluginAudit |
| Personal Space Feature | `user_spaces`、`user_space_contents`、`user_space_styles` | PublicProfile、SpaceContentQuery |
| RichText Feature | `richtext_articles`、`richtext_assets` | ArticleService、EditorProvider、RendererProvider、TemplateProvider |
| Schedule Feature | User Storage 下 `file/schedule/` 的学期 JSON | ScheduleQuery/Command、ScheduleImporter |
| Appearance Feature | 首页配置、主题偏好与 `data/plugin_data/*/style-packs` | PackageValidator、AppearanceCatalog、PreferenceStore |

第一阶段不移动表；先用所有权文档和 Port 固化边界。需要迁移时只新增 migration，不改写 `000001` 至 `000018`。

## 7. Agent、提示词与迁移安全

### 7.1 Agent 分类

- Agent Core：Core Module，只提供权限判定、任务/审计合同和安全 Port。
- Agent Center：Built-in Feature，负责用户界面、任务历史和授权确认。
- Agent Runner：External Plugin，未来独立进程/容器执行；不能获得 DB、JWT 私钥或宿主完整文件系统。
- Knowledge Provider/MCP：External Plugin，只返回声明范围的数据。
- Skills/Prompt/Persona：Resource Package，必须有 manifest、来源、版本、兼容范围和 checksum。

### 7.2 提示词助手输出标准

提示词助手必须要求 Agent：读取 Host API/Manifest/UI Contract 文档；选择外部 Runtime；声明最小权限；使用 `data/plugin_data/<id>`；提供 README、配置 schema、测试和迁移说明；运行 `campusosctl plugin inspect/dev`；不得导入 `internal/*` 或直接连接 PostgreSQL。

### 7.3 配置和 Token 导出策略

| 配置类型 | 默认导出 | 规则 |
| --- | --- | --- |
| CampusOS 用户 Access/Refresh Token、Session、Host Token、JWT/API key | 禁止 | 目标系统必须重新登录、授权或签发；导出包只记录“需要重新认证” |
| CampusOS JWT 私钥、数据库 DSN/密码、内部服务凭据 | 禁止 | 不进入资源包、插件包或普通配置导出 |
| 第三方平台 Token/API key | 可选、默认脱敏且不导出明文 | 仅在用户显式选择、目标支持加密 secret envelope、导入时再次确认时允许 |
| 非敏感插件配置 | 允许 | 经过 schema 校验，移除机器路径和运行时生成字段 |
| 路径、端口和实例 URL | 条件允许 | 标记 environment-specific，导入后必须重新确认 |

第三方 secret “可以迁移”不等于可以默认明文导出。v7 先交付分类、提示和可扩展 Secret Export Policy；加密封装与跨实例密钥协商在 P2 实现。

## 8. 测试与验收

每阶段必须执行定向测试和：

```bash
GOCACHE=/tmp/campusos-go-cache go test ./... -count=1
git diff --check
make docs-links
```

按改动追加：Web/Admin/docs-site/TypeScript SDK build、`make database-check`、架构同步、`make release-check`、真实 Chrome workflow 和 restore drill。

关键新增测试：依赖缺失/循环、确定启动顺序、启动失败回滚、逆序停止、Core 禁用拒绝、Feature 停用数据保留、跨模块 Repo 禁止、外部插件越权、Resource Package 无 Runtime、Secret 导出负向测试。

## 9. 回滚与兼容

1. 所有新 Registry/Port 先作为适配层接入，旧构造函数、路由和 manifest 继续工作。
2. 每次只迁移一个模块；保留开关以回退旧装配路径，验证稳定后再删除重复实现。
3. Built-in Feature 停用只注销路由/UI/事件订阅，不执行 DROP、DELETE 或目录清理。
4. `runtime: builtin` 不立即删除；已知内置业务映射到模块，未知历史 builtin 给出兼容警告。
5. 表和目录迁移必须先备份、提供幂等脚本、checksum/数量核对和可验证回滚。
6. API 或 UI Contract 变化必须走加法字段/新版本；旧前端和旧插件包至少保留一个过渡阶段。

## 11. 风险与禁止事项

- 禁止一次性重写 `server.go`、删除旧 API/表/目录或把模块化单体拆成大量微服务。
- 禁止以“模块化”为名引入全局 Service Locator、反射式自动装配或不可追踪依赖。
- 禁止 External Plugin/Agent Runner 直接导入 Core internal package、访问 DB 或获得 JWT 私钥。
- 禁止停用 Feature 时删除用户数据。
- 禁止为了通过测试取消权限、审计、安全 HTML/CSS、路径、配额或数据库约束。
- 禁止默认明文导出任何 Token；CampusOS token 永不导出，第三方 secret 必须显式授权并使用未来的加密封装。
- 禁止 Resource Package 注册业务路由、后台进程或数据库迁移。
- 禁止在缺少回滚、负向测试和文档时标记阶段完成。

## 12. 最终验收定义

只有 A0-A7、B1-B4 和 Final 全部通过各自验收，且以下条件同时成立，才标记 v7 架构优化完成：`server.go` 不再集中装配业务细节；四类能力可机器识别；关键模块有依赖/生命周期/健康；Moderation 为 Core；User Storage 独立；Space/RichText/Schedule/Appearance 为 Built-in Feature；Plugin Manager 只管理 External Plugin 并保留兼容 Facade；Resource Package 无业务生命周期；Agent/Secret 边界有代码合同和文档；现有数据/API/UI/插件包回归通过。
