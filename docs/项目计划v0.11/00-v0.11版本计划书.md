## 1. 计划结论

`v0.11版计划书思路.md` 同时提出了 v0.11 至 v0.13 的工作。经代码、迁移、
前后端、发布门禁和 v0.10 最终审计复核，正式 v0.11 只承担一条主线：

> 让高风险命令、授权审计和领域事件可靠提交，让异步任务在重启、重复执行和
> 多 Worker 竞争下可恢复，并把 Webhook 收紧到可治理的安全投递边界。

邮箱验证、多级板块、校园互助、二手交易、系统化容量压测和性能优化不纳入
v0.11。它们分别进入 v0.12 和 v0.13，不能以“顺便实现”的方式扩大本版本事务、身份、
社区和前端的改动面。

v0.11 不替换 v0.10 的 RBAC，不引入 Casbin、通用 ABAC、微服务或分布式事务框架。
稳定 Permission Code、路由 Operation、`global/category` 作用域、自定义角色、
版主范围和最后管理员保护继续有效；本版本补齐的是这些高风险写操作与审计、
事件之间的一致性。

## 2. 当前基线审查

### 2.1 已具备的基础

- 后端已经是模块化单体，Core、Built-in Feature、External Plugin 和 Resource
  Package 在实现、描述符、API 和数据目录上分离。
- v0.10 已建立稳定 Permission Code、路由 Operation、授权目录、板块作用域、
  自定义角色、越权保护、最后管理员并发保护和 `authorization_audits`。
- Community 已有内容治理状态机；Plugin Platform 已有安装预检、签名、快照、
  Runtime 和审计；Resource Package 已有检查、采用和回滚工具。
- 当前生成合同包含 194 条 HTTP 路由；历史兼容文件名中的 `v0.6` 不代表内容
  仍停留在 v0.6。
- v0.10 已通过 Go、Web、Admin、docs-site、SDK、数据库、联合恢复和七视口门禁。
- 本计划编写时再次通过全量 Go 测试、合同检查、架构边界和数据治理检查。

### 2.2 已由代码确认的缺口

| 缺口 | 当前事实 | v0.11 影响 |
| --- | --- | --- |
| 注册不是原子命令 | `UserService.Register` 先写 `users`，再独立写 `accounts` | 第二步失败会留下不完整用户 |
| 登录未消费验证状态 | `accounts.verified` 已存在，但凭据查询不读取它 | 记录为 v0.12 邮箱验证前置事实，v0.11 不开放验证流程 |
| 审计非原子 | 角色、范围和请求授权记录通过独立 Repository 调用写入 | 业务成功后审计失败，不能作为不可丢失账本 |
| 事件不持久 | Memory Bus 使用 goroutine，NATS 使用普通 publish | 提交后崩溃或消息系统异常时事件可能丢失 |
| Webhook 不可恢复 | 订阅回调再启动 goroutine，同一调用内 `time.Sleep` 重试 | 重启丢任务，失败无法可靠接管和重放 |
| Webhook SSRF 防线不足 | URL 只校验 `http/https` 和 host | 未阻止私网、loopback、重定向和 DNS 重绑定 |
| 投递幂等不足 | `webhook_deliveries` 没有可靠任务状态机和唯一投递约束 | 崩溃窗口可能重复产生外部副作用 |
| 可观测性较基础 | 当前 Collector 主要保存进程内计数和最近延迟 | 无积压年龄、lease 冲突、dead-letter 和审计失败指标 |
| 保留策略未执行 | 多类日志和审计表没有统一 dry-run/分批清理框架 | 长期运行容量不可预测 |

### 2.3 本计划不把推测写成事实

- NATS 仍可作为事件传输适配器，但不能被当作业务事务的持久来源。
- Webhook 只能承诺“至少一次投递”；HTTP 无法在发送成功而状态提交失败的窗口
  内提供真正的 exactly-once。接收方必须使用 `event_id + endpoint_id` 幂等。
- PostgreSQL 事务不能覆盖插件进程、文件替换或外部 HTTP。此类操作必须使用
  持久操作状态、临时目录、原子重命名和补偿步骤，不能伪装成数据库原子事务。
- v0.11 不删除旧权限表、旧审计表、旧事件接口、现有 API 或用户数据。

## 3. 范围与版本语义

### 3.1 必须完成

1. v0.10 基线冻结和可重复验证快照。
2. 高风险命令、事件、审计和失败模式目录。
3. 模块内可复用但不泄露 `pgx` 的 TxKernel/Unit of Work 边界。
4. 持久 Outbox、消费凭证、Worker lease、重试和 dead-letter。
5. Identity 注册、角色、权限矩阵和版主范围的原子命令。
6. Community 高风险治理命令的原子审计和事件写入。
7. External Plugin 与 Resource Package 的可恢复补偿流程。
8. Webhook 的持久投递、幂等、限流、响应限制和 SSRF 防护。
9. 保留策略 dry-run、兼容路径遥测和可靠任务可观测性。
10. Admin 可靠任务入口、故障注入、恢复演练和最终发布门禁。

### 3.2 明确不做

- 邮箱验证码、邮件 Provider、验证页面和旧用户验证迁移。
- 多级板块、父子权限继承、互助贴和二手交易结构化类型。
- 全站容量目标、长期压测、缓存优化和生产集群 HA。
- 标准 protobuf gRPC、标准 MCP Server、完整 Agent Center 或代码执行器。
- 通用工作流引擎、跨服务 2PC、Event Sourcing 重写或数据库拆分。
- 物理删除 v0.10 兼容表、兼容 API、历史数据或旧 Manifest。

## 4. 目标运行链路

### 4.1 数据库内高风险命令

```text
HTTP / Internal Caller
  -> Authentication
  -> Route Operation + Permission Code 候选检查
  -> Command Handler
  -> TxKernel
       -> 在事务内重新读取授权与资源事实
       -> Business Repository 写入
       -> Required Audit 写入
       -> Outbox Event 写入
  -> COMMIT
  -> Worker claim Outbox
  -> EventBus / Internal Consumer / Webhook Fan-out
```

规则：业务写入、必需审计或 Outbox 任一失败，高风险数据库命令全部回滚。事务
提交后才允许产生外部副作用。

### 4.2 授权拒绝

```text
Permission denied
  -> 始终拒绝请求
  -> 独立记录 deny audit
  -> 审计失败时增加指标和受控日志
```

拒绝审计失败不能把拒绝变成允许。没有业务写入，因此也不存在可回滚的业务事务。

### 4.3 文件、插件进程和外部系统

```text
Validate -> Persist operation intent -> Stage -> Apply -> Verify -> Commit outcome
                                          \-> Compensate / dead-letter
```

插件包、资源包、文件和进程生命周期采用 Saga/补偿语义。每一步必须幂等，临时
目录不能覆盖正式目录，失败状态必须可见且可人工重试。

## 5. 核心合同

### 5.1 TxKernel

最终 Go 接口由 A2 的 ADR 确认，但必须满足以下边界：

```go
type Manager interface {
    Within(context.Context, func(context.Context) error) error
}
```

- Service 不直接调用 `pool.Begin`，也不接收 `pgx.Tx`。
- 事务 Scope 只能由同一模块的 Repository Adapter 解析；不能演变为全局 Service
  Locator。
- 已有 Repository 接口保持兼容，新增 tx-aware Adapter 或命令级 Unit of Work。
- PostgreSQL 和 Memory Adapter 使用同一合同测试；Memory 模式也必须验证回滚。
- 不允许 External Plugin、Agent Runner、MCP 或 HTTP 客户端取得 TxKernel。
- 不把网络调用、NATS publish、文件替换或进程启动放进数据库事务。

### 5.2 命令目录

每个高风险命令至少记录：

```text
command_code, owner, operation_code, permission_code, risk_level
business_tables, required_audits, emitted_events
transaction_strategy, idempotency_key, retry_policy
sensitive_fields, timeout, rollback_or_compensation
```

首批命令：

- `identity.user.register`
- `identity.role.assign`、`identity.role.revoke`
- `identity.role.permissions.update`
- `moderation.scope.update`
- `community.thread.take_down/review/restore/trash/purge`
- `plugin.package.install/update/rollback/uninstall`
- `appearance.resource.apply/rollback`
- `integration.webhook.configure/deliver/replay`

Command Code 描述业务写命令，Permission Code 描述“谁可以做”，Operation Code
描述“从哪个传输入口进入”。三者不能互相替代。

### 5.3 Outbox 与 Worker

从 migration `000027` 起顺序追加，首版预计包含：

```text
platform_outbox
outbox_consumer_receipts
worker_leases
```

字段和约束至少覆盖：事件 ID、聚合信息、schema version、payload、headers、状态、
幂等键、尝试次数、下次可用时间、lease owner/期限、创建/发布时间、最后错误和
dead-letter 时间。Payload 不得保存密码、Token、验证码、Webhook Secret、JWT
或第三方密钥。

Worker 必须具备：

- `FOR UPDATE SKIP LOCKED` 或等价安全 claim；
- 有期限的 lease 和 fencing/条件更新，防止过期 Worker 覆盖新 Worker；
- 指数退避、抖动、最大重试和 dead-letter；
- `context` 驱动的优雅停止；
- 消费凭证与幂等键；
- 管理员受权限保护的手动重放；
- 多 Worker 并发、崩溃接管和重复消费测试。

### 5.4 权限与审计

v0.11 继续以 v0.10 权限目录为事实源。新增可靠性字段可包括：

```text
transaction_id
command_code
resource_version
sequence
```

最终迁移前必须确认哪些字段追加到现有业务审计表，哪些只进入统一审计 Envelope，
避免一次性合并 `authorization_audits`、Moderation、Plugin 和内容治理审计。

高风险允许路径必须在事务内重新读取操作者权限和资源真实作用域，降低“检查后
权限被撤销”造成的 TOCTOU 窗口。角色修改继续保留：禁止自助提权、操作者权限
上限、系统角色保护、版主显式板块范围和最后管理员原子保护。

完整入门和开发规则见 [v0.11 权限管理与可靠审计设计入门](../help/系统设计相关/v0.11权限管理与可靠审计设计入门.md)。

验收：每个进入 A2-A8 的命令都有 owner 和策略；未评审命令不得标记“可靠”。

### 6.5 A2：TxKernel

建议目录：`internal/platform/transaction/` 及各模块 Adapter；不得把模块 Repository
集中迁入平台层。

交付：

- PostgreSQL `Within`、嵌套调用规则、panic/error rollback 和 commit error 处理；
- Memory 事务语义；
- tx-aware Repository 适配；
- 超时、取消、隔离级别和重试边界；
- 架构检查阻止 Service 新增 `pool.Begin` 和跨模块取得 Tx。

回滚：新 Kernel 先以适配层接入，旧路径保留阶段开关；不得回退数据库结构。

### 6.6 A3：Outbox Store

建议目录：`internal/platform/outbox/`、`migrations/000027_*`、数据库检查器。

交付：schema、PG/Memory Repository、事务内 enqueue、payload 版本、幂等约束、
查询/claim 接口和迁移 up/down/up 演练。A3 不直接启动复杂业务消费者。

回滚：生产优先 forward-fix；隔离环境可在清空新表前提下 down。旧 EventBus API
继续存在，未迁移调用方不受影响。

### 6.7 A4：Worker Runtime

建议目录：`internal/platform/worker/`、`internal/server` 模块装配和定向脚本。

交付：Worker Module 生命周期、lease、重试、dead-letter、消费凭证、优雅停止、
健康状态和管理员只读查询 Port。禁止无跟踪 goroutine 和用 `time.Sleep` 代替持久
调度状态。

验收：两个 Worker 只能成功 claim 一次；崩溃后 lease 可接管；过期 Worker 的
完成写入被拒绝；重放保留原事件关联并生成新尝试记录。

### 6.8 A5：Identity 与权限原子命令

主要目录：`internal/modules/core/identity/`、`internal/modules/core/moderation/`、
`admin/src/modules/identity/`、权限文档。

交付：

- `users + accounts + required audit + user.created outbox` 原子注册；
- 角色授予/撤销与授权审计原子提交；
- 自定义角色权限矩阵更新、版主板块范围与审计原子提交；
- 最后管理员、操作者权限上限和自助提权负向测试继续通过；
- 高风险写入在事务内复核权限和真实 scope；
- Admin 清晰展示 command/transaction/request 关联，但不显示 Secret。

兼容：注册响应和现有登录 API 不变；`accounts.verified` 的登录语义仍留到 v0.12，
不得在没有邮件流程时突然阻止旧用户登录。

### 6.9 A6：Community 高风险治理

主要目录：`internal/modules/core/community/`、Moderation Gateway 和内容测试。

第一批覆盖下架、审核通过/拒绝、直接恢复、回收站恢复、移入回收站和永久清除。
每次操作必须锁定/校验内容版本，使用数据库中的真实板块和状态，原子写业务事实、
内容治理审计、授权审计和 Outbox。

兼容：公开/作者/Admin 查询语义、普通文本/RichText 适配和旧状态字段保持不变。
冲突使用稳定错误码返回，不允许静默覆盖并发操作。

### 6.10 A7：Plugin 与 Resource 补偿流程

主要目录：`internal/plugin/`、`internal/platform/resource/`、`data/` 治理脚本。

交付：

- 安装、升级、回滚、卸载和资源应用的持久 operation ID；
- staging 目录、checksum、原子 rename、版本快照和冲突停止；
- 数据库意图/结果、插件审计和 Outbox 关联；
- 进程启动失败、文件替换失败、数据库提交失败的补偿；
- 服务重启后能识别 `pending/applying/compensating/failed` 状态。

禁止在数据库事务中等待进程或网络。External Plugin 仍不能取得 TxKernel、DB、
JWT 私钥或用户 Token。

### 6.11 A8：Webhook 可靠安全投递

主要目录：`internal/modules/features/webhook/`、Outbox consumer、Admin Integration。

交付：

- Domain Event -> Outbox -> fan-out -> Delivery Job -> HTTP Sender；
- `event_id + endpoint_id` 唯一约束和接收方幂等说明；
- 网络/429/5xx 可控重试，普通 4xx 默认终止，支持 `Retry-After`；
- Endpoint 级并发、速率、超时、响应头/体大小限制；
- 每次解析和每次重定向校验目标，生产默认拒绝 loopback、私网、link-local、
  multicast、未指定地址和云元数据地址；
- DNS 解析结果与实际拨号目标一致，防止解析后替换；
- 签名版本、时间戳、重放窗口，Secret 不进入响应、日志、审计或 Outbox；
- dead-letter 查看和显式重放。

开发环境如需本地 mock，必须通过显式测试 profile/allowlist 开启，不能降低生产
默认策略。

### 6.12 A9：保留策略与兼容遥测

第一阶段只做 inventory、dry-run 和影响报告。纳管内容修订、内容审核、授权审计、
插件日志、Webhook 投递、MCP/Message/AI 日志和 Outbox 历史。

兼容遥测至少统计：旧 `permissions` 回退、旧 Built-in API、历史 Manifest 字段、
`user_space_contents`、`runtime: grpc` 兼容名称。没有连续版本证据前不得删除。

执行清理必须分批、有上限、可取消、记录 run 和数量/checksum 对账；法定或安全
保留记录不能被普通管理员随意清除。

### 6.13 A10：可观测性与 Admin

建议新增受控指标：

```text
outbox_pending_total
outbox_oldest_age_seconds
outbox_retry_total
outbox_dead_letter_total
worker_lease_conflicts_total
audit_write_failures_total
webhook_delivery_total
webhook_delivery_duration_seconds
compatibility_path_usage_total
```

Admin 新增“可靠任务”页面，展示积压、最老任务、Worker 健康、dead-letter、Webhook
失败、审计失败和保留任务。查询必须分页和限流；重放、保留执行使用独立高风险
Permission Code，不能只依赖 `admin` 角色名。

指标不得把 `user_id`、`event_id`、URL 或错误全文作为高基数 label；详细关联通过
受权限保护的日志/审计查询完成。

### 6.14 Final：全链路验收

必须验证：

| 故障场景 | 预期结果 |
| --- | --- |
| 用户写入成功、账号写入失败 | 两者和成功审计全部回滚 |
| 业务写入成功、必需审计失败 | 高风险命令回滚 |
| 业务与 Outbox 已提交后进程退出 | 重启后继续处理 |
| Worker claim 后崩溃 | lease 到期后其他 Worker 接管 |
| 两个 Worker 同时 claim | 只有一个获得有效 lease |
| 过期 Worker 回写 | fencing/条件更新拒绝 |
| Webhook 发送成功但状态写入失败 | 允许重试，接收方幂等阻止重复副作用 |
| Webhook 指向私网或重定向到私网 | 投递前拒绝并记录安全原因 |
| Plugin/Resource apply 中途失败 | 正式目录不损坏，可补偿或明确进入 failed |
| dead-letter 手动重放 | 权限、审计、幂等和关联字段完整 |

Final 必须生成实施回顾、兼容矩阵、未完成事项和 v0.12 进入条件，不能只写“测试通过”。

## 7. 权限管理专项设计

### 7.1 不变部分

- 权限事实仍是 Permission Code，不使用页面按钮或 URL 作为授权事实。
- 路由 Operation 负责传输入口，应用服务负责读取真实资源并做最终 scope 判断。
- `moderator` 仍必须绑定一个或多个明确板块；不自动获得全站权限。
- 系统角色保持受保护，自定义角色只能在操作者自身权限上限内调整。
- HTTP Handler 必须从认证上下文取得 actor，缺失时 `401`，不能降级到内部接口。
- External Plugin 的 Host 权限、用户 Grant 和管理员 RBAC 仍是三套独立合同。

### 7.2 v0.11 新增部分

- 每个高风险写操作有稳定 Command Code 和风险等级。
- 允许路径在事务内复核权限，写入业务事实、required audit 和 Outbox。
- 审计增加 request/transaction/command/event 关联，不保存敏感值。
- 重复请求通过 Idempotency Key 返回同一命令结果或稳定冲突，不重复授权副作用。
- 可靠任务查看与重放分别使用 `platform.reliability.read` 和
  `platform.reliability.replay` 等稳定 Code；最终名称由 migration 和合同生成器确定。
- 审计不可用时，高风险写操作 fail closed；授权拒绝仍保持拒绝并产生告警。

### 7.3 权限文档同步门槛

A5 和 A10 完成时必须同步更新：

- `docs/help/系统设计相关/v0.11权限管理与可靠审计设计入门.md`
- `docs-site/guide/permission-configuration.md`
- HTTP 路由与授权矩阵、OpenAPI 和 Permission Catalog
- Admin 权限页面、可靠任务页面和常见问题

文档必须把“当前已实现”和“计划目标”分开，不能让管理员按尚未存在的按钮操作。

## 8. 数据、迁移与兼容

1. 冻结 `000001` 至 `000026`，只允许从 `000027` 顺序追加。
2. 新表由 Platform Reliability/对应模块明确拥有；不得由 External Plugin 写入。
3. migration 必须 up、隔离环境 down/up、schema contract、架构视图和备份恢复同步。
4. 旧 EventBus、Webhook API、权限表和审计表先保留；新路径以 Adapter 渐进接管。

7. Outbox payload 采用显式 schema version；消费者先支持新旧版本再切换生产者。

## 11. 回滚策略

- TxKernel、Outbox producer 和新 consumer 先通过配置开关渐进启用；回退时停止新
  producer，排空/冻结队列，再回退消费者，避免双重投递。
- 数据库内命令回滚代码时，保留新表和新列，生产采用 forward-fix。
- Worker 回退前必须释放 lease 或等待到期，不能手工把 processing 全部改成功。
- Webhook 回退不得重新启用不安全 URL；失败投递保留为 dead-letter。
- 插件/资源补偿以 snapshot 和 operation run 为依据；冲突时停止，不覆盖用户文件。
- 每次阶段回滚后重新运行 schema contract、数据对账和适用的浏览器 smoke。

## 12. 风险与禁止事项

| 风险 | 等级 | 控制 |
| --- | --- | --- |
| 事务改造导致锁竞争或死锁 | 极高 | 小批迁移、固定锁顺序、超时、冲突测试 |
| Outbox 重复消费 | 极高 | 幂等键、消费凭证、唯一约束、至少一次语义说明 |
| Worker lease 脑裂 | 极高 | lease 期限、owner/generation 条件更新、故障注入 |
| 审计中泄露敏感值 | 极高 | 字段 allowlist、测试、日志扫描、禁止原始 payload |
| Webhook SSRF | 极高 | 解析和拨号绑定、重定向复核、生产默认拒绝私网 |
| 插件文件与数据库状态分裂 | 高 | staging、持久步骤、checksum、补偿与快照 |
| 兼容双写长期存在 | 高 | 遥测、退出标准、单一 owner、不得无限保留 |
| 指标高基数拖垮系统 | 高 | 固定 label 集合，详情进入日志/审计查询 |

禁止：

- 一次性重写 Identity、Community、Plugin Manager 或 EventBus。
- 在 Service 中新增散落的 `pool.Begin`。
- 在数据库事务内执行 HTTP、NATS、文件替换或进程启动。
- 宣称 HTTP Webhook exactly-once。
- 用无限重试、无 lease goroutine 或 `time.Sleep` 作为持久调度器。
- 为通过测试删除权限、审计、状态机、路径、配额或内容安全校验。
- 让 External Plugin/Agent Runner 取得 DB、TxKernel、JWT 私钥或用户 Token。
- 默认明文导出或记录任何 CampusOS/第三方 Token 和 Webhook Secret。
- 在没有遥测、备份和回滚证据前删除历史兼容对象。

## 17. Post-Final 专业复审闭环

2026-07-16 对计划逐项复核时发现，A10 的“查询必须分页和限流”只有服务端条数上限，
并非可翻页合同；可靠性事件 Handler 还直接序列化了内部 Event，可能把 payload、
headers 和幂等键返回给管理端；A3 虽有 migration down 文件，但没有独立的
`000027` up/down/up 自动化演练。这三项均属于原计划验收要求，不能作为后续版本范围
跳过。

复审已完成以下闭环：

1. Memory/PostgreSQL Store 返回分页结果和真实总数，Admin 各列表拥有独立分页状态，
   旧 `limit` 参数保持兼容。
2. 可靠性查询增加有界的单进程 actor/IP 限流，并为 `429` 返回 `Retry-After`。
3. Handler 改用显式安全响应 DTO，事件 payload、headers、幂等键及各类 raw details
   不再跨越运维 API 边界，并增加负向合同测试。
4. `database-check` 接入 v0.11 隔离数据库 migration up/down/up 演练，校验新增对象可
   回退、历史 Webhook endpoint 不丢失、再次 up 后合同恢复。

本次复审不扩大 v0.11 产品范围，也不把单进程限流宣称为集群治理。完整审查矩阵、残余
风险和 v0.12/v0.13 路线见 [v0.11 最终完成审查与后续路线](02-v0.11最终完成审查与后续路线.md)。

## 18. Post-Final 真实启动回归

专业复审后的真实 `STOP_EXISTING=true make dev-all` 暴露出生命周期时序缺口：Module
Registry 会先完成全部 `Register`，再按依赖顺序执行 `Start`；Reliability 原先直到
`Start` 才发布 Service，但 Appearance 和 Plugin Platform 已在 `Register` 查询该 Port，
导致当前后端无法启动，而仍运行的 Vite 页面只显示“可靠任务加载失败”。

修复后，Reliability 在 `Register` 构造并发布稳定 Service/Handler Port，在 `Start`
绑定已启动的 EventBus、恢复任务并启动 Worker。模块 Manifest 同步声明
`core.reliability` 依赖，并新增生命周期回归测试。真实开发环境已完成整个模块图装配，
可靠任务 summary、events、workers、operations、command-audits、compatibility 和
retention-runs 查询均返回 `200`。证据见
[`v0.11.14-dev`](../进度/v0.11-dev/v0.11.14-dev.md)。
