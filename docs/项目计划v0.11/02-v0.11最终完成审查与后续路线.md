## 1. 审查结论

本次没有直接接受“计划表全部打勾”等同于完成，而是从计划要求、运行代码、数据库
迁移、Admin 交互、自动化测试和运维文档六个方向重新核对。A0 至 A10 和原 Final 的
主体功能已经存在，但复审发现三个属于 v0.11 原验收范围的缺口：可靠任务列表没有真正
分页和查询限流、事件 API 直接暴露内部持久事件字段、`000027` 没有自动化
up/down/up 演练。

上述缺口现已补齐，完整 `release-check` 也已通过。v0.11 现在可以从“实现完成”正式
更新为“复审验收完成”。本次没有扩大到邮箱验证、多级板块、交易、集群限流或完整
指标平台。

## 4. 本次修复的验收缺口

### 4.1 真实分页与限流

Memory 和 PostgreSQL Store 现在都返回当前页与实际总数。HTTP 使用 `page`、
`page_size`，同时兼容旧 `limit`；Admin 的事件、尝试、Worker、操作、命令审计、兼容
遥测和保留运行各自维护分页状态。查询按 actor 或 IP 执行默认每分钟 120 次的有界
单进程限流，超限返回 `429` 和 `Retry-After`。分页使用稳定的时间与 ID 次级排序；
限流身份窗口也有容量上限和确定性淘汰，避免大量不同来源造成进程内状态无界增长。

### 4.2 最小化运维响应

事件列表和重放不再直接序列化内部 `Event`。显式 DTO 排除了 payload、headers、
idempotency key；operation、compatibility 和 command audit 同样排除 raw details。
新增 Handler 负向测试，防止敏感字段以后因结构体扩展而再次被自动暴露。

### 4.3 migration 回滚演练

`scripts/test-v11-reliability-migration.sh` 在隔离 PostgreSQL 中执行：

```text
000001-000026 up -> 保存历史 Webhook endpoint -> 000027 up
-> 写入可靠性证据 -> 000027 down -> 验证历史对象保留
-> 000027 up -> 验证表、权限、列和默认值恢复
```

该脚本已接入 `make database-check`。生产仍采用 forward-fix；脚本不是允许直接在生产
执行 down 的依据。

## 5. v0.11 已完成的功能

- 高风险数据库命令通过 TxKernel 原子提交业务事实、required audit 和 Outbox。
- 持久事件具备消费回执、尝试证据、lease、fencing、退避、dead-letter 和受控重放。
- Identity 注册、角色、权限和版主范围保持 anti-escalation 与最后管理员保护。
- Community 内容治理使用真实板块 scope、状态/版本校验、可靠审计和领域事件。
- Plugin 与 Appearance 跨文件操作具备 staging、checksum、snapshot 和可恢复 operation。
- Webhook 具备持久 fan-out、endpoint 级并发/速率保护、签名、响应边界和 SSRF 防护。
- Admin 可查看队列、Worker、操作、命令审计、兼容遥测与 retention dry-run，且查询已
  分页、限流并执行最小字段投影。
- `000027`、数据库合同、故障注入、恢复、浏览器和文档门禁形成发布证据链。

## 6. 兼容与安全结论

- 旧 API、响应包络、EventBus、Webhook endpoint/delivery、权限目录、Manifest 和
  Legacy Resource Source 未删除；可靠性列表保留 `limit` 兼容参数。
- migration 只追加；Feature 停用、Worker 停止或代码回退不会删除用户数据、Outbox、
  dead-letter、审计和操作记录。
- External Plugin、Resource Package、Agent Runner 和浏览器不能取得数据库、TxKernel、
  Reliability Service、JWT 私钥或 CampusOS 用户 Token。
- Webhook 与其他外部副作用明确是至少一次，接收方仍须按事件 ID 幂等。

## 9. 真实启动回归补充

在本审查发布后，管理后台实际访问暴露了一个单元/浏览器门禁未覆盖的启动缺口：
Reliability Service 在 `Start` 才发布，但 Appearance 与 Plugin Platform 在 `Register`
就需要该 Port。由于 Registry 的合同是“先全部 Register，再按拓扑 Start”，当前 API
会退出，已经启动的 Vite 管理页面则显示可靠任务加载失败。此前浏览器门禁复用了已
存在的服务进程，没有验证当前代码的新进程装配。

现已把稳定 Reliability Port 移到 `Register` 发布，把 Worker 和恢复扫描保留在
`Start`；同步模块依赖描述符并新增生命周期测试。使用当前代码重新执行
`STOP_EXISTING=true make dev-all` 后 API 正常就绪，管理页依赖的七个查询全部返回
`200`。完整 release-check 随后通过全量构建、隔离恢复、认证浏览器、风格包和七视口
回归。该缺口和验证证据记录在
[v0.11.14-dev](../进度/v0.11-dev/v0.11.14-dev.md)。
