## 1. 范围与目标

v0.7 只解决模块归属、依赖方向、启动装配和扩展安全边界，不重写现有业务。范围包括：Module Kernel 与 Bootstrap 拆分；Core Module、Built-in Feature、External Plugin、Resource Package 四类能力；Moderation Core；User Storage Core；Built-in Feature Registry；Appearance Facade；Plugin Platform 渐进拆分；Resource Package 基础合同；Agent、Runner、Knowledge、MCP 与 Secret 的接口和安全合同。

本轮不实现完整 Agent Center、知识库管理、Persona 管理、提示词助手、Agent 任务执行、任意代码执行器、跨实例 Secret 加密迁移和外部插件市场。这些能力只能在合同、威胁模型和隔离边界通过验收后进入后续版本。

## 2. 现状问题

| 问题 | 已确认现状 | v0.7 处理方式 |
| --- | --- | --- |
| 启动装配集中 | `internal/server/server.go` 同时装配基础设施、Repository、Service、Handler、Runtime 和大量路由 | 先冻结基线，再拆基础设施和业务模块装配；每次迁移一个职责 |
| 内置功能与插件混合 | 多个系统功能使用 `runtime: builtin` 进入 Plugin Manager | 保留兼容映射，逐步迁入 Core 或 Built-in Feature |
| Storage 边界不稳定 | RichText、Schedule 依赖 Personal Space 的具体文件实现 | 先定义 Port 和旧实现 Adapter，再切换调用方，最后迁移实现归属 |
| Appearance 职责重复 | homepage、webtheme、stylepack、space style 各自维护规则 | v0.7 只提供统一 Facade 和 Adapter，不物理合并全部实现 |
| 跨模块依赖具体实现 | Server 和部分功能直接组装或引用具体 Repository | 用 Port/Facade 收口，并以 allowlist 架构检查阻止新增违规 |
| Plugin Manager 职责膨胀 | Catalog、Runtime、Lifecycle、Config、UI、Event、Audit 混在一个 Manager | 保留 Manager Facade，分三步委托给独立子服务 |
| Agent 边界未固化 | Runner、Knowledge、MCP、Secret 缺少统一权限合同 | 本轮只实现安全接口、权限模型和负向检查 |

## 3. 目标架构与四类合同

```text
CampusOS Modular Monolith
├── Core Modules
│   ├── Platform Kernel / Identity / Community
│   ├── Moderation Core / User Storage Core
│   └── Plugin Security Boundary
├── Built-in Feature Modules
│   ├── Personal Space / RichText / Schedule
│   └── Appearance
├── Plugin Platform
│   ├── Catalog / Runtime / Lifecycle / Config
│   ├── UI / Event / Audit
│   └── gRPC / Wasm / HTTP / MCP / Agent Runner
└── Resource Packages
    └── Theme / Homepage / Space Style / Skill / Prompt / Persona / Knowledge Metadata
```

| 类型 | 生命周期 | 数据与卸载 | 访问边界 |
| --- | --- | --- | --- |
| Core Module | 编译进主程序，`always-on`，不可停用 | 不进入插件安装卸载；迁移只追加 | 通过公开 Port/Facade 协作 |
| Built-in Feature | 编译进主程序，`restart` 或 `hot-gated` | 可启停、不可普通卸载；停用保留全部数据 | 只依赖 Core Port |
| External Plugin | 可独立安装、升级、停用和卸载 | 只拥有声明的数据目录或 KV | 只能使用 Host API、Gateway、MCP 或公开 HTTP API |
| Resource Package | 仅校验、导入、应用、导出 | 无业务进程、路由和 migration 生命周期 | 不获得 DB、JWT、内部 Service 或任意文件系统能力 |

兼容期继续识别 `runtime: builtin`。已知内置功能通过 `legacy_builtin_mapping` 映射到 Core/Built-in Feature；旧 API、表、数据目录和 Manifest 不立即删除。

## 4. Module Kernel 合同

基础接口只承担注册，可选能力使用独立接口，避免要求每个模块实现空生命周期方法：

```go
type Module interface {
    ID() string
    Dependencies() []string
    Register(*AppContext) error
}

type Starter interface { Start(context.Context) error }
type Stopper interface { Stop(context.Context) error }
type HealthReporter interface { Health(context.Context) Health }
```

必须满足：

1. 模块 ID 稳定且唯一；启动前拒绝依赖缺失、禁用依赖和循环依赖。
2. 按确定的拓扑顺序 Register/Start；启动失败时逆序 Stop 已启动且实现 `Stopper` 的模块。
3. Core 不可禁用；External Plugin 不得获取 `AppContext` 或注册 Core Module。
4. `AppContext` 只保存明确命名的 Port；不得保存任意 Repository 集合或演变为全局 Service Locator。
5. 无 `Starter` 的模块注册后视为运行；无 `HealthReporter` 时健康状态为 `unknown`。

## 5. Built-in Feature 启停合同

| 模式 | 适用范围 | 行为 |
| --- | --- | --- |
| `always-on` | Core Module | 不允许配置为停用 |
| `restart` | 需要重新装配订阅或后台任务的 Built-in Feature | 配置变更记录为待重启，重启后生效 |
| `hot-gated` | 可由统一 Gate 拒绝请求的 Built-in Feature | 路由保持静态注册；Gate 热更新启停状态 |

禁止运行时增删 Gin 路由。Feature 停用时只隐藏 UI、由统一中间件拒绝 API、停止可停止的事件处理；不得删除表记录、用户文件或配置。需要重启的状态必须在 Admin 和 API 中明确显示。

## 6. 模块与数据所有权

| 所有者 | 数据或目录 | 首批公开 Port/Facade |
| --- | --- | --- |
| Identity Core | users、sessions、roles、permissions、user_roles、API keys | CurrentUser、UserReader、Authorization、RoleAdministration |
| Community Core | categories、threads、posts、tags 及关联表 | CategoryReader、ThreadReader/Writer、PostReader/Writer |
| Moderation Core | 版主作用域、权限策略、治理审计与完整性规则 | ModerationPolicy、CategoryScopeReader、ModerationAudit |
| User Storage Core | `data/personal-space/<user>/`、配额、路径和 Provider 配置 | UserStorage、Quota、SafePath、AssetStore、Provider |
| Plugin Platform | plugins、插件日志/API/事件/KV、`data/plugins` | PluginCatalog、RuntimeRegistry、Lifecycle、Gateway、Audit |
| Personal Space Feature | user_spaces、space content/style | PublicProfile、SpaceContentQuery |
| RichText Feature | richtext_articles、richtext_assets | ArticleService、Editor/Renderer/Template Provider |
| Schedule Feature | User Storage 中的学期 JSON | ScheduleQuery/Command、ScheduleImporter |
| Appearance Feature | 外观偏好与资源包索引 | AppearanceCatalog、PackageValidator、PreferenceStore、AppearancePolicy |

v0.7 不改写既有 migration。需要数据库变化时只新增 migration，并记录所有权、兼容读写和回滚方式。

## 8. 各阶段兼容与回滚

| 阶段组 | 兼容策略 | 回滚方式 |
| --- | --- | --- |
| A1-A2 | 新 Registry/Bootstrap 作为装配适配层，路由和构造器不变 | 切回旧装配入口；不回滚数据 |
| A3 | allowlist 只阻止新增违规，不要求一次清除历史依赖 | 回滚检查规则文件，不改运行时 |
| A4 | 旧 `category-moderation` 配置只读映射到系统功能配置 | 切回旧配置读取；Core 权限与审计不得关闭 |

| A6 | 路由静态注册；旧插件启停配置映射为 Feature 状态 | 切回 legacy mapping；停用不执行数据清理 |
| A7-A8 | 新资源仓库加法引入；旧 `data/plugin_data/*/style-packs` 继续只读/兼容读写 | 禁用新索引并继续从 Legacy Source 读取 |

## 9. Resource Package 合同

新统一仓库目标为：

```text
data/resources/
├── themes/
├── homepage-packs/
├── space-style-packs/
├── skills/
├── prompts/
├── personas/
└── knowledge-metadata/
```

现有 `data/plugin_data/*/style-packs` 是 `Legacy Resource Source`，v0.7 不立即搬迁或删除。Resource Package 必须有类型、稳定 ID、版本、兼容范围、入口、checksum 和来源；不得注册业务路由、后台进程或数据库 migration。

## 10. 架构边界检查

A3 新增自动检查器及 Makefile/CI 命令，首版使用有说明的 allowlist，只阻止新增违规：

- 业务模块直接导入其他模块的 PostgreSQL Repository 或内部实现。
- RichText、Schedule 依赖 Personal Space 内部实现。
- External Plugin 源码导入 CampusOS `internal/*`。
- Agent Runner 获取数据库连接、JWT 私钥、CampusOS 用户 Token 或宿主完整文件系统。

allowlist 必须包含责任模块、原因和移除阶段；不得用扩大 allowlist 代替修复新增违规。

## 11. Agent 与 Secret 安全合同

v0.7 B2 仅定义 Agent Core Port、Runner/Knowledge Provider/MCP 外部合同、权限声明、Secret 分类和拒绝策略。Runner 默认是外部进程或受限 Runtime，不获得 `AppContext`、数据库、JWT 私钥、CampusOS Session/Access/Refresh Token 或宿主完整文件系统。

| 配置类型 | v0.7 导出规则 |
| --- | --- |
| CampusOS Session、Access/Refresh Token、Host Token、JWT/API key | 永不导出，目标实例重新认证或签发 |
| JWT 私钥、数据库 DSN/密码、内部服务凭据 | 永不进入插件、资源或普通配置导出 |
| 第三方 Token/API key | 默认不导出明文；本轮只定义策略与脱敏合同，不实现跨实例加密迁移 |
| 非敏感插件配置 | schema 校验后允许；移除机器路径和运行时生成字段 |
| 实例 URL、端口和路径 | 标记 environment-specific，导入后重新确认 |

## 13. 统一 Definition of Done

每个阶段必须同时满足：

- 定向测试通过。
- `GOCACHE=/tmp/campusos-go-cache go test ./... -count=1` 通过。
- `git diff --check` 和架构边界检查通过。
- 涉及的 Web、Admin、docs-site、SDK 构建通过。
- API、路由、配置、Manifest、migration 和数据目录变化已记录。
- 兼容路径和可执行回滚路径已验证并记录。
- `docs/进度/v0.7-dev/` 中对应进度文档已生成。
- 本计划的实现状态、验收状态和证据路径已同步。

最终阶段执行 `RUN_RESTORE_DRILL=true RUN_BROWSER_SMOKE=true make release-check`。没有完整证据时不得标记“已验收”。

## 16. 风险与禁止事项

- 禁止一次性重写系统、删除旧 API/表/数据目录/兼容 Manifest，或拆成大量微服务。
- 禁止反射式自动装配、全局 Service Locator 和不可追踪的隐式依赖。
- 禁止运行时动态增删 Gin 路由；禁止 Feature 停用时删除数据。
- 禁止为了通过测试移除权限、审计、路径、配额、内容安全或数据库约束。
- 禁止 External Plugin 或 Agent Runner 直接访问核心数据库、内部 Service、JWT 私钥、CampusOS 用户 Token 或完整宿主文件系统。
- 禁止默认明文导出任何 Token；CampusOS 凭据永不导出。
- 禁止 Resource Package 获得业务插件生命周期。
- 禁止跳过基线、回滚验证或证据文档后标记阶段完成。

## 17. 最终验收

只有全部阶段均“已验收”时才完成 v0.7：`server.go` 不再集中装配业务细节；四类能力可机器识别；关键模块有明确依赖和生命周期；Moderation 为 Core；User Storage 独立且调用方只依赖 Port；Space、RichText、Schedule、Appearance 由 Built-in Feature Registry 管理；Appearance 通过 Facade 统一而旧风格包仍兼容；Plugin Manager 只作为 External Plugin 的兼容 Facade；Resource Package 无业务生命周期；Agent/Secret 边界有代码合同和负向测试；现有数据、API、前端和可用插件没有无说明破坏。
