## 一、项目现状与计划结论

### 1.1 当前完成状态

CampusOS v0.10 已经完成：

- 内容发布、审核、下架、整改、回收站与清除状态闭环；
- 稳定 Permission Code、角色、版主作用域和最后管理员保护；
- Core、Built-in Feature、External Plugin、Resource Package 物理隔离；
- 数据治理、迁移、备份恢复、浏览器业务流和七视口发布门禁；
- migration `000001`—`000026`；
- 模块、插件、资源和用户文件联合恢复。

上述状态已经在最终审计文档和 `v0.10.27-dev` 中形成验收证据。 

v0.10 应正式关闭，不再继续追加封版补强任务。

### 1.2 当前真实技术缺口

#### 注册流程

当前注册逻辑依次创建 `users` 和 `accounts`，两个写操作不在同一事务中；账号创建失败时，可能留下没有有效凭据的用户记录。

`accounts` 表已经存在 `verified` 字段，创建邮箱账号时默认为 `false`，但登录查询没有读取该字段，登录服务也没有检查邮箱验证状态。

注册成功后，前端目前直接提示用户前往登录，没有邮箱验证页面和重发流程。

#### 多级板块

板块领域对象和 PostgreSQL Repository 已经支持 `parent_id`。 

但目前仍缺少：

- 父板块存在性检查；
- 自引用和循环引用检查；
- 最大层级限制；
- 父子删除、移动规则；
- 版主权限继承规则；
- 树形查询合同；
- 子板块统计聚合；
- Admin 树形管理界面。

当前服务只是直接保存 `ParentID`，没有进行上述层级验证。 当前 Admin 仍采用平铺表格，创建和编辑表单也没有父板块字段。 

#### 可靠性和并发

当前高风险业务操作和审计记录尚未形成统一事务；Webhook 仍使用进程内 goroutine 和同步重试；External Plugin、用户文件和部分运行状态仍是单实例模型。

现有普通 CI 和 `release-check` 包含全量测试、数据库、前端构建、恢复和浏览器验证，但还没有系统化的持续并发压测、容量基线、长期稳定性测试和全量 `-race` 门禁。

## 二、版本拆分决策

本轮需求不得合并为一个超大型版本。

| 版本 | 核心目标 | 优先级 |
|---|---|---:|
| v0.11 | 事务、审计、Outbox、可靠任务、Webhook 和可观测性 | P0 |
| v0.12 | 邮箱验证、多级板块、校园互助和二手交易板块 | P1 |
| v0.13 | 并发测试、容量验证、性能优化和最终生产验收 | P2 |

版本依赖关系：

```text
v0.10 基线冻结
      ↓
v0.11 可靠性基础
      ↓
v0.12 邮箱验证与社区结构升级
      ↓
v0.13 并发测试与性能优化
      ↓
最终全方位审计
```

邮箱验证依赖可靠事件投递；并发测试依赖邮箱验证和多级板块功能稳定。因此不得调整上述主顺序。

## R1：统一事务管理 TxKernel

**依赖：R0。优先级：P0。**

建立统一事务接口，使 Repository 可以共享同一个 PostgreSQL 事务。

第一批改造：

1. 用户和账号原子注册；
2. 角色分配、撤销与授权审计；
3. 自定义角色权限更新；
4. 版主范围修改与治理审计；
5. 内容高风险状态转换；
6. 插件安装与插件市场审计。

### 强制约束

- 业务写入失败：不得生成成功审计；
- 审计写入失败：高风险业务必须回滚；
- 不得在 Service 中零散调用 `pool.Begin`；
- Memory 和 PostgreSQL Adapter 必须共享合同测试；
- 事务接口不能泄露到 External Plugin。

## R2：持久化 Outbox 与 Worker

**依赖：R1。优先级：P0。**

建议从 migration `000027` 开始新增：

Worker 必须支持：

- 多 Worker 抢占安全；

- 最大重试次数；
- dead-letter；
- graceful shutdown；
- 幂等消费；

- 只启动 goroutine 后立即返回；
- 只依赖内存队列；
- 使用 `time.Sleep` 作为持久任务调度器；
- 消费成功但不保存消费凭证；

## R3：高风险审计原子化

**依赖：R1、R2。优先级：P0。**

保留现有审计表的业务归属，不急于合并所有审计表，但统一公共字段：

```text

```

规则：

- 授权拒绝但没有业务写入：可直接写审计；

# 五、v0.12：邮箱验证与社区板块升级

# 第一部分：注册邮箱验证

## I0：邮箱验证安全设计

**依赖：v0.11。优先级：P0。**

必须先确定：

- 邮箱是否必须验证后才能登录；
- 验证邮件有效期；
- 重发间隔和每日上限；
- 同一 IP 注册上限；
- 旧用户迁移策略；
- 邮件发送失败后的用户状态；
- 邮件 Provider 不可用时的降级方式；
- 管理员人工验证权限和审计要求。

最终建议：

- 新用户必须验证邮箱后才能登录；
- 现有 v0.10 用户迁移时默认标记为已验证，避免全量锁号；
- `accounts.verified` 作为邮箱账号验证事实；
- 增加 `verified_at`，不把邮箱验证混入封禁状态；
- 验证 Token 只保存哈希；
- Token 单次使用；
- 默认有效期 30 分钟；
- 重发使旧 Token 失效。

## I3：邮箱验证 API

建议新增：

```text
POST /api/v1/auth/register
POST /api/v1/auth/email-verification/resend
POST /api/v1/auth/email-verification/confirm
GET  /api/v1/auth/email-verification/status
```

行为要求：

### 注册

返回：

```text
registration_id
verification_required=true
masked_email
resend_after
```

不得返回登录 Token。

### 重发

无论邮箱是否存在，外部响应尽量保持一致，防止账号枚举。

### 验证

验证成功后：

- 原子设置 `accounts.verified=true`；
- 写入 `verified_at`；
- 消耗 Token；
- 写审计；
- 发布 `identity.email.verified` 事件。

### 登录

密码正确但邮箱未验证时：

- 不签发 JWT；
- 返回稳定错误码；
- 前端跳转到邮箱验证页面；
- 不暴露其他账户信息。

## I5：邮箱验证安全测试

至少包括：

- 同一 Token 并发验证，只允许一次成功；
- 同一邮箱并发注册，只创建一个账号；
- 重发后旧 Token 失效；
- Token 哈希无法反推出原 Token；
- 登录不能绕过验证；
- 管理员封禁优先于邮箱验证状态；
- 邮件 Provider 故障不产生半注册用户；
- 响应不能用于枚举账号；
- 速率限制不能被简单并发绕过。

# 第二部分：多级板块

## C0：层级模型决策

**依赖：邮箱验证主流程稳定后开始。优先级：P1。**

当前已有 `parent_id`，因此本阶段不是重建表，而是补齐层级语义。

第一版建议只支持两级：

```text
一级板块：导航和治理边界
    └── 二级板块：实际发帖板块
```

暂不支持无限层级，避免：

- 路径查询复杂；
- 版主权限难以判断；
- 统计聚合成本不可控；
- 移动和删除规则过于复杂；
- 前端导航层级过深。

---

## C1：数据库与领域约束

建议补充：

```text
categories.parent_id 自引用外键
categories.depth
categories.posting_enabled
categories.category_kind
```

规则：

1. 最大深度为 2；
2. 板块不能以自己为父级；
3. 板块不能形成循环；
4. 一级容器默认不能直接发帖；
5. 二级板块允许发帖；
6. 有子板块时不能直接删除一级板块；
7. 有帖子时不能直接删除二级板块；
8. 移动板块必须验证深度、权限和目标状态；
9. 同一父级下 Slug 唯一；
10. ID 继续作为事实标识，Slug 只用于展示和路由。

现有板块迁移策略：

- 现有板块保持可发帖；
- 初始视为一级独立板块；
- 不强制批量移动；
- Admin 可逐步把现有板块移动到新的一级容器下。

---

## C2：树形 API

新增或调整：

```text
GET  /api/v1/categories?view=tree
GET  /api/v1/categories/:id/children
POST /api/v1/categories
PUT  /api/v1/categories/:id
POST /api/v1/categories/:id/move
```

列表过滤必须明确区分：

```text
category_id=<id>          只查询当前板块
category_scope=subtree    查询当前板块和所有子板块
```

禁止默认隐式扩大查询范围。

---

## C3：层级权限与版主作用域

这是多级板块中风险最高的部分之一。

默认规则：

- 现有 category scope 只作用于当前板块；
- 不因增加父子关系自动扩大已有版主权限；
- 一级板块管理员需要显式配置是否管理子板块。

建议增加：

```text
scope_mode=self
scope_mode=subtree
```

其中：

- `self`：只管理当前板块；
- `subtree`：管理当前板块及子板块；
- 默认值必须是 `self`；
- 每次授权必须在审计中记录父板块、scope mode 和实际目标板块。

测试必须覆盖：

- 父板块版主默认不能操作子板块；
- `subtree` 授权后可以操作子板块；
- 子板块版主不能反向操作父板块；
- 移动板块后不能造成权限静默扩大；
- 删除或停用子板块不删除历史授权审计。

---

## C4：Admin 树形板块管理

将当前平铺表格升级为树形管理：

- 树形表格；
- 展开和折叠；
- 新增一级板块；
- 在一级板块下新增二级板块；
- 移动板块；
- 排序；
- 设置是否允许发帖；
- 显示帖子数量和子板块数量；
- 删除前影响预览；
- 权限继承提示。

删除按钮必须显示：

```text
子板块数量
帖子数量
版主授权数量
删除或移动后的影响
```

不得只显示“确定删除吗”。

# 第三部分：校园互助和二手交易板块

## S3：特殊内容安全边界

### 校园互助

必须防范：

- 诈骗募捐；
- 冒充学校、老师或社团；
- 公开身份证、宿舍号、手机号等敏感信息；
- 医疗、法律、生命安全类紧急情况被普通帖子延误；
- 以互助名义引流至高风险外部平台。

建议：

- 敏感信息提示和内容扫描；
- 举报入口；
- 高风险关键词进入审核；
- 紧急情况显示官方求助渠道提示；
- 联系方式默认脱敏。

### 二手交易

必须建立禁售规则：

- 违法物品；
- 管制物品；
- 校园证件和账号；
- 考试答案、代写服务；
- 处方药和高风险药品；
- 盗版账号和非法数字商品；
- 无法确认来源的高价值物品。

同时增加：

- 价格异常提示；
- 重复发布限制；
- 举报和下架；
- 卖家历史发布记录；
- “已售出”状态；
- 发布者自行关闭；
- 管理员封禁交易贴能力。

不得在第一阶段保存身份证、银行卡或完整住址。

## S4：特殊板块验收

至少覆盖：

- 普通帖子不能伪造二手交易字段；
- 二手交易价格不能为负数；
- 已售出帖子不能重复标记为可售；
- 互助贴解决后仍保留历史内容；
- 下架状态优先于交易状态；
- 父子板块权限不能绕过内容审核；
- 未验证邮箱用户不能发布互助或交易内容；
- 被封禁用户不能通过验证链接恢复权限；
- 移动板块后帖子类型和审核状态保持不变。

# 六、v0.13：并发测试、容量验证与性能优化

## P0：性能基线和 SLO

**依赖：v0.12 完成。优先级：P0。**

性能优化前必须先建立基线，禁止凭感觉修改。

建议初始 SLO：

| 指标 | 初始目标 |
|---|---:|
| 普通读取请求 P95 | ≤ 500 ms |
| 普通写请求 P95 | ≤ 800 ms |
| 注册和验证接口 P95 | ≤ 1 s，不含邮件实际送达 |
| 业务错误率 | < 0.5% |
| 数据一致性错误 | 0 |
| 重复消费副作用 | 0 |
| goroutine 持续泄漏 | 0 |
| 数据库连接池长期饱和 | 不允许 |
| Outbox 最老事件等待时间 | 在批准阈值以内 |

具体并发用户数必须根据部署机器规格批准，不在编码前随意设定。

---

## P1：并发正确性测试

优先验证正确性，而不是先追求吞吐量。

必须覆盖：

### Identity

- 同一邮箱并发注册；
- 同一用户名并发注册；
- 同一 Token 并发验证；
- 验证和重发并发；
- 登录和封禁并发；
- 最后管理员并发撤销。

### Community

- 同一帖子并发发布和下架；
- 回复与锁帖并发；
- 板块移动和发帖并发；
- 删除父板块和创建子板块并发；
- 二手状态并发更新；
- 互助解决与管理员下架并发。

### Worker

- 多 Worker 抢同一个 Outbox；
- lease 到期接管；
- 重试与手动重放并发；
- Webhook 重复发送；
- 服务关闭时任务归还。

### Plugin

- 插件停止和重启并发；
- 插件更新和事件投递并发；
- 插件快照和回滚并发。

要求：

```bash
go test -race ./...
```

应进入定期门禁；无法一次性全量通过时，必须有明确豁免清单和关闭日期。

## P2：负载场景

建立固定压测场景：

1. 注册 → 邮件验证 → 登录；
2. 首页和帖子列表读取；
3. 帖子详情和回复；
4. 富文本图片上传；
5. 板块树读取；
6. 互助贴发布和状态更新；
7. 二手贴发布和标记已售；
8. Admin 内容审核；
9. Webhook 高失败率重试；
10. 插件事件和 Host API 调用。

压测类型：

```text
基准测试
阶梯加压
突发流量
持续稳定性测试
故障恢复测试
容量上限测试
```

压测必须使用隔离环境：

- 不连接真实 SMTP；
- 不调用真实 Webhook；
- 不写生产数据库；
- 不污染真实对象存储；
- 使用可重复生成和清理的测试数据。

---

## P3：优化顺序

必须按照证据依次优化：

### 第一优先：数据库

- 缺失索引；
- 慢查询；
- N+1 查询；
- 不必要的全表计数；
- 板块树递归查询；
- Outbox 锁竞争；
- 连接池配置；
- 长事务。

### 第二优先：应用层

- 重复 Repository 调用；
- 大对象反复序列化；
- 不受控 goroutine；
- 重复权限查询；
- 同一请求多次加载板块层级。

### 第三优先：缓存

仅缓存读多写少的数据：

- 公开板块树；
- Feature 描述符；
- 权限定义目录；
- Resource Package 元数据。

不得缓存：

- 高风险授权最终结果；
- 邮箱 Token；
- 内容下架状态的唯一事实；
- 二手交易最终状态；
- Outbox 锁状态。

### 第四优先：静态资源和前端

- 按路由拆包；
- 图片压缩；
- 长列表虚拟化；
- 请求去重；
- 分页；
- 资源缓存策略。

---

## P4：长期稳定性测试

至少检查：

- 内存是否持续增长；
- goroutine 是否持续增长；
- 数据库连接是否释放；
- Worker lease 是否残留；
- Outbox 是否持续积压；
- 插件进程是否频繁重启；
- Webhook 失败是否造成队列阻塞；
- 日志和审计表是否异常膨胀；
- 用户文件配额统计是否成为瓶颈。

# 七、统一风险登记表

| 风险 | 等级 | 控制措施 |
|---|---:|---|
| 事务改造造成大范围回归 | 极高 | 小批次改造、Repository 合同测试、migration 演练 |
| Outbox 重复消费 | 极高 | 幂等键、消费凭证、唯一约束 |
| 邮箱 Token 泄露 | 极高 | 随机 Token、只存哈希、短有效期、禁止日志 |
| 邮件重发被滥用 | 高 | IP、账号、邮箱多维限流 |
| 邮箱验证导致旧用户无法登录 | 高 | 旧邮箱账号迁移为已验证 |
| 多级板块形成循环 | 高 | DB、Service 双重验证 |
| 父板块权限静默扩张 | 极高 | 默认 `self`，显式开启 `subtree` |
| 二手交易诈骗 | 极高 | 不做支付担保、禁售规则、举报和审核 |
| 互助贴泄露个人信息 | 高 | 脱敏、风险提示、审核 |
| 压测误连生产服务 | 极高 | 独立环境、测试 Provider、启动保护 |
| 缓存导致权限或下架状态过期 | 极高 | 高风险事实不进入普通缓存 |
| 性能优化改变业务语义 | 高 | 优化前后合同测试和数据对账 |

# 九、阶段关闭标准

每个版本只有同时满足以下条件才能关闭：

## 代码

- 单元测试通过；
- Repository 合同测试通过；
- `go vet`、lint 和格式检查通过；
- 关键并发路径通过 `-race`；

- migration 只能追加；
- up 验证通过；
- down/up 仅在隔离环境验证；
- 数据数量和 checksum 对账；
- 有备份和恢复证据；
- 生产回退优先采用 forward-fix。

## 安全

- 高风险任务有安全设计文档；
- Token、密码和密钥不进入日志；
- 权限默认拒绝；
- 输入、URL、路径和文件均有边界验证；
- 二手和互助内容有明确治理规则。

## 产品

- Web 和 Admin 流程完整；
- 错误、空态和恢复流程可理解；
- 手机、平板、横屏和桌面通过回归；
- 旧 API 和旧数据有兼容说明。

## 运维

- 指标和日志可定位问题；
- 任务可以重放；
- 服务退出可以优雅停止；
- 恢复后可以继续处理积压任务；
- 发布和回滚步骤写入文档。

## 证据

每个阶段必须新增：


```text

发布验收
```

不得将“代码已写”标记为“阶段已完成”。

# 十一、最终计划审查结论

1. **先解决一致性，再增加新用户流程。**
2. **先完成可靠事件，再依赖邮件异步发送。**
3. **先定义板块权限，再开放层级管理。**
4. **先明确二手交易法律和安全边界，再开发页面。**
5. **先建立性能基线，再进行优化。**
6. **并发测试不仅检查速度，还必须检查数据正确性。**
7. **历史数据和 API 必须先观测，再弃用，最后才能删除。**
8. **每个版本可独立发布、验收和回滚。**

最终版本路线确定为：

```text
v0.10  产品语义和扩展边界闭环
v0.11  事务、审计、Outbox 和可靠运行
v0.12  邮箱验证、多级板块、互助和二手交易
v0.13  并发测试、性能优化和生产验收
```

该拆分能够避免一个版本同时修改身份、社区、异步任务、数据库、权限和性能基础设施，从而显著降低实施风险和回滚复杂度。
