## 1. 版本定位

v0.6 不以继续堆叠业务功能为主。它负责把 v0.1-v0.5 已经形成的社区和插件平台，从“主要功能可用”推进到“接口可依赖、权限可证明、数据可约束、插件可开发和版本可验收”。

```text
v0.5 feature baseline
  -> v0.6 contracts + authorization + database integrity + plugin developer ecosystem
  -> later marketplace + multiple adapters + scale-out deployment
```

本版计划的三个核心交付面：

1. 完善 HTTP、内部服务、插件 Host API 和外部协议接口，统一身份、权限、资源归属和审计边界。
2. 审查并优化数据库标识、关系、约束、索引、状态、删除和 migration 策略。
3. 整理插件生态，交付明确的开放 API、SDK/CLI、测试工具、模板、兼容政策和开发者帮助文档。

## 4. 接口体系规划

### 4.1 接口分层

v0.6 必须先区分接口使用者，避免把内部服务、管理员接口和插件接口混为同一套“开放 API”。

| 层级 | 使用者 | v0.6 交付 |
| --- | --- | --- |
| Public HTTP API | 浏览器、移动端和受信任第三方客户端 | OpenAPI、认证说明、错误模型、分页/过滤约定、兼容政策 |
| Admin HTTP API | CampusOS 管理端和运维工具 | 管理员权限、数据范围、敏感字段、审计和幂等规则 |
| Plugin Host API | Built-in/gRPC/Wasm 插件 | capability、permission、调用上下文、错误、超时、配额和版本说明 |
| Internal Service API | Go 内部领域模块 | 明确模块边界，不承诺为外部稳定 API |
| Standard Adapter API | 后续 MCP/Message adapter | 独立身份、最小作用域、协议映射、重试和审计 |

### 4.2 HTTP API 清单

从 `internal/server/server.go` 的实际注册路由生成或校验接口清单。每个接口必须记录：

| 字段 | 要求 |
| --- | --- |
| 请求 | method、path、content type、参数、body schema、上传限制和幂等要求 |
| 响应 | 成功 schema、分页元数据、空结果、下载/流式响应和敏感字段裁剪 |
| 身份 | anonymous、user JWT、admin/moderator、plugin/service token 中允许的主体 |
| 授权 | `resource:action` 权限、ownership、data scope 和管理员例外规则 |
| 错误 | 稳定 error code、HTTP status、message、details、request ID 和可否重试 |
| 审计 | 是否记录操作者、目标资源、结果、来源和变更摘要 |
| 验证 | 正向契约、未登录、无权限、跨用户、非法参数和重复请求测试 |

OpenAPI 只描述对外承诺的 HTTP 边界。内部服务和 Host API 分别维护自己的参考文档，避免生成一个无法表达运行时差异的超大规范。

### 4.3 统一错误和兼容政策

建议统一错误结构：

```json
{
  "error": {
    "code": "space.quota_exceeded",
    "message": "personal space quota exceeded",
    "details": {},
    "request_id": "..."
  }
}
```

兼容规则：

1. 同一主版本中允许增加可选字段，不直接删除或改变已发布字段语义。
2. 路由、字段或权限弃用必须给出 `deprecated` 标记、替代方式和至少一个开发阶段的迁移期。
3. 实验接口必须显式标记，不由稳定 SDK 默认暴露。
4. 列表接口统一分页、排序、过滤上限；上传接口统一 MIME、扩展名、大小和 checksum 规则。
5. 错误 `code` 供程序判断，`message` 供人阅读；客户端不得依赖 message 文本做分支。

## 5. 权限控制规划

### 5.1 统一授权模型

一次请求只有同时通过五层检查才可访问敏感资源：

```text
authentication
  -> resource:action permission
  -> ownership or data scope
  -> field filtering / operation constraints
  -> audit
```

| 层级 | 说明 |
| --- | --- |
| 身份认证 | 区分匿名用户、普通用户、版主/管理员、插件身份和服务身份；禁止共享万能 token。 |
| RBAC 权限 | 继续使用 `resource:action`，逐步拆分过宽的 `role:manage`。 |
| 对象归属 | 用户只能修改自己的帖子、文章、空间、头像、课表和草稿，管理员例外必须显式。 |
| 数据范围 | 公开、仅自己、指定版块、全站管理等范围独立于角色名称表达。 |
| 字段和操作限制 | 普通用户不能写 owner/status/audit 等系统字段，管理员响应也要裁剪密钥和隐私数据。 |
| 审计 | 高风险操作记录主体、权限、目标、结果和 request ID，不记录明文密码、token 或私密正文。 |

### 5.2 首批重点审查

以下路由组必须优先核对，不能仅凭“使用 JWT”认定授权完成：

| 路由/资源 | 审查重点 |
| --- | --- |
| `PUT /users/:id` | 必须证明只能本人修改允许字段，或由具备明确权限的管理员修改。 |
| category create/update/delete | 创建、修改和删除应使用独立权限，不依赖普通登录或粗粒度角色。 |
| thread/post/richtext update/delete | 同时覆盖作者 ownership、私密可见、版主范围和管理员治理。 |
| space/avatar/style/schedule | 禁止跨用户读写；公开主页与私有文件响应分离。 |
| plugin package/config/lifecycle | 拆分查看、安装、配置、启停、热加载和系统重启权限。 |
| webhook/AI/MCP-like/message | 配置密钥必须脱敏；调用、测试和查看日志使用不同权限。 |
| public users/events/assets | 重新确认公开字段、枚举上限、隐私数据和资源可见性。 |

### 5.2.1 版主与作用域模型

`v0.6.1-dev` 已将 `moderator` 收口为仅允许 `category` scope 的角色，完成置顶、锁定、删除回复、跨版块拒绝、审计、独立配置页和用户端入口。它是权限收口的首个可运行切片，不代表全路由授权矩阵已经完成。后续仍按以下边界扩展：

| 阶段 | 工作 | 验收 |
| --- | --- | --- |
| 核心作用域 | 已完成首版 `category` scope、category 校验和可管理版块集合；继续统一全站资源的数据范围表达 | 版块外的帖子、回复和治理操作返回 403，不能只靠前端隐藏。 |
| 治理动作 | 已完成置顶、锁定和删除回复；后续动作继续使用独立 `resource:action` | 版主不能读取/修改角色、插件、集成、密钥或全站配置。 |
| 审计与防升级 | 已记录版主范围变更和治理动作，通用角色接口拒绝全局版主；继续补齐 request ID 与全路由负向矩阵 | 跨版块、伪造 scope、自我提权和敏感操作均有负向测试。 |
| 系统级插件 | 已实现 `category-moderation` 内置插件、独立管理窗口和用户端操作入口 | 插件 UI 只展示后端确认可执行的操作；禁用插件不绕过或删除核心审计记录。 |

`category-moderation` 不是把授权逻辑搬出核心。核心负责身份、权限、作用域和拒绝；插件负责配置体验、版主工作流、用户端按钮和后续可扩展能力。

### 5.3 权限产物与测试门槛

1. 建立机器可读的权限目录，字段至少包含 permission、说明、适用主体、风险等级和审计要求。
2. 从目录生成管理员权限说明和插件 manifest 权限参考，避免文档手工漂移。
3. 每个敏感路由至少验证 401、403、跨用户访问和敏感字段写入失败。
4. Host API 继续坚持默认拒绝，覆盖精确权限、通配权限、缺失权限、插件身份伪造和跨插件数据访问。
5. 建立授权决策日志，但对高频成功请求采样，对拒绝请求完整记录并脱敏。

## 6. 数据库设计与迁移规划

### 6.1 当前问题基线

当前 migration 加上系统维护的 `schema_migrations` 共形成 30 张 schema 表。现有关系主要由服务层和索引维护，migration 尚未声明显式 foreign key。v0.6 不把“添加所有外键”作为机械目标，而是先审查数据质量和生命周期，再对稳定关系增加约束。

| 问题 | 当前表现 | 风险 |
| --- | --- | --- |
| 标识类型不统一 | 核心用户 ID 以 `BIGINT` 为主，部分空间、MCP 或 Message 相关 `user_id` 使用 `VARCHAR(64)` | join、迁移和 SDK 类型容易漂移 |
| 关系只有逻辑约束 | `user_id`、`thread_id`、`plugin_name` 等主要靠服务层维护 | 可能产生孤儿数据，删除行为不透明 |
| 插件引用使用可变名称 | 部分数据以 `plugin_name` 关联 | 插件重命名、覆盖更新和版本快照困难 |
| 标签双重表示 | 独立 tags 表与 thread/category 数组字段并存 | 查询语义、去重和索引策略不统一 |
| 状态/时间/删除策略不一致 | 各表对 status、deleted、created/updated 字段使用不一致 | 审计、恢复和数据保留难以统一 |
| 多态关联 | likes 等采用 `target_type + target_id` | 无法直接使用普通外键，需要专门完整性检查 |

### 6.2 设计原则

1. migration 从 `000014` 起追加，不重写已经执行的历史 migration。
2. 先检查和修复数据，再增加 `NOT NULL`、`UNIQUE`、`CHECK` 或 foreign key。
3. 稳定强关系使用数据库约束；确实需要多态或跨 Runtime 的关系保留逻辑约束，但必须记录检查器和清理策略。
4. 业务主键类型在 API、数据库和 SDK 中保持一致；外部平台 ID 单独使用字符串字段，不挤入内部用户 ID。
5. 删除行为必须明确为 restrict、cascade、set null 或软删除，不能依赖默认猜测。
6. 索引由查询和唯一性需求驱动，并通过 `EXPLAIN` 或基准验证，不为每个字段盲目建索引。

### 6.3 分阶段 migration

| 阶段 | 工作 | 验收 |
| --- | --- | --- |
| A：数据体检 | 输出孤儿记录、重复值、非法状态、空 owner、ID 类型和大表索引报告 | 报告可重复运行，不修改数据 |
| B：模型决策 | 为用户、内容、权限、插件、空间、集成领域确定主键、关系、状态和删除策略 | 形成 schema decision record |
| C：兼容补列 | 必要时新增标准列和 immutable ID，双写并回填；保留旧列读取兼容 | 回填可断点重试，前后计数一致 |
| D：约束和索引 | 对已清洁数据增加唯一性、检查、稳定外键和查询索引 | migration 通过，孤儿数为零，关键查询计划可接受 |
| E：收口旧模型 | 在弃用期结束后移除旧列/旧读路径 | 有备份、回退说明和版本兼容说明 |

### 6.4 领域优化清单

| 领域 | 优化重点 |
| --- | --- |
| Identity/RBAC | accounts、sessions、user_roles、role_permissions、permissions 的唯一性、过期清理、删除策略和权限键约束 |
| Community | categories、threads、posts 的 owner/parent/category 关系、私密状态、楼层号唯一性、软删除和计数一致性 |
| Tags | 确定规范化关联表或数组的唯一主模型，并提供兼容读取和迁移策略 |
| Plugin | 引入不可变 plugin/package ID，分离插件定义、安装实例、版本、配置和运行状态 |
| Personal space | 统一内部 user ID 类型、配额值与文件元数据；数据库记录和本地文件清理保持可核对 |
| Richtext/Schedule | 草稿/发布状态、学期唯一键、owner、资源引用和删除后的文件处理明确 |
| Integration/Audit | webhook、AI、MCP-like、message、platform log 的敏感字段、保留期、索引和清理任务明确 |
| Polymorphic data | 对 `target_type + target_id` 建立允许类型 CHECK、唯一性和定期孤儿扫描 |

### 6.5 数据库验收

1. `campusos-data-architecture-sync` 检查器继续保证 migration 与管理端静态架构视图一致。
2. 新增 schema contract test，验证关键表、列、索引和约束，不只比较表名。
3. 每个 migration 同时提供 preflight、up 验证、恢复/回退说明和数据计数核对。
4. 管理端架构页区分数据库强制关系和服务层逻辑关系。
5. 实时行数、大小和 migration 状态如需展示，只能通过管理员白名单元数据 API 提供，禁止 Web 端执行任意 SQL。

## 7. 插件生态规划

### 7.1 公开边界

| 能力 | 面向对象 | 稳定性承诺 |
| --- | --- | --- |
| Public HTTP API | 外部应用和需要联网访问 CampusOS 的插件 | 由 OpenAPI、token scope 和 HTTP 版本政策约束 |
| Plugin Host API | 由 CampusOS Runtime 托管的 Built-in/gRPC/Wasm 插件 | 由 capability、permission、Host API version 和 Runtime 限制约束 |
| SDK | 插件源码 | 封装模型、调用、错误、日志、配置、存储和测试工具，不越过 Host API 权限 |
| CLI | 插件开发和管理员 | 负责 scaffold、inspect、build、test、pack、verify、install 和本地 dev |
| Adapter Contract | MCP/Message 等外部协议适配器 | 负责协议映射，不直接耦合社区内部表结构 |

### 7.2 API 与权限规范

1. Manifest 明确 `api_version`、runtime、scope、permissions、capabilities、entrypoint、config schema 和数据目录。
2. Host API 每项能力记录调用方向、请求/响应模型、必要权限、失败码、超时、幂等和审计规则。
3. 插件默认无权限；安装页必须展示权限说明和风险等级，更新新增权限需要再次确认。
4. 系统级插件保持“修改后重启生效”，用户级插件保持受控热加载；SDK 不隐藏这一生命周期差异。
5. 制定兼容矩阵：CampusOS 版本、Host API 版本、SDK 版本、Runtime 和示例插件版本必须可查询。
6. 制定弃用政策：先告警、再停止新包使用、最后在主版本移除；禁止静默改变权限语义。

### 7.3 SDK 和 CLI 路线

| 组件 | v0.6 优先级 | 交付要求 |
| --- | --- | --- |
| Go SDK | P0 | 固化 module/version、错误类型、context/timeout、权限错误、配置/KV/日志/事件 API，示例可编译运行 |
| CLI | P0 | 在 init/inspect/pack/install 基础上增加 test、verify 和本地 dev；输出机器可读结果供 CI 使用 |
| Mock Host/Test Harness | P0 | 可注入权限、配置、KV、事件和失败，验证插件在无真实服务器时的核心逻辑 |
| 插件模板 | P0 | Built-in、gRPC、Wasm 至少各有最小模板，包含测试、manifest、config schema 和 README |
| TypeScript SDK | P1 | 优先覆盖 Public HTTP API 或明确可支持的 Runtime，不复制不适用的 Go Host API |
| Rust SDK | P2 | 只在 Wasm ABI 和版本策略稳定后启动 |

CLI 目标命令：

```text
campusosctl plugin init
campusosctl plugin inspect
campusosctl plugin build
campusosctl plugin test
campusosctl plugin pack
campusosctl plugin verify
campusosctl plugin install
campusosctl plugin dev
```

`publish` 在公开仓储、签名和审核策略完成前不作为 P0 命令。

### 7.5 插件生态验收

1. 新开发者只按快速开始即可生成、测试、打包并安装一个示例插件。
2. 所有 SDK 示例在 CI 编译并运行测试；模板 manifest 通过同一个 verify 工具。
3. 权限目录由机器可读来源生成文档，新增 Host API 没有权限说明时 CI 失败。
4. 插件包能说明来源、checksum、API/SDK 兼容范围和新增权限。
5. 管理端和 CLI 对同一个包给出一致的预检结论。

### 8.10 P2：一个标准外部边界

P0/P1 验收后，标准 MCP 只读服务与一个真实 Message adapter 二选一。首个版本只做认证、最小能力、限流、错误和审计，不开放高风险写操作，也不并行接入多个平台。

## 9. 执行顺序

```text
v0.6.0 inventory
  -> v0.6.1 HTTP contract
  -> v0.6.2 authorization
  -> v0.6.3 database integrity
  -> v0.6.4 plugin contract
  -> v0.6.5 SDK/CLI/test harness
  -> v0.6.6 developer docs
  -> v0.6.7 recoverability/supply chain
  -> v0.6.8 release acceptance
  -> optional one standard external boundary
```

接口和权限必须早于数据库强约束，因为需要先确定资源归属和公开字段；数据库模型必须早于 SDK 稳定版，因为 SDK 不应固化即将淘汰的 ID 和状态模型。

## 10. Definition of Done

每个工作包只有同时满足以下条件才可标记完成：

1. 代码、migration 或规范产物已经落地，不以设计稿代替实现。
2. 正向、失败和越权测试与风险相匹配，并记录实际验证命令。
3. 兼容、数据迁移、配置和回退方式已说明。
4. README、docs portal、API/插件帮助和管理端入口没有状态漂移。
5. 新增接口有契约和权限，新表/列有约束决策，新 Host API 有 SDK/权限/示例说明。
6. 进度文档只记录实际完成项；未通过的指标保留为未完成，不能用“基础支持”替代验收。

## 11. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 权限收口导致现有前端 403 | 先生成调用清单和兼容测试，再启用细粒度权限；为管理员角色提供显式迁移。 |
| 外键或类型变更阻塞 migration | 先 preflight、回填和观察，再启用约束；保留可回退列和备份。 |
| SDK 过早稳定后频繁破坏 | 先冻结 Host API/Manifest v1，再发布 stable SDK；实验能力单独命名。 |
| 文档与代码再次漂移 | 路由、schema、权限和 SDK 示例尽量使用机器检查或生成，CI 阻止漂移。 |
| v0.6 再次被新功能稀释 | P0 未完成前不并行建设市场、多平台适配和生产级高可用。 |
