**Document Title: **

# CampusOS v0.8 现有功能全面重构计划

> 版本定位：存量功能全面重构、架构收敛与技术债清零  
> 前置基线：`v0.7.0`  
> 核心原则：不增加新产品功能，不实现 Agent 运行能力，不将现有架构问题继续后移  
> 最终目标：v8 完成后，CampusOS 的现有功能全部运行在统一、清晰、可验证的模块化单体架构中

---

## 1. v8 版本定位

v7 已经完成模块化单体的基础架构建设，包括：

- Module Kernel；
- Core Port；
- Built-in Feature Registry；
- Plugin Platform 子服务框架；
- Resource Package Repository；
- User Storage 与 Appearance Facade；
- 架构检查和发布门禁。

但当前系统仍存在以下未完全收敛的问题：

1. 部分 Core Module 仍主要承担边界声明，业务对象仍在 Server 层统一创建。
2. `application.go` 仍集中装配绝大多数 Repository、Service、Handler 和路由。
3. PostgreSQL 和 Memory 模式存在重复业务装配。
4. 路由仍集中在 Server 层，业务模块没有真正拥有自己的 HTTP 入口。
5. Built-in Feature 状态仍依赖 Legacy Plugin 状态。
6. Plugin 子服务仍反向依赖 Manager，Manager 仍是实际状态中心。
7. Appearance 已有统一接口，但旧 Homepage、WebTheme、Space Style 仍是主要实现入口。
8. Web 和 Admin 的 Router、API、Store 和页面组织仍较集中。
9. 架构 allowlist 和部分跨领域具体类型依赖仍未清除。

因此，v8 的任务不是继续扩展平台，而是：

> 将所有现有功能迁移到 v7 已建立的架构中，完成业务所有权、装配、路由、数据访问、前端结构和兼容层的全面收敛。

## 2. v8 必须达成的总体目标

### 2.1 后端领域模块化完成

每个现有业务领域必须独立拥有：

- Module 定义；
- 依赖声明；
- Application Service；
- Domain 规则；
- Port；
- PostgreSQL Adapter；
- Memory Adapter；
- HTTP Handler；
- Route Registrar；
- 生命周期；
- 单元测试和集成测试。

现有领域包括：

1. Identity
2. Community
3. Moderation
4. User Storage
5. Personal Space
6. RichText
7. Schedule
8. Appearance
9. Plugin Platform
10. AI Gateway
11. Webhook
12. MCP-like Integration
13. Message
14. Platform Logs
15. Metrics 与 Integration Overview

### 2.2 Server 层彻底收缩

`internal/server` 最终只负责：

- 配置加载；
- 基础设施启动；
- Adapter Profile 选择；
- Module 注册；
- HTTP Server 启动；
- 优雅停止。

Server 层不得继续：

- 创建业务 Service；
- 创建业务 Handler；
- 知道领域内部 Repository；
- 读取 Built-in Feature 的旧插件配置；
- 注册具体业务路由；
- 执行业务配置迁移。

### 2.3 PostgreSQL 与 Memory 装配统一

PostgreSQL 和 Memory 只能是两套基础设施 Adapter Profile，不得维护两套业务装配代码。

目标结构：

```text
Application Modules
        ↓
Repository / Storage Ports
        ↓
┌───────────────────┬───────────────────┐
│ PostgreSQL Profile│ Memory Profile    │
└───────────────────┴───────────────────┘
```

所有业务 Module 只装配一次。

### 2.4 Built-in Feature 成为独立权威体系

Personal Space、RichText、Schedule、Appearance 的权威状态必须由 Feature Registry 和 Feature Config Store 管理。

旧 Plugin Manifest 和 Plugin API 只作为兼容投影存在：

```text
Feature Registry
       ↓
Legacy Built-in Projection
       ↓
旧 Plugin API / 旧 Admin 展示
```

不得继续由旧 Plugin 状态决定 Feature 是否运行。

### 2.5 Plugin Platform 完成自治拆分

Plugin Manager 最终只能作为兼容 Facade。

实际状态和业务逻辑分别归属：

- PluginCatalog；
- RuntimeRegistry；
- LifecycleService；
- ConfigService；
- UIRegistry；
- EventService；
- AuditService；
- PackageService；
- SnapshotService；
- Host Access Service。

子服务不得继续通过 Manager 反向访问自身状态。

### 2.6 前端按领域完成重构

Web 和 Admin 都必须完成：

- Router 拆分；
- API Client 拆分；
- Store 拆分；
- DTO 类型化；
- 页面和组件按领域归档；
- 权限和 Feature 状态统一处理；
- Built-in Feature 与 External Plugin 展示分离。

### 2.7 技术债清零

v8 完成时不得继续保留“后续再迁移”的架构技术债。

允许保留的只有明确的产品兼容合同，例如：

- 旧 API URL；
- 旧数据库表和历史 migration；
- 旧数据目录；
- 旧 Manifest；
- 旧配置字段读取；
- 旧客户端响应格式。

这些兼容代码必须满足：

- 位于独立 compatibility 包；
- 不包含核心业务逻辑；
- 不作为新代码主入口；
- 有自动兼容测试；
- 有明确的数据和调用方向。

# 8. 最终结论

v8 必须是 CampusOS 现有功能架构重构的结束版本，而不是又一个中间过渡版本。

v8 完成后应满足：

- 现有业务全部完成领域化；
- Server 层彻底退出业务装配；
- PostgreSQL 和 Memory 装配统一；
- Built-in Feature 和 External Plugin 彻底分离；
- Plugin Platform 完成自治；
- Appearance、Storage 和集成模块完成统一；
- Web 和 Admin 完成领域化；
- 架构 allowlist 清零；
- 兼容层退出主路径；
- 所有数据、API 和用户行为保持兼容。

除 Agent 和明确的新产品功能外，不再把任何当前已知的架构重构问题推迟到后续版本。

这版可以作为 v8 正式计划书的主体。下一步应将每个阶段继续补充“改动文件范围、前置依赖、禁止事项、回滚方法、测试命令和完成证据”，形成可直接交给开发 Agent 执行的版本。
