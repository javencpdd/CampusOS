## 1. 版本定位

v0.8 是 CampusOS 现有功能的架构收敛版本。v0.7 已建立 Module Kernel、Core Port、Built-in Feature Registry、Plugin Platform 子服务、Resource Repository、User Storage 和 Appearance Facade；v0.8 不再以新增 Facade 或占位接口作为完成标准，而是将现有业务真正迁入这些边界，使新架构成为唯一主路径。

本版本不增加新产品能力。现有功能、API、数据库数据、插件包、风格包和用户文件必须保持兼容。v0.8 完成后，不再把本计划已经识别的架构债务顺延到下一版本。

“全部重构完成”特指本计划冻结的存量范围和退出条件全部通过，不表示未来不会出现新缺陷，也不允许借重构名义无限扩大范围。

## 2. 当前基线与问题

### 2.1 v0.7 已完成基础

- Module Registry 支持依赖拓扑、可选生命周期、失败回滚和逆序停止。
- Identity、Community、Moderation、User Storage 已有 Core 边界和首批 Port。
- Personal Space、RichText、Schedule、Appearance 已登记为 Built-in Feature。
- Plugin Catalog、Runtime、Lifecycle、Config、UI、Event、Audit 已有子服务边界。
- Resource Package、Legacy Resource Source 和 Appearance Facade 已建立。
- 架构检查、合同检查、数据库检查、恢复演练和浏览器流程已进入发布门禁。

### 2.2 v0.8 必须消除的问题

| 问题 | 当前表现 | v0.8 退出要求 |
| --- | --- | --- |
| 业务装配仍集中 | `internal/server/application.go` 仍了解多个领域 Repository、Service、Handler 和路由 | Server 只选择 Profile、注册 Module、启动 HTTP 和停止 Runtime |
| PG/Memory 重复 | 两个分支重复创建同一批业务对象 | 业务 Module 只装配一次，差异只存在于 Adapter Profile |
| Core 仍有 marker 成分 | 部分 Core Module 的业务对象在 Server 创建 | 每个 Core Module 自己拥有装配、Port、Handler 和 Route Contributor |
| 路由集中 | 合同生成器仍依赖大型路由源文件 | Route Registry 聚合模块路由描述并生成合同 |
| Feature 状态仍有 legacy 权威 | Feature 启停仍需要旧 Plugin 状态投影 | Feature Config Store 成为唯一权威，旧 Plugin API 只读/写投影 |
| Plugin 子服务仍耦合 Manager | 部分子服务通过 Manager 反向调用 | 子服务直接协作，Manager 只保留无状态兼容转发 |
| Appearance 旧入口仍有规则 | Homepage、WebTheme、Space Style 各有业务路径 | 统一 Application Service 成为校验、应用、预览和回滚主路径 |
| 集成中心依赖具体 Service | Overview 聚合多个具体实现 | Integration Overview 只依赖 Summary Port |
| 前端结构集中 | Router、API、DTO、Store 和 App 根组件混合领域逻辑 | Web/Admin 按领域组织并有自动边界检查 |
| 架构债未清零 | v0.7 仍有 8 个 allowlist 项 | 业务架构 allowlist 为 0，兼容代码集中到 `compatibility/` |

## 4. 目标架构

```text
CampusOS Modular Monolith
├── Platform Kernel
│   ├── Module Registry / App Context
│   ├── Route Registry
│   ├── Application Runtime
│   └── Infrastructure Profiles (PostgreSQL / Memory)
├── Core Modules
│   ├── Identity
│   ├── Community
│   ├── Moderation
│   └── User Storage
├── Built-in Feature Modules
│   ├── Personal Space
│   ├── Controlled RichText
│   ├── Personal Schedule
│   └── Appearance
├── Plugin Platform
│   ├── Catalog / Runtime / Lifecycle / Config
│   ├── UI / Event / Audit / Host Access
│   └── Package / Snapshot
├── Integration Modules
│   ├── AI / Webhook / MCP-like / Message
│   └── Platform Logs / Metrics / Overview
├── Resource System
│   ├── Resource Repository
│   └── Legacy Source Compatibility
├── Web Domain Modules
└── Admin Domain Modules
```

依赖方向固定为：Transport -> Application -> Domain/Port <- Adapter。领域之间只能依赖公开 Port 或事件，不能导入其他领域的 Repository、具体 Service、Handler、Adapter 或数据库 Model。

## 5. 统一模块合同

### 5.1 后端目录

```text
internal/<domain>/
├── module.go
├── domain/
├── application/
├── port/
├── adapter/
│   ├── postgres/
│   └── memory/
├── transport/http/
├── compatibility/
└── *_test.go
```

不要求为了形式创建空目录。没有数据库、文件或 HTTP 能力的模块可以省略对应 Adapter/Transport，但所有依赖和所有权必须明确。

### 5.2 基础接口

```go
type Module interface {
    ID() string
    Dependencies() []string
    Register(*AppContext) error
}

type RouteContributor interface {
    Routes() []RouteDescriptor
    RegisterRoutes(RouteGroups)
}
```

Starter、Stopper、HealthReporter 继续作为可选接口。Module 不得直接获取另一个领域的具体 Adapter；External Plugin 不得获取 AppContext。

### 5.3 Infrastructure Profile

```text
Application Runtime
        ↓
Module Set + Port Bindings
        ↓
PostgreSQL Profile | Memory Profile
```

Profile 只负责提供数据库、缓存、事件总线、Repository、文件系统和日志 Adapter。业务 Service、Handler、路由及 Feature 规则只能装配一次。

## 6. 数据和兼容策略

### 6.1 冻结合同

- 148 条 HTTP 路由及其 method/path/auth/permission。
- 当前 OpenAPI、错误包络和分页语义。
- 18 个历史 migration，不允许修改 `000001` 至 `000018`。
- 9 个 Plugin Manifest 和 builtin/gRPC/Wasm 兼容行为。
- `data/personal-space/<user-id>`、`data/plugin_data`、`data/plugins` 和现有 URL。
- Web/Admin 页面 URL、核心操作流程和权限结果。

### 6.2 可新增的数据变化

Feature Config Store 预计使用追加 migration，例如 `000019_builtin_feature_state`。最终名称以 A0 数据审查为准，但必须满足：

1. migration 只追加且幂等。
2. 从已知 legacy builtin plugin 状态初始化 Feature desired/effective state。
3. 迁移期双读但只有 Feature Store 可写权威状态。
4. 旧 Plugin API 通过 compatibility projection 读写 Feature Service。
5. down migration 不删除现有 Plugin、Feature 用户数据或文件。

### 6.3 兼容代码规则

- 必须位于对应领域 `compatibility/`。
- 调用方向只能是旧入口 -> 新 Application Service。
- 不能拥有新的业务状态或规则。
- 必须有兼容测试和删除条件。
- 不允许新实现反向依赖旧入口。

## 8. 分阶段执行说明

### A0：基线与所有权冻结

**前置依赖**：v0.7.0 release-check 通过。

**主要工作**：

- 冻结 HTTP/OpenAPI/权限、18 个 migration、9 个 Manifest 和数据目录 checksum。
- 冻结 Web/Admin Router、导航、页面 URL、Feature 启停和插件生命周期。
- 建立“功能 -> 领域 -> 表/目录 -> Service/Handler -> API -> Web/Admin 页面”矩阵。
- 保存机器可读 JSON，标明稳定字段和运行时易变字段。

**目录**：`docs/architecture`、`docs/api`、`scripts`、`web/src/router`、`admin/src/router`。

**测试**：完整 `make release-check`、路由/页面快照、恢复演练。

**回滚**：纯加法基线，无运行时代码回滚。

**完成条件**：所有现有功能、表、文件目录、Handler 和页面均有唯一责任领域；无“暂未归属”。

### A1：模块规范与架构门禁

**前置依赖**：A0 所有权矩阵。

**主要工作**：

- 固化 Module、RouteContributor、Port/Adapter 和 compatibility 规范。
- 扩展后端检查：跨领域 Repository/Service/Handler/Adapter、Server 创建业务对象、Server 业务路由、Feature 读取 Manager、Plugin 子服务反向 Manager。
- 新增 Web/Admin 边界检查：禁止跨模块 internal 导入、集中 API/Router 回流。
- allowlist 冻结为 A0 数量，后续只能减少，不能新增。

**目录**：`internal/platform`、`scripts/check-architecture-boundaries.py`、`config/architecture-*`、CI/Makefile。

**测试**：检查器正负样例、CI YAML 解析、`make architecture-check`。

**回滚**：检查器规则可单项回退；不得借回滚扩大 allowlist。

**完成条件**：新增违规在本地、CI、release-check 三处都失败。

### A2：Application Runtime 与 Infrastructure Profile 骨架

**前置依赖**：A1 合同。

**主要工作**：

- 新增 Application Runtime、Module Set、Route Registry、Infrastructure/Repository Profile。
- PostgreSQL/Memory Profile 提供同一组 Port，不创建业务 Service/Handler。
- 保持旧 `application.go` 作为迁移期 compatibility composition root；每迁移一个领域即删除对应旧装配。
- 增加 Runtime 启动失败回滚、Profile 完整性和 Route 冲突测试。

**目录**：`internal/platform/runtime`、`internal/platform/route`、`internal/server`、`pkg/database`。

**测试**：两种 Profile 合同测试、Module 顺序、重复/缺失 Port、路由冲突测试。

**回滚**：可切回 v0.7 启动入口；不改变业务数据。

**完成条件**：新 Runtime 能同时承载 PG/Memory Profile；不能提前删除尚未迁移领域的旧装配。

### A3：Identity Core 完整迁移

**前置依赖**：A2 Runtime/Profile。

**主要工作**：Identity 自建用户、账号、JWT、角色、权限 Service/Handler/Route；PG/Memory Adapter 绑定 Profile；公开 UserReader、CurrentUser、Authorization、RoleAdministration；移除 Space 等模块对 Identity 具体 Model/Repository 的依赖。

**目录**：`internal/core/identity`，旧入口迁入 `compatibility/`。

**兼容**：认证 URL、JWT claim、角色/权限结果、默认管理员保持不变。

**测试**：注册登录、刷新/过期 Token、角色作用域、Admin 权限负向、PG/Memory Repository Contract。

**回滚**：Module 选择开关仅用于本阶段回退；A14 前删除开关。

**完成条件**：Server 不创建 Identity Service/Handler；其他领域不导入 Identity Repository/Model。

### A4：Community Core 完整迁移

**前置依赖**：A3 Identity Port。

**主要工作**：Category、Tag、Thread、Post、可见性、楼层和事件由 Community Module 拥有；缓存/EventBus 通过 Port；路由由 Community 贡献；RichText、Moderation、MCP-like、Host API 改用 Community Port。

**目录**：`internal/community`。

**兼容**：普通/私密帖子、编辑删除、默认标签、回复楼层和事件语义不变。

**测试**：PG/Memory Contract、帖子 CRUD、隐私越权、回复楼层并发、缓存失效、事件发布。

**回滚**：保留旧 Route Adapter 到本阶段验收完成；无表迁移。

**完成条件**：除 Community Adapter 外没有代码导入 Community Repository。

### A5：Moderation Core 完整迁移

**前置依赖**：A3 Authorization、A4 Community Command/Scope Port。

**主要工作**：使用 Authorization、Category Scope、Thread/Post Command Port；审计归 Moderation；动作配置不控制安全 Core；迁移路由；删除 Community/Identity 具体依赖和对应 allowlist。

**目录**：`internal/moderation`。

**测试**：管理员、分区版主、跨区拒绝、pin/lock/delete 开关、审计完整性。

**回滚**：旧 API Adapter 调新服务；不得回退服务端作用域检查。

**完成条件**：Moderation 跨领域具体依赖为 0，相关 allowlist 为 0。

### A6：User Storage Core 完整迁移

**前置依赖**：A3 UserReader、A2 Profile。

**主要工作**：统一 SafePath、Quota、UserStorage、AssetStore、分类、使用量、URL 和 Local Provider；Profile 创建 Provider；旧 personal-space 配置由独立 Legacy Storage Config Adapter 读取；Server/Feature 不再创建本地实现。

**目录**：`internal/core/storage` 或最终统一的 `internal/core/userstorage`，A0 后确定唯一命名并一次完成迁移。

**兼容**：根目录、分类目录、头像/文章/课表 URL 和默认 10 MiB 配额不变。

**测试**：路径逃逸、符号链接、跨用户、配额并发、覆盖写、文件分类、旧配置。

**回滚**：旧 Space helper 只能保留为 compatibility wrapper。

**完成条件**：所有文件访问经 User Storage Port；Server 和 Feature 无存储构造逻辑。

### A7：Personal Space、RichText、Schedule 完整迁移

**前置依赖**：A3、A4、A6；Feature Config Store migration。

**主要工作**：三个 Feature 各自拥有 Module/Application/Transport；只依赖公开 Port；Feature Store 成为唯一状态源；路由迁移；旧配置迁移为幂等 compatibility migration；删除启动时 `normalizePersonalStoragePluginConfigs()`。

**目录**：`internal/space`、`internal/richtext`、`internal/schedule`、`internal/platform/feature`、新增 migration。

**兼容**：旧 Plugin API 投影 Feature 状态；文章、头像、课表 JSON 和目录不移动。

**测试**：停用数据保留、restart/hot-gated、文章生命周期、HTML 清洗、图片配额、学期/导入/日历、Space 同步。

**回滚**：Feature Store 可读 legacy 状态进行回退；禁止双写冲突和删除新状态表数据。

**完成条件**：三个 Feature 可独立构造；不读取 Plugin Manager；跨领域具体依赖为 0。

### A8：Appearance 统一

**前置依赖**：A6、A7、Resource Repository。

**主要工作**：建立统一 Catalog、Validator、Policy、Application Service、Preference Adapter、Legacy Source Adapter 和 HTTP Transport；Homepage/WebTheme/Space Style 旧入口全部调用新服务；统一预览、应用、资源读取和回滚规则。

**目录**：`internal/appearance`、`internal/homepage`、`internal/webtheme`、`internal/stylepack`、`internal/space/compatibility`。

**兼容**：旧 API、旧目录、现有包格式和用户本地选择不变；不增加跨设备同步。

**测试**：三种 target、checksum/路径/HTML/CSS/JS 安全、回滚、所有者主页、PC/移动端对比度和响应式流程。

**回滚**：旧入口 Adapter 可切回，但新实现不得依赖旧 Service。

**完成条件**：旧 Service 不再拥有重复规则；Appearance Facade 是唯一业务入口。

### A9：Plugin Platform 自治

**前置依赖**：A7 Feature 权威状态、A8 Resource 边界。

**主要工作**：Catalog、Runtime、Lifecycle、Config、UI、Event、Audit、Package、Snapshot、Host Access 各自拥有状态和锁；通过明确依赖协作；Manager 只做旧方法转发；Legacy Built-in 仅是 Feature/Core 投影视图；Admin 模型区分 Feature 与 External Plugin。

**目录**：`internal/plugin`、`internal/plugin/compatibility`、SDK/CLI 合同。

**兼容**：9 个 Manifest、Host API、Gateway、动态 UI、gRPC/Wasm、导入导出和回滚保持。

**测试**：生命周期状态机、并发、token 轮换撤销、UI revision、事件、包路径、快照回滚、三 Runtime 模板。

**回滚**：Manager Facade 始终可调用新子服务；不能恢复 Manager 为状态中心。

**完成条件**：子服务不持有 Manager 引用；Manager 无核心锁和状态；Builtin 不能普通卸载。

### A10：现有 Integration Module 迁移

**前置依赖**：A3/A4 Port、A2 Runtime。

**主要工作**：AI、Webhook、MCP-like、Message、Platform Logs、Metrics 分别拥有 Module/Port/Adapter/Handler/Routes；Integration Overview 只读 Summary Port；MCP-like 改用 Community Reader，不升级标准 MCP。

**目录**：`internal/ai`、`webhook`、`mcp`、`message`、`platformlog`、`integration`、`observability`。

**测试**：权限、配置、Webhook 签名投递、MCP 只读/审计、Message local、日志路径白名单、指标聚合。

**回滚**：旧 Integration Handler 作为 compatibility 聚合器调用 Summary Port。

**完成条件**：Server 不创建集成业务对象；MCP Community Repository allowlist 删除。

### A11：Composition Root 与 HTTP 合同收口

**前置依赖**：A3-A10 全部领域 Module。

**主要工作**：删除 PG/Memory 重复业务装配；Server 只选择 Profile 和 Module Set；Route Registry 聚合模块 RouteDescriptor；合同生成器不再解析单个大型 Server 文件；统一 DTO、分页、错误、Trace、权限和 Feature disabled 映射。

**目录**：`internal/server`、`internal/platform/route`、`internal/projectaudit`、`cmd/campusos-contracts`。

**测试**：148 条路由集合、OpenAPI/权限 checksum、重复路由、模块所有者、错误映射、PG/Memory 全链路。

**回滚**：Route Registry 可生成旧 Gin 注册顺序；禁止恢复业务对象创建到 Server。

**完成条件**：`application.go` 不创建业务对象；Server 不导入领域 Repository/Service/Handler，不接收大型 Handler 参数。

### A12：Web 前端领域化

**前置依赖**：A11 稳定 HTTP/Feature/Plugin 合同。

**主要工作**：建立 `app/shared/modules/pages`；按 identity/community/space/richtext/schedule/appearance/plugin-runtime 拆 API、DTO、Store、Router；App 壳不查询领域数据；动态 UI 和主题查询归对应模块；增加边界检查和 bundle budget。

**兼容**：页面 URL、交互、localStorage key 和视觉行为不变。

**测试**：TypeScript、lint、format、组件/状态测试、权限路由、Feature disabled、Plugin degraded、浏览器和响应式流程。

**回滚**：领域 Router 可由旧总 Router 聚合；不能复制两套 API Client。

**完成条件**：集中式 API/Router/Store 退出主路径；既存大 chunk 告警消除或有可执行预算豁免。

### A13：Admin 前端领域化

**前置依赖**：A7 Feature API、A9 Plugin API、A11 合同。

**主要工作**：按 Identity/Roles/Community/Moderation/Features/Plugins/Appearance/Integrations/Logs/Architecture 拆 API、DTO、Store、Router 和页面；统一权限元数据、错误/加载/空状态；Built-in Feature 与 External Plugin 分开管理。

**兼容**：管理 URL 和权限结果不变；旧深链接可访问。

**测试**：TypeScript/build、权限矩阵、Feature restart 提示、Plugin lifecycle、Integration、日志和浏览器管理流程。

**回滚**：旧 Router 仅聚合新模块；不能恢复 Built-in 普通卸载按钮。

**完成条件**：Admin 无集中式大 API/Router；Feature/Plugin 模型和界面彻底分离。

### A14：兼容层收敛和技术债清零

**前置依赖**：A3-A13。

**主要工作**：业务 allowlist 清零；删除重复装配、无调用构造器、Server 业务配置/迁移、Feature->Manager、Plugin 子服务->Manager、Appearance 重复规则和前端跨域 internal 导入；保留项迁入 compatibility 并补自动测试。

**测试**：架构检查必须在空业务 allowlist 下通过；反向依赖和死代码检查；兼容 API/数据/Manifest/目录回归。

**回滚**：按单个 compatibility Adapter 回滚；禁止恢复旧主路径。

**完成条件**：allowlist=0；不存在 TODO“后续迁移”；旧入口只调用新实现。

### A15：稳定性、性能和故障测试

**前置依赖**：A14 主路径唯一。

**主要工作**：PG 失败、Redis/NATS fallback、Module Register/Start/Stop、Repository/Storage Contract、Plugin 状态机、Feature 模式、并发/race、前端 Auth/权限/错误/Feature/Plugin、bundle budget；旧数据库、配置、资源和用户文件恢复。

**测试命令**：全量 Go、关键包 `-race`、Web/Admin 单测与构建、database-check、restore drill、browser smoke。

**回滚**：测试与性能调整逐项回滚；不得删除安全检查换取性能。

**完成条件**：故障不破坏数据；fallback 可观察；关键包无 race；前端满足 bundle budget。

## 9. 每阶段 Definition of Done

每个阶段必须同时满足：

1. 阶段范围内代码和迁移完成，不以空接口、未接线 Facade 或文档代替实现。
2. 定向测试通过。
3. `GOCACHE=/tmp/campusos-go-cache go test ./... -count=1` 通过。
4. `make architecture-check`、`make contracts-check`、`git diff --check` 通过。
5. 涉及的 Web、Admin、docs-site、SDK 构建通过。
6. API、路由、配置、migration、Manifest 和目录变化已记录。
7. 兼容路径、数据保留和可执行回滚已验证。
8. 对应 `docs/进度/v0.8-dev/v0.8.N-dev.md` 已生成。
9. 本计划的实现状态和验收状态已分别同步。

没有完整证据不得标记“已验收”。一次阶段只处理一个可独立回滚的架构切片；阶段内部可再拆子任务，但只能在全部子任务验收后使用该阶段编号。

## 10. v0.8 硬性退出条件

### 10.1 后端

- 所有现有业务有明确运行中 Module，不是 marker。
- Server 不创建业务 Service/Handler，不注册具体业务路由。
- PG/Memory 共用业务装配。
- 业务架构 allowlist 为 0；所有路由有 Module owner。
- Feature Store 是 Built-in Feature 唯一权威状态源。
- Plugin Manager 只是无状态兼容 Facade，子服务不反向依赖 Manager。
- Appearance、User Storage 和所有现有 Integration 使用统一主路径。

### 10.2 前端

- Web/Admin API、Router、DTO、Store 按领域拆分并通过边界检查。
- App 根组件不承担领域业务。
- Built-in Feature 与 External Plugin 管理完全分离。
- 页面 URL、权限和核心交互兼容。

### 10.3 数据与兼容

- 148 条路由兼容，OpenAPI/权限无非预期漂移。
- `000001` 至 `000018` 未改写；新增 migration 可恢复、可审计。
- 9 个 Manifest、旧配置、旧目录、旧 URL 和旧响应格式兼容。
- 用户文件、RichText、Schedule、Space 和风格包无丢失。
- compatibility Adapter 无业务状态，调用方向全部为旧 -> 新。

### 10.4 测试与文档

- 全量 Go、关键 race、Web/Admin/docs-site/SDK 构建通过。
- database/schema/architecture/contracts 通过。
- PG/Memory、恢复、浏览器、Feature、Plugin 和响应式流程通过。
- 计划、进度、帮助、API 和代码状态一致。

任一条件缺少证据，版本只能保持 alpha/beta/rc，不得发布 `v0.8.0`。

## 11. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 一次改动过大 | 按领域迁移；旧入口先代理新实现；每阶段独立回滚 |
| 双主路径行为漂移 | 每个领域设置单一写入权威；双读期禁止双写 |
| Feature 状态迁移错误 | migration 前后数量/状态校验；旧 Plugin API 只作投影 |
| 路由重构丢权限 | RouteDescriptor 包含 owner/auth/permission；合同 checksum 门禁 |
| PG/Memory 行为不同 | Repository Profile Contract Test 使用同一测试集 |
| 文件路径或配额回归 | 真实目录 fixture、恢复演练和恶意路径负向测试 |
| Plugin 并发状态错误 | 子服务明确锁所有权；状态机和 race 测试 |
| 前端重构 URL/状态丢失 | Router 快照、localStorage 兼容和浏览器工作流 |
| “技术债清零”诱发删兼容 | 区分架构主路径与产品兼容合同；兼容层必须有测试 |
| Agent 范围侵入 | 架构检查禁止新增执行入口、页面、表和高权限 Runtime |

## 12. 禁止事项

- 禁止一次性重写全部领域或拆成大量微服务。
- 禁止在 A0 基线前移动表、目录、API 或路由。
- 禁止修改历史 migration、静默删除旧配置/Manifest/文件。
- 禁止以临时 Facade、空 Module、marker 或扩大 allowlist 宣称完成。
- 禁止新旧实现双写同一权威状态。
- 禁止 Server、前端 App 根组件或 Plugin Manager 重新吸收领域逻辑。
- 禁止为了通过测试移除权限、审计、配额、路径、内容安全或数据库约束。
- 禁止加入 Agent 执行、标准 MCP、新 Adapter、市场或其他新产品范围。
- 禁止在恢复、兼容和负向测试缺失时删除旧入口。

## 13. 文档与进度管理

每完成一个独立阶段，创建且只创建对应编号的进度文档：

```text
docs/进度/v0.8-dev/v0.8.N-dev.md
```

文档至少包含：阶段目标、实际完成内容、主要文件、架构变化、数据/API/前端兼容、测试证据、回滚证据、已知限制、下一阶段。若阶段未通过完整 DoD，进度文档必须标记“实现中”或“待验收”，不能写“已完成”。

计划状态、进度文档、代码和验证结果必须在同一阶段内同步。源思路文档保留作为决策输入，不覆盖、不改写。

## 14. 最终结论

v0.8 的目标是让 v0.7 建立的边界成为所有现有功能的唯一运行主路径：业务对象归领域 Module，基础设施差异归 Profile，路由归 Module，Feature 状态归 Feature Store，外部插件归自治 Plugin Platform，资源归 Appearance/Resource System，Web/Admin 归领域模块。

除明确排除的 Agent 和新产品功能外，本计划已经识别的现有架构问题必须在 A16 前解决。兼容 API、历史 migration、Manifest 和数据目录可以保留，但只能作为经过测试的单向 compatibility Adapter，不能继续承担核心业务。
