# CampusOS 当前架构概览

> 架构文档入口：[阅读顺序与历史边界](README.md)
> 第一次接触仓库：[开发者递进入门路线](../help/开发者递进入门路线.md)

> 当前应用启动/合同版本：`v0.13.0`；v0.14-dev 已确认开发收尾，`v1.0` clean database foundation 已进入开发

## 1. 运行拓扑

```text
web（Vue 3，:3000） ----------\
                              -> API（Go + Gin，:8080） -> PostgreSQL
admin（Vue 3，:3001） --------/                       -> Redis / NATS
                                                          -> 本地 data/

docs-site（VitePress，:3002） -> 独立静态文档站
```

`web/` 是普通用户界面，`admin/` 是管理员界面。业务规则和授权必须在 API 层执行；前端只负责调用已授权接口和呈现状态。`docs-site/` 不依赖业务 API，负责面向使用者和插件开发者的项目介绍、部署、接口与插件教程，可以独立构建、部署或迁移到单独仓库。

## 2. 后端模块

v0.7/v0.8 完成了模块化单体的 Core、Built-in Feature、External Plugin 和 Resource Package 边界。v0.9 在该边界上增加多端回归门禁、External Plugin Manifest v2、受管数据/文件、用户授权与本地目录治理；v0.10 又增加内容治理事实源、稳定权限 Code、路由操作目录和生成物治理；v0.11 新增 Reliability Core，用 TxKernel、持久 Outbox 和 Worker 约束高风险命令及提交后的外部副作用。

四类能力边界为：不可停用的 Core Module、可停用且保留数据的 Built-in Feature Module、只能走 Host/Gateway/公开 API 的 External Plugin，以及不拥有业务生命周期的 Resource Package。

| 模块 | 职责 |
| --- | --- |
| `internal/modules/core/identity` | 身份、验证式注册、Challenge/Ticket、邮箱账号状态、Session、独立管理员准入账号、角色、权限和后台授权。 |
| `internal/modules/core/emaildelivery` | Challenge 邮件的 SMTP/Fake Provider 边界；只消费不透明 Challenge ID，通过 Identity Dispatch Port 临时重建投递内容。 |
| `internal/modules/core/community` | 两级版块、标签、帖子、回复、可见性、板块帖子类型策略、可靠 Category/作者/结构化 Thread 命令和社区事件。 |
| `internal/modules/core/contenteditor` | 纯内容安全核心：受控 HTML 清洗、文本/Markdown/CampusDoc v1 校验与渲染；不依赖 Community、文档仓储、文件系统或 Plugin。 |
| `internal/modules/core/moderation` | 版块版主授权、作用域判定、治理动作和审计。 |
| `internal/modules/core/userstorage` | 用户目录、安全路径、配额、资产 Provider、对象元数据、Reservation 账本、只返回 Object ID 的 Object Port，以及按 keyset 批次和可恢复 checkpoint 执行的默认只读/显式受审计 apply 本地对象对账；对象/账本的多语句写入参与 TxKernel，且只导出低基数聚合指标。 |
| `internal/modules/core/academicterm` | 管理员维护 spring/fall 学期、第一周、open/closed/default 生命周期与乐观锁；默认学期切换等多语句写入参与 TxKernel，不依赖课表 JSON。 |
| `internal/platform/transaction`、`internal/platform/reliability` | 事务上下文、可靠命令审计、持久事件、lease Worker、兼容遥测、可恢复操作和保留预演。 |
| `internal/platform/observability` | 有界指标目录、Meter/Collector Port、Admin 摘要、数据库池与运行时快照，以及默认关闭的 loopback Prometheus 导出。 |
| `internal/plugin` | External Plugin 的 v1/v2 manifest、三轴生命周期、UI Contract/Revision/SSE、Extension Gateway、受管进程/Wasm runtime、安装包、Host API、受管数据/文件、Grant、Catalog、签名与配置。 |
| `internal/modules/features/personalspace` | 个人主页、内容同步、头像、个人空间和个人主页风格包。 |
| `internal/modules/features/appearance/stylepack` | `page-style-pack.v1` 与 `campusos.app-style-pack.v2` 的目录/zip 读取、Layout Recipe 和安全筛查。 |
| `internal/modules/features/appearance/webtheme` | 管理员提供的全用户前台主题目录、公开运行包和资源读取边界。 |
| `internal/modules/features/richtext` | 受控图文文章、草稿、图片资产，以及通过 `core.content-editor` 兼容 Adapter 使用的 HTML 清洗/渲染；仍与 Community Thread 同事务写入 Detail。 |
| `internal/modules/features/mutualaid` | 校园求助、提供、志愿协助和资源分享；只拥有 `mutual_aid_details` 及其业务状态，基础 Thread 与治理仍归 Community。 |
| `internal/modules/features/secondhand` | 校园闲置物品信息；只拥有 `secondhand_details` 的 CNY 分价、成色、交付方式和交易状态，基础 Thread 与治理仍归 Community。 |
| `internal/modules/features/schedule` | 受管 AcademicTerm 的个人课表、课程导入和日历计算；新写入先提交 immutable Object 与乐观锁引用，再原子刷新兼容 JSON 镜像，历史采用命令只复制已校验 JSON。 |
| `internal/modules/features/personaldocuments` | 私有文档、不可变版本、回收站和认证下载；创建与追加版本的多语句写入参与 TxKernel，并在同一事务发出最小化的 `document.preview.requested.v1` Outbox 事件。未启用受审查 Converter Runner 时，内置安全降级消费者仅严格校验允许字段并写 receipt，不读取内容或调用外部转换器。TXT/Markdown/CampusDoc 通过共享安全核心编辑与服务端预览，受信 Built-in ReadPort 仍保持 owner scope 且不进入 External Plugin Host；PDF/DOCX 在未满足隔离条件时仅上传与下载。 |
| `internal/modules/features/ai`、`webhook`、`mcp`、`message`、`integration`、`platformlog` | 可配置的 AI Gateway、Webhook、内部 MCP-like 只读工具、Message local adapter、集成摘要和平台日志。 |

AcademicTerm、User Storage Object 与 Personal Documents 的 PostgreSQL Repository 均从请求上下文通过
`transaction.ExecutorFor` 取得执行器；必须原子完成的多语句操作通过 `transaction.Manager.Within` 建立或复用
TxKernel 事务。这样服务层已有事务时不会绕开其边界，独立仓储调用也不会留下部分账本、版本或默认学期状态。

## 3. 插件边界

| 目录或概念 | 职责 |
| --- | --- |
| `modules/core/*/module.yaml` | 编译期 Core Module 描述符；Core 始终启用且不能卸载。 |
| `modules/features/*/module.yaml` | 编译期 Built-in Feature 描述符；由 Feature Registry 配置或启停。 |
| `data/plugins/<plugin>/` | 插件实现、manifest、运行入口和插件 README。 |
| `data/plugin_data/<plugin>/` | External Plugin 的 v1 SQLite KV、运行数据和版本快照。 |
| `data/module_data/<feature>/` | Built-in Feature 的本地可变数据。 |
| `data/resources/<type>/<package>/` | 无业务 Runtime 的主题、首页、个人主页风格、Skill、Prompt 等资源包。 |
| `plugin_records` / `plugin_file_metadata` | v2 受管记录与附件元数据；实际附件仍走 User Storage。 |
| `scope: system/user` | 只表示管理级别、安装权限和系统重要性，不再决定 Runtime 生效方式。 |
| `lifecycle.backend.activation_mode` | `restart`、`plugin-restart` 或 `hot`；旧 manifest 按 Runtime 推导。 |
| `lifecycle.frontend.activation_mode` | 当前固定为 `hot`；路由、导航、插槽、Surface 和 Action 可注册与完整清理。 |
| `target: web` | 只作用于用户前台应用根节点；Admin 是独立前端，不加载系统主题。 |

“用户级”不表示普通登录用户可自行安装插件。插件安装和配置仍受管理员权限保护。插件状态分为 BackendState、FrontendState 和 Health；后端重启或降级不会自动删除前端页面。

## 3.1 前端运行时

```text
CampusApp -> ThemeRoot -> AppShell
  -> Header / Navigation / Hero / Sidebars / PageOutlet / Floating / Footer / Safety
  -> Runtime Registry
  -> Route / Navigation / Slot / Surface / Action
```

`GET /api/v1/ui/runtime-manifest` 提供当前主体可见贡献，`GET /api/v1/ui/events` 以 SSE 通知 revision。第三方默认 UI 使用白名单声明式 renderer；复杂旧页面只能通过 Core 编译期 trusted module registry 迁移。业务 Action 统一经 `/api/v1/extensions/:plugin/*path` 分发，插件只信任 Core 注入的 caller。

## 4. 本地数据边界

```text
data/
├── plugins/                 External Plugin 代码和 manifest
├── plugin_data/             External Plugin 运行数据和版本快照
├── module_data/             Built-in Feature 本地可变数据
├── resources/               无 Runtime 的主题、首页、主页风格和 Agent 资源
├── personal-space/<user>/   用户本地数据
│   ├── file/                通用文件和课表数据
│   ├── img/
│   │   ├── avatars/         头像源文件与最近三项历史
│   │   ├── content/         普通帖子、校园互助、二手正文图片
│   │   └── richtext/        受控图文文章图片
│   ├── excel/ word/ pdf/    按类型归类的上传文档
│   ├── plugins/<plugin>/    v2 插件受控用户附件
│   └── file/schedule/
│       ├── index.json
│       └── terms/<year>-<semester>.json
├── images/                  非用户空间的全局图片
├── config/                  本地配置预留
├── dist/                    本地发布/构建产物预留
└── skills/                  本地 runtime/imported skills 预留
```

个人空间数据会计入配额。默认本地配额由 Personal Space Built-in Feature 配置，实际路径、所有权和配额由 User Storage Core 强制执行；新建个人文档通过 Object Port 以 Object ID 建立私有版本引用，业务 DTO 不包含 Provider key 或宿主绝对路径。头像、普通正文图片与富文本图片仍保留兼容文件边界；“我的文档 → 已上传资源”仅按当前上传者聚合它们的安全元数据和 URL 供预览，不将其伪装为可删除的私有文档，也不暴露宿主路径。Document Provider 的只读草案仅限受信编译内调用，未注册为 AppContext 或 External Plugin Host 能力，因此插件无法读取用户文档原文。

## 5. 安全与协议约束

- 页面风格包和自定义外观使用经过筛查的 HTML/CSS，不接受任意 JavaScript。
- `core.content-editor` 是 RichText 和个人文档共享的安全边界：Markdown 原始 HTML 一律转义；CampusDoc v1 图片只接受受控 `object_id`，不接受外部 URL；页面只渲染服务端返回的已清洗预览 HTML。
- 风格包可选 JavaScript 仅以 `sandbox-worker.v1` 运行；无同源、DOM、令牌、存储和任意网络权限。TypeScript 只是可选源码，运行前必须编译成受筛查的 JavaScript。
- CampusStyleSDK 只代理 manifest 声明的只读能力；个人主页数据固定到主页所有者，系统主题的私有能力还需当前用户单独授权。
- 插件包导入前检查路径安全、大小、checksum、manifest 和声明权限。
- `campusos.plugin/v2` 的结构化数据只能通过 Host API/Gateway 访问：Host 注入插件和用户所有权，插件不会获得表名、数据库连接、用户 Token 或宿主绝对路径。
- 用户对个人数据能力的 Grant 绑定插件版本和精确 `resource:action`；撤销后立即拒绝记录和文件调用，数据默认保留。
- Ed25519 包签名覆盖确定性内容摘要；必签名插件在 trust store 未验证时不能导入，管理员不能手工声明包已验证。
- MCP-like 工具是内部只读 API，不是标准 MCP Server。
- Message 是平台无关模型，只提供 local adapter；Discord、OneBot v0.11、NapCat 和 AstrBot 应作为适配器工作，而不是核心业务协议。
- 系统级授权和校验由 Go 服务强制执行，不能依赖浏览器侧检查。
- Built-in Feature 的 Gin 路由保持静态注册；Feature 停用时 Path Gate 默认拒绝全部对应业务路径。只有
  经过精确方法和路径白名单声明的只读状态接口（当前为 `GET /<feature>/status`）可返回
  `enabled=false`，白名单不得用于详情、列表、写入、配置或内部服务访问。
- `member` 是有效登录用户的隐式基础角色；`user_roles` 记录管理员全局授权和版主版块授权，`guest` 不会写入用户角色关联。
- Admin 管理平面使用独立的 `identity_admin_accounts` 准入事实。管理员专用登录和非 scoped Admin API 必须
  同时通过有效 Session、活动管理员账号和具体权限；该表引用 `accounts` 凭据但不复制密码哈希。声明了
  `category` scope 的治理路由仍允许版主按板块权限访问，不会把版主提升为管理员。
- 版主请求必须同时满足动作权限和主题所属版块的 `category` scope；客户端传入的版块 ID 不能作为授权依据。
- Category 的 `group` 仅为根级导航容器，`board` 才能接收帖子；board 可位于根级或一个 active group 下，
  归档/closed/group 节点均不可发帖。移动 board 不修改任何版主 scope，也不产生父级权限继承。
- Category 管理写入要求版本号。`community.category.*` 命令在同一 TxKernel 事务中写入层级事实、
  required audit 和 Outbox；旧 `DELETE /categories/:id` 只映射为 archive 并记录兼容遥测。
- 作者创建、编辑和回收普通 Thread 也使用可靠命令。RichText 作为 Built-in Feature 在一个外层命令内
  协调 Thread、Revision、Article Detail、command audit 和 Outbox；其 PostgreSQL Store 只通过
  `transaction.ExecutorFor` 获得当前事务。创建 Detail 失败会回滚 Thread，不再创建补偿式回收站内容。
- `threads.thread_type` 是稳定业务类型，`content_format` 只说明正文渲染。board 通过
  `category_thread_type_policies` 约束新的类型创建；默认只允许 `discussion/article`。
  结构化 Detail 只能由编译内 Built-in Feature Participant 在 Community 的同一可靠事务内写入，
  External Plugin、MCP 和 Agent 不会取得该能力。
- 校园互助通过 `feature.mutual-aid` 的一对一 `mutual_aid_details` 保存业务类型、状态、截止时间和
  受限地点/联系信息。其 `open/in_progress/resolved/closed` 状态机与 Community 发布、审核、回收状态
  分离；数据库触发器还会强制 Detail 指向 `mutual_aid` Thread 且作者一致。
- 校园二手通过 `feature.secondhand` 的一对一 `secondhand_details` 保存 CNY 分价、成色、交付方式、
  交易状态和受限地点。其 `available/reserved/sold/closed` 状态机与 Community 发布、审核、回收状态
  分离；数据库触发器强制 Detail 指向 `secondhand` Thread 且作者一致，不保存支付、订单或仲裁数据。
- 高风险数据库命令在同一事务内写业务事实、required audit、command audit 与 Outbox；Webhook 等外部副作用在提交后以至少一次语义处理。
- 邮件投递是始终启用的 Core Module。Outbox 不保存收件人、Code、Ticket 或正文；SMTP 故障只记录脱敏状态并由 Worker 重试，不能承诺 exactly-once。
- 公开注册必须依次申请 Challenge、校验六位 Code、提交一次性 Ticket。最后一步在同一个可靠命令中创建用户和 verified Email Account；旧一步式注册只返回稳定错误，不会创建 unverified 账号。

外部适配映射见 [接口协议适配器标准说明](../help/系统设计相关/接口协议适配器标准说明.md)。

## 6. 当前数据库与管理端数据架构

当前数据库不再使用历史 `000001-000049` 链。项目所有者明确允许丢弃全部测试数据后，Schema 已重建为：

| migration | 内容 |
| --- | --- |
| `000001_v1_schema_baseline` | 76 张当前业务表、外键、CHECK、索引、函数与触发器；时间点统一为 `TIMESTAMPTZ` |
| `000002_v1_plugin_authorization_foundation` | 发布者、不可变版本、Capability Declaration、Admin Grant、User Consent、Delegation、Secret 和判定证据 |
| `000003_v1_reference_data` | 系统角色、76 个 Permission Code、最小授权矩阵和身份安全策略；不含用户或默认凭据 |

执行器另建 `schema_migrations` 和 `schema_migration_locks`，保存 SHA-256、执行耗时、执行者和互斥锁。
旧 `permissions(resource, action)` 表已经删除，平台 RBAC 只使用
`permission_definitions + role_permissions`。当前插件 Runtime/市场仍使用 `plugins`、`plugin_permissions`、
`plugin_user_grants` 等现行业务表；v1 新表是后续统一授权服务的数据基础，表存在不表示业务切换已完成。

管理端 `/architecture` 是只读架构视图，当前列出 86 张业务/系统表和三段 migration：

- 数据库关系：表职责、关键字段、当前 migration 来源和可追踪关联；
- 数据与文件：PostgreSQL、`data/`、个人空间、插件实现/数据和日志边界；
- 迁移与维护：checksum、状态、up/down/reset 和备份边界。

页面不读取真实业务记录、Secret 或本地文件正文，也不和数据库实时反向同步。修改 migration 时必须同时更新
Admin 数据架构页、`scripts/schema-contract.sql`、[数据库全面重构方案](../项目计划书v1/项目计划v1.0/01-v1.0数据库全面重构方案.md)
和 [migration README](../../migrations/README.md)，然后运行：

```bash
make v1-database-baseline-check
make architecture-check
make database-check
```
