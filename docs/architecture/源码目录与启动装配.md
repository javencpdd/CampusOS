## 实际目录

```text
cmd/server/main.go                  API 进程入口
internal/server/                    装配、部署校验、HTTP 生命周期、管理员初始化
internal/transport/httpapi/          路由和公开/认证/管理员端点装配
internal/modules/core/              七个核心业务源码目录
internal/modules/features/          十三个内置业务源码目录
internal/platform/                 模块、功能、事务、可靠任务、资源、路由、运行时、监控、版本
internal/plugin/                    外部/第一方受管插件的安装或注册、运行、授权、Host API
pkg/                               配置、数据库、认证、中间件、事件、缓存等公共实现
modules/core/、modules/features/     嵌入编译的 module.yaml；不等同于 Go 包目录
web/src/、admin/src/                双前端入口、路由、组件和功能模块
docs-site/                         官方静态文档站
migrations/                        当前 SQL 及生成的 ER 产物
deploy/docker/、scripts/            开发与部署入口、校验和运维脚本
sdk/、examples/plugins/             SDK 与插件示例，不由 API 自动装配为业务
data/                              资源和运行数据，不是源码模块根
```

不存在统一的 internal/<domain> 新模块模板；核心实际在 internal/modules/core，
内置功能实际在 internal/modules/features。外观模块的 Go 装配入口是 appearance/runtime/module.go。

## API 启动与停止

1. [main.go](../../cmd/server/main.go) 调用 config.Load，再调用 Server.New/Run。
2. [server.go](../../internal/server/server.go) 先 startInfrastructure，再 runApplication，并延迟释放基础设施。
3. [bootstrap.go](../../internal/server/bootstrap.go) 校验部署配置，连接数据库、构造缓存与模块，选择 PostgreSQL 或 Memory Adapter。
4. [Runtime](../../internal/platform/runtime/runtime.go) 先绑定 Profile，再启动 Module Registry。
5. [Module Registry](../../internal/platform/module/module.go) 根据 Go Dependencies() 拓扑排序，先 RegisterAll，再 Start；失败回滚已启动模块，停止时逆序 Stop。
6. [application.go](../../internal/server/application.go) 初始化管理员、收集 Handler，调用 httpapi.Build，同步路由权限目录，进入 HTTP 监听。
7. [HTTP 生命周期](../../internal/server/http_server.go) 管理 HTTP 服务；模块退出清理由 Runtime 和基础设施 Stop 承担。

数据库连接失败会切换到 Memory Adapter；这条分支没有按 production 排除。
因此 API 能启动不代表数据一定持久化。NATS 连接失败也会回退内存事件总线；
两者都不是高可用或跨进程一致性方案。

## 依赖关系的两种含义

Go Dependencies() 决定启动顺序；module.yaml 的 dependencies 是目录/功能声明。
二者目前存在差异，不能把 YAML 图当作精确的启动图。例如：

| 模块 | Go Dependencies() 的事实 |
| --- | --- |
| Identity | event-bus、reliability、observability |
| Community | content-editor、event-bus、identity、feature-registry、reliability |
| User Storage | identity、observability |
| AcademicTerm | identity |
| Moderation | identity、community |
| RichText | community、user-storage、feature-registry、reliability、observability |
| Schedule | identity、academic-term、user-storage、feature-registry |
| Personal Documents | content-editor、identity、user-storage、reliability、feature-registry、observability |
| Personal Space | identity、community、user-storage、reliability、feature-registry、appearance |
| Integration Overview | plugin-platform、personal-space、integration.ai/webhook/mcp/message/platform-log |

表中简写保留原 ID 的后缀，前缀按具体 Go 模块定义。
Identity/RichText/Email Delivery 的 Go 依赖包含 observability，但相应 YAML 未全部列出；
Moderation YAML 额外列出 feature-registry。本文记录差异，不暗示本次已修改代码统一。

模块通过 AppContext.Provide/Lookup 提供 Port，也存在明确的具体 Service 指针依赖：
Integration Overview 会读取 AI、Webhook 等 Service，不能宣称全部跨模块调用均仅依赖抽象接口。

## HTTP 与前端调用链

请求进入 Gin 后经过监控、Recovery、CORS、TraceID、Logger 和指定路径的 Feature Gate，
再进入公开、已认证或管理员路由。业务服务继续检查所有权、状态和作用域。
并非所有接口都由同一个 PathGate 规则自动覆盖，附件和预览还依赖服务方法中的校验。

[Web main](../../web/src/main.ts) 与 [Admin main](../../admin/src/main.ts) 均初始化 Pinia、Router，
恢复用户/管理员会话后挂载应用。静态业务路由与 Campus UI 运行贡献共存。
Vite 使用 CAMPUSOS_API_PROXY_TARGET 代理 /api；生产 SPA 回退和代理见
[Nginx 配置](../../deploy/docker/nginx-spa.conf)。
