# 可靠事件与外部集成

> 实现基线：v1.1-dev
> 返回：[当前架构概览](../当前架构概览.md)

## 职责与关键流程

[可靠命令平台](../../../internal/platform/reliability) 管理高风险命令的持久状态、任务执行及可审计结果；
[事务平台](../../../internal/platform/transaction) 提供统一事务边界。

命令进入应用服务 → 在事务中写业务事实和必要的审计/Outbox → 提交 →
Worker 领取任务并执行副作用 → 持久化结果、重试或进入运维处理。
提交业务成功不表示邮件已经抵达收件箱；重复消费需靠业务幂等和任务状态控制，
不能宣称跨数据库和外部网络的端到端“恰好一次”。

## 邮件投递

[Email Delivery](../../../internal/modules/core/emaildelivery) 提供 fake 与 SMTP 适配。
Identity 拥有 Challenge，Outbox 传递不透明标识；投递时通过受控 Port 获取所需信息，
不在持久事件内放邮箱验证码、Ticket、Token 或邮件全文。

fake 表示开发模拟成功，不发送真实邮件。smtp 表示使用真实 SMTP，
“降级”意味着投递路径发生失败，应查服务端脱敏错误、网络/TLS、认证及重试状态。
Docker API 健康检查通过不能证明 SMTP 可用。

开发配置入口是 deploy/docker/.env.dev.local；不要将其秘密复制到仓库或架构文档。

## Webhook 与其他集成

Webhook 将订阅事件转成持久投递任务，处理签名、失败重试和外部地址安全边界；
模块实现见 [Webhook](../../../internal/modules/features/webhook)，出站配置键见 [配置与运行边界](../配置与运行边界.md)。

AI Gateway、Webhook、MCP 与消息适配为各自内置功能：
AI 请求需要独立的提供方与密钥配置；消息本地适配不等于所有渠道上线；
当前 MCP-like 只读集成不能对外宣传为已实现标准 MCP Server。

## 接口与依赖

用户访问仍经 /api/v1 下的业务或管理员接口；运维入口及其权限以
[路由矩阵](../../api/HTTP路由与授权矩阵-v0.6.md) 为准，不向普通用户开放原始任务载荷。

内部主要契约是事务 Executor、可靠命令/事件、Worker 处理器和模块 Port；
外部依赖包括 PostgreSQL、配置的消息基础设施、SMTP、Webhook 目标及 AI 提供方。
这些外部服务需各自超时、限流和失败策略，不能依赖一个健康端点代表全部依赖。

## 运维与验证

监控失败数、重试、积压和低基数错误分类；避免邮箱、文件名和用户内容成为指标标签。
日志应保留可关联的操作/任务标识但脱敏，管理员重试前确认幂等及目标状态。

变更需覆盖事务回滚、重复请求、重复投递、租约失效、进程重启、外部超时和秘密泄漏。
