## 数据所有权与迁移

[migrations](../../../migrations/README.md) 是数据库结构事实源。
当前重建基线已包含核心业务、插件三层授权与权限种子、附件资产、文章绑定、预览 Invocation、资产治理、
个人资产与 Personal Documents 的 owner-only PDF 预览上下文。它整合的是此前开发链的最终有效结构，而不是
可对旧数据库原地升级的补丁包。

表由模块拥有，跨模块通过显式服务或 Port 协作；管理端架构页是结构投影，不是实时全库数据浏览器。
`000001` 已含 `plugin_ui_invocations.personal_document_id`、外键、三类上下文互斥检查和部分索引；`000002`
只将 `plugins.runtime` 的受限枚举扩展为 `none`，供**没有后端进程**、但有已校验隔离 UI 产物的 v4 插件使用；它不创建
插件私有表，也不放宽管理员 Grant、用户 Consent 或业务资源 ACL。它们都不导入
或重写用户文档、版本或对象字节。旧链会因 checksum 被执行器拒绝，测试库必须先显式 reset。自本 clean baseline
进入共享环境后，新增变更必须从 `000002` 以有序 UP/DOWN 追加，并说明外键、索引、默认值、回滚损失和数据修复前置条件。

测试数据可重置并不意味着任何一次任务都应执行删除；重置或 destructive DOWN 前需确认目标库和授权。

## 持久数据边界

| 位置                       | 内容与约束                             |
| -------------------------- | -------------------------------------- |
| PostgreSQL 数据卷          | 业务事实、权限、资产元数据、任务与审计 |
| data/personal-space        | 用户对象字节及历史兼容布局             |
| 插件实现目录与 plugin_data | 安装实现与插件运行数据分离             |
| module_data、resources     | 内置模块数据与无运行时资源分别管理     |
| .campusos/logs             | 开发日志，注意脱敏与保留策略           |

准确的目录解析由运行配置和对应存储服务决定。备份必须关联数据库与用户字节，
仅备份数据库不能恢复附件；仅复制文件不能恢复所有权、引用和权限。

`data/personal-space` 是受数据库 `storage_objects`、资产、文档和业务绑定共同约束的物理字节层，不能仅凭目录名批量清空。
只有在确认目标为测试环境、对应对象/资产/文档引用均为零后，才可清理无引用的历史孤儿文件；仓库中的 `.gitkeep` 必须保留。
删除孤儿文件不需要 migration 或容器重启，但删除有引用字节会造成不可恢复的下载/预览失败。

API 当前会在 PostgreSQL 连接失败时选择内存适配器，不按生产环境排除此分支。
本地用户存储与插件 SQLite 限制为单实例写入，multi 模式在启动校验中被拒绝。
这些边界及准确配置键见 [配置与运行边界](../配置与运行边界.md)。

## Docker 开发与配置流程

[开发 Compose](../../../compose.dev.yml) 编排 API、Web、Admin、文档、Plugin UI 隔离网关、PostgreSQL、Redis 与 NATS。
开发本地配置由模板生成到 deploy/docker/.env.dev.local；应用根 .env.example、生产 Docker 模板与开发模板
不是四份需要同步手改的同一配置。

Windows 入口为 scripts/docker-dev.ps1，Linux 入口为 scripts/docker-dev.sh。
up 使用现有开发镜像；依赖、Dockerfile、构建配置或容器入口脚本变化需 rebuild。
普通 Go/Vue 源码由容器内开发进程监听，改源码通常不必重建镜像；配置变化需重新运行 up 让 Compose 按配置重建容器。插件包源码、`deploy/docker/dev-plugin-ui.sh`、插件网关或 Dockerfile 变更则执行 `docker-dev.* rebuild`：它重新构建插件前端、打包为不可变发布目录，再由 API 装载校验后的版本。开发 API 的源码监听会主动跳过测试夹具中可能由其他 UID 创建的 `data/`、`.campusos/` 目录；若已经运行的是旧入口脚本，执行一次 `rebuild` 才会载入此修复。
单纯 docker restart 不会重新读取新的 Compose 环境变量。

数据库检查脚本提供 `PSQL_MODE=auto|host|docker`。在 Windows Git Bash/WSL 的 Docker 开发环境中，若宿主也
安装了 `psql`，应使用 `PSQL_MODE=docker POSTGRES_CONTAINER=campusos-dev-postgres-1`，使检查明确在
Compose PostgreSQL 容器内运行，避免误连宿主 socket 或另一数据库。

端口绑定 0.0.0.0 只是局域网可达的必要条件之一，还需宿主防火墙、路由和服务监听允许。
API/数据服务默认回环约束与 UI 暴露分开，不能为方便预览顺便公开数据库端口。

## 健康、日志与验证

GET /api/v1/health 返回静态服务状态和版本，不检查各依赖；Docker healthcheck 的间隔不等于浏览器轮询间隔。
容器退出先查日志中的首次实际错误，不能把健康检查访问日志当失败原因。
容器日志与平台日志的采集链需要分别核实，文件权限错误也不等于数据库迁移失败。

按变更范围运行：

```bash
python scripts/check-doc-links.py
python migrations/tools/generate_er.py --check
make architecture-check
make data-governance-check
make database-check
```

数据库演练使用隔离环境；本次纯文档整理不执行迁移、重置或容器重启。
发布还需目标 Linux、浏览器、备份恢复与容量证据，文档更新不替代实际验收。
