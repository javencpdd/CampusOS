# 插件平台与授权体系

> 更新时间：2026-09-21 18:16（Asia/Shanghai）
> 实现基线：v1.1-dev；本文以当前代码为准，不把计划中的能力写成已交付功能。
> 返回：[当前架构概览](../当前架构概览.md)

## 1. 当前结论

CampusOS 正在从旧 External Plugin 目录迁移到 `campusos.plugin/v4` 自包含包模型。当前已经可以把
`campusos.pdf-viewer` 的用户端 PDF.js 页面、Worker、Manifest、配置 schema、测试与管理员页面产物放在根目录
[`plugins/campusos.pdf-viewer/`](../../../plugins/campusos.pdf-viewer/)；用户端由通用宿主以跨 Origin sandbox iframe
加载，不再从 `web/src/modules` 静态导入 PDF 页面。

这不等于 v1.1 插件重构已经完成。当前可实际使用的是 **UI-only (`runtime: none`) PDF v4 发布包 + 现有平台三层授权
记录 + 宿主受控资源 Bridge**。独立 Runner/Wasm 限制、管理员动态 Host、用户安装状态机、升级回退、第二示例和完整
浏览器/恢复验收仍是未完成项，详细状态以
[v1.1 插件自包含与动态加载重构计划书](../../项目计划书v1/项目计划v1.1/02-v1.1插件自包含与动态加载重构计划书.md)
和最新进度记录为准。

## 2. 目录、发布与数据边界

| 位置 | 所有者与用途 | 运行时边界 |
| --- | --- | --- |
| `plugins/<key>/` | Git 管理的 v4 源码包：`plugin.yaml`、`config/`、`frontend/`、可选 `backend/`、`storage/`、测试 | 源码不是生产执行入口；Docker 开发模式会显式打包它 |
| `plugins/.staging/` | 平台打包/校验时的私有暂存目录 | 不发现、不服务、不执行 |
| `plugins/.installed/<key>/<version>-<digest>/` | checksum 校验且原子安装后的不可变 release | v4 Runtime 与 3003 静态网关只从这里发现/服务产物 |
| `data/plugins/`、`data/plugin_data/` | 旧插件运行时目录、私有 SQLite/KV 与历史快照 | 不再作为 v4 源码或自动发现入口；仍按旧运行时边界备份 |
| `data/personal-space/<user>/plugins/<key>/config/` | 已安装 v4 插件的用户 JSON 配置、元数据和快照 | 只能在平台确认用户安装关系后创建；不能保存附件、对象字节、Token 或可执行文件 |

`internal/plugin/v4` 会拒绝目录逃逸、软链接、未声明 artifact、未知 Capability、错误 schema 和篡改摘要。
`campusosctl plugin v4 validate|stage|pack|sign|install` 可用于开发/CI；安装不会执行 `postinstall`、shell、npm 或插件包
内的任意脚本。已安装 release 的相同摘要可幂等重装；同一 key/version 不能悄悄换成不同字节。

插件禁止创建平台 PostgreSQL 表、提交 migration、取得平台数据库连接或把业务附件藏进 JSON/SQLite。可用的持久化范围仅为：
平台已开放的 `plugin_records`、Secret/Config 服务，自身 SQLite，及其受限文件配置。`000002_v1_1_ui_only_plugin_runtime`
只允许 `plugins.runtime = 'none'`，不创建 PDF 专用表，也不是权限绕过。

### 管理端页面的唯一边界

“外部插件运行管理”和“用户目录与授权”并不是两套插件或两份安装数据；后者是以前者的**当前运行时快照**同步出的目录投影。
它们分别解决不同的管理问题：

| 页面 | 路由 | 唯一职责 | 不负责的事 |
| --- | --- | --- | --- |
| 外部插件运行管理 | `/plugins` | 管理已发现的外部发布包、运行状态、管理员 Capability Grant、系统配置与运行日志 | 不发布给用户、不处理用户请求，也不显示一套独立安装记录 |
| 用户目录与授权 | `/plugin-center` | 决定当前外部插件是否在用户端可见，处理用户请求，显示聚合的用户/记录/文件用量和目录审计 | 不导入、启停、卸载插件，也不替代管理员 Grant |
| 用户端插件中心 | `/plugins`（Web） | 让用户查看已发布目录、阅读用途说明，并在需要时给出个人 Consent/管理自己的受管数据 | 不授予管理员能力，不访问其他用户个人空间 |
| 扩展总览 | `/extensions` | 只读汇总外部插件、内置功能、资源包和集成 | 不执行任一类别的生命周期操作 |

`plugin_catalog_entries` 是可再生的目录投影，不是历史安装账本。启动时 `MarketService.SyncCatalog` 会删除当前
Plugin Manager 未发现的旧条目，因而旧 `builtin.pdf-viewer` 不会和当前 `campusos.pdf-viewer` 同时出现。
当前 PDF Viewer 的唯一有效条目是外部、自包含的 `campusos.pdf-viewer`；其 `runtime: none` 表示纯隔离 UI release，
不是内置功能或可绕过授权的“无运行时”代码。

## 3. 运行时与动态界面

当前 `internal/plugin.Manager` 仍兼容旧 `builtin`、`grpc`、`process`、`wasm` 运行时。v4 另有一个 `none` Runtime：它不启动
子进程、不接收 Extension 请求，也不能直接访问文件或数据库；它只代表一个已经过包校验的隔离 UI release。

Docker 开发环境把已安装 release 交给 `plugin-ui` 服务（默认 `127.0.0.1:3003`）。该网关拒绝源码、`node_modules`、
`.staging`、配置目录、目录遍历和 Service Worker 请求，并以 CSP/`nosniff`/`no-referrer` 仅服务静态产物。API 的
`GET /api/v1/ui/runtime-manifest` 在 v4 release 可用时输出 `campusos.ui/v3`、精确的 `frame.src` 与 `frame.origin`；
宿主再以通用 `PluginSurfaceHost` / `PluginSurfacePage` 注册页面、弹窗、抽屉、全屏或新标签壳页。

实际加载链为：

```text
用户点击预览
  → 宿主确认当前资源的业务读取权与插件 Capability Consent
  → 创建/复用短期 invocation
  → runtime-manifest 指向已安装 release 的跨 Origin iframe
  → challenge + MessageChannel 建立 Bridge
  → iframe 仅请求 resource.describe / resource.readRange
  → 宿主携带自己的登录态调用 API；API 每次读取重新检查 invocation、插件版本、授权和资源 ACL
```

iframe 不得到 JWT、Cookie、API 基址、用户存储路径、数据库连接或下载直链。Host 只接受当前 iframe 的 `source` 与精确
`origin`，验证随机 challenge、MessagePort、资源句柄、Range 大小和 PDF MIME；任何未声明 Bridge 方法都会被拒绝。
因此 Worker/浏览器缓存可以缓存 JS 产物，却不能持久化受保护的 PDF 字节。

开发环境使用 `CAMPUSOS_PLUGIN_V4_DIR=/workspace/plugins`、
`CAMPUSOS_PLUGIN_V4_DEV_SOURCE=true` 和 `CAMPUSOS_PLUGIN_UI_ORIGIN=http://{host}:3003`。前者的源码打包便利仅限
Docker development；生产必须关闭它并只装载签名/摘要已验证的 release。局域网用户需要预览时，才将
`CAMPUSOS_DEV_PLUGIN_UI_BIND=0.0.0.0` 与 Web 放在同一可信网络范围，开放 TCP 3003；API、PostgreSQL、Redis 和 NATS
仍不可对 LAN 公开。生产应改为独立 HTTPS Origin 与精确 `frame-ancestors`，不能使用开发默认 `*`。

## 4. 三层授权与资源权限

Manifest 只能**申请**能力；不会给插件、管理员或用户自动授权。

1. 平台 Capability Catalog 审核 Manifest 的代码与 `self` 作用域。
2. 管理员在插件版本级别授予或拒绝所申请的 Capability。
3. 用户在明确操作时同意需要个人许可的 Capability；浏览器不生成密钥或长期 token。
4. 每个资源调用还必须通过业务 ACL：图文文章附件先检查当前读者是否有该文章阅读权；个人空间和 Personal Documents
   只允许 owner。调用方知道文件 ID 并不构成读取/下载/预览权。

PDF 插件当前申请 `article_attachment.self.preview`、`personal_space_file.self.read` 与
`plugin_ui.surface.open`，阅读进度才会额外申请 `plugin_record.self.read/write`。用户同意由宿主 UI 写入，不能由插件
自行伪造；管理员 Grant、用户 Consent、插件禁用、版本变化、文章下架或 invocation 过期后，下一次 `describe` 或
`readRange` 都会被平台拒绝。

插件授权记录的 PostgreSQL `BIGINT` ID 会以十进制字符串在 HTTP/JSON 中传递。前端不得将其转为 JavaScript `number`，
否则大于安全整数范围的版本 ID 会被悄悄改写，表现为“未声明能力”的假错误。

## 5. 配置、Secret 与生命周期现状

v4 已实现用户配置文件的受限 JSON Schema/defaults、CAS 写入、元数据摘要、快照与 pending 恢复工具；配置预算独立于
用户附件配额，Secret 只可由平台加密 Secret 服务保存，界面不会回显明文。当前仍缺少将这些文件自动接到“用户添加/禁用/
移除插件”平台状态机的实现，所以不能手动先建目录来假装用户已安装插件。

管理员页面 artifact 已随 PDF 包构建，但**通用 Admin 隔离 Host、配置 Bridge 与 schema 表单尚未交付**；当前不能把它
描述为可用的管理员插件配置台。用户端资源预览使用通用 Host；旧 `trusted-module` PDF 页面和旧 Go builtin 注册已移除。

计划中的升级、回退、全局卸载、个人退出、后台对账、Wasm/容器 Runner、跨插件隔离、第二示例和故障恢复没有因为出现
`plugins/` 目录就自动完成。它们需要独立的状态机、数据库/文件一致性和真实浏览器/目标环境证据。

## 7. 验证重点与未完成项

最低回归应覆盖篡改包、目录逃逸、错误 origin/source/challenge、旧 iframe 端口、超大或越界 Range、文章下架、跨用户
invocation、管理员撤权和用户撤回 Consent。运行 Docker 后检查 `/api/v1/health`、`/api/v1/ui/runtime-manifest` 和
`http://127.0.0.1:3003/health`，再以已登录用户覆盖文章附件、个人资产和个人文档三个入口。

完整验收还需要 Admin 动态界面、用户安装生命周期、独立 Runner、升级/回退、第二插件、Linux/LAN 浏览器与备份恢复
证据；这些缺口阻止将 v1.1 插件重构宣布为 Final。
