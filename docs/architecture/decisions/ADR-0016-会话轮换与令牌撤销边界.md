# ADR-0016：会话轮换与令牌撤销边界

> 状态：已接受并在 v0.12 A6 实施  
> 日期：2026-07-17  
> 关联：[v0.12 计划书](../../项目计划v0.12/00-v0.12版本计划书.md)、[会话 API 合同](../../api/v0.12会话与Token安全流程.md)

## 背景

历史 JWT Refresh Token 无法被按设备撤销、无法可靠识别重放，也会让长期凭据被误写入浏览器
存储或日志。仅校验 JWT 签名不能满足密码重置、注销全部、设备管理和账号风险处置的即时失效需求。

## 决策

1. Access Token 是短期 JWT，必须含 `typ=access`、`session_id` 和 `auth_version`。
2. Refresh Token 为 256 位随机不透明值，只在浏览器 HttpOnly Cookie 中保存；数据库只存 SHA-256
   摘要，且 `sessions.refresh_token` 始终为 `NULL`。
3. 每次刷新都锁定旧 Session、创建新摘要、标记旧行 `rotated`。对已轮换 Token 的重放提交整个
   `token_family_id` 撤销，而不是只拒绝单次请求。
4. 每个受保护请求检查 Session、用户状态和 `auth_version`。`logout-all`、密码重置和邮箱绑定
   增加 auth version 并撤销 Session。
5. Cookie 使用 SameSite Lax；Refresh 和全部写型 Session 操作采用双提交 CSRF。跨域凭据仅允许
   明确的本地开发 Origin，生产不以宽松 CORS 作为认证边界。

## 后果

- v0.11 JWT 不能兼容为 v0.12 登录态，升级时强制重新登录。
- Session 列表只返回 `SessionView`，不会返回摘要、原始 Token、IP 明文或 User-Agent 全量敏感值。
- `AUTH_REFRESH_BODY_COMPAT` 只保留受遥测控制的短期兼容，默认关闭；新前端必须使用 Cookie。
- 迁移时撤销历史 Session 并清除原始 Refresh 值。生产回退使用 forward-fix，不恢复长期凭据。

## 被拒绝的方案

- **继续签发 Refresh JWT**：无法可靠轮换、逐设备撤销或识别重放。
- **把 Refresh Token 放入 localStorage**：XSS 后可直接窃取长期凭据。
- **仅在 logout-all 删除 Session**：旧 Access JWT 在过期前仍可能被接受，不能满足安全恢复。
- **只靠 SameSite 不校验 CSRF**：不能覆盖所有同站和错误配置场景，且写操作缺乏明确验证。
