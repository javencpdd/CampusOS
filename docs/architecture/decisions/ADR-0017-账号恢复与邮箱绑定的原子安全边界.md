# ADR-0017：账号恢复与邮箱绑定的原子安全边界

> 状态：已接受并在 v0.12 A7 实施  
> 日期：2026-07-17  
> 关联：[v0.12 计划书](../../项目计划v0.12/00-v0.12版本计划书.md)、[账号恢复 API](../../api/v12账号恢复与邮箱绑定流程.md)

## 背景

密码重置、邮箱更换和历史账号恢复都会改变账号所有权与长期凭据。若只更新密码或邮箱，旧 Access
Token、Refresh Token 和已登录设备仍可使用，且失败路径可能留下已消费 Ticket 或半完成账号状态。

## 决策

1. Password reset 只面向 `verified` 且 active 的邮箱账号，公共请求使用不可枚举的统一受理响应。
2. Email binding 只允许当前已认证用户发起；新邮箱必须经独立 Challenge 证明拥有权。
3. 历史或未验证账号的忘记密码场景通过管理员 Case 处理。管理员只保存非敏感线下核验引用，不获得
   密码、Code、Ticket 或证明原文，更不能直接设置用户密码。
4. 每个完成命令在同一 Reliability/TxKernel 事务内消费 Ticket、更新凭据或邮箱、增加
   `auth_version`、撤销全部 Session、写 required audit 和最小 Outbox 事件。
5. 系统管理账号排除在公网恢复外，只允许可信本机交互式 CLI 重置；CLI 不提供 password flag 或管道
   输入。

## 后果

- 密码重置和邮箱绑定后旧设备必须重新登录；用户体验有明确安全原因，不能以兼容为由跳过撤销。
- `identity_account_recovery_cases` 作为流程事实表，和 User、Account、Challenge 之间由外键和唯一
  Challenge 约束保护；它不是凭据保管表。
- 管理端能处理业务恢复和会话处置，但只能看到脱敏投影。邮件投递状态同样只暴露 Provider 健康和
  脱敏错误。
- 失败时事务整体回滚，生产恢复采用 forward-fix，避免用删除安全证据来“修复”不完整状态。

## 被拒绝的方案

- **管理员直接填写新密码**：无法证明用户本人控制了新邮箱，且扩大内部人员对凭据的接触面。
- **把历史邮箱直接标为 verified**：将兼容登录误描述为邮箱所有权证明，破坏找回安全边界。
- **仅撤销 Refresh Token**：已签发 Access Token 在过期前仍可用，不能满足立即失效要求。
- **把 Code/Ticket/证明原文放到 Case、日志或 Outbox**：会把临时凭据和线下材料扩散到不必要的存储。
