# ADR-0021：校园互助使用独立结构化 Detail 与业务状态机

> 状态：已接受并在 v0.12 C2 实施  
> 日期：2026-07-17  
> 关联：[v12 校园互助设计](../../项目计划v12/06-校园互助子模块设计.md)

## 背景

校园求助、物资提供和志愿协助需要表达进度、粗粒度地点和截止时间。这些字段不属于所有 Thread，也不能用
正文解析或自由 JSON 代替。若把它们加到 `threads`，Community Core 会开始拥有互助业务状态；若让普通
External Plugin 写 Detail，则会绕过 Community 的类型策略、事务、审计和治理边界。

## 决策

1. 新增 Built-in Feature `feature.mutual-aid`，其业务数据只存放在一对一的
   `mutual_aid_details` 中。
2. 互助创建通过 Community `CreateStructuredThread`，固定创建 `thread_type=mutual_aid`，并在同一
   可靠事务内写 Thread、Revision、Detail、required command audit 和 Outbox。
3. Detail 的业务状态为 `open`、`in_progress`、`resolved`、`closed`，只能按显式状态机转换；它与
   Community 的发布、审核、回收和置顶状态完全分离。
4. Detail 的数据库触发器强制 Detail 指向 `mutual_aid` Thread，且 `created_by` 等于 Thread 作者；
   服务层同时做作者、Feature Gate、board policy 和乐观版本检查。
5. Feature 停用只拒绝其 Feature API 和停止其入口，不删除 Detail；Community 继续拥有并治理基础帖子。
6. 不引入支付、订单、担保、聊天、仲裁，且不将完整地址、身份证、银行卡等敏感信息建模为 Detail 字段。

## 后果

- 互助列表和详情可以稳定查询类型化字段，不需要解析正文。
- 互助状态的变更不会意外恢复被下架的内容，也不会改写社区审核事实。
- 详情写失败会整体回滚，不产生无法解释的半成品帖子或可靠任务证据。
- 新类型需要通过 Board Policy 显式开放；Feature 启用并不自动让所有板块接收互助内容。

## 被拒绝的方案

- **把进度字段放到 `threads`**：会污染 Community Core 的通用模型。
- **在通用帖子上附加任意 JSON**：没有固定约束、状态机、索引或安全审计边界。
- **将互助作为可卸载 External Plugin**：它需要事务内 Detail 写入，External Plugin 不应得到宿主数据库或
  Participant 能力。
- **复用帖子下架状态表示“已解决”**：业务完成和内容治理属于不同事实，不能互相覆盖。
