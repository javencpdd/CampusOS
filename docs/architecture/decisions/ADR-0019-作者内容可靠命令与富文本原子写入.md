# ADR-0019：作者内容可靠命令与富文本原子写入

> 状态：已接受并在 v0.12 C0 实施  
> 日期：2026-07-17  
> 关联：[v0.12 计划书](../../项目计划v0.12/00-v0.12版本计划书.md)、[结构化帖子事务内核](../../项目计划v0.12/05-结构化帖子事务内核设计.md)

## 背景

普通 Thread 的基础事实与 Revision 曾独立写入；RichText 又在 Thread 创建成功后单独写入 Article Detail。
Detail 写入失败时旧实现将 Thread 补偿性移入回收站。该方法无法保证 Revision、审计、Outbox 和用户可见
状态一致，也使失败请求看起来像一次真实删除。

## 决策

1. 作者创建、编辑、回收普通 Thread 统一通过 `ThreadService.executeAuthorCommand` 进入
   Reliability/TxKernel。
2. RichText 自己持有外层可靠命令，并通过 Community 的 `ContentGateway` 写基础 Thread；内层 Community
   服务检测 active transaction 后不创建嵌套 Audit/Outbox。
3. RichText PostgreSQL Store 必须使用 `transaction.ExecutorFor`，使 Article Detail 与 Thread/Revision
   使用同一个提交边界。
4. 成功后才做缓存删除和兼容 EventBus 投递；事件真相由 Outbox 表保存。
5. 删除 RichText 创建失败后的 `TrashThread` 补偿路径。失败应回滚，而不是产生一个已回收主题。
6. Memory Profile 必须对 RichText Store 注册 Snapshot/Restore，并以故障注入测试证明回滚。

## 后果

- 一次成功的作者内容动作产生一组一致的业务事实、command audit 和 Outbox 记录。
- Detail、Revision 或证据写入失败不会残留半写 Thread、Article 或事件。
- RichText 仍只依赖 Community Public Gateway，不直接访问 Community Repository。
- C1 可以在此基础上增加编译内 Participant 合同；本 ADR 不开放给 External Plugin、MCP 或 Agent。

## 被拒绝的方案

- **补偿式回收 Thread**：补偿本身也可能失败，且会把失败写入伪装成用户删除。
- **RichText 直接导入 Community Repository**：破坏模块所有权，并让未来类型 Feature 难以审计。
- **在 RichText 内部另建事务管理器**：会破坏 Thread 与 Detail 的单一提交边界。
- **将事务能力开放给外部插件**：无法限制数据库、网络、文件和长时间运行副作用，超出 v0.12 安全模型。
