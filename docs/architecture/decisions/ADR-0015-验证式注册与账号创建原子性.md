# ADR-0015：验证式注册与账号创建原子性

> 状态：已接受并在 v0.12 A5 实施  
> 日期：2026-07-17  
> 关联：[v0.12 计划书](../../项目计划v0.12/00-v0.12版本计划书.md)、[A5 进度](../../进度/v0.12-dev/v0.12.6-dev.md)

## 背景

在 v0.12 A2 之前，`POST /auth/register` 可以先创建状态为 `unverified` 的账号，登录路径又没有
强制读取验证状态。即使 A3/A4 已有安全的 Challenge、Ticket 和邮件投递，这个旧入口仍会绕过
邮箱所有权证明。

## 决策

1. 注册公开流程固定为 Challenge 请求、Code 校验和 Ticket 注册三步，Purpose 固定为
   `registration`。
2. `POST /auth/register` 保留路径以避免无说明的路由破坏，但现在必须携带 `challenge_id` 和
   `ticket`。缺少任一字段返回 `identity.verification_required`，不创建任何用户记录。
3. 最后一步调用 Challenge 的最小 `ConsumeTicketForCommand` 协作接口。Identity 用户服务在同一
   Reliability/TxKernel 命令中消费 Ticket、创建用户、创建 `verification_state=verified` 的 Account、
   写 required command audit 和公开用户投影 Outbox 事件。
4. 任何一项写入失败都会回滚 Ticket 和用户/Account。测试覆盖 Account 写失败后 Ticket 未消费、
   用户未残留的场景。
5. 客户端只能在内存中暂存 Challenge ID、Code 和 Ticket。CampusOS External Plugin SDK 不提供
   Identity 内部注册、Ticket 或 Challenge Store 能力。

## 后果

- 新账号的登录状态与邮箱拥有权一致；历史 `legacy_accepted` 和 `system_managed` 账号仍按 A2
  的兼容规则可登录。
- 老客户端会收到明确、机器可读的 400 错误，需要升级为三步流程；不提供绕过开关。
- User 创建事件改用 `PublicUser` 投影，避免把邮箱写入普通 Outbox 负载。
- Ticket 被验证后仍只会在最终注册成功时消费；因为临时网络/数据库失败而重试注册不会丢失
  Ticket，直到成功、过期或明确失效。

## 被拒绝的方案

- **继续创建 unverified 用户再异步激活**：会保留半注册数据，也让错误处理和账号唯一性混乱。
- **把 Ticket 放进 JWT**：不能以数据库行锁保证单次消费，也容易误被客户端当作登录凭据。
- **Handler 先消费 Ticket 再调用用户服务**：跨越了同一可靠命令，后续用户/Account 写失败会
  错误消耗 Ticket。
- **向 External Plugin SDK 暴露 Challenge Repository**：会突破 Core Identity 的验证码、密钥和
  账号边界。

## 验证与回退

`make identity-registration-check` 覆盖旧请求拒绝、三步 HTTP 流程、verified Account、Ticket
重放拒绝和 Account 失败回滚。回退旧二进制前必须停用公开注册或进行受控维护；不能重新开放
未验证的一步式创建。生产故障使用 forward-fix，保留 Challenge、Ticket 摘要和命令审计。
