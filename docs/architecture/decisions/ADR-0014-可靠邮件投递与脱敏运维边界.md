# ADR-0014：可靠邮件投递与脱敏运维边界

> 状态：已接受并在 v0.12 A4 实施  
> 日期：2026-07-17  
> 关联：[v0.12 计划书](../../项目计划书v0/项目计划v0.12/00-v0.12版本计划书.md)、[A4 进度](../../进度/v0.12-dev/v0.12.5-dev.md)

## 背景

Challenge 已在 A3 将请求、限流、审计和只含 `challenge_id` 的 Outbox 事件原子提交。若把
SMTP 直接放进 Identity Service，身份模块会持有网络 Provider 和 Secret；若将邮箱、验证码或
正文放进 Outbox，可靠队列、管理端和备份将成为凭据存储。

## 决策

1. 新增 `core.email-delivery`，它是 `always-on` Core Module，依赖 `core.identity` 与
   `core.reliability`，不属于 Feature Registry 或 External Plugin 生命周期。
2. Consumer 只订阅 `identity.email.challenge.requested.v1`，并只接受严格形状的
   `{"challenge_id":"..."}` payload。多余字段也会拒绝，避免未来把 Code 等敏感字段悄悄写入
   Outbox。
3. Consumer 通过 `identity.challenge-dispatch-reader` 取得短生命周期的地址、Code、用途和
   过期时间；它不导入 Identity Repository，也不接触 HMAC key、Ticket digest 或数据库连接。
4. 已过期、失效、消费或不存在的 Challenge 映射为不区分细节的
   `identityport.ErrChallengeNotDeliverable`，Consumer 安全确认 receipt，不调用 SMTP。
5. SMTP Sender 仅从环境或 Secret 注入；管理 API 只返回 Provider、健康、通用错误、计数和
   时间。SMTP host、用户名、收件人、Code、Ticket、正文和 Provider 原始错误不能进入 API、
   Outbox attempt、日志或审计。
6. `EMAIL_PROVIDER=fake` 只允许 `development`、`test`；生产或 staging 启动时拒绝。Fake
   只在进程内去重计数，不提供打印或 HTTP 邮箱，避免开发默认值泄露验证码。
7. 投递语义为 at-least-once。Consumer receipt、进程内 idempotency key 和 SMTP
   `X-CampusOS-Delivery-ID` 尽量减少重复；发送成功后进程崩溃仍可能造成重复，产品和文档不得
   声称 exactly-once。

## 后果

- SMTP 故障不会回滚已经接受的 Challenge；Worker 保存重试，邮件模块变为 `degraded`，API 也
  不会称邮件已经送达。
- 真实 SMTP Provider 可以替换，但只能实现 `Sender`，不能获得 Core AppContext、Identity
  Repository 或 Reliability Store。
- 本地 Fake Provider 只能验证流程连接；需要看到真实测试邮件时应部署隔离 SMTP 测试服务并改
  用 `smtp` 配置，而不是向日志开放验证码。

## 被拒绝的方案

- **Handler 直接发送邮件**：网络失败会混入请求事务，重启后没有可靠重试。
- **Outbox 保存完整邮件**：队列、备份和运维界面将保存可用验证码和用户邮箱。
- **把邮件模块做成可卸载插件**：注册、绑定和找回的安全基础会随插件状态消失。
- **Fake Provider 打印 Code**：开发日志、终端回放和平台日志会成为凭据泄露面。

## 验证与回退

`make email-delivery-check` 覆盖严格 payload、短生命周期 Dispatch、过期 replay、安全状态、
Provider 错误脱敏、Consumer receipt 和 Fake 环境限制。生产故障以停止新的 Challenge 请求、
修复 SMTP 后重试 Outbox 为主；不删除 Challenge、事件或 receipt，也不通过日志检索验证码。
