# ADR-0011：可靠命令与持久事件边界

> 状态：已接受并在 v0.11.0 实施  
> 日期：2026-07-16  
> 关联：[`v11 计划书`](../../项目计划v11/00-v11版本计划书.md)、[`v11 可靠命令、事件与数据所有权`](../v11可靠命令事件与数据所有权.md)

## 背景

v0.10 已有稳定 Permission Code、路由 Operation 和授权审计，但高风险业务写入、
审计记录与异步事件并不总是在同一提交单元中完成。进程在业务写入后退出，或者审计
和事件写入失败时，可能留下无法可靠恢复的半成品。Webhook 还曾依赖进程内回调和
重试，不能跨重启接管任务。

CampusOS 仍是模块化单体。本 ADR 解决单体内可靠提交和异步执行问题，不以此拆分
微服务、引入分布式事务或让外部插件取得数据库访问权。

## 决策

### 1. 纯数据库高风险动作使用 TxKernel

新增 `internal/platform/transaction`。业务服务通过
`transaction.Manager.Within(ctx, action)` 建立事务上下文；PostgreSQL Repository 通过
`transaction.ExecutorFor` 取得当前 executor，Memory Profile 通过可快照 Repository
模拟同样的失败回滚语义。

Service 不直接调用 `pool.Begin`，也不接收 `pgx.Tx`。事务内只允许数据库事实、
required audit 和 Outbox 行；HTTP、NATS、文件替换、进程启动和其他网络副作用一律
在提交后执行。

### 2. 可靠性能力是 Core Module

`core.reliability` 是始终启用的 Core Module，拥有：

- `platform_outbox`、消费回执、投递尝试、Worker lease；
- 可靠命令审计和可恢复操作记录；
- 兼容路径遥测和仅预演的保留运行记录；
- Worker 的 lease、fencing、退避、dead-letter、重放和优雅停止。

External Plugin、Agent Runner、MCP 和浏览器端永远不能取得 Reliability Service、
TxKernel 或这些表的直接访问权。

### 3. 命令审计与事件同事务提交

`reliability.Service.Execute` 在同一个事务中按以下顺序执行：

```text
业务 action -> Event/EventFactory -> platform_outbox -> platform_command_audits -> COMMIT
```

其中任一步失败都会回滚。授权拒绝不产生业务写入；若拒绝发生在一个随后回滚的
事务内部，服务在回滚后使用原始请求上下文记录独立的 deny/error authorization audit，
确保“拒绝仍然拒绝”且证据不会跟着失败事务消失。

### 4. 事件采用至少一次消费

Worker 使用 `FOR UPDATE SKIP LOCKED`、有限 lease 和 generation 条件更新。一个事件
可有多个具名消费者，每个消费者拥有独立 receipt；消费者 A 成功而 B 失败时，重试
不会再次执行 A 的外部副作用。手动重放只允许 dead-letter 事件，必须带
`Idempotency-Key`、操作者和 required command audit。

这不是 exactly-once。HTTP/Webhook 接收方仍必须按 `event_id + endpoint_id` 幂等。

### 5. 文件与插件操作采用持久补偿记录

插件导入和 Appearance 资源应用不能被数据库事务覆盖。它们先写
`platform_operation_runs`，再使用 staging、checksum、原子 rename、版本快照和补偿；
启动时未终结操作被标为 failed 并保留人工恢复信息。不得假装这些操作与数据库提交
具有同一原子性。

## 后果

- Identity 注册、角色/权限/板块范围，以及 Community 治理动作可以在 required audit
  或 Outbox 失败时完整回滚。
- 旧 EventBus、旧 Webhook API、旧权限表和旧 Manifest 保持兼容；新 producer 渐进
  接入 Outbox，兼容路径会被记录。
- 新 migration `000027` 只追加表、列、索引、约束和 Permission Code；生产回滚优先
  forward-fix，down 只用于有备份的隔离演练。
- 可靠性页只展示最小关联字段，不返回 Outbox payload、Webhook Secret 或任意审计
  `details`。
- 可靠性列表使用服务端分页和实际总数，查询入口按操作者或客户端地址做有界的单进程
  限流；多实例共享限流仍属于后续容量治理。

## 被拒绝的方案

- **仅依赖 NATS 或 Memory EventBus**：它们不能让业务事实和事件记录同一事务提交。
- **在事务中直接投递 Webhook**：会长时间占用数据库锁，失败恢复也不可靠。
- **全局 Service Locator 或反射 DI**：会模糊模块依赖和安全边界。
- **让外部插件直接写 Outbox**：插件可以伪造平台事件、绕过授权和审计。

## 验证与回退

关键回归覆盖事务失败回滚、panic snapshot 恢复、lease fencing、消费者回执、dead-letter
幂等重放、注册/治理审计和插件替换恢复。命令见：

```bash
make reliability-check
make outbox-check
make failure-injection-check
./scripts/test-v11-reliability-migration.sh
GOCACHE=/tmp/campusos-go-cache go test ./... -count=1
```

迁移脚本只连接隔离测试数据库，并执行 `000027` 的 up/down/up。HTTP Handler 的合同
测试还会断言事件 payload、headers 和幂等键不会进入管理端响应。

若必须回退代码，先停止新的 producer，等待或冻结 lease，并保留 `000027` 数据和
dead-letter；不要把 `processing` 任务直接改成成功，也不要删除审计或 Outbox 历史。
