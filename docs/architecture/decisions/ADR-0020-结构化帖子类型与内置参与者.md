# ADR-0020：结构化帖子类型、板块策略与内置参与者

> 状态：已接受并在 v0.12 C1 实施  
> 日期：2026-07-17  
> 关联：[v12 计划书](../../项目计划v12/00-v12版本计划书.md)、[结构化帖子事务内核](../../项目计划v12/05-结构化帖子事务内核设计.md)

## 背景

`content_format` 描述正文的渲染方式，不能表达一条内容是否具有互助状态、交易价格或其他业务 Detail。
如果让通用 `/threads` 接收任意 JSON Detail，Community 会开始拥有各 Feature 的业务字段，外部插件也可能
试图参加宿主数据库事务，最终破坏表所有权与审计边界。

同时，版块需要能明确决定未来允许发布哪些内容，但关闭一个类型不能使已有内容消失或破坏其治理能力。

## 决策

1. `threads.thread_type` 固定为 `discussion`、`article`、`mutual_aid`、`secondhand`；它是业务类型，
   `content_format` 继续只描述渲染格式。
2. `category_thread_type_policies` 由 Community Core 所有。每个 board 初始仅启用
   `discussion/article`；管理员通过版本化、可靠命令显式调整允许类型。
3. 创建时 Community 同时检查：可发帖 board、固定类型、Built-in Feature 启用状态和 board 策略。
   策略仅限制新建，不重写或隐藏旧内容。
4. `CreateStructuredThread` 只接受编译进主程序的 Built-in Feature Participant。Participant 只能在已激活
   的 Community 事务内写入自己的一对一 Detail，不能获得 Repository、AppContext、网络、文件系统或
   External Plugin Runtime。
5. RichText 是首个 `article` participant。历史 RichText Thread 原地回填为 `article`，不改变 Thread ID、
   Article ID、URL、草稿或治理状态。
6. External Plugin、SDK、Host API、MCP 和 Agent Runner 不暴露 Participant 或事务参与接口；它们仍只能
   使用公开 API、Gateway 或受控 Host API。

## 后果

- Community 继续拥有 Thread、Revision、治理状态和板块策略，互助、二手等 Feature 将拥有各自的 Detail 表
  和状态机。
- Detail 写入失败时，基础 Thread、Revision、required command audit 和 Outbox 一起回滚。
- 管理员可以在功能部署前预先配置类型，但 Feature 停用时创建仍被服务端拒绝。
- 新结构化类型需要新增固定 schema、Feature、API、migration、策略检查和测试；不能通过普通插件动态注册。

## 被拒绝的方案

- **以 `content_format` 推断业务类型**：富文本与普通文本是渲染差异，不足以承载业务生命周期。
- **通用 Thread Detail JSON**：会让 Community 成为所有 Feature 的字段仓库，无法进行类型和状态机审计。
- **允许 External Plugin 参加事务**：插件可能执行网络、文件或长时间操作，也无法保证宿主数据安全。
- **关闭类型时删除或隐藏已有数据**：会伤害历史可读性和 Community 的治理职责。
