# CampusOS v1-v5 计划严格审查

> 审查日期：2026-07-10
> 审查基线：`v0.5.34-dev`
> 审查范围：历史计划书、`v0.1-dev` 至 `v0.5-dev` 进度记录、当前代码、数据库 migration、测试、API 与帮助文档
> 审查原则：历史计划保留原貌；只有同时具备实现、验证和文档的目标才认定为严格完成。

## 1. 严格完成标准

本次不以“存在代码文件”作为完成依据。每项历史目标按以下六个维度检查：

| 维度 | 严格完成要求 |
| --- | --- |
| 功能实现 | 主流程和关键失败流程均可运行，不以占位接口、静态页面或设计文档代替实现。 |
| 接口契约 | 路由、请求、响应、错误码、认证方式和兼容策略有权威说明。 |
| 权限安全 | 路由权限、资源归属、数据范围和敏感字段处理明确，并有越权负向测试。 |
| 数据完整性 | 表关系、唯一性、状态、删除策略、索引和迁移/回滚边界明确。 |
| 自动验证 | 有可重复的单元、集成、契约或端到端验证；历史性能指标必须有测试报告。 |
| 运维文档 | 启动、配置、迁移、故障处理和开发者使用方式能从文档入口找到。 |

状态定义：

| 状态 | 含义 |
| --- | --- |
| 严格完成 | 六个维度均达到计划承诺，且当前仍可验证。 |
| 基础闭环 | 主路径可用，但契约、权限、数据约束、自动化或生产保障仍有缺口。 |
| 部分完成 | 只有部分模型、接口、页面或试验实现，不能作为完整能力交付。 |
| 未完成/后置 | 当前没有可用闭环，或已经明确移出本阶段。 |

## 2. 总体结论

v1-v5 已形成可运行的社区、双前端、插件运行时、个人空间、内容、课表和集成基础，但没有一个历史大版本的全部原始目标达到“严格完成”。主要原因不是核心功能缺失，而是早期计划同时包含了生产级 API、权限、数据库、SDK、运维和性能目标，后续实现以功能迭代为主，没有同步建立统一验收门槛。

| 版本 | 主线完成度 | 严格结论 | 需延续到 v6 的重点 |
| --- | --- | --- | --- |
| v1 | 社区、认证、数据库迁移、gRPC 插件基础已落地 | 基础闭环 | 当前全量 API 契约、数据关系约束、通知/搜索等未完成项重新定级 |
| v2 | 双前端、RBAC、管理和插件仓储已落地 | 基础闭环 | 细粒度权限、审核状态机、真实外部适配器仍不完整 |
| v3 | Built-in/gRPC/Wasm、Host API、Go SDK 和 CLI 基础已落地 | 基础闭环 | SDK/CLI 工程化、插件测试工具、资源隔离和兼容策略不足 |
| v4 | AI Gateway、个人空间/主页、风格包、Webhook 已落地 | 基础闭环 | 标准 MCP、真实 IM、AI 审核和生产交付未完成 |
| v5 | 内容治理、课表、生命周期、日志和数据架构视图已落地 | 基础闭环 | API/权限矩阵、数据库硬约束、插件开发者生态和恢复演练未严格验收 |

## 3. v1 审查

| v1 目标 | 结论 | 依据与缺口 |
| --- | --- | --- |
| 注册、登录、JWT、用户和社区对象 | 基础闭环 | `internal/core/identity`、`internal/community` 与双前端均有实现；尚缺统一接口契约和全量越权测试。 |
| PostgreSQL migration、Docker 开发依赖、NATS 事件 | 基础闭环 | migration 已到 `000013`，Compose 管理 PostgreSQL/Redis/NATS；应用完整交付和恢复演练未完成。 |
| RBAC、管理员用户/版块/帖子管理 | 基础闭环 | 角色与权限表、后台管理路径存在；部分接口仍依赖粗粒度 `role:manage` 或服务层隐式检查。 |
| gRPC 插件、Manifest、Host API、事件分发 | 基础闭环 | 后续已扩展到 Built-in/Wasm 和 Host API 权限；公开契约、版本协商和兼容矩阵不足。 |
| OpenAPI 覆盖全部 API | 部分完成 | `docs/api/openapi-v0.3-pre.yaml` 只是历史草案，不能代表当前全部 HTTP 路由。 |
| MinIO/统一对象存储 | 未完成/后置 | 当前使用本地个人空间和插件数据目录；对象存储需要先建立存储抽象与迁移策略。 |
| 通知、任务队列、邮件 | 未完成/后置 | 事件总线、Host API 日志或数据库记录不能替代面向用户的通知闭环。 |
| 点赞、全文搜索、完整帖子状态机 | 部分完成 | 存在部分表或治理能力，但缺少 API、UI、权限和测试组成的完整闭环。 |
| 核心覆盖率不低于 70%、结构化日志和性能指标 | 未完成/后置 | 当前有模块测试和平台日志，但无持续覆盖率门槛，也没有原计划性能指标的可复验报告。 |

## 7. v5 审查

v5 的实际工作量已经超过第一版 `v0.5.0` 至 `v0.5.7` 的拆分，进展延续到 `v0.5.34-dev`。功能范围详见 [v5 第二版计划书](../项目计划v5/01-v5版本计划书第二版.md)。

| v5 目标 | 结论 | 依据与缺口 |
| --- | --- | --- |
| 管理后台集成中心、平台日志和基础指标 | 基础闭环 | 管理端有固定来源的日志和集成入口；集中日志、告警、trace 与数据脱敏策略未完整。 |
| 个人主页/风格包运营化 | 基础闭环 | 快照、回滚、恢复默认、安全筛查和标准目录已落地；任意脚本继续禁止。 |
| 富文本与普通文本治理 | 基础闭环 | 草稿、预览、发布、上下架、编辑、删除、私密和离开提醒已实现；仍需统一接口契约与对象级权限测试。 |
| 个人空间与课表 | 基础闭环 | 分类存储、配额、头像、按学期 JSON 和日历浏览已实现；云盘只作为后续存储适配方向。 |
| 插件包治理与系统/用户级生命周期 | 基础闭环 | 包预检、导入、scope、重启生效和热加载已实现；兼容策略、SDK 工具链和版本回滚仍不足。 |
| Webhook、MCP-like、Message local adapter | 基础闭环 | 有基础操作路径，但外部标准协议和真实平台接入尚未完成。 |
| 数据架构可视化和同步 Skill | 基础闭环 | 管理端展示 30 张 schema 表并可检查 migration 漂移；视图是仓库快照，不是实时数据库浏览器。 |
| 备份恢复、Docker 运行说明 | 已完成文档，未完成演练 | 有步骤说明，但没有可重复、留痕并验证数据完整性的恢复演练。 |
| 完整 v0.5 API、权限和端到端回归门槛 | 部分完成 | 单元测试、构建和 smoke 存在；全量 OpenAPI、路由权限矩阵、敏感接口负向测试和浏览器 E2E 门槛未建立。 |
| 数据库关系和约束 | 部分完成 | 当前 30 张 schema 表主要通过服务层维护逻辑关系，migration 没有显式外键；ID 类型、标签表示、状态和删除策略仍需统一审查。 |

## 8. 跨版本遗漏清单

以下不是把全部历史愿望重新塞入 v6，而是按风险和依赖重新定级。

### 8.1 v6 P0：必须收口

| 遗漏 | 当前证据 | v6 收口方式 |
| --- | --- | --- |
| 当前全量 HTTP API 契约缺失 | OpenAPI 仍是 `v0.3-pre` 历史草案 | 建立路由清单、OpenAPI、统一错误模型、兼容政策和契约测试 |
| 权限规则分散 | JWT、`RequirePermission`、`role:manage` 和服务层 ownership 检查并存 | 建立主体、权限、资源归属、数据范围和审计矩阵，补齐 401/403/跨用户负向测试 |
| 数据库关系约束偏弱 | 业务表没有显式 foreign key，ID 和状态字段策略不统一 | 先做数据质量预检和兼容迁移，再分批补类型、索引、唯一性、检查约束和稳定外键 |
| 插件公开开发契约不足 | Go SDK/CLI 有基础能力，但 Host API、权限、兼容和测试工具分散 | 固化 Public API/Host API 边界、权限目录、SDK 版本、CLI、模板、mock host 和开发文档 |
| 自动化发布门槛不足 | 有单测/构建/smoke，无统一契约和 E2E 门槛 | 将 API、权限、migration、SDK 示例、文档链接和双前端 smoke 纳入版本验收 |

### 8.2 v6 P1：在 P0 稳定后推进

| 遗漏 | 处理原则 |
| --- | --- |
| 单节点可恢复交付 | 完成配置检查、备份/恢复演练、升级预检和可重复启动路径。 |
| 插件来源信任与回滚 | 增加来源、checksum/签名策略、版本快照、安装后健康检查和人工回滚。 |
| 标准 MCP 只读边界 | 复用已收口的身份和权限模型，仅开放白名单只读工具。 |
| 一个真实消息适配器 | 只能选择一个协议做最小闭环，不能与 P0 并行扩大。 |

### 8.3 继续后置

公开插件市场、多平台 IM、AI 强制审核、任意 JavaScript 风格包、Kubernetes/高可用、完整搜索/邮件/关注系统均不作为 v6 P0。它们需要先依赖本次接口、权限、数据库和插件生态收口。

## 9. 审查结论

1. v1-v5 的功能主线已经可用，后续不应重写社区核心或插件 Runtime。
2. 历史计划不能整体标记为严格完成；未被测试和契约证明的部分继续保留为缺口。
3. v6 的第一优先级应是接口与权限、数据库完整性、插件开发者生态，而不是新增更多业务页面。
4. 每个 v6 工作包都必须同时交付实现、migration、负向测试、操作文档和进度记录；只完成其中一项不能关闭任务。
