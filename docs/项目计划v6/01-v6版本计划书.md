# CampusOS 项目计划 v6

> 文档状态：规划
> 编写日期：2026-07-10
> 实现阶段建议：`v0.6-dev`
> 依据：[v1-v5 计划审查](00-v1-v5计划审查.md)、[v5 第二版计划书](../项目计划v5/01-v5版本计划书第二版.md)、当前 `v0.5.33-dev` 基线

## 1. 定位

v6 不是继续堆叠所有未完成能力，也不是把 `v1.0` 生产目标一次前移。它的目标是让 CampusOS 从“功能闭环较多的开发系统”走向“接口可依赖、数据可恢复、插件可追溯、外部连接可验证”的下一阶段。

```text
v0.5: feature and operational baseline
  -> v0.6: contract + recoverability + plugin trust + one verified external boundary
  -> later: marketplace / multiple adapters / AI enforcement / scale-out deployment
```

## 2. v6 总目标

| 优先级 | 目标 | 成功标准 |
| --- | --- | --- |
| P0 | API 契约收口 | 当前公开 HTTP API 有可审查的 OpenAPI 基线、兼容性规则和契约测试。 |
| P0 | 可恢复交付 | 能从零启动单节点环境，并完成一次有记录的备份恢复演练。 |
| P0 | 插件信任与回滚 | 用户级插件包具有来源/版本快照、安装后健康检查和明确回滚操作。 |
| P1 | 标准 MCP 只读服务 | 在现有 MCP-like 之上实现独立、标准、只读的协议入口，不开放高风险写操作。 |
| P1 | 一个真实协议适配器 | 选择 Discord 或 OneBot v11/NapCat 之一，按 Adapter Contract 完成最小收发与失败处理闭环。 |
| P1 | 自动化质量门槛 | 核心用户、管理员、插件和备份路径具备分层测试与发布前检查。 |
| P2 | 课表和个人空间运营增强 | 在不破坏一学期一 JSON 边界的前提下提供导出、删除、冲突提示或云盘存储适配预研。 |

## 3. 工作包

### 3.1 `v0.6.0-dev`: 基线冻结与文档入口

目标：冻结 v0.5 真实范围，清理“计划”和“已实现”混写。

| 工作 | 验收 |
| --- | --- |
| 文档入口 | `README.md` 只保留当前基线和入口；`docs/README.md` 能定位运行、架构、API、插件和计划。 |
| 历史审查 | v1-v5 的完成、部分完成和后置项有明确审查结论。 |
| 目录职责 | `data/plugins`、`data/plugin_data`、`data/personal-space` 责任保持一致。 |
| 回归基线 | Go 全量测试、双前端构建、README 链接检查和 `git diff --check` 通过。 |

### 3.2 `v0.6.1-dev`: HTTP API 契约

目标：把当前 HTTP API 从“读路由和前端调用猜测”转为可消费的契约。

| 工作 | 验收 |
| --- | --- |
| OpenAPI v1 | 覆盖 auth、community、space、schedule、richtext、plugin、webhook、message 和管理端主要接口；明确认证与错误响应。 |
| API 变更政策 | 定义字段新增、弃用、路由变更、实验接口和版本升级规则。 |
| 契约测试 | 每个关键模块至少有请求/响应 shape 测试；前端 client 的关键请求与规范不漂移。 |
| 文档生成 | 规范可被 CI 校验，且不会再把 `openapi-v0.3-pre.yaml` 当作当前全量文档。 |

非目标：不在这一任务中重写所有内部服务，也不通过破坏性改名追求“整齐”。

### 3.3 `v0.6.2-dev`: 单节点部署与恢复演练

目标：让开发期依赖服务之外的应用本身也有明确、可重复的启动和恢复路径。

| 工作 | 验收 |
| --- | --- |
| 配置检查 | 启动时校验必要环境变量，区分开发默认值和生产必填密钥。 |
| 健康检查 | 区分 liveness、readiness 和关键依赖状态，避免“进程存在”被当作“服务可用”。 |
| 应用交付 | 提供单节点 API、web、admin 的容器化或等价可复现发布路径，并固定版本与配置说明。 |
| 备份恢复演练 | 从 PostgreSQL、`data/plugins`、`data/plugin_data`、`data/personal-space` 和配置备份恢复到可登录、可读内容、可加载插件的环境；保留演练记录。 |
| 升级预检 | 迁移、备份和回滚前置检查可执行且失败可读。 |

非目标：Kubernetes、跨区域高可用、零停机升级和原生 Windows 产品部署。

### 3.4 `v0.6.3-dev`: 插件供应链和回滚

目标：在开放更多用户级插件前，提高包的可追溯性和故障可恢复性。

| 工作 | 验收 |
| --- | --- |
| 版本快照 | 覆盖更新前保留已加载用户级插件的受控快照，包含 manifest、checksum、来源和时间。 |
| 来源信任 | 定义本地开发、受信任导入和未受信任导入的来源字段；签名验证可先从可选策略开始。 |
| 安装后检查 | 插件加载后执行最小健康检查、日志采样和事件订阅校验；失败时保留明确原因。 |
| 回滚操作 | 管理端或 CLI 可查看可回滚版本并恢复一个版本；审计记录操作者和结果。 |
| 生命周期测试 | 系统级重启生效、用户级热加载、覆盖更新、失败回滚均有回归测试。 |

非目标：公网插件市场、评分评论、自动审核和普通用户自助安装。

### 3.5 `v0.6.4-dev`: 一个标准外部边界

目标：只选择一个外部标准化方向，先建立质量模板，避免同时接入多个不稳定平台。

#### A. 标准 MCP 只读服务（推荐优先）

| 工作 | 验收 |
| --- | --- |
| 独立服务边界 | 标准 MCP transport 与现有内部 `/mcp/*` 解耦；内部工具层可以作为实现依赖，但不伪装成标准服务。 |
| 身份和授权 | 明确 token、用户/服务主体、只读工具白名单和审计字段。 |
| 协议测试 | 能用标准客户端列出工具、调用至少三个只读工具、处理错误和未授权请求。 |
| 风险限制 | 不开放写操作、密钥读取、文件系统读取或跨用户数据查询。 |

#### B. 真实消息适配器（仅在 A 稳定后选择一个）

| 工作 | 验收 |
| --- | --- |
| 适配器选择 | 在 Discord 与 OneBot v11/NapCat 中选择一个，不并行建设多个平台。 |
| 标准映射 | 使用 `campusos.message.v1`、`NormalizeInbound`、`RenderOutbound`、`Health` 等 Adapter Contract。 |
| 最小闭环 | 完成认证/连接、入站文本、出站文本、关联关系、限流、错误记录和健康状态。 |
| 安全边界 | 原始平台 payload 不直接驱动高权限业务操作；敏感配置不进入日志或页面。 |

非目标：全功能机器人、跨平台抽象的所有消息段、群管理自动化和多适配器市场。

### 3.6 `v0.6.5-dev`: 质量门槛和版本验收

| 层级 | 验收 |
| --- | --- |
| Go | `GOCACHE=/tmp/campusos-go-cache go test ./... -count=1` 通过。 |
| 前端 | `web`、`admin` 的 `pnpm build` 通过；关键流程补浏览器级 smoke。 |
| API | OpenAPI 校验和契约测试通过。 |
| 安全 | 插件路径穿越、恶意风格包、权限越界、MCP 未授权、适配器签名/认证失败有回归测试。 |
| 恢复 | 按 v0.6.2 文档完成一次实际恢复演练。 |
| 文档 | README、docs portal、API、操作手册、迁移记录和 progress 文档互相无旧路径或夸大状态。 |

## 4. 依赖与顺序

```text
v0.6.0 baseline and docs
  -> v0.6.1 API contract
  -> v0.6.2 recovery path
  -> v0.6.3 plugin trust/rollback
  -> v0.6.4 standard MCP read-only
  -> optional one real message adapter
  -> v0.6.5 release verification
```

`v0.6.4` 的真实消息适配器不是强制项。若标准 MCP 或恢复演练未稳定，应把适配器推迟，而不是降低前置质量门槛。

## 5. 明确不做

| 不做项 | 原因 |
| --- | --- |
| 公网插件市场与普通用户一键安装 | 需要强签名、审核、兼容策略、计费/运营和隔离模型。 |
| 同时接入 Discord、OneBot、NapCat、AstrBot 等多个平台 | 会把协议差异、认证和运维风险乘倍放大。 |
| MCP 写操作和 AI 自动管理 | 权限、审计和误操作风险尚未满足要求。 |
| AI 强制内容审核 | 需要样本、人工复核、申诉和误伤治理。 |
| 任意 JavaScript 风格包 | 当前 HTML/CSS 安全模型不能安全承载任意脚本。 |
| Kubernetes/Helm/多实例高可用 | 应先完成单节点恢复、配置和升级路径。 |
| 大规模重写论坛或插件运行时 | 当前应修补契约和交付，不重建已可用的领域模块。 |

## 6. 文档与进度规则

1. 每个 `v0.6.X-dev` 工作包结束时，新增一份 `docs/进度/v0.6-dev/` 进度记录，列出实际运行的验证命令。
2. 历史计划保持历史事实；新的结论写入审查文档或新版本计划，不回填成过去已完成。
3. README 只写当前已实现能力和最短入口。详细教程进入 `docs/help`，接口进入 `docs/api`，结构边界进入 `docs/architecture`。
4. “标准 MCP”“真实适配器”“备份恢复演练”必须以可运行验证为准，不能仅因存在设计文档就标记完成。
