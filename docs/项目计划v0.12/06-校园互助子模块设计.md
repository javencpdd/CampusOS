> 状态：C2 已实施，待随 v0.12 Final 做全链路回归
> 日期：2026-07-17
> 关联：[v0.12 版本计划书](00-v0.12版本计划书.md)、[结构化帖子事务内核](05-结构化帖子事务内核设计.md)

## 1. 目标和范围

`feature.mutual-aid` 是编译进 CampusOS 的 Built-in Feature，用于发布校园求助、物资提供、志愿协助和资源分享。
它不是支付、接单、即时聊天或担保系统。本阶段只保存发布内容和明确的业务状态，避免把联系方式、身份证、
银行卡、完整宿舍门牌等敏感信息写进结构化字段。

一条互助内容由两部分组成：

```text
Community Core
  threads / revisions / visibility / moderation / replies
          1 : 1
feature.mutual-aid
  mutual_aid_details / aid business state
```

Community 始终拥有基础帖子与治理事实；互助 Feature 只拥有其 Detail 和状态机。停用 Feature 后，已有基础
Thread 仍可被 Community 管理、下架、恢复和审计，不会删除 Detail 或数据。

正文可使用兼容的 `markdown` 纯文本或 `safe_html` 图文格式。图文清洗属于 Community Core，图片上传属于
User Storage Core；互助不依赖图文文章 Feature 的启停。管理端把它显示在“图文文章”下只代表能力分组，
不改变独立生命周期与数据所有权。

## 2. 详情字段和状态机

`mutual_aid_details` 使用 `thread_id` 作为一对一主键，包含：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `aid_type` | 互助类型 | `request`、`offer`、`volunteer`、`resource_share` |
| `aid_status` | 业务进度 | `open`、`in_progress`、`resolved`、`closed` |
| `deadline` | 可选截止时间 | 创建/修改时必须是未来时间；数据库也拒绝早于创建时间的值 |
| `location_scope` | 粗粒度地点说明 | 最长 160 个字符，不保存完整住址 |
| `contact_mode` | 联系方式类别 | `comment`、`in_app`、`email`、`other` |
| `version` | 乐观并发版本 | 每次 Detail 修改递增 |
| `created_by` | 作者事实 | 必须与基础 Thread 作者一致 |

允许的状态转换为：

```text
open -> in_progress / resolved / closed
in_progress -> open / resolved / closed
resolved -> closed
closed -> （不可再次转换）
```

业务状态不会覆盖 Community 的 `publication_status` 或 `moderation_status`。例如，互助已解决的帖子仍可能被
管理员下架；管理员恢复帖子也不会把互助状态擅自改回 `open`。

## 3. 创建、修改和事务边界

创建请求经过固定类型、Feature Gate 和 board 类型策略检查后，走 Community 的
`CreateStructuredThread`：

```text
作者请求
  -> 校验互助输入和 board policy
  -> Thread(mutual_aid) + Revision
  -> mutual_aid_details
  -> required command audit + Outbox
  -> COMMIT
```

Detail 写入失败时，基础 Thread、Revision、审计和 Outbox 一起回滚。作者编辑正文或 Detail、以及作者修改
业务状态也走可靠命令，并使用 `version` 拒绝并发覆盖。编辑或状态写入前必须确认基础 Thread 仍处于
active（未回收）状态；已进入回收站的内容返回稳定冲突，不更新 Detail，也不产生新的审计或 Outbox。Feature
通过 `ContentGateway` 和 `ContentQuery` 访问 Community，不导入 Community PostgreSQL Repository。

## 4. API 和访问规则

| 方法 | 路径 | 认证 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/mutual-aid/status` | 无 | 返回功能是否启用。 |
| `GET` | `/mutual-aid/threads` | 无 | 按互助类型读取公开内容，支持分页、`category_id`、`keyword`、`tag`。 |
| `GET` | `/mutual-aid/threads/:id` | 无 | 读取公开互助内容和 Detail。 |
| `POST` | `/mutual-aid/threads` | JWT | 创建本人互助内容。 |
| `GET` | `/mutual-aid/threads/:id/me` | JWT | 作者读取自己的编辑投影。 |
| `PUT` | `/mutual-aid/threads/:id` | JWT + 作者 | 完整编辑正文和可编辑 Detail，必须提供当前 `version`。 |
| `POST` | `/mutual-aid/threads/:id/status` | JWT + 作者 | 仅转换互助业务状态，必须提供当前 `version`。 |

管理员要先在对应 board 的帖子类型策略中允许 `mutual_aid`。Feature 未启用、board 不允许类型、作者不匹配、
状态转换非法或版本过期时，服务端分别拒绝请求；前端隐藏入口只是辅助，不能替代后端检查。
基础 Thread 已回收时，编辑和状态更新同样返回 `409 / 40009`。未分类的 Repository、数据库和网络错误
只返回通用 `500 / 10006`，具体原因仅供服务端 trace 和日志使用。

## 5. 启停、迁移和回滚

该 Feature 的 activation mode 是 `restart`。管理员修改启停配置后，下一次服务启动才装配或拒绝其 Feature
路径；运行中的 Gin 路由不会动态增删。Path Gate 会拒绝已停用 Feature 的 API，Web 的互助页面也会显示
不可用状态。

`000034_v12_mutual_aid` 只追加 Detail 表、约束、索引和作者/类型守卫触发器，不移动原有 Thread 或用户数据。
生产问题优先使用兼容 forward-fix。`down` 迁移只用于隔离的 up/down/up 演练；生产恢复使用备份和受控发布
窗口，不能以删除 Detail 表代替数据恢复。
