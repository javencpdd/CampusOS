## 1. 计划结论

v12 不继续扩大插件平台或重做 v7-v11 已建立的架构，而是在现有模块化单体、
稳定权限 Code、TxKernel、Outbox 和 Worker 基础上，按依赖顺序完成三条主线：

```text
可信账号与邮件验证
  -> 两级板块与可靠管理
  -> 结构化帖子事务内核
  -> 校园互助与二手信息模块
```

三条主线必须串行通过阶段出口。Identity 未完成会话撤销前，不进入密码恢复验收；
Category 未完成可靠写命令前，不开放层级移动；普通帖子和 RichText 未实现原子创建前，
不开发互助和二手详情表。

本计划不会把 `v12计划思路.md` 中的建议直接当作现状。A0 制定时已经按当时代码、
205 条生成路由、8 个 Core Module、10 个 Built-in Feature、migration `000027` 和
v11 最终启动回归重新核验。当前快照为 256 条生成路由、9 个 Core Module、12 个
Built-in Feature 和 migration `000038`；阶段进度以第 18 节及对应进度文档为准。

### 2.2 不把以下内容当作已实现

- 没有可用的邮箱验证码、SMTP Provider、密码重置或邮箱绑定流程。
- 没有服务端 Session 校验、Refresh Token 轮换、Token family 或重用检测。
- `parent_id` 存在不等于已经支持两级板块和权限安全移动。
- `content_format=richtext` 不等于存在稳定的结构化帖子类型合同。
- v11 的治理命令原子化不代表普通发帖和 RichText 业务写入已经原子化。
- 现有 Message 本地 Adapter 不能承载验证码邮件，邮件正文不得进入 `message_logs`。
- `1904650862@qq.com` 当前只出现在思路文档中，仓库代码和迁移没有把它绑定给用户。

### 2.3 当前基线验证边界

v11 已有完整发布证据，但它不能代替 v12 的 A0.5 冻结。A0.5 必须用当前提交从冷
启动重新生成测试、构建、路由、迁移、目录和恢复证据，避免再次出现“复用旧 API
进程导致门禁假通过”的问题。

## 3. v12 目标、优先级与非目标

### 3.1 P0：安全与数据完整性

1. 删除默认管理员密码日志，区分开发默认凭据与生产 Bootstrap Secret。
2. 收敛规范化邮箱事实，安全迁移历史账号验证语义。
3. 建立 Challenge、一次性 Ticket、持久限流和可靠邮件投递。
4. 新注册强制验证邮箱，历史账号继续可登录但不能伪装成已验证。
5. 建立 Session、Refresh 轮换、重用检测、logout/logout-all 和 `auth_version`。
6. 完成密码重置、邮箱绑定和管理员辅助恢复的原子命令与审计。
7. 以独立管理员账号准入表隔离管理平面入口，并保持 Session、RBAC 和密码凭据单一事实源。
8. Category Repository 接入 TxKernel，修复 `color` 合同并可靠化写操作。
9. 普通帖子、Revision、RichText Detail、required audit 和 Outbox 原子提交。

### 3.2 P1：社区产品能力

1. 两级 Category、移动、归档、恢复、影响预览和树形管理。
2. Thread Type、板块类型策略和编译内 Structured Thread Command Port。
3. RichText 迁入 `article` 类型并保持旧 API、ID、URL 和内容可读。
4. 校园互助与二手信息作为独立 Built-in Feature，使用类型化 API 和详情表。
5. Web/Admin PC、移动端交互和 Feature 停用回归。

### 3.3 P2：不阻断发布的完善项

- 邮件模板国际化和多 Provider 主备切换接口。
- 更细的账号安全通知、Session 设备命名和管理员运营报表。
- 结构化帖子更多只读筛选和数据导出。

P2 未完成必须记录，但不得用来掩盖 P0/P1 的验收缺口。

### 3.4 本版本明确不做

- 手机号登录、OAuth 登录重构、Passkey、MFA 和第三方人机验证强依赖。
- 无限级 Category、父级角色/版主权限动态继承和跨板块自动扩权。
- 支付、订单、托管、担保、退款、物流、交易仲裁和即时聊天。
- External Plugin 自定义 Thread Type 或参与宿主数据库事务。
- 分布式 Session/限流、Prometheus/SLO 全面建设和生产集群 HA。
- 修改 `000001` 至 `000027`，物理删除历史账号、帖子、板块或 RichText 数据。

## 4. 目标架构

### 4.1 账号与邮件链路

```text
Web / Admin / API Client
  -> core.identity Challenge / Session / Account commands
  -> core.reliability TxKernel
       -> Identity tables
       -> required audit
       -> Outbox(identity.email.challenge.requested.v1)
  -> COMMIT
  -> core.email-delivery consumer
       -> Identity Dispatch Reader
       -> platform.mail.Sender
            -> SMTP Provider
            -> Fake Provider (test/local only)
```

模块关系：

```text
core.identity        -> core.reliability
core.email-delivery  -> core.identity + core.reliability
```

`core.identity` 不导入 SMTP；`core.email-delivery` 为 `kind: core`、`always-on`，不进入
普通 Feature 开关。SMTP 不可用时模块报告 degraded，Outbox 保留并重试，但 API 不能
假报“邮件已经送达”。External Plugin、MCP、Agent Runner 和浏览器不能读取验证码
重建 Port、邮件 Secret 或 Challenge 内部数据。

### 4.2 Category 链路

```text
Admin command
  -> Operation/Permission Code
  -> CategoryService
  -> Reliability.Execute
       -> lock current node/parent
       -> validate version and two-level invariant
       -> Category Repository through ExecutorFor
       -> required audit + Outbox
  -> COMMIT
  -> cache/event/UI refresh
```

Category 始终属于 `core.community`。两级层级只是导航与发帖策略，不是权限继承树；
版主仍只能管理显式分配的 board。

### 4.3 结构化帖子链路

```text
Typed Built-in Feature API
  -> feature DTO/state validation
  -> community.StructuredThreadCommands
  -> Reliability.Execute
       -> validate category + type policy + feature state
       -> Thread + Revision
       -> participant.PersistDetail(ctx, threadID)
       -> required audit + Outbox
  -> COMMIT
```

Participant 只允许编译内 Built-in Feature 使用，只能执行同一数据库内的有界写入；
不得在事务中上传文件、调用网络、启动进程或等待外部 Provider。External Plugin 仍只走
Host API/Gateway，v12 不开放事务参与能力。

## 5. 数据与接口所有权

| 对象 | 权威所有者 | 兼容投影或消费者 |
| --- | --- | --- |

## 6. Identity、安全邮件与 Session 设计

### 6.1 邮箱事实和状态

`accounts(type=email)` 作为个人登录邮箱权威事实，新增：

```text
identifier_normalized
verification_state: unverified | legacy_accepted | verified | system_managed
verified_at
verification_source
password_changed_at
credential_version
```

`users` 新增：

```text
auth_version
must_change_password
```

规范化只允许 `trim + lowercase`。v12 不对 QQ/Gmail 执行点号、大小写以外的供应商
特定折叠，避免错误合并合法地址。

迁移语义：

| 账号 | 状态 | 登录 | 邮件找回 | 含义 |
| --- | --- | ---: | ---: | --- |
| 新注册且 Ticket 已消费 | `verified` | 是 | 是 | 已证明拥有邮箱 |
| 历史非系统账号 | `legacy_accepted` | 是 | 否 | 仅为升级兼容，不声明已验证 |
| 尚未完成验证的凭据 | `unverified` | 否 | 否 | 不得绕过 Challenge |
| 默认管理员等系统账号 | `system_managed` | 是 | 否 | 通过部署/本机恢复，不走公网邮箱找回 |

`accounts.verified` 在 v12 保留为兼容投影，不再作为唯一事实；所有邮箱写操作只能通过
Identity Service，禁止 Handler/Admin 直接更新 `users.email` 或 `accounts.identifier`。

### 6.2 历史共享邮箱占位

若产品确认使用 `1904650862@qq.com` 标记历史账号，只能写入独立的
`identity_legacy_email_placeholders`，并明确：

- 不参与登录、注册唯一性、验证码、密码重置或所有权证明；
- 不写入 `users.email`、`accounts.identifier` 或 Session；
- 加入 Identity reserved identifier 策略，不能被新用户当作个人邮箱注册或找回密码；
- Admin 文案显示“历史占位标记”，不能显示成“已绑定邮箱”；
- 用户绑定个人邮箱后记录 `resolved_at`，不物理删除历史迁移证据；
- SMTP 发件地址必须来自独立 Secret 配置，和用户邮箱事实完全分离。

### 6.3 Challenge 与一次性 Ticket

`identity_email_challenges` 至少包含：

```text
id/public_id, purpose, email_normalized, account_id
key_id, nonce, expires_at, attempt_count, max_attempts
verified_at, ticket_digest, ticket_expires_at, consumed_at, invalidated_at
requested_ip_hash, created_at, updated_at
```

Purpose 固定为 `registration`、`email_binding`、`password_reset`，不同 Purpose 的 Code
和 Ticket 不能互换。

验证码采用 HMAC 密钥环可重建方案：

```text
code = Truncate6(HMAC(secret[key_id], public_id + nonce + purpose))
```

数据库和 Outbox 不保存验证码明文。Ticket 使用至少 256 bit 随机值，服务端只存摘要；
消费时使用 `SELECT ... FOR UPDATE` 检查 Purpose、邮箱、有效期、状态和摘要，并原子写入
`consumed_at`。

默认策略：验证码 10 分钟、最多尝试 5 次；同邮箱任意连续 10 分钟最多发送 5 次，同 IP 任意连续
60 分钟最多发送 10 次；Registration Ticket 15 分钟。邮箱和 IP 只以带部署 Secret 的 HMAC 摘要
参与限流。窗口和次数由 Identity Core 的有界、版本化策略热更新，限流本身不可关闭。
已消费、过期或失效 Challenge 必须进入有界 retention；默认 30 天后分批匿名化/清理
邮箱和 IP 摘要，执行数量、失败和恢复结果进入 Reliability 运维证据。

### 6.4 邮件投递

Outbox 事件只保存：

```json
{"challenge_id":"..."}
```

禁止写入邮箱、验证码、Ticket、SMTP Secret 或完整邮件正文。Consumer 在执行时通过
编译内 Dispatch Reader 读取收件地址、模板、有效期并重建 Code。过期、失效或已消费
Challenge 的 replay 必须安全跳过。

SMTP 配置只从环境/Secret 读取；Admin 只能看到 Provider、健康和最近脱敏错误。Fake
Provider 仅用于测试和显式本地开发，生产环境启动时发现 Fake Provider 必须失败。
邮件投递语义明确为 at-least-once：Consumer Receipt 和 Provider 幂等键尽量抑制重复，
但发送成功后进程崩溃仍可能产生重复邮件，不能在文档或 UI 中承诺 exactly-once。

### 6.5 Session 与 Token

登录流程改为：

```text
验证凭据和 verification_state
  -> 创建 Session + token_family_id
  -> 生成含 session_id/auth_version/typ=access 的 Access JWT
  -> 生成不透明随机 Refresh Token
  -> 数据库只保存 Refresh Token 摘要
```

新增：

```text
POST /api/v1/auth/refresh
POST /api/v1/auth/logout
POST /api/v1/auth/logout-all
GET  /api/v1/auth/sessions
DELETE /api/v1/auth/sessions/:id
```

Refresh 每次使用都轮换；旧 Token 再次出现时撤销整个 family。JWT Middleware 必须校验
`typ=access`、Session 未撤销/未过期、用户状态和 `auth_version`。Refresh Token 不能当
Access Token 使用。

Web/Admin 切换为 HttpOnly、Secure(生产)、SameSite=Lax 的 Refresh Cookie，并为 Cookie
写接口增加 CSRF 防护。现有 JSON `refresh_token` 字段保留一个版本兼容窗口，由显式
`AUTH_REFRESH_BODY_COMPAT` 控制并输出弃用遥测；前端不得持久化该字段。

Access Token 默认缩短为可配置的 15 分钟，Refresh 默认 30 天；`expires_in` 从真实配置
计算，不再硬编码 7200。Web/Admin 清理历史 localStorage Token，Access Token 只保存在
进程内存，并在页面恢复时通过 HttpOnly Refresh Cookie 获取新 Access Token。

v12 上线时，缺少 `session_id/auth_version` 的 v11 JWT 不再接受，所有在线用户需要重新
登录。该安全不兼容必须在发布说明中提前声明，不能静默放宽校验。

### 6.6 密码重置、邮箱绑定和管理员恢复

密码重置必须在同一可靠命令内完成：

```text
锁定 Reset Ticket
-> 更新密码和 credential_version
-> auth_version + 1
-> 撤销全部 Sessions
-> 消费 Ticket
-> required audit + Outbox
-> COMMIT
```

公开请求统一返回“如果该邮箱符合条件，系统将发送验证码”，不得暴露邮箱是否存在、
是否验证或账号是否封禁。

历史用户登录后可以绑定新个人邮箱；成功后状态变为 `verified` 并撤销其他 Session。
没有验证邮箱且忘记密码的历史用户只能走管理员辅助恢复：管理员线下核验，创建恢复
Case，系统向用户提供的新邮箱发送验证，不允许管理员查看或设置明文密码。

新增权限：

```text
identity.account.recovery.override
identity.session.read
identity.session.revoke
platform.email_delivery.read
```

默认管理员 `admin@campusos.local` 不走公网邮件恢复。提供本机
`campusosctl identity reset-password`，要求交互式输入、required audit、Session 撤销，
且日志不输出明文密码。

### 6.7 注册 API 兼容决策

正式注册仍使用 `POST /api/v1/auth/register`，但必须携带 Registration Ticket；请求中的
email 可暂时保留，服务端必须与 Ticket 绑定邮箱一致。旧一步式请求返回稳定错误
`identity.verification_required`，不再创建未验证用户。

这是有意的安全收紧。Web、文档、OpenAPI 和 SDK 必须在 A5 同步发布，不提供绕过开关。
SMTP 故障只会让 Challenge 等待重试，不会生成半注册账号。

## 7. 两级 Category 设计

### 7.1 数据模型

在现有表增量新增：

```text
node_kind: group | board
lifecycle_status: active | archived
version
color
```

发帖资格由以下事实共同决定，不新增容易冲突的 `posting_enabled`：

```text
node_kind == board
AND lifecycle_status == active
AND is_closed == false
```

层级规则：根级可为 group 或 board；group 只能位于根级；board 可位于根级或一个 group
下；board 不能拥有子节点；不能移动到自身或后代；archived 节点不能接收新帖或子节点。

所有历史 Category 默认回填 `board/active/version=1`。若预检发现三级、循环或孤立父节点，
迁移必须中止并输出清单，不自动拍平。

### 7.2 权限规则

- group 是导航容器，不产生版主权限继承。
- 版主权限继续绑定显式 board；移动 board 不修改授权范围。
- Category 创建、更新、移动、归档、恢复和类型策略使用独立 Permission Code。
- Admin 管理命令在事务内重新读取角色、版本、当前父节点和影响事实。
- 旧 `category:write/delete` 通过兼容映射进入新 Code，并记录调用遥测。

### 7.3 API

保留：

```text
GET /api/v1/categories
GET /api/v1/categories/tree
GET /api/v1/categories/:id
GET /api/v1/admin/categories...
POST/PUT /api/v1/categories...
```

新增：

```text
GET  /api/v1/categories/tree
PUT  /api/v1/categories/:id/parent
GET  /api/v1/categories/:id/archive-impact
POST /api/v1/categories/:id/archive
POST /api/v1/categories/:id/restore
```

旧 `DELETE /categories/:id` 在 v12 映射为 archive 并记录弃用遥测，不物理删除。移动使用
独立请求以区分“未提交 parent_id”和“显式设为 null”。所有修改请求携带 `version`，
冲突返回稳定 `409`。

`color` 正式支持 `#RRGGBB` 和 `#RRGGBBAA`，Admin Color Picker 必须输出同一格式并通过
严格合同测试。

## 8. 结构化帖子设计

### 8.1 Thread Type 与板块策略

`threads.thread_type` 固定首批值：

```text
discussion | article | mutual_aid | secondhand
```

`content_format` 继续表示正文渲染格式，`thread_type` 表示业务类型。回填规则：存在有效
`richtext_article_contents` 的 Thread 为 `article`，其余为 `discussion`。

`category_thread_type_policies` 由 Community 所有。历史板块默认允许 `discussion` 和
`article`；`mutual_aid`、`secondhand` 必须由管理员显式开启。Core 创建前检查 Category
可发帖、类型已注册、策略允许、对应 Feature 有效。

### 8.2 类型化接口

禁止通用 `/threads` 接收任意 Detail JSON。使用：

```text
POST /api/v1/threads                     -> discussion
POST /api/v1/richtext/articles           -> article（旧路径保留）
POST /api/v1/mutual-aid/threads          -> mutual_aid
POST /api/v1/secondhand/threads          -> secondhand
```

每个 Built-in Feature 负责自己的 DTO、字段约束、状态机、详情表、前端表单和业务审计；
Community 只拥有基础 Thread、Revision、治理状态、Category Policy 和事务协调 Port。

### 8.3 RichText 迁移

先让普通 Create/Update/Author Trash 进入可靠命令，再把 RichText Store 切换到
`transaction.ExecutorFor`。Create/Update/Publish/Offline/Delete 和 Admin 治理镜像更新
必须与 Thread、Revision、Article、required audit、Outbox 同事务。

原有 RichText 路径、Thread ID、Article ID、资产 URL、草稿和历史状态保持可读。文件
上传不进入数据库事务；未绑定资产沿用 User Storage 的安全路径和后续 retention/补偿
规则。

### 8.4 校园互助

新增 `feature.mutual-aid`，详情至少包含：

```text
thread_id, aid_type, aid_status
deadline, location_scope, contact_mode
version, created_at, updated_at
```

状态：`open -> in_progress/resolved/closed`，`in_progress -> open/resolved/closed`，
`resolved -> closed`。不保存身份证、银行卡和完整宿舍门牌，不提供支付或担保。

### 8.5 二手信息

新增 `feature.secondhand`，详情至少包含：

```text
thread_id, price_minor, currency=CNY
item_condition, trade_method, trade_status
location_scope, version, created_at, updated_at
```

状态：`available -> reserved/sold/closed`，`reserved -> available/sold/closed`。平台只提供
信息发布、状态标记、内容审核和举报入口，不形成订单或资金关系。

两个 Feature 停用后，专用 Feature API 除显式声明的只读 `GET /<feature>/status` 外都由 Path Gate
拒绝；因此客户端不会把已停用功能误显示为可用。历史基础 Thread 仍可按 Community 的公开、作者和
治理规则读取和处理，停用不得删除详情表或绕过 Moderation。Feature 的专用详情读取恢复必须先重新启用
Feature，而不是绕过 Gate。

1. 不修改历史 migration。
2. 每个 migration 提供 up/down 和独立 up/down/up 演练；生产采用 forward-fix。
3. 预检失败必须输出可定位的 ID/规范化值，不自动选择“正确数据”。
4. 新表和列先允许旧二进制读取，再切换写路径；切换后回滚旧二进制时必须进入受控只读。
5. 架构可视化、schema contract、备份清单和恢复脚本同步更新。

## 13. 兼容、迁移和回滚

| 对象 | v12 策略 | 回滚限制 |
| --- | --- | --- |
| 历史用户 | 迁移为 `legacy_accepted`，继续用原邮箱密码登录。 | 不得批量标记 verified；冲突数据先人工治理。 |
| 新注册 | 同一路径增加 Ticket 要求，旧请求返回稳定错误。 | 回滚旧二进制前必须关闭公开注册，防止重新开放未验证注册。 |
| v11 JWT | 上线时强制重新登录，不接受缺少新 Claims 的 Token。 | 二进制回滚需轮换 JWT Secret 并进入认证维护窗口。 |
| Login 响应 | Access 字段保持；Refresh body 保留受控弃用窗口，Web 使用 Cookie。 | 兼容开关有遥测和移除日期，不能永久保留。 |
| `users.email` | 继续读取并由 Identity 原子同步。 | 不允许独立写；删除字段留到后续版本。 |
| `sessions.refresh_token` | 历史值撤销并清理，新 Token 只存摘要。 | 生产不恢复原始 Token；schema down 只用于隔离演练。 |
| Category API | flat list 保留；新字段为加法；DELETE 映射 archive。 | 回滚旧二进制时 Category 写入口设只读，避免绕过层级约束。 |
| Thread/RichText | ID、旧 URL、内容和治理状态不变；新增 `thread_type`。 | 旧二进制可读基础 Thread，但结构化写入口必须关闭。 |
| Mutual/Secondhand | 停用时专用 Feature API 仅保留只读 status 发现端点；历史基础 Thread 仍由 Community 读取和治理。 | 不删除详情表和用户数据；恢复专用详情入口必须先重新启用 Feature。 |

生产数据库以 forward-fix 为默认策略。down migration 只用于隔离测试和恢复验证，不是
生产直接回滚授权。

## 15. 主要风险与禁止事项

### 15.1 风险控制

| 风险 | 控制 |
| --- | --- |
| 历史邮箱冲突导致错误合并 | 迁移前对账并中止，不自动覆盖。 |
| SMTP 故障阻断注册 | Challenge/Outbox 先提交，Provider 异步重试并报告 degraded。 |
| 验证码泄漏 | HMAC 重建、Ticket 摘要、日志/Outbox 负向扫描、最小 Dispatch Port。 |
| Session 切换导致用户掉线 | 明确发布公告、一次性强制重登、稳定错误和前端拦截。 |
| 回滚重新开放弱认证 | 注册维护开关、JWT Secret 轮换和受控只读回滚。 |
| Category 并发产生非法层级 | version、行锁、稳定锁顺序和并发测试。 |
| 跨模块事务膨胀 | Participant 仅编译内、只做数据库写、禁止网络/文件/进程。 |
| 结构化业务范围失控 | 互助/二手不含支付、订单、聊天和仲裁。 |
| Feature 停用造成数据不可治理 | Community Core 始终拥有基础 Thread 和治理状态。 |
| Detail 编辑半写 | 编辑 Detail 失败时通过 TxKernel 回滚 Thread、Revision、Detail、Audit 与 Outbox；Memory 故障注入与 PostgreSQL 演练分别提供证据。 |
| 回收内容继续产生业务事件 | 状态写入先验证 Community 删除维度，非 active Thread 返回稳定冲突且不新增可靠证据。 |
| 底层错误泄露 | Feature Handler 只回显已分类的输入/权限/冲突错误，未分类错误返回通用 `internal server error` 和 trace。 |
| 发布门禁漏跑迁移演练 | `release-check` 显式调用 `v12-migration-check`；Final 必须保留实际输出。 |
| 图文正文注入活动内容 | Community Core 统一清洗元素、属性、URL 和 CSS；预览与保存使用同一实现，客户端 `v-html` 只读取已清洗值。 |
| 超大或越权图片写入 | User Storage 在 multipart 解析前限制请求体，并校验 MIME、安全路径、随机文件名、单文件上限和用户总配额。 |
| 二级显示被误解为启停继承 | `presentation_parent` 只供界面分组；Feature Registry 仍分别保存三个功能的目标状态和数据生命周期。 |
| 未发布图片形成孤立资产 | 当前不自动删除；先保留用户所有权与配额约束，后续以有审计的引用索引和延迟回收处理。 |
| 路由 code 与数据库约束漂移 | Platform Route Registry 复用数据库格式规则，生成合同测试保留兼容别名；冷启动核对目录同步日志。 |

### 15.2 禁止事项

- 禁止修改历史 migration 或用脚本静默修正冲突账号。
- 禁止把共享邮箱写进多个 `accounts.identifier` 或用于密码重置。
- 禁止把历史 `verified=false` 直接批量改成真实 verified。
- 禁止保存验证码、Ticket、Refresh Token、SMTP Secret 或用户密码明文。
- 禁止邮件 Worker 读取数据库连接以外的 Identity 内部 Repository；只能使用声明 Port。
- 禁止在通用 `/threads` 接受任意 Detail JSON。
- 禁止 External Plugin、MCP 或 Agent Runner 获得 TxKernel、AppContext 或事务 participant。
- 禁止 Category 父级自动扩大版主权限。
- 禁止为了兼容继续接受无 Session 的旧 JWT 或未验证的一步式注册。
- 禁止 Feature 停用、归档板块或回滚代码时删除用户数据。
- 禁止在没有完整证据时更新 README 为“v12 已完成”或切换应用版本。

## 16. 最终验收定义

只有 A0-A7、B1-B3、C0-C3 和 Final 全部通过，才可声明 v12 完成：

1. 新注册必须验证个人邮箱，规范化邮箱全局一对一。
2. 历史账号可登录但不会被错误标记为已验证；共享占位邮箱不具备凭据能力。
3. 默认管理员密码不出现在生产代码配置和日志，系统账号使用安全恢复入口。
4. 密码重置、邮箱变更、logout-all 后旧 Session、Refresh 和 Access Token 均失效。
5. 数据库、Outbox、日志、Admin API 和导出物不出现 Code、Ticket、原始 Refresh 或 Secret。
6. Category 只有两级，group/closed/archived 不可发帖，写操作原子审计并可恢复。
7. 版主权限仍只作用于显式分配的 board，移动和父级关系不扩大权限。
8. 普通帖子和 RichText 不再留下半写 Thread、Revision 或 Article。
9. Thread Type 和 Category Policy 有稳定合同，RichText 兼容迁移完成。
10. 互助与二手使用独立类型化模块，业务状态不能覆盖内容治理状态。
11. Feature 停用不删除详情或阻断 Community 的治理能力。
12. 空库安装、v11 历史升级、迁移演练、备份恢复、冷启动、PC/移动端和完整发布门禁通过。
13. 计划、进度、API、帮助站、README、版本和生成合同一致。
14. `make release-check` 的实际输出包含 `make v12-migration-check`，且 C3 的
    `000035` up/down/up 触发器、约束和错误路径均有隔离 PostgreSQL 证据。
15. 普通邮箱找回不要求用户手填 Challenge ID；验证码发送限制由始终启用的 Identity Core 按有界
    策略执行，管理端热更新有权限、版本冲突、required audit 和迁移回滚证据。
16. Outbox 的 Complete、Retry、DeadLetter、Attempt 和 Receipt 持久化错误可观测；Claim 不超过
    `max_attempts`，历史越界事件保留次数并收敛到 dead，Consumer Receipt 不被删除或绕过。
17. 公开 group 点击后才显示活动子 board；互助与二手可发布、编辑、预览安全图文和图片，并在 PC/移动端
    自适应显示；二级功能展示不得把 RichText、互助和二手的启停或数据生命周期耦合。

## 17. v13 候选方向

v12 Final 后再评估：MFA/Passkey、OAuth、共享 Session/限流、邮件多 Provider、retention
物理执行、更多结构化帖子类型、External Plugin 受限内容类型 Provider、全站容量压测、
Prometheus/SLO 和生产集群能力。可靠 Worker 的 complete/state-transition/exhausted/lease-lost/
attempt-overflow 指标留到统一指标层实现；当前先以结构化脱敏日志和 Attempt 证据覆盖。互助和二手当前按页逐条读取 Detail，数据量增长前需以受测的批量
Detail 查询或 join 投影替换 N+1 读取，而不改变现有 HTTP 合同。进入条件必须由 v12 回顾文档重新确认，
不能提前混入本计划。
