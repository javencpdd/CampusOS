# v0.12 结构化帖子事务内核设计

> 状态：C0-C3 已验收
> 日期：2026-07-17
> 关联计划：[v0.12 版本计划书](00-v0.12版本计划书.md)
> 实施记录：[v0.12.12-dev](../进度/v0.12-dev/v0.12.12-dev.md)

## 1. 目的

Community 的 `threads` 是所有内容的基础事实，Revision 是不可缺少的历史证据。RichText 还拥有独立的
Article Detail。过去这些记录分步写入：先创建 Thread，再创建 Detail；Detail 失败时把已创建的 Thread
移入回收站。这不是原子操作，会留下对用户和管理员都难以解释的中间状态。

C0 的目标是先收敛已有写路径，再在 C1 引入正式的结构化 Thread Type 和 Participant 合同。C0 不引入
任意 Detail JSON，也不允许 External Plugin 参与宿主事务。

## 2. C0 已实现边界

```text
普通作者请求
  -> ThreadService.executeAuthorCommand
  -> Thread + Revision + command audit + Outbox
  -> COMMIT

RichText 创建草稿
  -> Community.CreateStructuredThread
  -> Thread + Revision + article participant Detail
  -> command audit + Outbox
  -> COMMIT

RichText 作者或管理员后续请求
  -> RichText.executeArticleCommand
  -> Community ContentGateway（复用当前 TxKernel）
       -> Thread + Revision / 治理状态
  -> RichText Article Store
  -> command audit + Outbox
  -> COMMIT
```

普通主题的创建、作者编辑、作者回收和 Built-in Feature 基础 Thread 更新都通过
`ThreadService.executeAuthorCommand`。RichText 的创建由 Community 的结构化创建命令拥有外层可靠边界，
Article participant 在基础 Thread 与 Revision 已写入后、审计与 Outbox 提交前保存 Detail。保存、发布、下线
和治理等既有动作继续由 RichText 在外层持有一个可靠命令；它调用 Community Public Gateway 时，Community
检测到已有事务后只执行领域写入，不生成嵌套 Audit 或 Outbox。这样一次用户动作只产生一组持久证据和一个
提交后的事件。

成功提交后才清理列表缓存。EventBus 兼容事件由现有 Outbox Worker 在提交后投递；事务内不会发布事件、
调用网络、上传文件或等待前端刷新。

## 3. 存储和回滚

`richtext.PgStore` 的所有数据库访问通过 `transaction.ExecutorFor(ctx, pool)` 取得执行器，因而在
外层 TxKernel 中使用同一个 PostgreSQL transaction。内存 Profile 为 Thread Repository、Governance
Repository、RichText Memory Store 和 Reliability Store 注册 Snapshot/Restore，便于测试过程与生产
PostgreSQL 的回滚语义一致。

故障注入覆盖以下关键点：

| 注入位置 | 预期结果 |
| --- | --- |
| 普通 Thread 的 Revision 写入失败 | Thread 创建、编辑或回收全部回滚，且没有 command audit/Outbox。 |
| RichText Article 创建失败 | 不留下 Thread、Revision、Article、command audit 或 Outbox。 |
| RichText Article 更新失败 | Thread 与 Article 都保留提交前状态，且不追加 audit/Outbox。 |

`richtext_create_rollback` 补偿调用已从 RichText 创建路径移除。文件上传是独立的本地资产流程，不能放进
数据库事务；未绑定资产沿用 User Storage 的安全路径和后续 retention 策略处理。

## 4. 兼容性

- HTTP 路由、Thread ID、Article ID、资产 URL、草稿和治理状态均未改变。
- 未安装 Reliability 的隔离测试或旧进程仍按原有直接调用路径运行；正式 Module Graph 强制 RichText 依赖
  `core.reliability`，生产写入不会走该兼容回退。
- C0 不改数据库 schema，因此不需要 migration；C1 的 `000033` 才会追加 `thread_type`、板块类型策略
  和 RichText 的历史回填。
- 已有回收站内容保持可读、可恢复；不会为了消除旧补偿记录而删除历史数据。

## 5. C1 已实现的受控扩展

`000033` 已提供固定 `discussion`、`article`、`mutual_aid`、`secondhand` 类型和
`category_thread_type_policies`。历史 board 默认只允许 `discussion/article`；管理员通过有版本号的
策略写入端点显式开放其他类型。策略只控制新的创建，不能隐藏或损坏已经存在的结构化内容。

只有编译内 Built-in Feature 可以通过受限 Participant 接口在同一事务内保存一对一 Detail；Participant
不会获得数据库连接、AppContext、网络或文件权限。RichText 已作为第一个 `article` participant 完成
迁移。External Plugin 继续只能使用 Host API、Extension Gateway 和公开 HTTP API。

C2 已将 `mutual_aid` 落地为第一个独立结构化业务模块：它使用 `mutual_aid_details` 保存互助类型、
业务状态、截止时间、地点范围和联系渠道，并通过同一个 Participant 合同与 Thread、Revision、审计和
Outbox 原子提交。其业务状态不会覆盖 Community 的发布或治理状态。具体边界见
[校园互助子模块设计](06-校园互助子模块设计.md)。

C3 已将 `secondhand` 以同一边界落地：`secondhand_details` 保存 CNY 分价、成色、交付方式、
交易状态和地点范围；创建仍由 Participant 与 Thread、Revision、审计和 Outbox 原子提交。交易状态不会覆盖
Community 的发布或治理状态，支付、订单和仲裁仍明确不在本模块范围。具体边界见
[二手信息子模块设计](07-二手信息子模块设计.md)。
