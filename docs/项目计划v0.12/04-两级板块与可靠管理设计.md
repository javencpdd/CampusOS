## 1. 目标和边界

本阶段强化现有 `categories` 表，不新建平行的导航表、权限树或帖子分区表。目标是让管理员能够用
两级结构组织社区，同时保证移动、归档和并发修改不会破坏发帖资格、版主范围或审计证据。

它不实现无限级目录、父级自动授权、按 group 授权版主或物理删除板块。这些能力会使治理范围难以
解释，也会让旧帖子与已分配的 board scope 失去稳定依据。

## 2. 模型和不变量

| 字段 | 值 | 作用 |
| --- | --- | --- |
| `node_kind` | `group` / `board` | group 是导航容器；board 是唯一可发帖节点。 |
| `lifecycle_status` | `active` / `archived` | archived 节点保持数据和管理可见性，但不进入公开导航。 |
| `version` | 正整数 | 管理写入的乐观并发版本。 |
| `color` | 空或 `#RRGGBB` / `#RRGGBBAA` | 管理端展示色；数据库和服务同时校验。 |

两级规则如下：

```text
root group
  └── board

root board
```

group 必须在根级。board 可以在根级，也可以只挂在一个 active group 下。board 不能拥有子节点；
archived group 不能拥有 active child board。发帖与回复前必须满足：

```text
node_kind == board
AND lifecycle_status == active
AND is_closed == false
AND (无父级 OR 父级是 active group)
```

这套规则由 migration 预检、数据库 CHECK/触发器和 Community Service 三层共同执行。数据库层保护
绕过 HTTP 的写入，Service 层给调用方稳定的业务错误并在创建主题、回复时复用相同判断。

## 3. 权限与治理范围

板块层级不是权限继承树。group 不获得版主，也不会把自己的任何权限传播给 child board。管理员给
版主分配的 scope 仍然是一个或多个明确的 board ID；移动 board 前后，该 scope 的 ID 不变，因此不会
扩大或缩小版主可操作的主题集合。

| Permission Code | 动作 | 风险 |
| --- | --- | --- |
| `community.category.create` | 创建 group 或 board | 中 |
| `community.category.update` | 修改名称、标签、颜色、关闭状态和排序 | 中 |
| `community.category.move` | 改变 board 的父级 | 高 |
| `community.category.archive` | 归档节点和读取归档影响 | 高 |
| `community.category.restore` | 恢复归档节点 | 高 |

`category:write` 与 `category:delete` 仅在兼容窗口内映射到相应的新 Code。新实现和新角色应直接使用
稳定 Permission Code。管理读取继续使用既有 `category:read`，避免把只读权限误提升为管理写入权限。

## 4. 可靠写入边界

创建、更新、移动、归档和恢复都由 `CategoryService` 进入 Reliability/TxKernel。PostgreSQL Repository
通过 `transaction.ExecutorFor` 取得当前事务执行器，避免回退到 pool 直接提交。成功命令在同一个事务内
完成：

```text
读取/锁定当前节点与必要父节点
-> 校验 version 和两级不变量
-> 写 categories
-> 写 required command audit
-> 写 platform_outbox
-> COMMIT
```

任一步失败会回滚业务事实和必需证据。提交后由现有 Outbox/Worker 处理事件；不会在事务中等待前端刷新
或任何外部网络调用。

更新、移动、归档和恢复要求客户端提交当前 `version`。冲突返回 `409`，客户端必须重新读取最新状态再让
操作者决定。`parent_id` 的移动请求单独定义，显式 `null` 表示移动到根级，省略字段则直接拒绝，避免
序列化过程把“无意改变”误当成“移到根级”。

## 5. API 与前端分工

公开接口只返回 active 数据：

```text
GET /api/v1/categories
GET /api/v1/categories/tree
GET /api/v1/categories/:id
```

管理端读取使用不与公开接口冲突的命名空间：

```text
GET /api/v1/admin/categories
GET /api/v1/admin/categories/tree
GET /api/v1/admin/categories/:id
```

管理写操作保留原有 `/categories` 路径，以避免无说明地破坏已有后台调用；每条路由都具有显式
Operation Code、Permission Code 和审计策略。旧 `DELETE /categories/:id?version=<n>` 不再物理删除，
而是调用 archive 并写入 compatibility telemetry。

管理端提供树形创建、编辑、移动、归档影响预览、归档和恢复。用户前台只将 active、未关闭 board 显示为
可点击导航或发帖目标；group 只显示为分组标签。前端过滤不替代后端检查。

## 6. 迁移、兼容和恢复

`000032_v12_category_hierarchy` 先检测三级、循环和孤立 parent。发现任一历史异常即中止并输出具体 ID，
不会自动拍平、改父级或删除数据。通过预检后，历史父节点回填为 group，其余历史节点回填
`board/active/version=1`。

生产问题使用 forward-fix 或经验证的备份恢复。down migration 仅用于隔离数据库的 up/down/up 演练；
它不应在生产环境删除归档事实、审计或 Outbox 证据。若必须短时回退旧二进制，应先把 Category 写入口
置为只读，避免旧实现绕开 version 和层级约束。
