## 2. 实际完成内容

- 核验 v0.6 已实现 `viewport_support`、响应式 CSS 规则检查、文字背景对比度、用户可配置 token/layout 和
  Aurora PC/移动端浏览器 smoke，并保留了对应帮助与进度文档。
- 确认 `campusos.app-style-pack.v2` 缺少双端声明会被拒绝，但 `page-style-pack.v1` 缺少声明仍可能只产生
  warning，不能代表全部风格包已经强制双端交付。
- 确认当前 `web/tests/style-pack-responsive.mjs` 只真实应用和检查 `aurora-campus`，没有遍历
  `campus-canvas`、`clean-blog`、`kinetic-journal`，也没有覆盖个人主页所有者/访客和内容状态矩阵。
- 在 v13 计划中新增 `campusos.appearance-delivery/v1` 方向，要求 PC/Mobile 声明、双预览、响应式规则、
  对比度、reduced-motion、配置复验和 checksum 绑定的双端渲染报告。
- 规定受控 Appearance Render Runner 不得获得数据库、JWT、Cookie、用户 Token 或网络能力，并具有临时目录、
  超时、资源和并发上限；Runner 不可用时包只能进入 `pending-validation`，不能应用。
- 新增 `valid`、`invalid`、`pending-validation`、`legacy-readonly` 状态；历史已应用包兼容读取，新导入、
  重新选择和发布不能再通过 warning 绕过严格门禁。
- 新增 A5 和 A6 两个 P0 阶段：先统一合同、Validator、CLI/导入/应用硬门，再迁移四个内置包、生成双预览、
  建立系统主题和个人主页状态矩阵并接入 `release-check`。
- 将 Final、DoD、测试矩阵、兼容、文档、风险、禁止事项和最终验收同步为全包双端标准。

## 4. 架构变化

本阶段没有运行时架构变化。计划明确后续边界：

```text
Resource Package source
  -> static safety validator
  -> bounded appearance render runner
  -> checksum-bound desktop/mobile report
  -> valid catalog
  -> preview/apply/runtime fallback
```

- 系统主题仍由 Appearance Built-in Feature 管理，只作用于用户前台，不进入 Admin。
- 个人主页包仍只作用于主页根节点；访客看到主页所有者应用的风格。
- 管理员提供的包保存在 `data/resources/{themes,space-style-packs}`。
- 用户上传包通过 Personal Space/User Storage 保存受控编译结果和归属数据。
- 风格包不进入 External Plugin Runtime，也不能访问 Token、数据库、任意 API 或宿主文件系统。

## 5. 兼容和迁移处理

- `page-style-pack.v1`、`campusos.app-style-pack.v2`、`viewport_support` 和旧 `preview.png` 继续读取。
- v13 新发布要求两张端侧预览和严格渲染报告；旧单预览不能满足新发布门禁。
- 已应用历史包不在升级时被直接删除；严格验证失败时回退 Core 默认主题并保留用户偏好和诊断证据。
- 内置 `aurora-campus`、`campus-canvas`、`clean-blog`、`kinetic-journal` 必须在 A6 迁移为严格
  `valid`，不能以 `legacy-readonly` 完成 Final。
- Appearance 合同是资源文件级变化，不预设数据库 migration；如实现中需要持久验证任务，必须重新评估
  数据所有权和迁移编号，不能借用插件表。
