## 1. 问题

README 已说明首次 `setup`、日常 `up` 和配置修改后需要重新创建容器，但没有集中回答“每次修改源码是否需要
重启”。开发者容易把源码 HMR、API 自动重编译、镜像重建和 Docker Desktop 重启混为一谈，进而反复执行
`down/up`、误用 `docker restart`，或只运行不会启动容器的 `build`。

## 2. 文档收口

- README 新增按改动类型划分的加载决策表，并同时列出 Windows PowerShell 与 Linux/WSL2/Git Bash 命令。
- 明确普通 Go、Web、Admin、Docs 源码不需要手工重启：API 轮询构建并切换，前端使用 HMR。
- 明确 `.env.dev.local`、前端依赖/lockfile、开发 Dockerfile、Compose 和容器入口脚本需要重新执行
  `docker-dev.* up`。
- 解释 `up` 已包含 `-d --build --wait`，无需先 `down`；`build` 不启动容器，`docker restart` 不重读环境。
- 补充分支切换/拉取后建议运行 `up`，以及 migration 只向前执行、不会因切回旧分支自动回滚的边界。
- 官方 Docker 文档和仓库开发指南同步相同规则，故障排查先使用 `ps` 与对应服务日志。

## 3. 数据与运行影响

本轮只修改文档，没有 API、前端运行逻辑、Compose、环境变量或 migration 变化，不需要重启当前开发栈。
`docker-dev.* down` 保留命名卷；文档继续明确只有显式 `reset --confirm`/`reset -Confirm` 才会删除开发卷。
