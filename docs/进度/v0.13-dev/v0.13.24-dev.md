## 1. 目标

在不维护 Windows/Linux 两套源码的前提下，建立可自动执行的仓库文本策略：

1. Git 中的文本使用 UTF-8 和 LF。
2. Windows、Linux、Docker 检出的普通文本保持 LF。
3. Windows 专用脚本在工作区保持 CRLF。
4. 二进制文件不参与换行转换。
5. 编辑器、开发机检查、发布门禁和双平台 CI 使用同一规则。
6. 资源包 checksum 不再因宿主机换行策略产生漂移。

## 2. 方案结构

| 层级 | 文件/入口 | 作用 |
| --- | --- | --- |
| Git | `.gitattributes` | 定义提交与检出时的文本、EOL 和二进制规则 |
| 编辑器 | `.editorconfig` | 约束新建/保存文件的 UTF-8、LF、末尾换行和尾随空格 |
| 本地检查 | `scripts/check-line-endings.py` | 只读校验 Git 属性、编码、BOM、LF/CRLF 和二进制声明 |
| 本地修复 | `scripts/check-line-endings.py --fix` | 只规范化工作区换行，不暂存、不提交、不推送 |
| Make/发布 | `make line-endings-check`、`make release-check` | 把 tracked 文件检查纳入统一发布门禁 |
| CI | `.github/workflows/ci_test.yml` | Ubuntu 与 Windows runner 同时执行只读检查 |

该方案不需要维护一个“转换全部代码”的日常脚本。Git 和编辑器负责预防，检查器负责发现漂移；只有旧工作区
或误保存文件需要一次性执行 `--fix`。

## 3. Git 与编辑器规则

### 3.1 `.gitattributes`

- 默认 `* text=auto eol=lf`。
- `.sh`、Dockerfile、YAML 显式为 LF。
- `.ps1`、`.bat`、`.cmd` 在工作区显式为 CRLF。
- `data/resources/**`、`data/module_data/**`、`data/plugin_data/**` 的文本显式为 LF。
- 图片、字体、Office 文件、压缩包、音视频、WASM、数据库、可执行文件和根目录 ELF `main` 显式
  `-text`。

资源目录的文本规则写在二进制规则之前，后面的扩展名规则优先，因此 PNG/WebP/WASM 等资源不会被误转换。

### 3.2 `.editorconfig`

- 默认 `charset = utf-8`、`end_of_line = lf`。
- 默认插入文件末尾换行并清理尾随空格。
- Windows 专用脚本覆盖为 CRLF。
- Markdown 不设置强制行宽。

`.editorconfig` 是编辑器预防层，不替代 Git 属性和 CI。

## 4. 检查器行为

日常只读检查：

```powershell
python scripts/check-line-endings.py --include-untracked
```

显式修复：

```powershell
python scripts/check-line-endings.py --include-untracked --fix
```

检查器具有以下边界：

- 默认只检查 tracked 文件；`--include-untracked` 会追加未跟踪且未被 `.gitignore` 忽略的文件。
- 跳过 Git symlink、submodule 和显式 `-text` 二进制。
- 文本必须有明确的 `eol=lf` 或 `eol=crlf`。
- 文本必须是无 BOM 的 UTF-8。
- 含 NUL 的文件必须显式声明为二进制。
- `--fix` 只改换行字节，不运行 `git add`、commit、push 或 PR。

本轮首次运行发现 Windows 工作区有 1264 个文本文件使用 CRLF。显式 `--fix` 将它们按 Git 属性规范化；
这些文件中的绝大多数规范化后与 Git 索引内容哈希一致，没有产生业务代码差异。本轮多文件方案仍在工作区
修改过程中，因此没有执行 `git add --renormalize .`，避免在审查完成前批量暂存。

## 6. CI 与发布门禁

`.github/workflows/ci_test.yml` 新增 `cross-platform-text` matrix：

```text
ubuntu-latest
windows-latest
```

两个 runner 都使用 Python 3.12 执行 `python scripts/check-line-endings.py`。CI 只读检查，不自动修复。
原来被整段注释的 Windows Go job 已移除；本轮验证的是跨平台文本合同，不宣称完整 Windows Go、数据库或
浏览器发行认证。

`scripts/release-check.sh` 在文档链接检查前调用 `make line-endings-check`，因此发布门禁也会阻止 tracked
文件的换行或编码漂移。

## 9. 已知限制

- 双平台 GitHub Actions 需要提交并推送后才会产生远端运行证据；本轮只完成 workflow 语法和本地行为验证。
- Windows runner 当前只验证文本合同，不等于完整 Windows 原生运行认证。
- 本轮未执行完整 `make release-check`；已直接执行与本方案相关的编码、资源、文档、YAML、Docs 构建和
  资源加载定向测试。
- `.editorconfig` 需要编辑器安装或内置 EditorConfig 支持，但 Git/CI 不依赖编辑器插件。
- 新增未知二进制格式时，应先在 `.gitattributes` 中声明 `-text`；检查器会拒绝含 NUL 但未声明的文件。
- `.gitattributes` 尚未提交的迁移窗口中，Windows `git status` 可能按索引旧规则暂时显示大量 `M`；
  应结合只读检查、`git diff` 和 dry-run 审查，规则提交并重新检出后会稳定。

## 10. 回滚

如需回滚本方案，应成组处理：

1. 回退 `.gitattributes` 和删除 `.editorconfig`。
2. 删除检查器、Make target、release-check 调用和 CI matrix。
3. 回退五个资源 manifest checksum。
4. 回退本轮 README、Help、docs-site 和进度索引更新。

只回退 manifest 或只回退换行策略会再次造成资源 checksum 不一致。
