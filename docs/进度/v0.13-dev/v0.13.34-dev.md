# v0.13.34-dev：分组聚合帖子 PostgreSQL 类型修复

> 日期：2026-08-03
> 状态：实现并在当前 Docker 开发栈验证
> 范围：Community PostgreSQL Repository、分组 WebUI 数据链路、Help 与官方文档

## 1. 现象与根因

“校园”是 group，“互助”和“二手”是其活动子 board。前端点击“校园 · 全部帖子”正确请求：

```text
GET /api/v1/threads?category_id=1785430473317232766
```

Thread Service 也正确把 group 展开为两个子 board ID，但 PostgreSQL 查询将 `threads.category_id BIGINT`
与 `$n::text[]` 比较，数据库返回：

```text
operator does not exist: bigint = text
```

Web 列表捕获请求失败后保持空数组，因此用户看到“暂无帖子”，容易误判为导航或层级关系丢失。

## 2. 修复

- PostgreSQL Repository 将展开后的 `[]string` 逐项去空白、校验为正十进制 BIGINT，并转换为 `[]int64`。
- SQL 改为 `category_id = ANY($n::bigint[])`，保持列类型同型比较并可继续利用 `category_id` 索引。
- 非法、零值或空字符串 ID 显式失败；空 group 保持非 nil 空数组，对应 SQL 空集合，不回退全站列表。
- 新增三组 Repository 单元测试，覆盖 Snowflake ID、非法 ID 和空集合。
- Help、官方 WebUI 行为页与 Community API 文档同步数据库边界。

## 3. 验证证据

| 验证 | 结果 |
| --- | --- |
| Repository + Thread Service Go 测试 | 测试包通过；宿主 Go 最后仅因全局 cache trim 权限返回非业务错误 |
| 当前 Docker API 修复前请求 | `500 / operator does not exist: bigint = text` |
| 当前 Docker API 热重载后同一请求 | `200`，`total=7` |
| 聚合内容 | 3 条 `mutual_aid` + 4 条 `secondhand`，全部属于两个子 board |
| 单 board 对照请求 | “互助” board 返回 3 条，不混入二手 |
| 文档链接 / 官方文档构建 | 478 个本地链接通过；VitePress production build 通过 |

当前 Codex 会话没有可连接的浏览器实例，因此未做自动点击截图；真实 WebUI 使用的同一 HTTP 路径已完成
运行态验收。开发者刷新或重新进入“校园 · 全部帖子”即可读取热重载后的结果，无需重启 Docker Desktop。

## 4. 回滚与限制

回滚 PostgreSQL Repository 的数组类型会立即恢复 500/空列表，不建议回滚。该实现依赖 Category ID 的
既有 BIGINT 合同；若未来迁移到 UUID，必须同时迁移数据库列、领域 ID 和数组参数类型，不能只改 SQL cast。
