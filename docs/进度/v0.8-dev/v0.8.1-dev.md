# v0.8.1-dev：A1 模块规范与架构门禁

> 阶段状态：已验收  
> 完成日期：2026-07-13  
> 对应计划：[v0.8 现有功能架构收敛计划书](../../项目计划书v0/项目计划v0.8/00-v0.8版本计划书.md)

## 阶段目标

将 A0 识别出的架构约束转为可执行门禁，阻止在重构期间引入新的跨领域具体依赖、服务器业务装配、Feature/Plugin 反向依赖或未来前端模块内部导入。

## 实际完成内容

- 将 `config/architecture-boundary-allowlist.json` 升级为带冻结计数的精确边 allowlist：最多 8 个来源、23 条具体跨域实现边。每项都有移除阶段和原因；新增来源或边会直接失败。
- 重写 `scripts/check-architecture-boundaries.py`，检查跨领域 `repository`、`service`、`handler`、`adapter` 导入，Server 业务构造和业务路由注册，Feature 直接取得 Plugin Manager，Plugin Platform 子服务反向引用 Manager，External Plugin 内部包访问和 Agent Contract 敏感依赖。
- 新增 `scripts/check-frontend-boundaries.py` 和零例外的 `config/frontend-boundary-allowlist.json`。A12/A13 建立 `src/modules/<domain>/internal` 后，跨模块导入该私有目录会被阻止。
- 新增 `scripts/test-architecture-checks.py`，覆盖后端同域允许、跨域 Repository 拒绝、allowlist 扩张拒绝和前端跨域内部导入拒绝。
- 更新 `make architecture-check`，使本地、CI 和 `release-check` 使用相同的后端、前端和正负样例门禁。
- 新增 [`v0.8模块贡献规范.md`](../../architecture/v0.8模块贡献规范.md)，定义 Module、Port、Adapter、Compatibility、Route Contributor、Infrastructure Profile 和前端领域模块的贡献规则。

## 架构变化

本阶段不迁移业务逻辑。架构债务从此前按文件名说明的 allowlist 变为具体导入边的冻结集合；Server 的两个过渡 Composition 文件和 Plugin Platform 的一个反向 Manager 文件也被单独标记。未来模块目录一旦落地，前端检查器立即保护其 `internal/` 边界。

## 兼容和迁移处理

- 现有 8 个历史来源和 23 条边仍可编译，未被删除或改写；其唯一用途、移除阶段和原因已写入配置。
- 不改变 HTTP、OpenAPI、权限、迁移、Manifest、持久化目录、Web/Admin URL 或 Feature 状态。
- allowlist 只允许减少；将代码暂时放入 `compatibility/` 不能绕过跨领域具体实现检查。

## 回滚方式

恢复 A1 前的 Makefile、两个检查器和配置即可撤销门禁。禁止通过扩大 allowlist 回滚实际违规；需要回退业务迁移时应恢复对应单向 compatibility Adapter。

## 已知限制

- 当前业务仍由 `internal/server/application.go` 集中装配；A2-A11 将按领域移除相应允许项。
- 前端检查器当前没有 `src/modules` 目录，因此只验证自身正负样例；A12/A13 才会对实际模块移动产生约束。
- Homepage/WebTheme 仍以兼容 DTO 使用 Plugin 类型，但没有直接取得 `*plugin.Manager`；A8 将把它们接入 Appearance Application Service。
