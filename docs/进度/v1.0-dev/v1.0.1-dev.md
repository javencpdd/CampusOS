## 1. 决策与范围

项目所有者明确允许将当前全部数据库数据视为可丢弃测试数据，并要求不再兼容旧数据库。基于这一授权，本轮先梳理
现有业务模型，再将 49 组历史追加 migration 重构为从空库可重复建立的三段基线。完整模型、需求、索引和逐步影响见
[v1.0 数据库全面重构方案](../../项目计划书v1/项目计划v1.0/01-v1.0数据库全面重构方案.md)。

本轮没有实现全部 v1.0 插件运行时或授权界面；只交付数据库基础、应用查询适配、迁移治理、架构视图、验证工具和说明文档。

## 2. 实际完成

### 2.1 三段新建库基线

| migration | 职责 | 主要影响 |
| --- | --- | --- |
| `000001_v1_schema_baseline` | 从空库创建当前 76 张业务表、约束、函数和索引 | 历史中间态和补丁噪声不再进入新库；所有无时区时间统一为 `TIMESTAMPTZ` |

应用表总数为 84；加上 `schema_migrations` 与 `schema_migration_locks` 两张治理表，空库建成后共有 86 张
`public` 表。旧 `permissions` 表已删除，运行查询统一使用 `permission_definitions` 与 `role_permissions`。
Session 同时删除明文 Refresh Token 与原始 IP 列，只保留必填、全局唯一的 Token 摘要和 IP 摘要；数据库触发
函数固定 `pg_catalog, public` search path。当前 97 个外键全部有引用端前导索引，并由 Schema 合同持续检查。

### 2.2 迁移执行器与治理

- `scripts/migrate.sh` 与 `scripts/migrate.ps1` 统一提供 `up`、`down`、`reset`、`status`、`check`。
- 文件名必须是六位版本号且 up/down 成对；已应用文件通过 SHA-256 防止漂移。
- 每个 migration SQL 与执行记录处于同一事务；数据库互斥锁阻止两个发布任务并发迁移。
- `reset` 仅接受 `CAMPUSOS_ENV=development|test`，并要求 `CAMPUSOS_RESET_CONFIRM` 与数据库名完全一致。
- 旧格式 `schema_migrations` 会被明确拒绝，不提供隐式兼容或自动破坏性升级。
- 历史专项 migration 检查脚本保留为兼容入口，但统一转发到新的 v1 空库基线演练，避免重复维护旧链假设。

### 2.5 本机 Docker 开发库切换与启动修复

- 启动失败的第一原因已确认：既有 `campusos` 库仍登记旧版三列 `schema_migrations`，新执行器按不兼容边界拒绝隐式升级。
- 在只读确认目标库名称为 `campusos`、旧库共有 79 张表后，使用
  `CAMPUSOS_ENV=development` 与精确的 `CAMPUSOS_RESET_CONFIRM=campusos` 完成受保护重置；没有删除其他 Docker 卷或服务。
- 重置后发现全新库默认管理员创建语句尚未写入 v1 必填身份字段。`internal/server/seed.go` 已补齐
  `identifier_normalized`、`verification_state=system_managed`、验证时间/来源、密码变更时间及凭据版本。
- 修复热加载后，默认管理员账号为 `admin@campusos.local / system_managed / verified`，与“部署管理账号不走公网邮箱找回”的既有身份合同一致。
- 主开发库审计进一步发现默认版块缺少帖子类型策略；启动初始化现以单条原子 SQL 在新建版块时写入
  `discussion/article` 默认策略，已存在且经过管理员配置的策略不会被覆盖。

## 4. 影响、升级与回滚

这是一条不兼容边界：任何仍使用旧 `000001-000049` 历史链的开发库都不能直接执行 `up`。操作者必须先备份
需要保留的内容，再按文档显式确认数据库名并执行 `reset`。重置会删除目标库 `public` Schema 中的全部对象和数据，
因此脚本不会替用户自动执行。

本次代码回滚可以恢复旧 migration 文件与旧执行器，但已经重置的数据不能由 down migration 恢复，只能从操作者事先创建的
备份恢复。新基线投入共享或生产环境之前，必须保留目标环境备份与恢复演练证据。
