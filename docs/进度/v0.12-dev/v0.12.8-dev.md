## 4. 架构变化

Recovery Service 是 Identity Core 的业务编排边界。它只依赖受控 User/Account、Challenge、Session、
Recovery Case 和 Reliability Port；邮件模块仍只能通过最小 Dispatch Port 获取投递所需数据。Case、
Challenge、Ticket、密码更新、认证版本和 Session 撤销不会被拆成跨事务的 Handler 拼接流程。

管理端、Web 和 CLI 都通过同一服务边界完成状态变更。前端只保存短期 Ticket 于页面内存，长期
Refresh Token 仍仅在 HttpOnly Cookie，数据库和日志均不保存原始凭据。

## 5. 兼容和迁移处理

- `users.email` 继续作为兼容投影；所有写入由 Identity 原子同步，历史 `legacy_accepted` 用户仍可
  使用原密码登录，但不能用旧邮箱公共找回。
- 计划中原先错误复用了 `000031`。实际以追加的 `000031` 放置 Recovery Case，Category hierarchy
  与之后结构化内容迁移顺延为 `000032-000035`，不修改已存在 migration。
- 系统管理员继续排除在邮件恢复和管理员 Case 之外。生产故障用 forward-fix，Case/Session/audit/
  Outbox 保留为证据；down migration 只用于隔离演练。

## 7. 回滚方式

生产回滚暂停新的账号安全写入并使用 forward-fix 或经过验证的备份恢复；不要尝试恢复已失效的旧
Refresh Token，也不要删除 Case、Ticket 消费、Session、Outbox 或审计记录。`000031` down 只供隔离
数据库演练使用，演练脚本已验证再次 up 后约束和默认 admin 权限可恢复。

## 8. 已知限制

- 邮件投递仍是 at-least-once。成功受理不等于邮件已到达，运维应从脱敏邮件状态和可靠任务检查。
- 辅助恢复前的线下身份核验属于组织流程，CampusOS 只保留非敏感编号，不替代证件或工单系统。
- 多 Provider 邮件主备、模板国际化、设备命名优化和更细的账号安全通知仍属 P2。
