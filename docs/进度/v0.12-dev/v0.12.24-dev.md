# CampusOS v0.12.24-dev 管理员账号与管理平面准入

> 日期：2026-07-19
> 阶段：A7.2
> 状态：已完成并完成阶段验收

## 1. 阶段目标

核对管理端“只读架构视图 -> 系统数据架构”与当前 migration 是否同步，并把管理员管理平面准入从普通
用户角色事实中独立出来。管理员凭据、Session 和 RBAC 必须保持单一事实源，不能通过复制密码或放宽
版主作用域换取表面上的账号分离。

## 2. 实际完成内容

- 审查确认原架构视图在修改前与 `000001-000037` 同步；新增数据结构后将页面同步到 `000038`、64 张表。
- 新增 `identity_admin_accounts`，独立保存管理员准入状态、凭据引用、来源、最近认证时间和版本。
- 保留 `users/accounts` 作为身份与凭据事实，不在管理员表复制密码哈希、JWT、Session 或 Token。
- 新增 Admin 专用 `POST /api/v1/auth/admin/login`；普通用户即使密码正确，也必须有活动管理员准入才能
  获得管理端 Session。
- 非 category scoped 的管理 API 统一要求有效 Session、活动管理员准入和 Permission Code；明确声明
  category scope 的治理路由继续允许版主按分配板块访问，不扩大为全局管理员。
- 角色分配、撤销、Bootstrap Seed 和数据库触发器同步管理员准入；`suspended` 不会被普通角色刷新静默恢复。
- 最后管理员保护按“有效身份 + 有效凭据 + 活动准入 + 全局 admin 角色”计算，避免把暂停账号误算为
  可恢复管理平面的管理员。
- 生成路由、授权矩阵和 OpenAPI 已记录 `admin-account` 门禁；架构同步检查接入 `make architecture-check`。

## 4. 架构变化

```text
users / accounts
  身份主体与唯一登录凭据
          |
          v
identity_admin_accounts
  管理平面准入：active / suspended / revoked
          |
          v
roles / permission_definitions
  进入管理平面后允许执行的动作
```

管理员请求的后端结论不再只依赖 `admin` 角色。External Plugin、普通用户前端和 category scoped 版主不会
获得管理员准入 Port；前端按钮可见性仍不能替代后端三重门禁。

## 5. 兼容和迁移处理

- `000038` 在建表前检查每个有效全局管理员恰好有一个活动邮箱凭据，冲突时中止而不猜测绑定关系。
- 迁移自动回填现有全局管理员；旧 `/auth/login` 和现有 Session 数据保持兼容。
- 分配/撤销 admin 角色仍使用原管理 API，服务和触发器负责准入投影一致性。
- 管理员表只引用现有凭据，不移动用户 ID、不改变密码、不删除角色或历史审计。
- 本地开发数据库已应用到 `000038`；架构页面、schema contract 和数据库审计使用同一基线。

## 7. 回滚方式

生产优先 forward-fix。隔离演练可执行 `000038.down.sql`，它只删除管理员准入表、触发器和函数，不删除
`users`、`accounts`、`user_roles`、Session 或审计。回退到不理解该准入合同的旧二进制前必须进入维护
窗口并关闭公网 Admin 入口；不能把删除门禁当作在线降级方式。

## 8. 已知限制

- 当前管理员准入主要随 admin 角色和部署 Bootstrap 管理；尚未提供独立的管理员账号暂停/恢复管理页面。
- `suspended` 已有数据库和请求门禁语义，后续增加 UI 时必须复用可靠命令、版本检查和 required audit。
- 架构视图是由 migration 和目录合同维护的只读静态视图，不读取生产业务记录；实时一致性由检查器和
  发布门禁保证。
