## 1. 本阶段目标

建立可重启、可审计而不泄露验证码的邮箱 Challenge 基础：HMAC Code、Purpose 隔离、一次性
Ticket、持久限流和只含不透明 ID 的 Outbox 事件。此阶段不发送邮件，也不切换公开注册流程。

## 2. 实际完成内容

- 新增 `000029_v12_identity_challenges`：`identity_email_challenges` 保存用途、规范化邮箱、
  账号关联、key ID、nonce、过期状态、尝试次数和 Ticket digest；没有 Code 或原始 Ticket 列。
- 新增 `identity_challenge_rate_limits`，用 keyed digest 而非原始邮箱/IP 保存分钟、日、小时
  窗口；默认限制为邮箱每分钟 1 次、每天 5 次、IP 每小时 10 次。
- 新增 `ChallengeService`：Code 由 HMAC 密钥环按 `public_id + nonce + purpose` 临时重建；
  错误 Code 计数持久化，达到上限或过期会失效。
- 验证成功生成至少 256 bit 随机 Ticket，数据库只保存 SHA-256 digest；消费使用锁定读取和
  `consumed_at` 保障一次性，并严格绑定 Purpose 和规范化邮箱。
- Challenge 创建、限流、必要命令审计和 `identity.email.challenge.requested.v1` 事件通过
  Reliability/TxKernel 同事务提交。Outbox payload 只有 `challenge_id`。
- 新增 `identity.challenge-dispatch-reader` Core Port，为 A4 邮件模块预留短生命周期投递投影；
  它不向插件、前端或 HTTP Handler 暴露 HMAC key、Store 或 Code。
- 新增密钥环与 IP hash 环境配置，生产环境拒绝 development sentinel、空 key 或弱 hash secret。
- 更新 Admin 数据库架构视图、schema contract、数据库审计、迁移演练和开发/部署文档。

## 4. 架构变化

Identity 现在拥有 Challenge 状态、Code 重建和 Ticket 消费的 Core 边界。邮件投递将通过最小
Dispatch Port 在进程内获得临时 Code；它不会读取 Identity Repository。可靠事件只携带
Challenge ID，使数据库、Outbox、Admin 可靠任务列表和日志不成为凭据存储位置。

## 5. 兼容和迁移处理

- 未改写 `000001-000028`；`000029` 仅添加新表、约束和索引。
- 现有 `/auth/register`、`/auth/login` 和历史 `legacy_accepted` 账号行为未在本阶段改变，
  因此不会因为邮件模块尚未启用而阻断用户。
- Key rotation 通过保留旧 `key_id` 对应 Secret 直到最晚 Challenge/Ticket 过期完成；移除旧
  key 前必须确认没有有效记录。
- 生产故障默认暂停新 Challenge 写入并 forward-fix。down migration 只用于隔离演练，不能
  恢复原始 Ticket 或已经消费状态。

## 7. 回滚方式

先冻结 Challenge 请求入口，保留表、Outbox 事件、审计和密钥配置，再按 forward-fix 排查。
隔离环境可执行 `000029` down/up；生产环境不能通过删除表来使已发出的 Code 或 Ticket 无效，
应使用发布窗口和密钥轮换的受控恢复流程。

## 8. 已知限制

- A3 创建的是可靠邮件请求事件，不包含 SMTP Sender 或真实邮件投递；Worker 当前没有该
  Consumer，事件会留在 Outbox，直到 A4 启用 Email Delivery Core。
- 公开注册仍是旧兼容路径；A5 才会要求验证 Ticket 并更新 Web、SDK 与 API Contract。
- Rate limit 是 PostgreSQL 持久边界；Memory Profile 只用于隔离测试和无数据库本地回退。
