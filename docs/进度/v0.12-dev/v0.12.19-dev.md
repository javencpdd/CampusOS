> 日期：2026-07-18
> 阶段：A4.1 可靠事件 Worker 收敛
> 实现状态：完成
> 验收状态：已验收（单元/race、管理端、真实 PostgreSQL Claim 与 `000037` up/down/up）

## 1. 本阶段目标

修复消费者已经保存 Receipt，但 Outbox 主事件因最终 Complete 失败而每隔 lease 周期重新领取的问题。
关键目标是让错误可见、最大次数真正生效、历史越界事件安全收敛，同时继续保留 Consumer Receipt、
at-least-once 语义和 lease owner/generation fencing。

## 2. 根因与实际完成内容

根因由三个问题叠加形成：

1. Worker 对 Complete、Retry、DeadLetter 和 FinishAttempt 使用 `_ =` 丢弃错误，ProcessOnce 和启动循环
   都无法感知最终状态写入失败。
2. PostgreSQL `finish` SQL 将同一个 `$4` 参数同时用于 varchar 赋值和未显式定型的比较，真实演练复现
   PostgreSQL `42P08: inconsistent types deduced for parameter $4`。因此 Complete、Retry 和 DeadLetter
   都可能在 fencing 条件执行前失败。
3. Memory/PostgreSQL Claim 没有 `attempts < max_attempts` 条件，也没有把已耗尽非终态事件收敛到 dead，
   导致 `97/8`、`103/8` 继续增长。

本阶段完成：

- `process` 改为返回错误，`ProcessOnce` 用 `errors.Join` 汇总每个事件错误；Heartbeat、Claim、Receipt、
  Attempt 和状态转换错误均可被调用者感知。
- Worker 输出固定字段的结构化脱敏日志：event/type、worker、lease generation、attempts/max、operation
  和安全错误类别；不输出 payload、headers、邮箱、验证码、Token、Secret 或幂等键。
- 所有消费者成功或因 Receipt skipped 后创建 `system:outbox-finalize` Attempt。Complete 成功记录
  succeeded；失败后按剩余次数进入 retry/dead；状态转换也失败时记录 failed 并返回组合错误。
- PostgreSQL `finish` 显式固定 status/message 参数类型，Complete、Retry、DeadLetter 继续使用
  processing + owner + generation 条件；零行更新返回可用 `errors.Is` 判断的 `ErrLeaseLost`。
- Memory/PostgreSQL Claim 先将 attempts 已耗尽的 pending、retry、过期 processing 原子改为 dead，
  再只领取 `attempts < max_attempts` 的事件。历史 `103/8` 保留 103，不 clamp、不继续增长。
- 新增 migration `000037`，只扩展 Attempt 状态约束以允许 `failed`；down 会先把 failed 安全映射为
  旧约束支持的 retry，不修改已发布的 `000027`。
- Admin 可靠任务页显示 attempts/max、lease owner/until/generation、available/dead 时间，并标记
  “尝试次数越界”“处理租约已过期”和有明确 finalize failed 证据的“消费者已完成，事件尚未最终化”。
- Admin API 改用显式 Event/Attempt DTO，原始 payload、headers、idempotency key 和任意历史错误不进入
  浏览器；错误消息按 allowlist 输出。
- 新增安全恢复文档。历史耗尽事件先自动进入 dead，再由管理员逐条核对并通过受控 Replay 恢复；Replay
  保留 Receipt，已有消费者继续 skipped，禁止删除 Receipt 或直接把 processing 写成 published。
- `outbox-check` 增加最大次数、finalize migration 和关键持久化错误不得静默丢弃的回归门禁。

## 4. 架构与状态机变化

正常路径：

```text
pending -> processing(1/8)
        -> consumer receipts
        -> system:outbox-finalize succeeded
        -> published
```

Complete 前崩溃：lease 过期后重新 Claim，已有消费者因 Receipt skipped，finalize 成功后 published；
真实副作用不重复。Complete 本身失败时，`attempts < max_attempts` 进入 retry，达到上限或永久错误进入
dead。若 lease 已被其他 Worker 取得，Retry/Dead 同样被 generation fencing 拒绝，旧 Worker 不覆盖新状态。

Claim 的维护阶段处理所有已耗尽 pending/retry 和过期 processing。它不根据 Receipt 数量自动发布事件，
因为运行时消费者集合可能变化；只负责使异常非终态安全收敛到 dead。

## 5. 兼容和迁移处理

- 不删除或重建 `platform_outbox`、Consumer Receipt、历史 Attempt、审计或 Worker 心跳。
- API 路径、Replay 权限、事件 payload 合同和现有消费者注册方式不变；新增 DTO 字段是加法兼容。
- Replay 仍只接受 dead 事件并要求权限、actor、命令审计和 Idempotency-Key。
- `runtime` 继续保持 at-least-once + consumer idempotency，不承诺 exactly-once。
- migration 只追加 `000037`；生产优先 forward-fix，down 仅用于隔离演练。

## 7. 回滚方式

应用问题优先 forward-fix。必须回退二进制时，先停止新 Worker 和 Producer，等待有效 lease 结束并保留
Outbox、Receipt、Attempt 与审计。`000037` down 只在隔离环境使用：它把 failed Attempt 映射为 retry
后恢复旧约束。不得在回滚中删除 Receipt、重置全部 attempts 或把 processing 批量写成成功。

## 8. 已知限制

- 统一指标层尚未接入。complete/state-transition/exhausted/lease-lost/attempt-overflow 目前由结构化日志、
  finalize Attempt 和 Admin 诊断覆盖，后续应增加对应 Prometheus counter。
- Admin 不会仅凭 Receipt 数量推断全部消费者完成；只有明确 finalize failed 证据才显示最终化警告。
- 本阶段没有执行生产 SMTP、完整 `database-check`、备份恢复、候选冷启动或真实浏览器流程；这些仍是
  v0.12 Final 的独立环境级验收，不能由本次 PostgreSQL migration drill 代替。
