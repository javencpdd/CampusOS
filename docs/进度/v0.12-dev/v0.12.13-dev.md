## 1. 本阶段目标

为 Community 建立固定的业务帖子类型、按 board 生效的创建策略和只供编译内 Built-in Feature 使用的
结构化 Detail Participant 合同；将既有 RichText 无损迁移为第一个 `article` 类型。

## 2. 实际完成内容

- 新增 `threads.thread_type`，固定为 `discussion`、`article`、`mutual_aid`、`secondhand`。普通
  `POST /threads` 继续只创建 `discussion`；`content_format` 保持为正文渲染字段。
- 新增 `category_thread_type_policies`。`000033` 会为历史 board 写入 `discussion/article` 默认策略，
  RichText Detail 对应的历史 Thread 原地回填为 `article`，不变更 ID、URL、草稿或治理状态。
- Community 创建路径会在同一可靠命令内检查可发帖 board、固定类型、Feature 启用状态和 board 策略，
  然后提交 Thread、Revision、Detail、required command audit 和 Outbox。
- 新增 `CreateStructuredThread` 与 Participant 合同。它仅位于编译内 Community/Built-in Feature 边界；
  External Plugin、SDK、Host API、MCP 与 Agent Runner 没有事务参与入口。
- RichText 创建草稿改为 `article` Participant；Detail 创建失败时不留下 Thread、Revision、审计或 Outbox。
  既有保存、发布、下线和治理路径继续复用 C0 的可靠命令。
- Category Service 在新建 board 时自动写入默认策略；管理员可使用版本化策略接口查看和整体替换允许类型。
  管理端“版块管理”新增带 tooltip 的类型策略按钮、复选配置对话框和冲突提示。
- 生成 OpenAPI、HTTP 路由/授权矩阵；管理端数据架构页同步 `000033`、策略表、关系和 Thread 字段。

## 4. 架构变化

Community Core 继续拥有 Thread、Revision、治理状态和 Category 类型策略。Built-in Feature 只通过
`ContentGateway` 请求创建结构化内容，并在当前 TxKernel 中写自己的 Detail 表；它不读取 Community
Repository。Participant 不属于 Plugin Platform 或 SDK 合同，因此外部扩展不能取得数据库事务、AppContext、
用户 Token、任意文件系统或网络权限。

## 5. 兼容和迁移处理

- `000033` 先检查 RichText Detail 是否存在对应 Thread；发现孤立记录会中止迁移并给出修复提示，不自动删除
  历史内容。
- 历史 Thread 默认是 `discussion`；具有 RichText Detail 的历史 Thread 是 `article`。原有富文本 API、
  Thread/Article ID、URL、资产路径和旧客户端读取字段保持可用。
- 已有 board 默认允许 `discussion/article`。后续启用或关闭互助、二手类型只影响新的创建请求，不影响
  历史内容与 Community 治理。
- down migration 仅用于隔离 `up/down/up` 演练。生产故障采用 forward-fix 或经过验证的备份恢复，
  不通过 down migration 删除结构化内容事实。

## 7. 回滚方式

服务端问题优先以兼容的 forward-fix 修复。若必须短时回退旧二进制，先关闭新的结构化创建入口；旧二进制
仍可读取基础 Thread，但不得允许它绕过 `thread_type` 和 board 策略写入。孤立环境可使用
`000033` down migration 验证恢复流程，生产恢复必须使用同一时间点的数据库备份和受控发布窗口。

## 8. 已知限制

- `mutual_aid` 与 `secondhand` 目前只是固定类型与策略候选，尚无可创建的 Feature 路由或详情表。
- 策略管理页不根据未来 Feature 的部署状态隐藏候选类型；服务端仍在创建时强制 Feature Gate，管理员可提前
  为随后启用的功能配置 board。
