## 1. 本阶段目标

修复 `POST /api/v1/auth/registration/challenge` 在已应用全部 migration 的 PostgreSQL 环境中仍返回
`400 registration verification request was not accepted` 的问题；保留邮箱/IP 滑动限流、事务原子性、
错误脱敏和现有数据，不通过关闭限流或绕过可靠命令规避故障。

## 2. 实际完成内容

- 定位到 PostgreSQL advisory lock 的文本参数包含 Go 内部 NUL 分隔符。PostgreSQL 不接受 text 中的
  `0x00`，因此 `hashtextextended` 返回 `SQLSTATE 22021`，事务在写入 Challenge 前回滚。
- `PgChallengeRepository` 现在先对 `scope + NUL + keyed digest` 元组计算 SHA-256，再把固定 64 位
  十六进制文本传给 advisory lock。锁顺序、并发串行化和限流统计语义不变。
- 新增锁键单元测试与可选 PostgreSQL 集成测试，覆盖首次消费成功、达到上限后拒绝，并自动清理唯一测试
  限流记录。
- 注册 Challenge HTTP 错误分层为：输入无效 `400`、策略限流 `429`、策略存储/事务/可靠队列等依赖故障
  `503`。内部日志只用 `request_id` 关联错误链，不记录邮箱、IP 原文、验证码或 Ticket；浏览器只收到
  脱敏通用错误。
- OpenAPI 为该端点补充 `429` 和 `503`，注册 API 文档、测试矩阵、风险登记和 v12 计划状态同步更新。

## 4. 架构变化

本次没有新增模块、Port、表或 migration。Identity Core 仍拥有 Challenge、策略和限流；可靠命令继续把
Challenge、限流、Command Audit 与 Outbox 放在同一 PostgreSQL 事务中。修复仅改变数据库 advisory lock
键的传输编码，不改变业务键、用户可见 Challenge ID、HMAC Code、Ticket 或现有数据目录。

## 5. 兼容和迁移处理

- migration `000001-000037` 不变，不需要数据迁移或清空历史限流计数。
- HTTP 成功响应、Challenge/Ticket 字段和 `400`、`429` 稳定错误保持兼容；未分类依赖故障由错误的
  `400` 修正为可重试 `503`，旧客户端仍可按非成功状态处理。
- 回滚代码不需要执行 down migration，但会重新引入 PostgreSQL NUL 锁键故障，因此应 forward-fix，
  不应以关闭限流、删除计数或改用内存 Repository 作为生产回滚。

## 7. 回滚方式

优先发布本修复的 forward-fix。若必须回退 HTTP 错误合同，可以独立回退 OpenAPI 与 `503` 映射，但不得
回退安全锁键编码。任何情况下都不得清空限流表、把邮箱/IP 原文写入锁键或日志，也不得绕过可靠命令直接
创建 Challenge。

## 8. 已知限制

- 当前本地 `.env` 未配置 SMTP，服务使用 development-only `EMAIL_PROVIDER=fake`。它会完成可靠事件但
  不会把验证码发送到真实邮箱，也不会把验证码写入日志；真实收件验收必须配置隔离 SMTP 测试服务或正式
  SMTP Provider。
- 本阶段验证的是注册 Challenge 请求和异步消费；真实 SMTP 收件、Code 校验与最终注册的浏览器流程仍归
  v12 Final 候选环境验收。
