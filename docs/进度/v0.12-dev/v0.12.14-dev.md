## 1. 本阶段目标

将校园互助落实为一个独立的 Built-in Feature：使用固定 Thread Type、一对一 Detail、明确业务状态机和
类型化 API，同时保持 Community 对基础帖子、回复、可见性、审核、回收和审计的所有权。

## 2. 实际完成内容

- 新增 `feature.mutual-aid` 模块描述符和 `internal/modules/features/mutualaid`。模块仅通过
  Community `ContentGateway`、`ContentQuery` 与 Reliability Port 协作，不导入 Community
  PostgreSQL Repository。
- 新增 `mutual_aid_details` 和 migration `000034_v12_mutual_aid`。Detail 固定记录互助类型、
  业务状态、可选截止时间、地点范围、联系渠道、作者和乐观并发版本。
- 数据库 CHECK、外键、索引和触发器共同保证：Detail 必须一对一指向 `mutual_aid` Thread，且 Detail
  作者必须等于 Thread 作者。孤立 Detail、错误类型、非法枚举、无效版本和不安全截止时间不能通过数据库层。
- 互助创建经 Community Structured Thread Command，在同一个可靠命令里写入 Thread、Revision、Detail、
  command audit 和 Outbox。Detail 失败时不会留下半写 Thread、Revision、审计或事件。
- 新增 `open -> in_progress/resolved/closed`、`in_progress -> open/resolved/closed`、
  `resolved -> closed` 状态机；业务状态不会改写 Community 的发布或审核事实。
- 新增公开状态、列表、详情和认证作者的创建、编辑、状态更新 API。作者编辑使用 `version`，陈旧版本返回
  冲突，非作者和非互助 Thread 被拒绝。
- 新增 Web 端校园互助列表、筛选、发布、详情、编辑和状态操作页面，并注册用户前台路由。页面可读取 Feature
  状态并在功能不可用时显示明确状态。
- 将互助路由加入 Feature Path Gate、服务器 Module Graph、HTTP owner 映射、生成路由/授权合同和管理端
  数据架构图；Community 的类型启用检查已对 `mutual_aid` 生效。

## 4. 架构变化

Community Core 仍拥有 Thread、Revision、板块策略、回复和所有内容治理状态。Mutual Aid Feature 只拥有
`mutual_aid_details` 的业务字段与状态机。它通过编译内 Structured Participant 进入当前事务，
External Plugin、SDK、MCP、Agent Runner 和浏览器不会获得数据库、Repository、AppContext 或 Participant
能力。

Feature 已停用时，Path Gate 和 Service 都拒绝互助 Feature 请求；普通讨论、历史 Thread 与 Community
治理不受影响。activation mode 为 `restart`，修改启停状态后需重新启动服务才会切换有效状态。

## 5. 兼容和迁移处理

- `000034` 只追加 Detail 表、约束、索引和触发器，不移动 `threads`、用户数据或历史 URL。
- 新类型仍要由管理员在目标 board 显式允许；Feature 启用不自动开放所有 board。
- 旧通用 `POST /threads` 保持只创建 `discussion`，不接受互助 Detail JSON。
- 生产问题采用兼容 forward-fix 或备份恢复；`down` 仅用于隔离数据库演练，不作为生产数据删除手段。

## 7. 回滚方式

先关闭互助入口并发布兼容 forward-fix；基础 Thread 仍可由 Community 读取和治理。隔离环境可以使用
`000034` 做 up/down/up 演练。生产恢复必须使用同一时间点备份、受控维护窗口和恢复后数量/约束核对，
不能以删除 Detail 表作为常规回滚。

## 8. 已知限制

- 本阶段不提供支付、订单、聊天、担保、仲裁或任意联系方式托管。
- 管理端暂不单独提供互助业务运营页；通用 Feature 管理和 Community 治理仍可控制功能与基础帖子。
- 业务列表在当前阶段逐条读取一对一 Detail；数据量显著增长前应在保持 API 不变的前提下增加受测的批量查询。
