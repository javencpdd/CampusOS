## 1. 本阶段目标

在不扩大 v0.12 产品范围的前提下，对校园互助和校园二手的结构化写路径、错误边界和发布门禁做一次
可验证审查。目标是补齐编辑路径的事务回滚、回收内容写保护、HTTP 错误脱敏，以及 Final 真实迁移演练
不能被静态 schema 检查替代的问题。

## 2. 实际完成内容

- 为互助和二手分别补充 Detail 更新失败的故障注入测试。测试确认 Thread、Revision、Detail、required
  command audit 和 Outbox 在同一可靠命令中回滚，失败更新不会留下新的可靠证据。
- 为两类 Feature 的编辑和状态更新增加 active（未回收）状态检查。基础 Thread 已进入 Community 回收站时，
  服务返回稳定冲突，不再修改 Detail 或产生新的业务状态、审计和 Outbox。
- 收紧两组 Handler 的未分类错误输出。已经声明的停用、权限、输入和并发冲突保持原 HTTP 与机器码；
  未分类 Repository、数据库或网络错误统一返回 `500 / 10006` 和 `internal server error`，不回显底层
  表名、查询或用户标识；原始错误仅与请求 trace ID 一起写入服务端日志。
- 增加两组 Handler 合同测试，验证未知错误不会出现在响应体中，且回收内容写保护稳定映射为
  `409 / 40009`。
- 新增 `make v12-migration-check`，将 v0.10/v0.11 兼容迁移和 v0.12 的 `000028-000035` 隔离
  up/down/up 演练集中为一个门禁；`database-check` 与 `release-check` 现在显式调用该门禁。
- 强化二手 `000035` 演练脚本的 re-up 断言，重新升级后除表存在外还必须确认
  `trg_secondhand_detail_guard` 和 `chk_secondhand_details_currency` 已恢复。
- 完善 v0.12 计划书、测试与发布验收矩阵、风险与回滚方案、实施回顾草案、API/帮助文档和文档门户，
  明确未完成的 PostgreSQL、恢复和浏览器验收不能被标记为完成。

## 4. 架构变化

Community Core 仍是基础 Thread、回收状态、Revision、审核和治理的唯一所有者。互助和二手 Feature
只通过 Community Port 读取基础 Thread，并在可靠命令中写入各自 Detail；它们不会绕过回收状态、
直接访问 Community Repository 或获得独立事务。

发布门禁不再把“当前数据库 schema 通过审计”当作所有历史迁移都已演练。真实 PostgreSQL
up/down/up 仍是独立的阻断证据，且由完整发布门禁显式执行。

## 5. 兼容和迁移处理

- API 路径、请求字段、既有机器码和已分类错误保持不变；新增的回收写保护使用既有冲突语义
  `409 / 40009`。
- 不新增或修改 migration、表、用户目录和旧 URL。`000035` 演练脚本只增加了验证断言。
- Feature 停用、Community 治理和基础 Thread 恢复语义保持不变；专用 Feature API 仍只在停用时保留
  声明的状态发现端点。

## 7. 回滚方式

本阶段没有数据迁移。若需要回退，恢复本次 Feature Service、Handler 和 Makefile 的兼容实现即可；
不会删除 Detail、Thread、审计或 Outbox 数据。生产问题仍优先采用兼容 forward-fix，数据库恢复只能使用
已验证的备份和维护窗口。
