## 1. 问题定位

图文文章附件并非写入失败。`internal/modules/features/richtext/attachments.go` 的
`UploadAttachment` 调用 `core.user-storage` 的 `ObjectPort.Put`；实际由
`internal/modules/core/userstorage/object_service.go` 的 `ObjectService.Put` 先写临时文件、`Sync`，再
原子重命名，并提交对象和配额账本。

本地 Provider 的受管附件字节位于：

```text
data/personal-space/<user_id>/file/objects/<storage_object_id>.bin
```

文件使用 Object ID 和 `.bin` 扩展名，不按上传时的原始文件名保存。原始名称、MIME、大小、owner 与业务状态分别由
`storage_objects`、`user_assets`、`richtext_article_attachments` 保存；这是避免把宿主路径和 Provider key 暴露到
API/浏览器的有意设计。运行时已核对存在的对象元数据和相同 Object ID 的本地 payload。

## 2. 实现内容

### 2.1 个人空间下载与预览

- 新增 `GET /api/v1/assets/:id/download`。`OpenMyUserAsset` 仅在当前登录用户等于 `user_assets.owner_user_id` 且资产
  为 `active` 时才经 Object Port 打开对象；跨用户、已删除和不存在均返回 `404`，不泄露资产归属。
- 新增 `POST /api/v1/assets/:id/pdf-invocations`。它只接受 owner 的 PDF，创建短期、不透明的预览 Invocation。
- 个人主页设置页新增“个人附件”面板，列出当前账号的活动附件，提供下载；PDF 以现有 Plugin UI v2 Surface 打开。

### 2.2 两个入口共用同一预览插件

- 图文文章附件列表继续通过文章访问策略创建 PDF Invocation；草稿/下架文章不会因知道附件 ID 而变成可下载资源。
- 个人空间入口创建 `context_kind=personal_asset` 的 Invocation；文章入口使用
  `context_kind=article_attachment`。`OpenPDFInvocation` 每次读取内容都重新检查调用用户、过期/撤销状态、PDF Viewer
  Feature 状态和对应资源访问策略。
- `000010_v1_1_personal_asset_preview` 将 `plugin_ui_invocations.article_content_id` 变为按上下文可空，并用 CHECK
  约束两种上下文的字段组合。向下回滚时仅删除短期的个人预览 Invocation，恢复旧的文章必填合同；不会删除用户附件
  或对象 payload。

项目计划书中所谓 PDF “插件”实际是第一方 Built-in Feature 的受信 `trusted-module`，通过
`builtin.pdf-viewer.preview` Surface 注册。它不是可安装 External Plugin；v1.1 仍禁止第三方动态前端 Bundle、远程
PDF.js 或 iframe 注入，以保留主站的 CSP、令牌和对象访问边界。

## 4. 使用与边界

1. 在图文文章详情中，访问者只能下载该访问者有权看到的开放文章附件；PDF 可通过文章附件卡的预览入口打开。
2. 在“个人主页 → 个人附件”中，只显示当前账号自己的附件；下载和 PDF 预览不会授予其他用户个人空间访问权。
3. PDF 预览把经过认证的字节交给浏览器，因此不能宣传为 DRM 或“绝对不能保存”；它的安全目标是防止路径、Token、
   跨用户个人空间和下架文章附件的越权访问。

目标 Linux 浏览器矩阵、PDF Range 容量/慢客户端报告、数据库与 Object payload 成套恢复演练仍属于 `v1.1 Final`
发布门禁，尚未由本机开发环境替代。
