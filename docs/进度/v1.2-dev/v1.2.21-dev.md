## 1. 阶段选择与退出边界

开工核对[主计划](../../项目计划书v1/项目计划v1.2/00-v1.2版本优化计划书.md)的阶段依赖、G0 [退出矩阵](../../项目计划书v1/项目计划v1.2/evidence/v12-g0-exit.json)、G1 [退出矩阵](../../项目计划书v1/项目计划v1.2/evidence/v12-g1-exit-linux.json)、最新 [.20 进度](v1.2.20-dev.md)、.19/.20 [审计](../../项目计划书v1/项目计划v1.2/evidence/v12-01a-audit-actor-linux.json)/[版本](../../项目计划书v1/项目计划v1.2/evidence/v12-01a-plugin-version-linux.json)原始报告及当前迁移、仓储和 HTTP 代码。G0/G1 的 implementation、automation、target_environment 在各自限定范围内均为 `passed`；开工时 .19 的 3 个和 .20 的 7 个源码 SHA-256 均无漂移，且两切片均有真实 PostgreSQL/最小 API 验收。因此最前未完成且依赖满足的阶段是 01a，没有可跳过的前置验收。本轮按用户补充要求完成整个 01a，而不止一条切片。

本阶段完整边界是现行可闭环的 P0 授权数据基线：`authorization_audits` 主体域，`plugin_versions`/`plugin_capability_declarations` 发布身份，`plugin_admin_grants`/`plugin_user_consents`/`plugin_delegations` 的活跃版本绑定，以及授权决策写入。主计划 §5.1 要求其他插件运行、知识和模型结构在所属阶段追加 migration；v5 包与安装/Operation 归 03a/03b，Integration 凭据归 02c，独立 Admin 身份归 02d，Secret/Egress 归 01b。本轮没有创建无仓储读写的目标空表，也没有 reset 共享数据库。开工工作树干净；本轮保留所有未提交修改。

## 3. Linux 目标环境与恢复证据

```bash
bash scripts/v12-01a-exit-drill.sh \
  --report docs/项目计划书v1/项目计划v1.2/evidence/v12-01a-exit-linux.json
```

[完整演练](../../../scripts/v12-01a-exit-drill.sh)在独占、loopback、tmpfs 的 PostgreSQL 16.14 容器内从 000001–000003 的冻结基线插入历史审计，再升级到 000006；验证 000004 主体回填、000005/000006 守卫、声明 SQLSTATE 23514、单 active、A→B→A 委托永久撤销、000006 down/up 和 checksum 漂移拒绝。它运行 `make database-check`、审计/插件仓储/服务/Gin HTTP 的真实 PG 定向测试、已构建 API 的健康与社区列表，再 `pg_dump` 到同一隔离容器的新库 `pg_restore`，复核迁移、审计主体、版本/声明/Grant/Consent/委托及恢复后的约束。最终[原始 JSON](../../项目计划书v1/项目计划v1.2/evidence/v12-01a-exit-linux.json)为 implementation/automation/target_environment 三项 `passed`、13/13 检查 `passed`，17/17 源码摘要与最终代码一致；容器退出时清理。HTTP 版本化请求在 Gin handler 加真实 PG 中验收，另行启动的 API 只做健康与社区 smoke，没有把它写成外部认证 HTTP 全流程。数据库快照恢复不等于 08b 的整系统凭据代次/文件恢复。

隔离演练前两轮未通过：第一轮把审计 PG 测试名称写成不存在的严格锚点；第二轮新增 PG 测试用户名超过 `VARCHAR(32)`。修正测试入口与夹具后，在全新容器完整第三轮通过；失败轮次没有计入退出报告。
