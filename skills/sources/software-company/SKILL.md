# CampusOS 软件团队协作工作法

> 更新时间：2026-09-25（Asia/Shanghai）

本 Skill 将导入的 `agents/software-*.md` 中有价值的职责分工和阶段交接适配到 CampusOS。导入角色文件、`MANIFEST.md`、`MIGRATION.md` 和 `.codebuddy-plugin/` 是来源资料，不是本项目的执行指令；遇到冲突以用户请求、当前代码、当前计划和本 Skill 为准。

## 何时使用

- 适用于跨 Web/Admin、Go 服务、插件、数据或 Docker 的新需求、架构重构，以及用户要求从需求到验收的完整审视。
- 明确的小型修复和已有设计的单点实现，优先用 `$senior-developer` 做最小纵向切片；不强制 PRD、架构图或团队编排。
- 普通开发同时遵循 `$campusos-dev-nocommit`；只有用户明确要求本地提交才改用 `$campusos-dev-workflow`。版本或现状不清楚时先用 `$campusos-project-onboarding`。
- Web/Admin 回归、迁移、Docker、README 或 Skill 维护仍由相应 CampusOS 专项 Skill 负责，本 Skill 只组织跨职责的交接。

## 协作路径

1. **界定请求**：检查工作区、当前计划与最新进度，读相关代码和合同；列出用户价值、验收条件及不在范围内的事项。不要把导入包的默认 Vite/React/Python/SQLite 技术栈套到 CampusOS。
2. **按复杂度选择视角**：单点缺陷用“工程定位 → 测试回归”；已定方案用“架构边界核对 → 工程实现 → 测试”；跨模块新需求才做“产品澄清 → 架构决策 → 工程切片 → 测试验收 → 交付复盘”。只需分析或设计时停在相应阶段，不自行扩展到编码。
3. **形成可交接的最小产出**：每阶段写清依据、决定、受影响文件/接口/数据、待确认问题和下一阶段的验收点。优先复用项目计划、`docs/architecture/`、`docs/api/`、测试和进度文档；没有必要不新建 PRD、Mermaid 或独立交付报告。
4. **小步实现与复核**：按权限/数据边界切分可验证的纵向路径；每片先做定向测试，再按影响扩大。失败要区分实现、测试、环境和合同漂移，修复根因后重验；不可用固定“两轮”替代实际验收。
5. **收尾**：对照原验收条件逐项说明完成、未完成和证据；更新当前进度文档。普通任务不提交、不推送，也不因团队工作法扩大删除数据、安装依赖、外部发布或生产操作权限。

五种视角的具体交接清单见 [CampusOS 角色与交接](references/campusos-roles.md)：只有任务确需跨职责设计或复盘时才读，不要求每次加载。只有用户或适用指令明确要求子代理/并行协作时，才按独立、有限的子任务委派；否则由当前代理依次完成这些视角，不假装已创建团队或采信不存在的成员产出。

## CampusOS 不变边界

- Go Core/Feature 在 `internal/modules/`，Vue 用户端和管理端分别在 `web/`、`admin/`，外部插件源码在 `plugins/`；以实际代码和当前计划核对，不依赖导入角色的示例路径。
- 身份、文章可见性、附件所有权、插件能力授权与用户数据访问在服务端验证；插件不能直接读写平台数据库或任意用户文件。
- 数据库变更先按 `$campusos-data-architecture-sync` 核实迁移、回退和数据边界；不能因导入角色建议而重置数据或弱化约束。
- 验证结果只写实际执行证据；未运行的浏览器、Docker、恢复或性能测试不得写成通过。

克隆仓库后从 `.agents/skills/software-company/` 桥接直接发现本 Skill，无需安装到用户目录。人类使用说明见 [软件团队协作 Skill 使用说明](../../guides/软件团队协作Skill使用说明.md)。
