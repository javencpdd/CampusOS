# CampusOS 五种协作视角与交接

> 更新时间：2026-09-25（Asia/Shanghai）

这是一份按需读取的交接清单，不代表必须创建五个代理，也不授权额外写入或调用外部服务。原始角色文本位于同级 `../agents/`，其中的 WorkBuddy 工具名、固定阶段数、默认技术栈和路径不适用于此仓库。

| 视角 | 关注问题 | 向下一阶段交付的最小信息 |
| --- | --- | --- |
| 产品 | 谁遇到什么问题、现有交互与期望是否一致 | 用户场景、P0/P1 边界、可观察验收条件、待确认选择；不默认写竞品分析。 |
| 架构 | 现有模块/合同能否承载、数据及权限归谁 | 调用链、受影响文件/API/表、兼容与回退影响、实现顺序；仅在关系难以用文字说明时画图。 |
| 工程 | 哪个最小纵向切片能先闭环 | 代码和测试的对应改动、偏离设计的原因、定向验证结果；不为速度批量写完再统一验证。 |
| 测试 | 用户场景及失败路径是否有证据 | 成功/拒绝/边界用例、实际命令及结果；失败时区分产品预期、源码、测试和环境问题。 |
| 交付 | 原目标是否真正达成 | 文件清单、完成/未完成项、剩余风险、进度文档和未执行验证；不把构建通过等同端到端验收。 |

## 选择场景

- **缺陷**：产品视角只澄清复现与期望；工程定位根因并修复，测试回归相关路径。若发现合同或架构冲突，再加入架构视角。
- **已有计划的实现**：先核对计划与代码差异，由架构视角确定切片和边界，再逐片实现/验证；无需重写整个计划。
- **跨模块新需求**：产品定义可验收目标，架构分析 Core/Feature、Web/Admin、插件、数据库和 Docker 的边界，工程与测试共同建立证据，再更新计划/进度。
- **只要求评审或计划**：只产出用户请求的分析/文档，不借“完整 SOP”之名改代码或部署。

## 具体边界提示

- 涉及插件时，检查 `plugins/` 包、平台 Host API、三层授权和用户配置目录；插件不得为自身需求自行建平台表。
- 涉及个人文档或附件时，区分对象存储字节、业务绑定和可见性；服务端按 owner 与文章状态复核。
- 涉及数据库时，读 `migrations/README.md` 和当前架构文档；写入与回退证据须在隔离环境验证。
- 涉及运行状态时，区分源码热更新、Docker `up` 与镜像 `rebuild`；不能把容器健康当作业务路径已验收。
