> 规范源：[`skills/sources/senior-developer/SKILL.md`](../sources/senior-developer/SKILL.md)

## 1. 作用与边界

`senior-developer` 是 CampusOS 的工程工作法 Skill。它把导入专家角色“学长小文”倡导的“小步实现与验证”收敛为
适合本仓库的可执行流程：先核实代码事实，再完成一个可独立验证的纵向切片，立即留下测试和文档证据，最后再继续下一项。

它不提供新的运行时框架、云服务、浏览器登录态或外部 CLI，也不会替代项目既有的专项 Skill。用户没有明确授权时，
不得因为导入资料中含有脚本或工具说明而安装 `browser-use`、调用 MiniMax、创建隧道或访问外部账号。

## 2. 何时调用

| 场景 | 推荐调用方式 |
| --- | --- |
| 会话恢复、版本阶段或代码现状不清楚 | 先用 `$campusos-project-onboarding`，再用 `$senior-developer`。 |
| 普通功能开发、缺陷修复、跨层回归 | `$senior-developer` + `$campusos-dev-nocommit`。 |
| 用户明确要求本地提交 | `$senior-developer` + `$campusos-dev-workflow`。 |
| Web/Admin 展示、表单、路由或接口结果不一致 | 再组合 `$campusos-webui-regression`。 |
| Docker、Windows/Linux 运行、热加载、健康检查 | 再组合 `$campusos-docker-development`。 |
| migration、持久化边界或 Admin 架构视图变更 | 再组合 `$campusos-data-architecture-sync`。 |
| README 与文档信息架构调整 | 再组合 `$campusos-readme-update`。 |

示例：

```text
使用 $senior-developer 与 $campusos-dev-nocommit 修复个人文档附件列表缺失问题。
先按最小纵向切片定位数据来源、API、页面状态和权限判断；每一步立即验证；不要提交或推送。
```

### 两个 Skill 如何分工

| Skill | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `$senior-developer` | 确定最小纵向切片，保护模块与安全边界，先定向验证再扩大验证 | 不自行决定版本阶段，不替代 v1.2 计划，也不负责提交代码 |
| `$campusos-dev-nocommit` | 读取版本计划和最新进度，选择依赖已满足的任务，维护阶段证据并保持未提交 | 不允许跳过未验收阶段，也不会因计划存在就把功能视为已完成 |

两者一起使用时，不是启动两个独立开发者，而是让同一个任务同时遵守工程纪律和版本化交付纪律。
本项目统一使用以下写法：

```text
使用 $senior-developer 与 $campusos-dev-nocommit ...
```

## 3. 按 v1.2 计划开始或继续开发

当前权威计划是
[`docs/项目计划书v1/项目计划v1.2/00-v1.2版本优化计划书.md`](../../docs/项目计划书v1/项目计划v1.2/00-v1.2版本优化计划书.md)。
截至 2026-09-26，计划仍标记为“待实施”，所有实施阶段均未在计划状态表中验收；已有 `v1.2.0-dev` 至
`v1.2.4-dev` 主要记录计划审查和文档工作，不能据此跳过 `V12-G0`。

### 3.1 第一次开始 v1.2 开发

```text
使用 $senior-developer 与 $campusos-dev-nocommit，依据
docs/项目计划书v1/项目计划v1.2/00-v1.2版本优化计划书.md 开始 v1.2 开发。

本次只完成 V12-G0：冻结当前代码、数据边界、场景、目标环境、样本以及容量和质量基线。
先读取 v1.2 主计划、架构审查与扩展合同决策、docs/进度/v1.2-dev 下最新进度和真实代码；
检查现有工作区并保留无关改动。按“读、写、验、记录”完成一个可独立验收的纵向切片，
只报告实际证据，不把设计或命令清单写成已验收。

完成后更新计划中的实现状态与验收证据，新增且仅新增一份下一编号的 v1.2 进度文档，
执行该阶段要求的定向检查和共同门禁。不要提交，不要推送；不得削弱权限、审计、隔离、
Secret、数据约束或错误处理来通过测试。
```

`V12-G0` 完成并有证据后，下一次再进入 `V12-G1`。发现基线失败时，应记录失败、环境和阻塞，
不能把“已经运行命令”写成“基线已通过”。

### 3.2 继续 v1.2 的后续开发

```text
使用 $senior-developer 与 $campusos-dev-nocommit 继续 v1.2 开发。

先核对 v1.2 主计划的阶段状态和依赖、docs/进度/v1.2-dev 的最新证据及当前代码，
不根据文件名或旧总结猜测完成度。选择“依赖已经满足的最前一个未完成阶段”；
如果上一阶段只有代码、没有自动化或目标环境验收，先补齐上一阶段，不得直接跳过。

本次只完成一个阶段，或该阶段内一个可独立验收的最小纵向切片。每完成一条路径立即运行
定向测试，再执行与影响范围相称的共同门禁；同步实现状态、自动化验收、目标环境验收和
证据路径，并新增且仅新增一份下一编号的 v1.2 进度文档。保留无关改动，不提交、不推送。
```

“最前一个未完成阶段”必须同时满足依赖。例如 `V12-G1` 依赖 `V12-G0`，`V12-02d` 依赖
`V12-02a` 与 `V12-01b`。计划表的顺序和依赖列共同决定下一项，不能只按编号选择。

### 3.3 已明确要做某个阶段

以下示例只适用于 `V12-G0` 已验收后：

```text
使用 $senior-developer 与 $campusos-dev-nocommit 完成 v1.2 的 V12-G1 合同冻结阶段。
严格按计划中 G1 的范围，只建立 Principal/Policy、插件 v5、非侵入式安装、独立用户/管理员
身份域、宿主资源策略、双向 API/事件合同、配置 Schema 子集和旧机制删除清单；
不要提前实施 V12-01a 数据库重建。将合同映射到 DTO、错误语义、机器 Schema 和验收测试，
验证不存在 Core 到 Feature 的反向依赖。完成后同步计划状态和一份下一编号进度文档，
不提交、不推送。
```

指定阶段时至少写清：阶段 ID、范围边界、验收证据、是否提交。不要只写“完成 v1.2 全部任务”；
它会把有依赖关系的高风险阶段压成一次不可验证的大改动。

### 3.4 每次交付应看到什么

1. 一个阶段或一个最小纵向切片的实际实现。
2. 与风险匹配的测试和门禁结果，失败项及未运行项均有原因。
3. 分开的“实现、自动化验收、目标环境验收”状态和证据链接。
4. `docs/进度/v1.2-dev/v1.2.N-dev.md` 中恰好一份本任务进度记录。
5. 明确未提交、未推送；只有用户另行要求提交时才改用 `$campusos-dev-workflow`。

## 4. CampusOS 的小步工作流

1. **建立范围**：读取用户引用的计划、最新进度与相关源码，确认当前分支和工作区，列出不超过五项的最小实现计划。
2. **先定边界**：明确权限事实、数据归属、插件/存储/迁移约束；不会为了快捷而只修改某一层或削弱服务端校验。
3. **完成一条路径**：按“读 → 写 → 验 → 记录”完成一个能独立验收的路径，例如“服务端返回正确作者昵称 → 页面显示昵称 → 测试覆盖回退”。
4. **马上验证**：先跑定向检查，成功后扩大到与改动风险相称的构建、测试或 Docker 冒烟；同一阻塞连续三次无法解决时停止试错并报告证据。
5. **如实交付**：说明已做行为、验证证据、进度文档、未执行项和原因；普通开发默认不提交、不推送。

用户明确要求安静执行时，工作流仍然生效，但不发送阶段性进度，只在结束时集中报告。

## 5. 验证基线

所有改动至少执行：

```powershell
git diff --check
python scripts/check-line-endings.py --include-untracked
```

再按受影响区域补充验证：

| 改动 | 最低验证 |
| --- | --- |
| Go、API、鉴权、服务 | 相关包测试；完成后使用仓库内 Go 缓存运行 `go test ./...`。 |
| Web 或 Admin | 对应 `pnpm format:check`、`pnpm build`；本机依赖不可用时，可使用已启动 Docker 容器并记录事实。 |
| 数据库与迁移 | 迁移演练、`make database-check`，并使用数据架构专项 Skill。 |
| Docker 工作流 | 相关服务健康端点和用户路径冒烟；区分 `up`、热加载与 `rebuild`。 |
| 文档和 Skill | 本地链接检查、桥接同步检查、`quick_validate.py`。 |

构建通过不等于浏览器交互、恢复、安全或性能验收已经通过；交付中只能陈述实际运行过的验证。

## 6. 原始角色与导入资料

`skills/sources/senior-developer/agents/senior-developer.md` 是原始角色配置，显示名已改为“学长小文”。
它与 `skills/fullstack-dev/`、`skills/frontend-dev/`、`skills/browser-use/` 及字体、模板、脚本一起保留，目的是追溯和按需参考，
并非 CampusOS 的自动执行入口。

这些资料的正确使用方式如下：

- 通用全栈、Node/Django/React 示例只能作为设计参考，CampusOS 实现仍以 Go、Vue、PostgreSQL、Docker 和现有模块边界为准。
- `frontend-dev` 中的 MiniMax 媒体生成脚本需要明确的媒体生成需求、密钥和外部调用授权；不得自动运行。
- `browser-use` 说明依赖外部 CLI；未获授权时不要安装、不要读取真实浏览器 Cookie、不要创建账号或公网隧道。
- `MANIFEST.md` 记录导入快照。适配后它的历史哈希不能用于校验当前目录；正式入口及桥接以本指南和根级 `SKILL.md` 为准。

## 7. Clone 后的使用与维护

仓库 clone 后，根级规范源与 `.agents/skills` 桥接已经随项目存在，无需安装到用户级 `.codex` 或 `.agents` 目录。若当前打开的
Codex 会话没有刷新 `$senior-developer`，重启 Codex 一次即可。

修改 `skills/sources/senior-developer/` 后，维护者应在仓库根目录执行：

```powershell
python skills/sources/campusos-skill-repository-sync/scripts/sync_skill_bridges.py --root . --write
python skills/sources/campusos-skill-repository-sync/scripts/sync_skill_bridges.py --root . --check
python C:\Users\19046\.codex\skills\.system\skill-creator\scripts\quick_validate.py skills/sources/senior-developer
```

不要手改 `.agents/skills/senior-developer/SKILL.md`：它是由规范源生成的桥接文件。完成后还应检查本指南、
`skills/guides/README.md` 和贡献工作流是否仍能正确描述可调用的入口。
