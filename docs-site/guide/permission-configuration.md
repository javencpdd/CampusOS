# CampusOS 权限配置入门

这是一份面向第一次管理 CampusOS 权限的操作教程。它不会要求你先理解数据库表，也不会让你直接修改数据库。你将从“一个用户为什么能做某件事”开始，逐步完成自定义角色、权限分配、板块版主和授权审计的完整配置。

本页在本地文档站的固定地址是：

```text
http://localhost:3002/guide/permission-configuration
```

## 1. 先用一句话理解权限

CampusOS 的权限判断不是简单地问“这个人是不是管理员”，而是依次确认：

```text
谁在操作
  -> 他通过哪个角色获得了什么权限
  -> 这个权限是否适用于当前板块或资源
  -> 当前功能和动作是否已启用
  -> 资源状态是否允许这次操作
  -> 记录允许或拒绝的结果
```

可以把几个概念理解成：

| 概念 | 通俗理解 | 示例 |
| --- | --- | --- |
| 用户 | 实际使用系统的人 | `user1` |
| 角色 | 一组工作职责 | 管理员、版主、内容审核员 |
| Permission Code | 角色随身携带的一把“钥匙” | `community.thread.review` |
| 作用域 | 这把钥匙能在哪些地方使用 | 全站，或者只限“编程交流”板块 |
| 动作开关 | 系统为某类操作设置的总开关 | 是否允许版主置顶主题 |
| 审计 | 谁在什么时候使用了哪把钥匙，结果如何 | 允许、拒绝、错误 |

最终有效权限可以简化为：

```text
有效权限 = 已登录且账号有效
         + 角色拥有 Permission Code
         + 作用域匹配真实资源
         + 功能与动作开关允许
         + 业务状态允许
```

缺少其中任何一项，后端都可以拒绝请求。前端显示了按钮，不代表后端一定放行；前端没有显示按钮，也不能代替后端权限检查。

## 2. 认识当前的角色

打开管理后台：

```text
http://localhost:3001
```

进入“用户与权限 -> 角色与权限”，或者直接访问：

```text
http://localhost:3001/permissions
```

当前角色分为两类。

### 2.1 系统角色

| 角色 | 用途 | 是否能在权限矩阵中直接修改 |
| --- | --- | --- |
| `admin` | 平台管理与高风险操作 | 否 |
| `moderator` | 管理指定板块中的内容 | 否，作用范围在“版主管理”配置 |
| `member` | 已登录普通用户的基础身份 | 否，也不能手工分配或撤销 |
| `guest` | 未登录访问边界 | 否，也不能手工分配或撤销 |

系统角色属于平台安全约束。权限页允许查看它们，但不会让管理员随意勾选和取消权限。

### 2.2 自定义角色

自定义角色用于组合一组明确的工作权限，例如：

- `content_reviewer`：审核待处理帖子。
- `plugin_operator`：查看或维护外部插件。
- `support_operator`：处理用户和内容支持工作。

自定义角色可以创建和调整权限，但操作者只能授予自己当前实际拥有的权限，不能通过创建角色让自己或别人越权。

::: warning 当前管理端准入边界
Admin 前端目前只允许拥有 `admin` 或 `super_admin` 角色的账号登录。自定义角色可以获得后端 Permission Code，也可以用于公开 API 或后续专用工作台的授权，但“拥有自定义角色”本身不会自动获得 Admin 页面登录资格。
:::

## 3. 配置前先做准备

### 3.1 确认服务和 migration

在仓库根目录运行：

```bash
curl -fsS http://localhost:8080/api/v1/health
make migrate-status
```

权限目录由 clean baseline 的 `000003_v1_reference_data` 写入。如果权限页提示“权限目录迁移尚未完成”，先执行：

```bash
make migrate-up
make migrate-status
```

不要为了让页面临时可用而直接修改 `roles`、`permission_definitions` 或 `role_permissions` 表。旧
`permissions` 表已经删除；直接改表会绕过防越权检查和授权审计。

### 3.2 准备两个测试账号

建议使用：

- 一个管理员账号，用来配置角色。
- 一个普通测试账号，用来验证权限结果。

不要拿唯一的管理员账号做撤销管理员角色的实验。CampusOS 会保护最后一个有效的全局管理员，但仍应在测试环境中演练权限变更。

### 3.3 先写清楚“谁、做什么、在哪里”

在创建角色前先回答三个问题：

```text
谁：内容审核人员
做什么：审核、下架帖子
在哪里：全站，还是指定板块
```

如果第三个答案是“指定板块”，优先考虑专门的版主作用域，而不是给用户一个全局自定义角色。

## 4. 第一步：读懂权限矩阵

进入 `http://localhost:3001/permissions` 后，页面分为三个区域：

1. 左侧是角色列表。
2. 右侧是当前角色拥有的权限。
3. 下方是授权记录。

点击一个角色后，每项权限会显示：

| 字段 | 如何理解 |
| --- | --- |
| Permission Code | 稳定的业务权限名称，不使用 URL 或数字 ID |
| 说明 | 该权限实际允许的操作 |
| 风险等级 | 低风险、中风险或高风险 |
| 允许范围 | 全局范围或板块范围 |
| 强审计 | 使用或调整该权限时需要重点记录 |

Permission Code 使用以下格式：

```text
<领域>.<资源>.<动作>
```

例如：

| Code | 含义 |
| --- | --- |
| `community.thread.review` | 审核帖子 |
| `community.thread.take_down` | 下架帖子 |
| `community.thread.purge` | 永久清除帖子 |
| `identity.role.create` | 创建自定义角色 |
| `identity.role.update_permissions` | 修改自定义角色权限 |
| `identity.role.read_audit` | 查看授权记录 |

::: danger 高风险权限不是“方便选项”
永久清除、直接恢复、角色创建、权限矩阵调整等操作会扩大影响范围或造成不可逆结果。只按实际工作需要授予，不要为了省事勾选全部权限。
:::

## 5. 第二步：创建一个最小自定义角色

下面以“内容审核员”为例。

### 5.1 先确定最小权限

假设这个角色只需要：

- 查看待处理内容。
- 审核帖子。
- 必要时下架帖子。

不要顺手加入 `community.thread.purge`、角色管理或插件安装权限。能够完成工作即可。

### 5.2 在管理端创建

1. 打开“用户与权限 -> 角色与权限”。
2. 点击右上角“新建自定义角色”。
3. 角色标识填写 `content_reviewer`。
4. 说明填写“负责审核和下架待处理内容，不负责永久删除”。
5. 在初始权限中选择 `community.thread.review` 和 `community.thread.take_down`。
6. 点击“创建角色”。

角色标识需要满足：

```text
以小写字母开头，只能使用小写字母、数字和下划线
```

推荐使用工作职责命名，不要使用具体人名。例如使用 `content_reviewer`，不要使用 `user1_role`。

### 5.3 创建失败时怎么看

| 提示 | 常见原因 | 处理方式 |
| --- | --- | --- |
| 权限 Code 格式无效 | 选择或提交了目录中不存在的 Code | 刷新权限页后重新选择 |
| 超出当前操作者权限范围 | 当前管理员自己没有准备授予的权限 | 换用有权管理员，或减少角色权限 |
| 权限目录迁移尚未完成 | `000003` 未应用 | 执行 migration 并重启 API |
| 角色标识不合法 | 使用了大写、空格、连字符或中文 | 改用小写字母、数字和下划线 |

## 6. 第三步：调整角色权限

1. 在权限页左侧选择刚创建的 `content_reviewer`。
2. 在右侧按领域查看权限。
3. 勾选需要增加的权限，取消不再需要的权限。
4. 查看页面顶部的“新增”和“移除”数量。
5. 点击“保存权限变更”。
6. 在确认框中逐项核对新增和移除的 Code。

保存成功后，新的权限矩阵会写入授权审计。

如果选择的是 `admin`、`moderator`、`member` 或 `guest`，页面只读是正常现象。不要通过数据库直接改系统角色；系统角色变化应由 migration 和专用功能配置完成。

## 7. 第四步：把角色分配给用户

进入：

```text
http://localhost:3001/users
```

按以下步骤操作：

1. 找到测试用户。
2. 点击该用户所在行的“角色”。
3. 在“分配新角色”中选择 `content_reviewer`。
4. 点击“分配角色”。
5. 重新打开角色窗口，确认角色已经出现在“当前角色”中。

撤销角色时，点击当前角色标签上的关闭按钮。

服务端还会执行以下保护：

- 不能给自己分配或撤销角色。
- 不能分配自己无权授予的能力。
- `member` 和 `guest` 不能通过普通角色接口变更。
- `moderator` 不能作为没有板块范围的全局角色分配。
- 不能撤销最后一个有效的全局管理员。

::: info 自定义角色当前是全局分配
通用“用户管理 -> 角色”流程会把自定义角色作为全局角色分配。需要限制到具体板块时，请使用下一节的版主管理，不要把全局角色误当成板块角色。
:::

## 8. 第五步：配置板块版主

版主和普通自定义角色的最大区别是：版主必须明确负责哪些板块。

打开：

```text
http://localhost:3001/moderators
```

### 8.1 设置所有版主的动作上限

页面顶部有三个动作开关：

| 开关 | 版主可以做什么 |
| --- | --- |
| 置顶主题 | 置顶或取消置顶负责板块中的主题 |
| 锁定主题 | 锁定或解锁主题 |
| 删除回复 | 删除负责板块中的回复 |

这些开关是所有版主的能力上限，保存后立即影响下一次后端检查，无需重启 API。

关闭开关不会删除版主的板块分配，也不会删除历史审计。它只让对应动作暂时不可执行。

### 8.2 给某个用户分配板块

1. 在“用户与板块范围”中找到用户。
2. 点击“配置范围”。
3. 选择一个或多个板块。
4. 点击“保存范围”。
5. 返回列表，确认对应板块标签已经显示。

保存空列表表示撤销该用户的全部版主范围，同时撤销其有效版主角色。

### 8.3 版主为什么不能跨板块操作

假设 user1 只负责“编程交流”：

```text
user1 请求置顶主题 823
  -> 后端读取主题 823
  -> 后端确认主题属于“编程交流”
  -> 检查 user1 的 category scope
  -> 检查“置顶主题”总开关
  -> 允许并写入审计
```

如果主题实际属于“校园生活”，请求会被拒绝。后端使用数据库中的真实 `category_id`，不会信任浏览器提交的板块 ID。

版主的置顶、锁定和删除回复不等同于帖子下架、审核、直接恢复、回收站恢复或永久清除。后面这些属于独立的内容治理权限，不会因为用户是版主就自动获得。

## 9. 第六步：验证配置是否真的生效

权限配置不能只看“保存成功”。至少完成一次允许测试和一次拒绝测试。

### 9.1 验证自定义角色

1. 使用管理员分配角色。
2. 让测试用户重新登录，获取新的会话状态。
3. 通过该角色对应的公开 API 或专用前端操作执行被允许的动作。
4. 再尝试一个没有授予的动作，确认后端返回 `403`。

由于当前 Admin 前端只允许管理员登录，不要用“自定义角色能否登录 Admin”作为唯一验证标准。应验证具体 API 或用户端业务动作。

### 9.2 验证版主

1. 给测试用户分配板块 A。
2. 确保“置顶主题”开关已开启。
3. 使用测试用户登录用户前台。
4. 打开板块 A 中的主题，确认可以置顶和取消置顶。
5. 打开板块 B 中的主题，确认操作不可用或请求返回 `403`。
6. 回到 Admin 关闭“置顶主题”，再刷新用户端，确认板块 A 中也不能置顶。

### 9.3 验证撤销

1. 从用户身上撤销自定义角色，或者把版主板块保存为空。
2. 让测试用户刷新页面或重新登录。
3. 重复原操作，确认已经被拒绝。
4. 确认用户数据、帖子和历史审计仍然存在。

## 10. 第七步：查看授权记录

返回：

```text
http://localhost:3001/permissions
```

页面下方“授权记录”会显示：

- 操作时间。
- 操作者 ID。
- Permission Code。
- 路由或业务操作 ID。
- 允许、拒绝或错误结果。
- 可记录的拒绝原因。

授权记录用于回答“谁为什么能做或不能做这件事”。记录不会保存 Access Token、Refresh Token、Session、JWT 私钥或第三方 Secret 明文。

版主范围调整和版主治理动作还会进入 Moderation 审计。权限审计和业务审计用途不同，排查问题时可以结合查看。

### 10.1 查看高风险命令与可靠任务

v0.11 起，注册、角色/权限调整、版主范围和内容治理等高风险写操作会将业务结果、
必要审计和后续事件放入同一事务。拥有运维权限的管理员可以打开：

```text
http://localhost:3001/reliability
```

在“可靠命令审计”中查看命令、操作者、资源、request ID 和 event ID 的关联；这里不会
显示请求正文、Token、Webhook Secret 或任意 Outbox payload。查看失败队列不等于可以
重放：重放需要独立的 `platform.reliability.replay` 权限，并且只能对已进入 `dead`
状态的事件进行二次确认操作。

不要因为想让一个内容审核员“看起来像管理员”就授予 replay 权限。可靠任务重放可能
再次触发外部副作用，应该只由明确负责恢复工作的最小角色使用。

## 11. 可选：使用 API 检查配置

界面操作已经足够完成日常配置。需要自动化或排障时，可以使用管理 API。

先登录并取得本地测试 Token，然后将它放入环境变量。不要把 Token 写进文档、代码仓库或日志：

```bash
export CAMPUSOS_TOKEN='<temporary-admin-access-token>'
```

查看权限目录：

```bash
curl -fsS \
  -H "Authorization: Bearer ${CAMPUSOS_TOKEN}" \
  http://localhost:8080/api/v1/permissions
```

查看角色权限：

```bash
curl -fsS \
  -H "Authorization: Bearer ${CAMPUSOS_TOKEN}" \
  http://localhost:8080/api/v1/roles/<role-id>/permissions
```

查看最近授权记录：

```bash
curl -fsS \
  -H "Authorization: Bearer ${CAMPUSOS_TOKEN}" \
  'http://localhost:8080/api/v1/authorization-audits?limit=100'
```

配置版主板块：

```bash
curl -fsS -X PUT \
  -H "Authorization: Bearer ${CAMPUSOS_TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"category_ids":["<category-id>"]}' \
  http://localhost:8080/api/v1/moderation/admin/moderators/<user-id>
```

API 仍会执行与管理端相同的防越权、作用域和审计检查。直接调用 API 不是绕过权限的方式。

## 12. 不要混淆三套权限

CampusOS 中有三套彼此独立的授权：

| 权限体系 | 回答的问题 | 在哪里配置 |
| --- | --- | --- |
| 管理员 RBAC | 某个用户能否管理角色、用户、内容或平台能力 | Admin 的角色、权限和版主管理 |
| External Plugin Host 权限 | 某个外部插件能否调用特定宿主 API | 插件 Manifest、导入预检和管理员审批 |
| 用户对插件的数据授权 | 某个用户是否同意插件读取自己的数据 | 用户端插件中心的授权流程 |

下面这些推论都是错误的：

- 管理员批准插件，不代表用户同意插件读取个人数据。
- 用户授权插件，不代表插件获得管理后台权限。
- 插件 Manifest 声明权限，不代表安装后自动批准。
- 管理员 RBAC 不会把数据库连接、JWT 私钥或用户 Token 交给插件。

插件权限继续阅读：[Host API 与权限](/plugins/host-api) 和 [插件中心、受管数据与签名](/plugins/market-managed-data)。

## 13. 常见问题排查

### 权限页面打不开或目录为空

1. 运行 `make migrate-status`，确认 `000025` 已应用。
2. 确认当前账号是有效管理员。
3. 检查 API 健康状态和 `.campusos/logs/api.log`。
4. 不要手工补写权限表，先修复 migration 或数据库连接。

### 保存自定义角色时提示越权

当前操作者不拥有准备授予的全部 Permission Code。减少权限，或让拥有这些权限的管理员执行操作。系统故意禁止“通过创建角色获得自己原本没有的权限”。

### 已分配自定义角色，但用户不能登录 Admin

这是当前设计边界。Admin 前端只接受 `admin/super_admin`。自定义角色控制后端业务能力，并不自动打开 Admin 工作台。后续如果增加委派式管理工作台，需要同时改造前端路由准入和菜单能力检查，不能只取消登录限制。

### 选择 moderator 时要求板块

这是正确行为。版主不能成为无范围的全局角色。请在“版主管理”选择至少一个板块，或者在用户角色窗口中选择版主后配置“管理板块”。

### 版主在正确板块仍不能置顶

依次检查：

1. 用户是否仍有该板块的版主范围。
2. “置顶主题”动作上限是否开启。
3. 用户是否重新登录或刷新了页面。
4. 主题是否真实属于该板块。
5. API 日志和授权记录是否显示拒绝原因。

### 不能撤销某个管理员

不能撤销自己的角色，也不能撤销最后一个有效的全局管理员。先准备另一个经过验证的管理员账号，再进行交接。

## 14. 安全配置清单

每次权限调整前后检查：

- [ ] 用工作职责命名角色，不以具体用户名命名。
- [ ] 只授予完成工作所需的最少 Permission Code。
- [ ] 高风险和强审计权限已逐项复核。
- [ ] 需要板块限制的人员使用版主范围，不使用全局角色替代。
- [ ] 使用独立测试账号做了允许和拒绝测试。
- [ ] 验证了撤销后权限立即失效，数据没有被删除。
- [ ] 在授权记录中找到了对应变更和判定。
- [ ] 没有直接修改数据库权限表。
- [ ] 没有在日志、截图或文档中暴露 Token 和 Secret。
- [ ] 生产环境变更前已有备份和回滚负责人。
